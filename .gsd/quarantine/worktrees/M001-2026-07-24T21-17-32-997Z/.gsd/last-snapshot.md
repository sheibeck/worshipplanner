# GSD context snapshot (2026-07-24T19:41:15.930Z)

## Top project memories
- [MEM007] (pattern) Song lyrics use append-only versioning: each saveLyrics creates a new Firestore doc in a subcollection, while updateCurrentLyrics patches the active doc for auto-save efficiency. revertToVersion copies old data into a new doc to preserve full audit trail. performanceOrder lives on the Song doc, not the lyrics subcollection, so it persists across lyric version changes.
- [MEM008] (convention) SortableJS drag-and-drop uses DOM-revert pattern: revert the DOM move in onEnd, update the reactive array, and let Vue re-render as single source of truth. This pattern is used in both ServiceEditorView and PerformanceOrderBuilder. SortableJS is mocked in tests since jsdom lacks drag events.
- [MEM009] (pattern) Scripture editors (ScriptureSlideEditor, CongregationalEditor) follow the same fetch-split-edit-autosave pattern as SongLyricEditor. They use create-on-first-fetch (createReading on initial ESV fetch, updateReading on edits) and share the useAutoSave composable. Reading mode toggle on ScriptureSlot in ServiceEditorView switches between normal and congregational editors inline.
- [MEM001] (architecture) Slide data model structure Chose: Unified slide type with content-kind field (lyric, scripture, image, video, text) rather than distinct types per content. Rationale: Simpler for the editor, reordering, and user mental model. One slide is one slide regardless of content. Avoids multiplying UI components for each content type..

Rationale: Eliminates the wrong-slides-at-rehearsal problem from juggling multiple ProPresenter versions. Edit once, every service sees the update.
