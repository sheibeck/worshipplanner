<objective>
Build the Run-time loop timer that consumes Plan 01's per-item `loop` config: auto-advance a looping
item's slides on its interval, loop back to the item's FIRST slide, and tear down cleanly on every
exit path — with "Go to black" explicitly PAUSING the loop (R306 runtime half, R308).

This is the risky half of Phase 106 (v2.7 PITFALLS Pitfall 4). The timer lives in ONE place — a small
`useLoopTimer` composable driven from `useRunControl.ts` — and every advance flows through the existing
`postIndex()` single-writer choke point, so the loop and manual navigation can never fight or double-drive
the output windows.

Purpose: Deliver predictable, leak-free per-item looping during Run, with the "Go to black PAUSES the
loop" decision (106-CONTEXT.md) implemented and verified in a real output-window context.

Output: `useLoopTimer.ts`, the loop integration in `useRunControl.ts`, a dedicated behavioral suite, and
(drop-if-costly) a Run-rail "Loop" indicator.
</objective>

    - useLoopTimer() returns { arm(intervalMs, tick), disarm(), isArmed } and holds exactly one interval id; arm() disarms any prior interval first (only ONE active timer ever) and onUnmounted(disarm) guarantees no leak on route-away/unmount.
    - advanceLoop() advances WITHIN the current item's filmstrip: from the last slide it posts the item's FIRST global index (wrap); otherwise the next; it NEVER advances into another item; it is a no-op when the item has ≤1 slide.
    - Every advance goes through postIndex() (the single writer) so outputs stay in sync.
    - reconcileLoop() arms iff live && !blackout && current item's loop.enabled && the item has >1 slide; otherwise disarms. arm() is called with the item's clamped intervalSeconds*1000, and arming resets the clock (so manual nav within the looping item restarts the interval rather than fighting a stale tick).
    - reconcileLoop runs from postIndex (after the post), postBlackout (pause on true, resume on false), watch(currentSlotIndex), and watch(live); confirmExit/endServiceTeardown also disarm defensively.
    - intervalSeconds is clamped to 1–3600 (fallback 10 on NaN) before arming.
  </behavior>
  <action>

    `ReturnType<typeof setInterval> | null` id. `arm(intervalMs, tick)` calls `disarm()` first then starts
    one setInterval; `disarm()` clears and nulls the id; expose `isArmed` (true when the id is non-null) for
    tests; register `onUnmounted(disarm)`. Mirror the existing `clearInterval`/`onUnmounted` teardown

    - Instantiate `const loopTimer = useLoopTimer()`.
    - `clampInterval(n)`: return an integer clamped to the inclusive 1–3600 range, falling back to 10 for a
      non-finite value (defensive against a hand-edited persisted interval — T-106-05).
    - `currentLoopSlot()`: resolve the current item's ServiceSlot via
      `rail.value.find((r) => r.index === currentSlotIndex.value)?.slot` and read its `loop`.
    - `advanceLoop()`: using `filmstrip.value.indices` (the current item's slides' GLOBAL indices) and the
      current `index.value`, find the within-item position; if it is the last, `postIndex(indices[0])` (wrap
      to the item's FIRST slide); otherwise `postIndex(indices[position + 1])`. Return early when
      `indices.length <= 1`. This wraps WITHIN the item and never calls goByItem — the loop stays inside its
      own item per 106-CONTEXT.md.
    - `reconcileLoop()`: compute `shouldArm = live.value && !blackout.value && currentLoopSlot()?.enabled ===

      * 1000, advanceLoop)` (arm resets the clock — this is what makes manual nav restart the interval from the

      `current.value` recomputes synchronously). This single wiring covers "manual nav restarts on the looping
      item" and "item change to a non-looping item disarms".
    - Call `reconcileLoop()` at the END of `postBlackout()` (after posting): blackout true → disarm (PAUSE the
      loop per the explicit 106-CONTEXT.md decision "Go to black PAUSES the loop"); blackout false → re-arm
      (RESUME). Add `watch(currentSlotIndex, reconcileLoop)` and `watch(live, reconcileLoop)` so go-live/
      rehearse arms (live flips true with index already at 0) and End Service/End Rehearsal disarms.
    - In the existing exit/teardown path (confirmExit / endServiceTeardown, wherever `blackout.value` is reset
      on exit), also call `loopTimer.disarm()` (defense-in-depth alongside useLoopTimer's onUnmounted, which
      already covers a plain route-away/unmount).
    - Gate on `live` (not on outputs being open) so rehearse honors the loop for on-screen parity
      (ARCHITECTURE Feature 5). Introduce NO runChannel protocol change — from the channel's view a loop tick
      is indistinguishable from a manual next-slide.

    ARCHITECTURE anti-patterns). Do NOT add a parallel advance path that bypasses postIndex.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| control window → runChannel → output windows | The loop drives slide index across the single-writer BroadcastChannel to the receive-only output windows. |
| persisted slot.loop → run-time timer | A stored (possibly hand-edited) `intervalSeconds` is consumed to arm a client-side interval. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-106-03 | Denial of Service | leaked/duplicate loop timer after unmount, route-away, or item change | high | mitigate | useLoopTimer holds ONE interval id, disarms before each arm, and clears on onUnmounted; reconcileLoop disarms on non-looping item, live=false, and blackout; confirmExit/endServiceTeardown disarm defensively — no interval fires against stale state. |
| T-106-04 | Tampering | control↔output desync from a parallel advance path | high | mitigate | Every loop advance routes through postIndex() (the single writer); no timer runs in any output window; no runChannel protocol change — the loop is indistinguishable from a manual next-slide. |
| T-106-05 | Tampering | persisted intervalSeconds out of range | low | mitigate | clampInterval() bounds the interval to 1–3600s (fallback 10 on NaN) before arming, so a hand-edited tiny/huge value cannot drive a runaway or zero-delay loop. |
| T-106-SC | Tampering | npm/pip/cargo installs | low | accept | No dependency installs in this phase — pure in-repo Vue/TS timer logic; no Package Legitimacy Gate applies. |
</threat_model>
