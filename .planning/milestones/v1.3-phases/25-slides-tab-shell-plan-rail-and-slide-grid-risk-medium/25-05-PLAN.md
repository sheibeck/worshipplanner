Make the grid editable in the two ways R031 and R032 require of it: add a slide to a group, and put a
group's slides in the order the operator wants. Both need a real group document to write to, so this
plan also opens the on-demand materialization seam that 25-07's drop and import paths reuse.

Purpose: without the on-demand seam, every write path in this phase fails for exactly the plan items
R032 is about — the empty ones a user wants to add a deck or a video to.
Output: one composable addition, one prop thread, a drag handle, a reorder write and an add-slide write.
</objective>

  <action>
Add an on-demand materialization function to `useSlideshowAssembly` and include it in the composable's
return interface. It takes a slot id and resolves to the group's current slide entries plus its stored
source signature, or to nothing when it cannot act (no service, no org, no such slot, or the caller
cannot write).

It must RETURN the entries rather than expecting the caller to re-read the groups map. The store's write
does not update that map until the Firestore snapshot round trip lands, so a caller that appended to a
freshly re-read map would append to an empty list and destroy the derived slides. This return contract
is the whole reason this function exists rather than the callers each calling the store directly.

When a group already exists, return its stored entries and signature without writing. When it does not,
derive the input with `buildInitialGroup` — which also performs Phase 24's D-05 media migration from the
slot's deprecated media fields — and create it through the store's existing create-if-missing action,
then return the input's entries and signature.

Deliberately do NOT reuse `materializationCandidates`' zero-slide skip here. That skip implements
Phase 24 D-02's "groups are always populated" rule for AUTOMATIC materialization, where creating an
empty document would be creating something nobody asked for. This function only ever runs because a user
just asked to put something into that plan item, which is the opposite situation and is what R032
requires ("added at any point in the service").

Reuse the existing in-flight slot-id set as the re-entrancy guard so an explicit call and the automatic
watcher cannot both create the same document; the store's deterministic doc id already makes the worst
case a harmless overwrite, so this is belt and braces rather than the primary defence.

Thread the function down: destructure it at the single `useSlideshowAssembly` call site in
`ServiceEditorView`, pass it to `SlidesTab` as a prop alongside the org id and service id already being
passed, and pass it through to `SlideGrid`. Keep it a plain function prop — do not have any component
under `src/components/slides/` import the composable.

Note the documented consequence for a plan item whose source is assigned AFTER slides were added to it
by hand: the group's stored signature no longer matches the new source, and 25-01 makes a hand-added
entry count as customization, so reconciliation routes that group to the confirm-required path rather
than replacing the user's work. That is the intended behaviour under Phase 24 D-02 ("never silently drop
a user's added slide"); the confirm dialog that resolves it is Phase 26 (R033). Record this in the plan
summary as a known, deliberate limitation — do not build a confirm here.
  </action>
