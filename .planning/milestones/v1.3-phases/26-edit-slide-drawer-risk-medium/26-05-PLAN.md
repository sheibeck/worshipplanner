    - Typing in either field persists after a short pause, with no button press.
    - Rapid typing produces one write, not one per keystroke.
    - Each write replaces only that one entry within the group's slides; every other entry is passed through by value, unchanged.
    - Each write passes the group's slides as they are AT WRITE TIME, not as they were when the panel opened.
    - Switching to a different slide mid-edit flushes the pending write for the slide being left, so a change is never silently dropped.
    - The status area shows a saving state during the write and a brief saved state after it.
    - A rejected write surfaces as a failure rather than a false saved state, and leaves the field's content alone.

  <action>
Add a small entry-update helper local to this component (not to the store — the store's contract is
deliberately "accepts a whole array"). It takes the changed fields for the current entry, reads the
group's slides FRESH from the live prop at the moment it is called, maps that array replacing only the
matching entry, and calls the store's whole-array replace passing the group's current source signature
and that same freshly-read array as the base snapshot.

The freshness is the point. A base snapshot captured when the panel opened would be stale for every
later write in a long-open session, and would silently discard anything that landed in between — the
exact data loss the compare-and-swap mechanism exists to prevent. Put that reasoning in a comment on the
helper, referencing the pitfall, because the wrong version of this code looks perfectly reasonable.

Add the label and notes fields using the UI-SPEC's exact labels and the notes sub-label, styled with the
established field-label and input classes named in the UI-SPEC's typography and colour sections. Keep a
local editable copy of each value so typing is responsive, and re-sync it from the persisted entry when
that entry changes identity or its persisted value changes — but do not clobber what the user is
currently typing.

Debounce each text field's write by the interval the UI-SPEC specifies. Flush any pending write when the
edited entry changes and when the component unmounts, so leaving a slide never drops the edit in flight.
Clear the timer on unmount as well — a leaked timer here is a known recurring problem in this codebase's
tests.

Drive the status area from the write: a saving state while it is in flight, a brief saved state after it
resolves, and a failure state if it rejects. Reuse the existing saving-then-saved feedback convention
named in the UI-SPEC rather than inventing wording. On rejection, do not show saved and do not revert
what the user typed.

Gate both fields on the write-capability prop, exactly as the grid and the group-music control already
gate their write controls. A viewer still reads the slide's information.

Handle a rejection the way the grid's existing handlers do: report it and leave state alone. Never write
slide data through the service document's autosave.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser client → Firestore | Every panel write crosses it; the org-editor rule is the real authority |
| Concurrent writers → one group document | A long-open panel is the longest-lived writer in this feature |
| User text → stored slide entry | Label and notes are free text persisted to a shared document |
