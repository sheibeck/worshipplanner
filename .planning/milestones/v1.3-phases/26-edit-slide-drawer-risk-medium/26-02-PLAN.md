<objective>
Build the destination half of the drawer's "Edit in song" link (D-14/D-15) before the drawer exists to
call it: a single link contract, an opening-tab input on the song editor, and the song list view
honouring an arriving link.

Purpose: 26-RESEARCH.md Pitfall 4 establishes that this application has no per-song address at all —
the song editor is opened purely from local click state, so "navigate by route" has literally nowhere to
land today. Left inside the drawer's own plan this would become a one-line router call that arrives at
the song LIST and quietly fails D-15. Building it separately, and pure-testing the contract, means the
drawer plan only has to call a function.
Output: one new pure module with its own test suite, one new prop on the song editor, one arrival
handler on the song list view.
</objective>

  </read_first>
  <behavior>
    - A builder produces a router location targeting the song list route, carrying the requested song id and the requested tab as query values.
    - The builder accepts only the two tab values the song editor actually has; anything else is a type error rather than a runtime surprise.
    - A parser reads an arriving query and returns the requested song id and tab, or nothing when the query does not carry a song request.
    - The parser tolerates a repeated query parameter (routers can deliver an array) by taking the first value.
    - The parser returns no tab when only a song id is present, so the editor falls back to its own default.
    - The parser ignores an unrecognised tab value rather than passing it through.
    - A clearing helper produces the same query with the request removed and every unrelated parameter preserved.
  </behavior>
  <action>
Create a small pure module owning the whole link convention, so the sender and the receiver can never
drift apart. It exports three things and imports nothing from Vue, the router, or any store.

First, a union type of the tabs the song editor genuinely has today — read them off the editor's own tab
buttons rather than inventing names.

Second, a builder taking a song id and one of those tab values and returning a plain router location
object naming the song list route and carrying both as query values. Use the route's registered NAME,
not a hand-built path string.

Third, a parser taking a route query object and returning either the requested song id with its optional
tab, or nothing at all. Normalise a value that arrives as an array by taking its first element — routers
deliver a repeated parameter that way and a naive read yields an array where a string was expected.
Validate the tab against the union and drop anything unrecognised rather than forwarding it.

Fourth, a helper returning the same query object with the request's own keys removed and everything else
untouched, mirroring how the existing import-parameter clearing preserves the rest of the query.

Document at the top of the file WHY a query convention exists here rather than a per-song route: this
application has no per-song address, the editor is opened from local click state, and adding a route
would be a larger change than this phase's scope allows — with a pointer to the existing
auto-open-import parameter as the precedent being extended.
  </action>
  <acceptance_criteria>
    - A test asserts the builder returns a location naming the song list route with the song id and tab in its query.
    - A test asserts the parser returns the song id and tab for a well-formed query.
    - A test asserts the parser returns nothing for a query with no song request.
    - A test asserts the parser takes the first value when a parameter arrives as an array.
    - A test asserts the parser returns no tab when the tab parameter is absent, and also when it is unrecognised.
    - A test asserts the clearing helper removes only the request's keys and preserves an unrelated parameter.
    - `npx vitest run src/utils/__tests__/songEditLink.test.ts` exits 0.
