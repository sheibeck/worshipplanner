<objective>
Make song-group reconciliation correct when a section is referenced more than once.

D-02 settles that a repeated chorus is one section referenced N times. That makes N stored slide
entries share a single `sectionId` — the one key `reconcileSongGroup` diffs on. Phase 26-09 changed
the stored-entry index from a map-of-one to a map-of-array so a duplicated entry could survive; with
repeats now a first-class part of the model, the merge loop that consumes that index re-emits the
entire array once per occurrence and multiplies entries on every pass.

This plan replaces that loop with occurrence-aware consumption, and proves stability by reconciling
twice and comparing.

Purpose: the hard constraint in 28-CONTEXT.md is that a lyrics edit must still flow through to every
service referencing the song, and that 26-09's fix must not regress. Both are settled here, as
assertions rather than assumptions.
Output: a reconciler that is idempotent under repeats, with a test block that would catch the
multiplication defect if it ever returned.
</objective>

<interfaces>
`reconcileSongGroup(group, slot, inputs)` in `src/utils/slideGroupMaterializer.ts` runs, in order:

1. A song-IDENTITY swap check (stored entries referencing a different song id than the slot's current
   one). Confirm-gated. **Out of scope — do not touch this branch.**
2. `freshOrder` — the resolved section order, filtered to ids that still resolve to a pooled section.
3. `storedBySectionId` — `Map<string, GroupSlideEntry[]>`, built by walking stored lyric entries in
   stored order and pushing each onto its section's array. This is Phase 26-09 Task 1's array fix.
4. Leading/trailing copyright entries, matched by kind and position, never by section id.
5. **The merge loop — the only thing this plan changes.** For each `sectionId` in `freshOrder` it
   looks up the stored array and, when present, pushes EVERY element of it.
6. A retained run for stored entries whose section id is absent from `freshOrder` — never deleted.
7. A carry-through run for entries that are neither lyric nor copyright (a dropped video, an authored
   text slide) — D-17.
8. A `changed` computation comparing merged length and per-index JSON against the stored slides.

Steps 1, 2, 3, 4, 6, 7 and 8 stay as they are. `ReconcileResult`'s shape does not change.

Worked example of the defect, with `freshOrder = [verse-1, chorus, verse-2, chorus]` and one stored
entry per occurrence (so `storedBySectionId.get('chorus')` holds two entries): the loop reaches the
chorus key twice and pushes both entries each time, producing four chorus entries. The next pass sees
four, and produces eight.
</interfaces>

  <name>Task 1: Occurrence-aware consumption of the stored-entry index</name>
  <files>src/utils/slideGroupMaterializer.ts, src/utils/__tests__/slideGroupMaterializer.test.ts</files>
  <behavior>
    - Order `[verse-1, chorus, verse-2, chorus]`, stored entries one per occurrence: the merge emits
      exactly two chorus entries, in their two order positions, preserving each stored entry's id.
    - The same case reports `changed` as false when nothing about the group actually differs.
    - Feeding the merge's own output back in returns a value-equal result — reconciliation is
      idempotent under repeats.
    - Order `[verse-1, chorus]` with TWO stored chorus entries (the 26-09 Duplicate case): both
      survive, adjacent, at the chorus position — byte-identical to the behaviour shipped in 26-09.
    - Order `[chorus, verse-1, chorus]` with THREE stored chorus entries: three entries out, two
      consumed positionally and the surplus emitted next to the last occurrence; a second pass is
      value-equal to the first.
    - Order `[chorus, verse-1, chorus]` with ONE stored chorus entry: the stored entry takes the first
      occurrence and a freshly minted entry takes the second; the minted entry has a distinct id.
    - Occurrence-level customisation stays put: with two chorus occurrences where only the second
      stored entry carries `audioUrl`, the merged result has that audio on the second chorus entry
      only.
    - A stored entry whose section id is absent from the fresh order is still retained, after the
      resolvable run and before the trailing copyright entry.
  </behavior>
  <action>
Rewrite ONLY the merge loop in `reconcileSongGroup`.

Before the loop, build an occurrence-count index over `freshOrder`: for each section id, how many
times it appears. Keep a separate running consumption counter per section id as the loop proceeds.

For each `sectionId` in `freshOrder`, let `i` be the number of times this id has already been emitted
in this pass and `stored` be its stored array (possibly absent):

- If `i` is a valid index into `stored`, push that stored entry carried through by value with only
  its `order` renumbered. The occurrence keeps its own id, label, notes and audio.
- Otherwise mint a fresh lyric entry for the section, exactly as the current code does when a section
  is newly present.
- If this is the LAST occurrence of the id in `freshOrder` and `stored` holds MORE entries than the
  id has occurrences, push each surplus stored entry — in stored order, carried through by value —
  immediately after this occurrence.

That surplus rule is what preserves Phase 26-09. When a section has one occurrence and two stored
entries, the first occurrence is also the last, so both entries emit adjacently at the section's
position — the exact output 26-09 shipped. When occurrences and stored entries are equal in number,
there is no surplus and no growth. Re-running over the merged output reproduces it, because the
stored array then has exactly the entries the previous pass emitted for that section.

Replace the comment block above `storedBySectionId` so it explains both halves of the contract: why
the index holds an array (26-09 — a duplicated entry must survive) and why the array is consumed
positionally with a surplus tail (D-02 — a section may be referenced more than once, and re-emitting
the whole array per occurrence multiplies entries on every pass). Describe the failure mode by
behaviour rather than restating the old code.

Leave the identity-swap branch, the retained-but-unresolvable run, the D-17 carry-through run, the
copyright handling and the `changed` computation untouched.

Write the tests first, in a new describe block in
`src/utils/__tests__/slideGroupMaterializer.test.ts`, covering every behaviour bullet above. Write
the idempotence cases as an explicit two-pass assertion: reconcile, feed the result back in as the
group's slides, reconcile again, and compare the two outputs by value. Also assert that a two-pass
run leaves the entry count for the repeated section equal to its occurrence count, so the
multiplication defect fails loudly rather than as a subtle ordering mismatch.
