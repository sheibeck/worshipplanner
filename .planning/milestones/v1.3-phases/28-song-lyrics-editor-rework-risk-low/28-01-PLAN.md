<objective>
Establish the section-order model this phase's editor is built on: `sections` as a canonical pool,
`performanceOrder` as the single ordered list of references that IS the slide order, and a pure helper
module that derives option 2a's numbered row list from that pair and mutates it safely.

Nothing in this plan changes behaviour. It adds the vocabulary and the pure functions the four plans
after it consume, so the component work never has to re-derive list arithmetic inline.

Purpose: D-01 chose one always-draggable list. That list is `performanceOrder`. D-02 made a repeat a
reference. Both statements are arithmetic before they are UI, and arithmetic belongs in a tested pure
module rather than inside a Vue component.
Output: `src/utils/songSectionOrder.ts` plus its test file, and invariant documentation on the
existing lyric types.
</objective>

  <files>src/types/songLyrics.ts, src/utils/songSectionOrder.ts, src/utils/__tests__/songSectionOrder.test.ts</files>
  <behavior>
    - `buildSectionRows([verse1, chorus], ['chorus','verse-1','chorus'])` returns three rows in order,
      with `position` 1,2,3; row 1 and row 3 both carry `sectionId: 'chorus'`; row 3 has
      `isRepeat: true` and `repeatOfPosition: 1`; rows 1 and 2 have `isRepeat: false` and
      `repeatOfPosition: null`.
    - Every returned row carries a `rowKey` unique within the returned array.
    - `buildSectionRows` skips an order id that resolves to no pooled section rather than emitting a
      row with an undefined section.
    - `normalizeLyricOrder` drops order ids that resolve to nothing, drops pooled sections that share
      an id with an earlier pooled section (keeping the first), and — only when the resulting order is
      empty while the pool is not — seeds the order from the pool's stored sequence.
    - `normalizeLyricOrder` returns a value-equal result for input that already satisfies the
      invariants (so a caller can detect "nothing needed changing").
    - `moveRow(['a','b','c'], 0, 2)` returns `['b','c','a']`; a from/to index outside the array is a
      no-op returning an equal array.
    - `duplicateRow(['a','b'], 0)` returns `['a','a','b']` — the copy lands immediately after the row
      it was made from.
    - `removeRow` on one occurrence of a twice-referenced section removes only that occurrence and
      keeps the section pooled.
    - `removeRow` on the last remaining occurrence of a section removes the occurrence AND drops that
      section from the pool.
    - `addSection(sections, order, 'Chorus')` when a section labelled `Chorus` already exists returns
      a new pooled section labelled `Chorus 2` under a fresh id, appended to the end of the order,
      with empty `lines`, and reports the new id.
    - `mintSectionId('Chorus', ['chorus'])` returns an id not present in the supplied list.
  </behavior>
  <action>
Add doc comments to `src/types/songLyrics.ts` recording the model this phase settles on (D-03 — the
shapes themselves do not change, only what they are contractually required to mean):

- On `LyricSection`: it is a member of a canonical pool; each id appears at most once across a
  document's `sections`.
- On `SongLyrics.sections`: an unordered POOL of canonical section text, not a running order.
- On `SongLyrics.performanceOrder`: the single ordered list of section-id references, and the slide
  order itself. A repeated id means the same section shown again — a reference, so editing that
  section's text changes every place it appears (D-02). Every id here resolves to a pooled section,
  and every pooled section is referenced at least once.

Create `src/utils/songSectionOrder.ts` as a PURE module — it may import types from
`@/types/songLyrics` and nothing else. No Vue, no store, no Firestore, mirroring the stated purity
contract of `slideshowAssembler.ts`.

Export a `SectionRow` interface carrying: `rowKey`, `sectionId`, `section` (the resolved
`LyricSection`), `position` (1-based display number), `occurrenceIndex` (0-based count of this
section id among preceding rows), `isRepeat` (`occurrenceIndex > 0`), and `repeatOfPosition` (the
1-based position of occurrence zero, or null on a non-repeat).

Export `buildSectionRows(sections, order): SectionRow[]`. Index the pool by id once, walk the order,
skip ids that resolve to nothing, and compose `rowKey` from the section id and the occurrence index
joined by a separator that cannot occur inside a slugified id — the Phase 18 builder's
`${sectionId}-${index}` form is unsafe here because a slug legitimately contains hyphens; use a `#`
separator instead.

Export `normalizeLyricOrder(sections, order): { sections, performanceOrder }` enforcing the
invariants above. Order of operations: de-duplicate the pool by id keeping the first occurrence; drop
order ids with no pooled section; if the surviving order is empty and the pool is not, seed the order
from the pool's stored sequence; then drop pooled sections referenced zero times. This runs on the
WRITE path (the editor normalises what it holds and lets the existing dirty-check decide whether to
persist) — it is deliberately not a read-time fallback in the assembler, which D-19 forbids.

Export the mutation helpers, each taking and returning plain values and never mutating its arguments:
`moveRow(order, fromIndex, toIndex)`, `duplicateRow(order, index)`,
`removeRow(sections, order, index)`, and `addSection(sections, order, kind)`. `removeRow` and
`addSection` return a `{ sections, performanceOrder }` pair; `addSection` additionally reports the id
it minted so the caller can auto-expand that row.

Export `mintSectionId(label, existingIds)` and `uniqueSectionLabel(kind, existingLabels)`. The id
minter must reproduce `ccliParser.ts::slugify`'s transformation for the base case so ids stay
consistent with pasted ones, then append an incrementing numeric suffix until the id is unused.
The label helper returns the bare kind when unused, otherwise the kind followed by the smallest
integer above one that makes it unused.

Export `ADD_SECTION_KINDS` as a readonly tuple holding, in this order, the five quick-add kinds the
Turn 2 option 2a mockup draws: Verse, Chorus, Bridge, Tag, Ending.

Write the tests in `src/utils/__tests__/songSectionOrder.test.ts` first and let them fail, then
implement. Cover every bullet in the behaviour block above, plus: `buildSectionRows` on an empty
order returns an empty array, and every helper leaves its input arrays untouched (assert by value
comparison against a pre-call clone).

<task type="auto" tdd="true">
  <name>Task 2: Paste normalisation — a repeated section marker becomes a reference, not a copy</name>
  <files>src/utils/songSectionOrder.ts, src/utils/__tests__/songSectionOrder.test.ts</files>
  <behavior>
    - A parse result whose sections are `[Chorus(4 lines), Verse 1(5 lines), Chorus(no lines)]`
      normalises to a pool of two sections and an order of three ids, the first and third being the
      same chorus id — one canonical chorus, referenced twice (D-02).
    - A parse result whose two `Chorus` blocks carry IDENTICAL lines normalises the same way: one
      pooled section, two order entries.
    - A parse result whose two `Chorus` blocks carry DIFFERENT non-empty lines keeps both, under two
      distinct ids, both labelled `Chorus`, with two order entries pointing at the two different ids.
    - A parse result with no repeated ids passes through with a pool equal to its sections and an
      order equal to those ids in sequence.
    - The returned pair satisfies the pool/order invariants — feeding it to `normalizeLyricOrder`
      changes nothing.
  </behavior>
  <action>
Add `normalizeParsedSections(parsed)` to `src/utils/songSectionOrder.ts`, taking the `ParsedCCLI`
shape (or just its `sections` array — choose whichever keeps the module free of parser coupling) and
returning `{ sections, performanceOrder }`.

Walk the parsed sections in sequence, building a pool keyed by id:

- Id not yet pooled: add the section to the pool and append its id to the order.
- Id already pooled and the incoming section's lines are empty, or are value-equal to the pooled
  section's lines: this is a REPEAT MARKER. Append the pooled id to the order again and add nothing
  to the pool. This is the case the mockup's linked row draws and the case D-02 defines.
- Id already pooled and the incoming lines differ and are non-empty: these are two genuinely
  different sections that merely share a label. Mint a fresh unique id via `mintSectionId`, pool the
  incoming section under it keeping its original label, and append the new id to the order.

Compare line arrays by value after trimming each line, so trailing-whitespace differences in a CCLI
paste do not split one chorus into two pooled sections.

This function is the ONLY collision guard over `ccliParser.ts`'s unguarded `slugify(label)` ids. Note
that in a comment on the function so the coupling is discoverable from either side.

Extend `src/utils/__tests__/songSectionOrder.test.ts` with a describe block covering every behaviour
bullet above. Build the fixtures as literal section arrays rather than by running the parser, so this
module's tests stay independent of parser behaviour.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-28-01 | Tampering | `normalizeParsedSections` id collision handling | medium | mitigate | A colliding id never overwrites a pooled section's text; the collision branch either references the existing section or mints a fresh id. Asserted by the different-lines test. |
| T-28-02 | Denial of Service | `mintSectionId` suffix loop | low | mitigate | The suffix search is bounded by the size of the supplied id list, which is bounded by the pool; it terminates on the first unused candidate and cannot loop unbounded. |
| T-28-03 | Tampering | `removeRow` pool garbage collection | medium | mitigate | Removing the last occurrence removes the pooled section in the same returned pair, so no unreferenced-and-unreachable text can be persisted once the second list is gone in 28-02. |
| T-28-SC | Tampering | package installs | high | accept | This plan installs nothing. No package-manager command runs, so the legitimacy gate has no input to audit. |
</threat_model>
