  <behavior>
    - `createSlot('SONG')` returns an object whose `id` is a non-empty string, and two calls return different ids.
    - `buildSlots('1-2-2-3')` returns nine slots with nine distinct ids.
    - `reindexSlots()` on a reordered array preserves each slot's `id` while rewriting `position`.
    - `backfillSlotIds(service)` on a service whose slots all have ids returns the identical object reference.
    - `backfillSlotIds(service)` on a service with no ids returns a NEW service whose every slot has a distinct id, leaving all other keys byte-identical.
    - `backfillSlotIds(remote, local)` reuses `local.slots[i].id` when `local.slots[i].kind === remote.slots[i].kind` and the remote slot has no id; it mints a fresh id when kinds differ or the reference slot is absent.
  </behavior>
  <action>
In `src/types/service.ts`, add `id: string` to the `MediaAttachableSlot` interface. Every variant
(`SongSlot`, `ScriptureSlot`, `NonAssignableSlot`, `HymnSlot`, `ImportedSlot`) already extends that
mixin, so this is the single least-invasive edit that satisfies D-01's "every variant carries it".
Document on the field that it is minted by `createSlot`/`buildSlots` for new slots and by
`backfillSlotIds` for legacy documents, and that it is the anchor for `slideGroups/{slotId}`.

In `src/utils/slotTypes.ts`:
- `createSlot()` gains `id: crypto.randomUUID()` in every branch. Unlike `section`, `id` is ALWAYS
  written — the omit-the-key discipline established in Phase 20 applies only to `section`, because
  there is no legacy absent-id shape to preserve for a brand-new slot.
- `buildSlots()`'s three inner builders (`songSlot`, `scriptureSlot`, `nonAssignableSlot`) each gain
  `id: crypto.randomUUID()`.
- `reindexSlots()` needs NO change — its spread already carries `id` through every reorder. Add a
  one-line comment saying so, so a future refactor does not "helpfully" rebuild the object.
- Export a new pure function `backfillSlotIds(service: Service, reference?: Service | null): Service`.
  For each slot by array index: keep an existing non-empty `id`; else, when `reference` is supplied
  and `reference.slots[i]` exists with a non-empty `id` and the SAME `kind`, reuse that id; else mint
  `crypto.randomUUID()`. Track whether anything changed and return the ORIGINAL `service` object
  reference when nothing changed — returning a fresh object unconditionally would make the caller's
  dirty-comparison in plan 24-06 permanently true.

The two-argument form is a planner correction to RESEARCH.md Pattern 2, which specified a
single-argument backfill. Rationale to record in the function's doc comment: `ServiceEditorView`'s
load watcher also has a REMOTE-MERGE branch that compares `JSON.stringify(remote)` against
`JSON.stringify(local)`. A legacy Firestore document has no slot ids, so a one-argument backfill
would mint fresh UUIDs on every snapshot, the comparison would never match, and each snapshot would
re-anchor every group to a brand-new slot id — silently orphaning group documents. Reusing the
local id positionally (guarded by kind) makes the comparison stable. Accepted residual limitation to
note in the comment: if a concurrent editor inserts or removes a slot in the same window, positional
alignment can shift and one slot may take a fresh id; the window closes permanently on the first
real save, which persists the ids to Firestore.

Extend `src/utils/__tests__/slotTypes.test.ts` with the behaviors above, following the existing
describe/it style in that file.
