<objective>
Introduce the `superAdmin` custom claim end-to-end on the Functions side: the `syncSuperAdminClaim` Firestore trigger (source-of-truth = `superAdmins/{uid}` existence), the `setSuperAdminClaim` privileged `onCall` for in-console grant/revoke, and the owner-run `bootstrapSuperAdmin` script for the first super-admin (R174, R175 direction B, R176, R179).

Every claim write routes through Plan 01's shared `claimsHelpers` (hard dependency — this plan is Wave 2 so the merge-safety fix always precedes the new claim). The onCall copies this repo's own privileged-callable security contract: re-verify the caller server-side (token AND Firestore doc, defense-in-depth), resolve the target by email via the Admin SDK, and perform exactly one well-defined write. The trigger — not the onCall — is the sole claim writer, mirroring the existing source-doc → trigger → claim indirection.

Purpose: Grantable, claim-merge-safe super-admin authority (R174/R175/R179) plus a chicken-and-egg-safe bootstrap for the very first grant (R176).
Output: `superAdminClaims.ts` (trigger + onCall + testable handlers), its unit test, two new `index.ts` exports, and the `bootstrapSuperAdmin.ts` script (+ test).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → setSuperAdminClaim (onCall) | An authenticated (possibly non-admin) client invokes a privileged cross-user write; the server must independently re-verify authority. |
| superAdmins/{uid} Firestore write → syncSuperAdminClaim trigger | The doc's existence is the source of truth that drives the claim; Admin SDK writes bypass rules by design. |
| Owner shell (bootstrap script) → Firebase Auth/Firestore | The only grant path that exists before any super-admin does; must be non-deployed and owner-run. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-68-03 | Elevation of Privilege | setSuperAdminClaimHandler | high | mitigate | Re-verify caller server-side BOTH ways (token.superAdmin AND superAdmins/{callerUid} re-read); resolve target via getUserByEmail server-side; never trust client-declared authority or uid. Unit test asserts a non-super-admin caller is permission-denied. |
| T-68-04 | Elevation of Privilege | bootstrapSuperAdmin.ts | high | mitigate | Bootstrap is a NON-deployed, owner-run-once Node script, not exported from index.ts, requiring admin credentials; no in-app code path grants super-admin without either the bootstrap OR an existing super-admin's onCall. |
| T-68-06 | Tampering | bootstrap deploy-ordering | medium | mitigate | Bootstrap calls mergeAndSetCustomClaims directly (not solely via the trigger), so the first grant's claim lands even if the trigger is not yet deployed (Pitfall 6). |
| T-68-05 | Elevation of Privilege / Tampering | revoke session cutoff | medium | mitigate | Revoke deletes the doc AND calls revokeRefreshTokens(targetUid); the residual ≤1hr token-lifetime window is documented (Plan 05 runbook) rather than treated as instantaneous. |
| T-68-SC | Tampering | npm installs | low | accept | Zero new dependencies (68-RESEARCH.md Package Legitimacy Audit) — no install step exists. |
</threat_model>
