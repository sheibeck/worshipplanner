  </behavior>
  <action>
Add `removeSongAttachment(id: string, attachment: SongAttachment)` to the store immediately after
`addSongAttachment` (~L313-319) and export it in the store's return object next to `addSongAttachment`
(~L533). Guard `if (!orgId.value) return` exactly like the sibling methods.

REMOVAL-ATOMICITY DECISION (implements the CONTEXT remove-atomicity decision; R368, and the
editor-removal half of R371): use a read-latest-then-filter-by-id write, NOT Firestore `arrayRemove`.
Justification to record in the SUMMARY: `arrayRemove` matches array elements by deep equality, and each
attachment carries a `createdAt` Firestore Timestamp that may not round-trip identically after
onSnapshot normalization, so `arrayRemove(liveObject)` can silently no-op and leave the "removed" file
to reappear on the next snapshot — the exact failure the acceptance truth forbids. `id` is a
guaranteed-unique stable field, so filter-by-id is deterministic and immune to the Timestamp
round-trip; the concurrent-add lost-update window is negligible because removal is a user-initiated
one-at-a-time action and the store already holds the latest onSnapshot array in `songs.value`.

Implementation: look up `songs.value.find(s => s.id === id)`; if absent, return. Compute
`filtered = (song.attachments ?? []).filter(a => a.id !== attachment.id)`. Write
`updateDoc(doc(db,'organizations',orgId.value,'songs',id), { attachments: filtered, updatedAt: serverTimestamp() })`.
THEN best-effort Storage cleanup mirroring hardDeleteSong's R371 loop (~L348-355): if
`attachment.storagePath` is set, `try { await deleteObject(storageRef(storage, attachment.storagePath)) }
catch (err) { console.error(...) }`; skip entirely for link-kind attachments (no storagePath). A failed
Storage delete must NEVER throw past the caller or revert the record removal (a rare orphaned blob is
acceptable per CONTEXT). Reuse the already-present imports (`updateDoc`, `serverTimestamp`, `doc`;
`deleteObject`, `ref as storageRef`; `storage`) — no new imports needed.

Add store tests in the existing `songs.test.ts`, mirroring the `addSongAttachment` and
`hardDeleteSong — Storage attachment cascade (R371)` describe blocks: seed `store.songs.value` with a
song carrying two upload attachments and one link, then assert the four behaviors above. To assert the
filtered write, read `vi.mocked(updateDoc).mock.calls[0]` and check `data.attachments` is a plain array
whose ids exclude the removed one; assert `serverTimestamp` was used for updatedAt. For the
failed-deleteObject case use `vi.mocked(deleteObject).mockRejectedValueOnce(...)` then reset it, and
assert `expect(store.removeSongAttachment(...)).resolves` plus updateDoc still called.
  </action>

  </verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Firestore (song doc write) | An editor's Remove issues updateDoc on `organizations/{orgId}/songs/{id}` — untrusted client mutation crosses into the org's song data. |
| client → Cloud Storage (deleteObject) | Remove best-effort deletes the object under `orgs/{orgId}/song-files/…` — a client-initiated Storage delete. |
| denormalized downloadUrl | The uploaded row's Download navigates to `attachment.downloadUrl`, a Storage download-token (bearer) URL embedded in the DOM. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-124-01 | Tampering/Elevation | removeSongAttachment write + deleteObject | medium | mitigate | Removal is gated at three layers already present: the `/songs` route is `requiresEditor` (Phase 122 finding), Firestore rules gate `songs/{id}` writes to org editors (R372, Phase 122), and `storage.rules` gates the `orgs/{orgId}/song-files/…` prefix to org members (R369/R372, Phase 122). The client method only calls those editor-gated paths; the UI renders Remove only where an editor already is. No new rule surface is added by this plan. |
| T-124-02 | Repudiation/Data-loss | filter-by-id write racing a concurrent attachment add | low | accept | Removal is a user-initiated, one-at-a-time action; the store reads the latest onSnapshot `songs.value` array immediately before the filtered write, so the lost-update window is negligible. Documented in the CONTEXT remove-atomicity decision. Choosing filter-by-id over arrayRemove specifically prevents the silent-no-op reappearance failure. |
| T-124-03 | Information Disclosure | downloadUrl bearer token in the Download anchor | low | accept | The download-token URL is a capability URL readable by anyone with the link — identical exposure to every existing media downloadUrl across the app. Scoped hardening (signed/short-lived URLs for anonymous playback) is explicitly deferred to the Rehearse milestone per REQUIREMENTS.md. |
| T-124-SC | Tampering (supply chain) | npm/pip/cargo installs | n/a | accept | This plan adds NO new dependencies (SEED-003 no-new-deps constraint; the PDF page-count library is intentionally omitted). No install tasks → no package-legitimacy gate required. |
</threat_model>
