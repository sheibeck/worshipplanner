`SettingsView.vue` does between its stacked sections — kept identical rather than inventing a new
gap for this one screen.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 |
| Label | 12px (`text-xs`) | 400 (regular) | 1.4 |
| Heading | 14px (`text-sm`) | 600 (semibold) | 1.2 |
| Display | 20px (`text-xl`) | 600 (semibold) | 1.2 |

Two weights only, matching every other screen in this app: **400 regular** for body/label copy,
**600 semibold** for the page title and card/section headings. A monitor's own label (e.g. "Dell
U2720Q") is rendered at 16px (`text-base`) — the one size between Body and Display — at weight 600,
since it is the card's own title, not body copy; this is still within the declared 400/600 pair and
the 3–4 declared sizes (12 / 14 / 16 / 20).

Buttons and pills across the rest of the app (`SettingsView.vue`, `AppSidebar.vue`) use
`font-medium` (500) — a third weight. This spec does **not** introduce a new 500 weight for THIS
phase's new elements; it reuses those existing button/pill classes verbatim as an inherited,
pre-existing convention (not a new declaration this phase adds), consistent with "don't re-invent
what the app already has."

## Screen Layout

Route: `/monitor-setup` · View: `src/views/MonitorSetupView.vue` · Router meta:
`{ requiresAuth: true }` **only** — mirrors `/services`'s gate, not `/settings`'s
`requiresEditor: true`. Per `92-CONTEXT.md`, any authenticated org member (editor or viewer) can
open and use this screen; do not add `requiresEditor` or any new RBAC tier here.

Page shell — identical wrapper to `SettingsView.vue`:

```
<AppShell>
  <div class="px-6 py-8 max-w-4xl">
    <!-- header: h1 "Monitor Setup" + subtext, mb-6 pb-4 border-b border-gray-800 -->
    <!-- state-driven content below -->
  </div>
</AppShell>
```

- **Page header** (`mb-6 pb-4 border-b border-gray-800`): `<h1 class="text-xl font-semibold
  text-gray-100">Monitor Setup</h1>` + one line of subtext (`text-sm text-gray-400 mt-1`):
  "Set up which screen shows your congregation and which shows your team. You only need to do this
  once per computer."
- Everything below the header is exactly ONE of the states in the state machine — never more than
  one visible at a time (no stacked/competing cards).

### Nav entry point (Claude's discretion per CONTEXT.md, this spec's concrete recommendation)

Add a "Monitor Setup" item to `AppSidebar.vue`'s Group C, placed directly after "Settings"
(`separatorBefore` not repeated — same group). **Gate it on `authStore.orgId` only, matching the
`/services` pattern — do NOT gate it on `authStore.isEditor`** the way the adjacent "Settings" link
is gated, since R267/CONTEXT.md require this screen to be reachable by every authenticated org
member, not just editors. This is a deliberate divergence from its neighbor and should be called out
in the plan so it isn't copy-pasted with the wrong gate.

### State machine (resolved on mount, before rendering)

1. Feature-detect `'getScreenDetails' in window`. **False → State D** immediately. Do not show a
   "Detect" button that would only fail (PITFALLS Pitfall 3 — the fallback is the entry point, not a
   post-failure redirect).
2. True → optionally pre-read `navigator.permissions.query({ name: 'window-management' })` for UI
   state only (never as the actual gate — PITFALLS Pitfall 1).
   - If it reports `'granted'`: a fresh user gesture is not required to call `getScreenDetails()`
     again once already granted for this origin — auto-call it on mount (no button click needed).
     This is what makes a RETURNING visit to this screen (and, later, the Run flow) feel like the
     "one click, ever" experience R268 describes. Proceed to step 3 with the resolved screen list.
   - Otherwise (`'prompt'`, `'denied'`, or the query itself unsupported): render **State A** and wait
     for the "Detect My Monitors" click. The click handler calls `getScreenDetails()` synchronously,
     first line, with no `await` before it (PITFALLS Pitfall 1/9).
3. `getScreenDetails()` resolves with a live screen list →
   - `loadMapping()` returns `null` (nothing saved) → **State B** (fresh, nothing pre-selected).
   - `loadMapping()` returns a mapping and `matchMapping(saved, live).status === 'matched'` →
     **State B2**.
   - `loadMapping()` returns a mapping and `matchMapping(...).status === 'needs-reprompt'` →
     **State B3** (banner + State B's editable grid, nothing pre-selected — never guess, PITFALLS
     Pitfall 2).
4. `getScreenDetails()` rejects (any rejection, not just `NotAllowedError`) → **State C**.

### State A — Before detection (permission `prompt`, first visit or first click needed)

Single centered hero card (`bg-gray-900 border border-gray-800 rounded-lg p-6`, content
`text-center`, `max-w-md mx-auto`):
- Monitor-glyph icon, `h-10 w-10 text-gray-600`, centered.
- Heading (`text-base font-semibold text-gray-100 mt-3`): "Set up your displays"
- Body (`text-sm text-gray-400 mt-1`): "Click below to find the monitors connected to this
  computer."
- Primary button (`mt-4`, full CTA styling below): **"Detect My Monitors"**
- Below the button, a small escape hatch (`text-xs text-gray-500 hover:text-gray-300 underline
  underline-offset-2 mt-3`): "Set up manually instead" — jumps straight to State C's fallback panel
  without waiting for a permission failure, for an operator who already knows this browser/profile
  won't cooperate.

Button label swaps to "Detecting…" (disabled, `opacity-60`) between click and
`getScreenDetails()` settling — same pattern as `SettingsView.vue`'s `Saving...`/`Saved!` swap, no
separate spinner component.

### State B — Monitors detected, editable (permission granted, nothing saved yet, or a forced
reassignment from State B3)

- Section row: `<h2 class="text-sm font-semibold text-gray-300">Your displays</h2>` + a small
  secondary "Re-detect" button (`text-xs`, `bg-gray-800 hover:bg-gray-700 text-gray-300 rounded-md
  px-3 py-1.5`) at the row's right edge, for a mid-session replug refresh without a full page reload.
- Monitor grid: `grid grid-cols-1 md:grid-cols-2 gap-4 mt-3`. One card per detected screen
  (`bg-gray-900 border border-gray-800 rounded-lg p-4`):
  - Row 1: monitor label (`text-base font-semibold text-gray-100 truncate`) + inline "Primary"
    badge (only if `isPrimary`) — reuses `SongBadge.vue`'s pill shape: `inline-flex items-center
    px-2 py-0.5 rounded text-xs font-medium bg-gray-800 text-gray-300 border border-gray-700`.
  - Row 2 (`text-xs text-gray-500 mt-0.5`): resolution, e.g. "1920 × 1080".
  - Row 3 (`mt-3`): the role selector — two pill buttons, "Audience" and "Confidence", grouped as
    `role="radiogroup" aria-label="Role for {label}"` (see Interaction & Keyboard below).
    Selected: `bg-indigo-600/20 text-indigo-300 border border-indigo-600` (matches
    `AppSidebar.vue`'s active-nav-link treatment exactly). Unselected: `bg-gray-800 text-gray-400
    border border-gray-700 hover:bg-gray-700`.
  - Row 4 (`text-xs text-gray-500 mt-1.5`), static caption under the pills (not per-selection):
    "Audience — what the congregation sees · Confidence — what your team sees".
  - Selecting a role on one card automatically clears that same role from whichever other card
    previously held it (exclusive across the whole grid, not per-card) — enforced in component
    state, not by native radio-name grouping (see Interaction & Keyboard).
- Action row (`mt-6 flex items-center gap-3`):
  - Primary "Save monitor setup" button — disabled until Audience and Confidence are both assigned
    AND point at two *different* monitors.
  - Inline validation copy (`text-red-400 text-sm`) when the same monitor is picked for both roles:
    "Choose two different displays for Audience and Confidence."
  - On successful save, the action row swaps to a persistent confirmation strip: checkmark icon +
    `text-green-400 text-sm font-medium` **"Saved for this device"**, plus a `text-xs text-gray-400
    underline` **"Change"** link that reopens the editable grid (pre-filled with the just-saved
    selections, not blanked).

### State B2 — Already configured, saved mapping still matches (R268's silent-reuse case)

Skips State A/B entirely on a matching load. A single condensed summary card
(`bg-gray-900 border border-gray-800 rounded-lg p-4`):
- Checkmark icon (`text-green-400`) + heading (`text-base font-semibold text-gray-100`):
  "Your displays are set up"
- Body (`text-sm text-gray-400 mt-1`): "This computer's setup still matches what you saved —
  nothing to do."
- Read-only recap, two rows (`text-sm text-gray-300 mt-3`): "Audience → {label} ({resolution})" /
  "Confidence → {label} ({resolution})".
- Secondary "Reassign roles" button (`bg-gray-800 hover:bg-gray-700`, `mt-4`) — expands in place
  into the full editable State B grid, pre-selected with the current saved assignments (this is the
  ONE case where pre-selection is correct, since it's a confirmed-matching reassignment, not a
  layout-changed reprompt).

### State B3 — Saved mapping no longer matches (layout changed — R268's re-prompt case)

Amber banner card (`bg-amber-900/20 border border-amber-800/60 rounded-lg p-4 mb-4`, above the
grid): exclamation-triangle icon (`text-amber-300`) + heading (`text-sm font-semibold
text-amber-200`): "Your monitor setup changed" + body (`text-xs text-amber-200/80 mt-1`): "We found
different displays than last time. Please assign roles again below." Directly below: State B's
editable grid, rendered with **nothing pre-selected** — never guess a new mapping from a stale one
(PITFALLS Pitfall 2).

### State C — Permission denied (first-class, not an error toast)

Replaces the "Detect" hero entirely with a fallback panel card
(`bg-gray-900 border border-gray-800 rounded-lg p-6`):
- Heading (`text-base font-semibold text-gray-100`): "No problem — let's set this up by hand"
- Body (`text-sm text-gray-400 mt-1`): "Your browser blocked automatic detection. You can still get
  both displays working with a few clicks:"
- Numbered instructional list (`text-sm text-gray-300 mt-4 space-y-2 list-decimal list-inside`):
  1. "When you click Run on a locked service, two windows will open — one for the Audience display,
     one for the Confidence monitor."
  2. "Drag each window onto the correct physical screen."
  3. "Click the Fullscreen button in each window."
- Closing line (`text-xs text-gray-500 mt-4`): "You'll do this each time you Run a service on this
  browser." — **deliberately does NOT claim the browser "remembers" this setup**: without screen
  enumeration there is no fingerprint to persist, so promising persistence here would be a false
  claim (see UI Considerations row on this).
- "Try automatic detection again" link (`text-xs text-gray-500 hover:text-gray-300 underline
  underline-offset-2 mt-3`) — re-attempts `getScreenDetails()` from a fresh click, in case the
  operator flips the site's permission setting later.

### State D — API unavailable (non-Chromium browser)

The exact same fallback panel component as State C, with only the heading/body swapped (see
Copywriting Contract) — never a separate "unsupported browser" error screen. No "Detect My
Monitors" button is rendered anywhere in this state.

## Interaction & Keyboard

- Every interactive element is a native `<button>` (or a native `<input type="radio">` visually
  styled as a pill) — Enter/Space activate by default, no custom key handling required.
- Tab order follows DOM order top-to-bottom: primary CTA (State A) → per-card role pills, left to
  right then top to bottom through the grid → Save button → (once saved) Change link.
- Role pills: implement each monitor card's Audience/Confidence pair as `role="radiogroup"
  aria-label="Role for {label}"` containing two `role="radio" aria-checked="{true|false}"` buttons.
  Cross-card exclusivity (selecting Audience on card 2 clears it from card 1) is enforced in the
  parent's selection state and reflected by updating `aria-checked` on the previously-selected
  card's pill — not by native `name`-based radio grouping, since the exclusivity is per-ROLE across
  ALL cards, not within one card.
- No new global keyboard shortcuts (arrows, Escape-to-exit, etc.) belong on this screen — those are
  Phase 95's Run/Control-screen territory. This is an ordinary form page with ordinary Tab/Enter
  semantics only.
- The "Detect My Monitors" click handler is the single most gesture-sensitive line in this phase:
  `getScreenDetails()` must be the FIRST statement in the handler, with no `await`, store dispatch,
  or router action ahead of it (STACK.md, PITFALLS Pitfall 1).
- Labels: every input-like control has a visible, associated label (native `<label>` for text/select
  inputs elsewhere in the app; `aria-label`/`aria-labelledby` for the icon-only or pill-shaped
  controls here) — consistent with the app's existing WAI-ARIA usage in `SettingsView.vue`
  (`v-model` + adjacent `<label>` pairs) and `RosterView.vue`'s `aria-label="Close"` pattern.

## Responsive & Dark-Mode Notes

- Dark-mode only — this app has no light-theme toggle anywhere; this screen does not introduce one.
  All colors above are the app's one canonical palette (`gray-950`/`gray-900`/`gray-800`), not a
  `dark:` variant pair.
- This is fundamentally a desktop/booth-laptop task (Chrome/Edge + physical multi-monitor hardware),
  but the page must still not break on a narrow viewport since `AppShell.vue`'s responsive sidebar
  applies globally: the monitor grid collapses `grid-cols-1 md:grid-cols-2`, and the fallback
  panel's numbered list is already single-column at every width.
- No new breakpoints — reuse Tailwind's existing `md:`/`lg:` usage exactly as `AppShell.vue`/
  `AppSidebar.vue` already do; no bespoke breakpoint logic for this screen.
- Touch targets: buttons use the app's existing `px-4 py-2`/`px-5 py-2.5` sizing; role pills should
  use at least `py-2` to stay consistent with that sizing floor — an app-wide convention, not a new
  deviation introduced here.

## UI Considerations

Applicable state considerations resolved: 9 covered, 2 backstop, 1 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | monitor list | ✅ covered | The Window Management API always returns at least one screen (the display running the browser) — a true empty-list state is not reachable and this screen does not need to design for it. |
| zero-one-many | monitor count | ✅ covered | The grid (`grid-cols-1 md:grid-cols-2`) renders 1 card through N cards identically; no special-casing for the common 2-monitor case vs. 3+. |
| long-text | monitor label | 🧪 backstop | OS-provided screen labels (e.g. long manufacturer strings) truncate (`truncate`) on the card's label row rather than wrapping and breaking card height; exact real-world label strings can't be scripted, so verify visually once real hardware is available (per `92-CONTEXT.md`'s human-UAT note). |
| loading | Detect click → `getScreenDetails()` settling | ✅ covered | The button label swaps to disabled "Detecting…" between click and resolve/reject, mirroring `SettingsView.vue`'s `Saving.../Saved!` label-swap — no separate spinner component. |
| error | permission denied | ✅ covered | Routes directly to the first-class fallback panel (State C), never a toast or dead click (CONTEXT.md decisions; PITFALLS Pitfall 1/3). |
| error | API unavailable (non-Chromium) | ✅ covered | Feature-detected on mount before any button renders — the fallback panel (State D) is the ENTRY POINT, not a post-failure redirect (PITFALLS Pitfall 3). |
| partial | same monitor assigned to both roles | ✅ covered | Save stays disabled with inline validation copy until Audience and Confidence point at two different monitors. |
| populated | saved mapping matches live screens | ✅ covered | Renders the condensed "already configured" summary (State B2) instead of the full editable grid, satisfying R268's silent-reuse requirement. |
| populated | saved mapping stale (layout changed) | ✅ covered | Renders the amber "setup changed, please reassign" banner (State B3) above a forced-blank editable grid — never pre-guesses the new mapping (PITFALLS Pitfall 2). |
| overflow | many monitors (3+, e.g. via a dock/hub) | 🧪 backstop | Grid wraps to additional rows at `md:grid-cols-2`; not exercised against real 3+-monitor hardware in this spec — flagged for the human-UAT pass `92-CONTEXT.md` already defers. |
| error | `saveMapping()` silent no-op (private-mode/disabled storage, by `monitorConfig.ts` design) | ⚠ unresolved | `saveMapping()` never throws and silently no-ops on a storage failure (T-91-04, by design). This screen currently has no signal to distinguish a successful save from a silent no-op, so "Saved for this device" could render even when nothing persisted. Planner should decide: add a `saveMapping` → `loadMapping` round-trip check before showing the confirmation, or explicitly accept the silent-no-op risk as out of scope for this phase. |
| long-text | fallback-panel instructional copy on a narrow viewport | ✅ covered | The numbered list is paragraph copy in a single column at every width inside `max-w-4xl` — no truncation risk, unlike a fixed-width label. |
