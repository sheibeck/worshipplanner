# Phase 98 — UI Design Contract

> Visual and interaction contract for the Automatic Fullscreen setup helper, an additive section on
> `MonitorSetupView.vue`. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

| Property | Value |
|----------|-------|

Declared values (must be multiples of 4), reusing the scale already in `MonitorSetupView.vue`:

| Token | Value | Usage |
|-------|-------|-------|

| sm | 8px | Compact spacing (`gap-2`, `mt-1.5`/`mt-2`) — icon+heading rows, badge padding |
| md | 16px | Default element spacing (`p-4`, `mt-3`/`mt-4`) — card internal padding, button-to-text gaps |

| xl | 32px | Gap between the new Automatic Fullscreen panel and the existing monitor-assignment grid above it (`mt-8`) |

Exceptions: none. The 44px touch-target minimum does not apply — this is a desktop-only,
mouse/keyboard admin flow (setting a browser policy requires a desktop OS), so no icon-only touch
targets are introduced.

## Component Inventory & Structure

### New files

1. **`src/components/FullscreenSetupPanel.vue`** — the panel itself (status + download + confirm +
   troubleshooting). Self-contained; takes no required props (reads `window.location.origin` and
   `navigator.userAgentData`/UA string internally, mirroring how `useOutputWindow.ts` reads
   `navigator.permissions` internally rather than via props).
2. **`src/composables/useFullscreenReadiness.ts`** — owns the `navigator.permissions.query({
   name: 'fullscreen', allowWithoutGesture: true })` check (verbatim reuse of the descriptor
   `attemptAutoFullscreen()` in `useOutputWindow.ts` already uses), exposing a `status: 'checking' |
   'ready' | 'not-ready' | 'unsupported'` ref, a `recheck()` method, and a window-`focus` listener
   registered in its own `onMounted`/removed in `onUnmounted` (self-correcting behavior, R287).
3. **`src/utils/fullscreenPolicyFiles.ts`** — pure, framework-free (mirrors `monitorConfig.ts`'s
   style) generator functions: `buildWindowsRegFile(origin, scope: 'HKCU' | 'HKLM')`,
   `buildMacProfile(origin)`, `buildLinuxPolicyJson(origin)`, plus `detectOsAndBrowser()` (feature
   + UA-based, no dependency). Origin is ALWAYS taken from `window.location.origin`, never
   hardcoded — this is the load-bearing decision in 98-CONTEXT.md §Decision 2.

### Placement in `MonitorSetupView.vue`

Add `<FullscreenSetupPanel class="mt-8" />` **once, at the bottom of the page**, **outside and below**
the existing `phase`-based `v-if`/`v-else` chain (i.e., it is NOT one of the mutually-exclusive
`prompt`/`detecting`/`denied`/`manual`/`unavailable`/`granted` branches — it renders unconditionally,
in every phase). Rationale: automatic-fullscreen readiness is gated by a completely different
browser permission (`fullscreen`, not `window-management`) and is relevant even to an operator who
chose "Set up manually instead" or whose window-management permission is denied — those operators
still benefit from auto-fullscreen on whichever window they do open. This keeps the panel additive
and never blocks or reorders the existing monitor-assignment UI above it (Preserve constraint in
98-CONTEXT.md).

```
<div class="px-6 py-8 max-w-4xl">
  <!-- existing page header -->
  <!-- existing phase-based v-if/v-else chain (unchanged) -->

  <FullscreenSetupPanel class="mt-8" data-testid="fullscreen-setup-panel" />
</div>
```

### Panel shell (all states)

```html
<div class="rounded-lg bg-gray-900 border border-gray-800 p-4" data-testid="fullscreen-setup-panel">
  <h2 class="text-base font-semibold text-gray-100">Automatic fullscreen</h2>
  <p class="text-xs text-gray-500 mt-1">
    One-time setup so both displays go fullscreen on their own when you click Go live — no per-window clicking.
  </p>
  <!-- state body below, one of: checking / ready / not-ready / unsupported -->
</div>
```

The heading + subhead are constant across all four states (never re-worded per state) — only the
status body below changes. This keeps the panel recognizable and avoids restating "what is this
for" every time it re-renders.

## State 1 — `checking` (transient, on mount and during `recheck()`)

Brief, non-alarming, shown only until the permission query resolves (typically < 1 frame; guard
against flash-of-loading by not adding an artificial delay).

```html
<div class="flex items-center gap-2 mt-3" data-testid="fullscreen-setup-status-checking">
  <svg class="h-4 w-4 text-gray-500 animate-spin" ...><!-- simple spinner path --></svg>
  <span class="text-sm text-gray-400">Checking this computer's setup…</span>
</div>
```

No button is shown while checking (the Confirm button below is what triggers a re-check — showing
it disabled here is unnecessary chrome for a sub-second state).

---

## State 2 — `ready` ✓ (positive, minimal, no action needed)

```html
<div class="flex items-center gap-2 mt-3" data-testid="fullscreen-setup-status-ready">
  <svg class="h-5 w-5 text-green-400" ...><!-- check-circle, identical path to the existing
       "Your displays are set up" icon in MonitorSetupView.vue --></svg>
  <span class="text-sm font-semibold text-green-400">
    This computer is set up for automatic fullscreen.
  </span>
</div>
```

No CTA, no download block, no troubleshooting — deliberately minimal per 98-CONTEXT.md ("Minimal,
reassuring, no action needed"). This is the terminal, steady state the other two states are
working toward.

## State 3 — `not-ready` (neutral/attention, primary flow)

```html
<div class="mt-3" data-testid="fullscreen-setup-status-not-ready">
  <div class="flex items-center gap-2">
    <svg class="h-5 w-5 text-amber-300" ...><!-- info/exclamation-triangle, identical path family
         to the existing "Your monitor setup changed" icon --></svg>
    <h3 class="text-sm font-semibold text-amber-200">One-time setup needed</h3>
  </div>
  <p class="text-sm text-gray-400 mt-1">
    This computer hasn't been set up for automatic fullscreen yet. Download the setup file below,
    run it once, then come back here.
  </p>

  <!-- Primary download -->
  <button
    type="button"
    data-testid="fullscreen-setup-download-button"
    class="mt-4 inline-flex items-center justify-center gap-2 bg-indigo-600 hover:bg-indigo-500 text-white rounded-md px-4 py-2 text-sm font-medium transition-colors"
    @click="onDownload"
  >
    Download setup file for {{ browserLabel }} on {{ osLabel }}
  </button>

  <!-- Windows-only secondary link, no admin badge/lock icon — deliberately quiet -->
  <p v-if="os === 'windows'" class="text-xs text-gray-500 mt-2">
    No admin rights on this computer?
    <button
      type="button"
      data-testid="fullscreen-setup-admin-download-link"
      class="text-gray-400 hover:text-gray-200 underline underline-offset-2"
      @click="onDownloadAdmin"
    >
      Download the admin (IT-installed) version instead
    </button>
  </p>

  <!-- Per-OS numbered instructions -->
  <ol class="text-sm text-gray-300 mt-4 space-y-2 list-decimal list-inside" data-testid="fullscreen-setup-instructions">
    <li>Download the file above.</li>
    <li><!-- OS-specific verb, see Copywriting Contract --></li>
    <li>Fully quit and reopen {{ browserLabel }} (closing the tab is not enough).</li>
    <li>Come back to this page and click <strong>Confirm fullscreen support</strong> below.</li>
  </ol>

  <!-- Honest friction caveat — inline helper text directly under the steps, not buried -->
  <p class="text-xs text-amber-300/80 mt-3" data-testid="fullscreen-setup-caveat">
    <!-- OS-specific, see Copywriting Contract -->
  </p>

  <button
    type="button"
    data-testid="fullscreen-setup-confirm-button"
    class="mt-4 inline-flex items-center justify-center gap-2 bg-indigo-600 hover:bg-indigo-500 text-white rounded-md px-4 py-2 text-sm font-medium transition-colors"
    @click="onConfirm"
  >
    Confirm fullscreen support
  </button>
</div>
```

**Confirm button placement rule:** it always sits directly under the caveat, as the last element of
the not-ready block — the natural "I did the steps, now check" action. It is the SAME button
(same testid) used for the on-demand re-check after a failed attempt (State 3b below); it never
duplicates.

## State 3b — Troubleshooting (shown after a `Confirm` click that is STILL not-ready)

Appended below the Confirm button, not replacing anything above it — the operator can retry the
same download/instructions without losing them.

```html
<div class="mt-4 pt-4 border-t border-amber-800/40" data-testid="fullscreen-setup-troubleshooting">
  <h4 class="text-xs font-semibold text-amber-200/90 uppercase tracking-wide">Still not working?</h4>
  <ul class="text-xs text-gray-400 mt-2 space-y-1.5 list-disc list-inside">
    <li>Make sure you fully quit {{ browserLabel }} (all windows) and reopened it — a policy change only takes effect after a full restart, not a tab refresh.</li>
    <li v-if="os === 'windows'">If your IT department locks down the registry, ask them to install the <button type="button" class="underline" @click="onDownloadAdmin">admin version</button> instead.</li>
    <li v-else>If you don't have an administrator password on this computer, ask whoever manages it to run the setup file.</li>
    <li>Using Firefox, Safari, or another non-Chromium browser? Automatic fullscreen setup isn't available there — switch to Chrome or Edge, or keep using the "Fullscreen displays" button / tap-to-fullscreen when you Run a service (works today either way).</li>
  </ul>
</div>
```

`fullscreen-setup-troubleshooting` only mounts after at least one `Confirm` click has resolved to
`not-ready` (i.e., not on first paint) — it is a response to an attempt, not upfront noise.

---

## State 4 — `unsupported` (muted/informational, never a dead end)

Shown when the permission descriptor throws (non-Chromium) or `navigator.permissions` itself is
absent.

```html
<div class="mt-3" data-testid="fullscreen-setup-status-unsupported">
  <div class="flex items-center gap-2">
    <svg class="h-5 w-5 text-gray-500" ...><!-- info-circle, same family as MonitorFallbackPanel's icon --></svg>
    <h3 class="text-sm font-semibold text-gray-300">Not available in this browser</h3>
  </div>
  <p class="text-sm text-gray-400 mt-1">
    Automatic multi-monitor fullscreen needs Chrome or Edge on this computer. You can still run
    services here — each display just needs one tap to go fullscreen, or use the
    <strong class="text-gray-300">"Fullscreen displays"</strong> button on the Run screen.
  </p>
  <button
    type="button"
    data-testid="fullscreen-setup-confirm-button"
    class="mt-3 text-xs text-gray-500 hover:text-gray-300 underline underline-offset-2"
    @click="onConfirm"
  >
    Check again
  </button>
</div>
```

Note the Confirm button is visually DEMOTED here (quiet text-link style, not the indigo primary
button) — in the unsupported state there is usually nothing new to check (the browser itself
doesn't support the API), so it reads as "just in case you switched browsers," not a call to
action. Same `data-testid="fullscreen-setup-confirm-button"` — one stable hook regardless of which
visual treatment it takes in a given state, since it always does the same thing (`recheck()`).

## Self-Correcting Behavior (R287)

- **Re-check triggers:** (1) the `Confirm fullscreen support` / `Check again` button click, (2) a
  `window` `focus` event fired while `status !== 'ready'` (registered by `useFullscreenReadiness`'s
  own `onMounted`, matching the composable-owns-its-lifecycle idiom of `useOutputWindow.ts`; removed
  in `onUnmounted`). Do NOT re-check on every focus once `ready` — no need to keep polling a
  confirmed-good state.
- **No reload required:** flipping `status` from `not-ready`/`unsupported` to `ready` is a plain
  reactive ref update — the whole not-ready block (download button, instructions, caveat,
  troubleshooting) unmounts and the ready block mounts in place, same as how `MonitorSetupView.vue`
  already swaps `phase`-based branches without a reload.
- **Never regress a previously-ready state:** if a `recheck()` ever resolves to something other than
  `'granted'` after having been `ready` (e.g., an admin revoked the policy), degrade to `not-ready`
  --- do not silently keep showing "ready ✓" (dishonest status is explicitly disallowed by R277's
  precedent on this same milestone: "no alarming/false status").

## Data-testid Hooks (executor contract)

Reusing the exact kebab-case, semantic-name convention already in `MonitorSetupView.vue`/
`MonitorCard.vue` (`detect-button`, `save-button`, `monitor-role-{fingerprint}-{role}`,
`refresh-kept-notice`) — every new hook is prefixed `fullscreen-setup-` so it never collides with
the existing monitor-assignment testids on the same page:

| testid | Element | Present in states |
|--------|---------|--------------------|
| `fullscreen-setup-panel` | Root panel container | all |
| `fullscreen-setup-status-checking` | Loading status row | checking |
| `fullscreen-setup-status-ready` | Ready status row | ready |
| `fullscreen-setup-status-not-ready` | Not-ready status block | not-ready |
| `fullscreen-setup-status-unsupported` | Unsupported status block | unsupported |
| `fullscreen-setup-download-button` | Primary "Download setup file for…" button | not-ready |
| `fullscreen-setup-admin-download-link` | Windows-only "admin version" link | not-ready, Windows only |
| `fullscreen-setup-instructions` | Numbered `<ol>` steps | not-ready |
| `fullscreen-setup-caveat` | Honest-friction inline note | not-ready |
| `fullscreen-setup-confirm-button` | Confirm/Check-again button (same hook, both visual treatments) | not-ready, unsupported |
| `fullscreen-setup-troubleshooting` | "Still not working?" block | not-ready, only after a resolved-still-not-ready `Confirm` click |

Accessibility hooks (non-testid, still contractual):
- Every status block's icon+text pairing satisfies "non-color-only" (icon shape AND text both
  change per state — checkmark/"set up", triangle/"setup needed", info-circle/"not available" —
  never color alone), matching `MonitorFallbackPanel.vue`'s existing pattern.
- `fullscreen-setup-download-button` and `fullscreen-setup-confirm-button` are real `<button
  type="button">` elements (never `<div onclick>`), inheriting the existing
  `focus:outline-none focus:ring-1 focus:ring-indigo-500` focus-visible treatment used throughout
  `MonitorCard.vue`.
- The troubleshooting `<ul>` uses plain semantic list markup (`list-disc list-inside`), screen-reader
  navigable without additional ARIA.
