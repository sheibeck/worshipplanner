<objective>
Layer the output-window integration seam onto RunControlView: give the operator an EXPLICIT "Go live"
control that, on click, opens BOTH output windows and places them on their assigned monitors in the
sanctioned direct-handler path, with a first-class amber fallback when the monitors aren't matched and an
honest blocked state when the browser refuses the pop-ups. This is what makes the control screen "stay in
charge of both output windows" — the channel writer from 95-03 already drives state; this plan gives it real
windows to drive, opened and positioned from a fresh operator gesture on the control screen itself.

Purpose: R261 (the control screen opens/owns the standalone output windows) and R266 (the single-selection
state drives real audience + confidence outputs). The open+place runs SYNCHRONOUSLY in the Go live click so
window.open and requestFullscreen({screen}) execute within that click's live transient activation (the same
idiom MonitorSetupView uses for getScreenDetails). Every failure mode — needs-reprompt / denied / unavailable
/ blocked pop-out — degrades calmly and HONESTLY: matched → placed windows; not-matched → un-positioned
pop-outs + the amber "Finish setting up your displays" banner; pop-up-blocked (window.open null) → a distinct
"your browser blocked the display windows" banner that never claims success. Never a dead end, never a throw.

Output: an extended src/views/RunControlView.vue. Orchestration + placement + fallback + blocked behavioral
tests land in 95-06. Real two-monitor open+place+fullscreen is human-UAT (deferred to milestone end).
</objective>

<ui_spec_deviation>
The 95-UI-SPEC §5 was written assuming the outputs auto-open on Run (i.e. from the control screen's mount).
This plan DIVERGES: it opens the outputs from an explicit "Go live / Open displays" gesture on the control
screen instead. This is a small, forced, justified divergence — NOT a scope change. Rationale: window.open
(pop-up blocker) and requestFullscreen({screen}) both require live transient user activation traceable to a
gesture task, and after the Run click's router.push (History pushState) + the lazy route-chunk import() + any
async auth/org beforeEach guard + the mount tick, Chrome/Edge no longer honor that activation on mount — the
pop-up is blocked and fullscreen is rejected. Auto-opening on mount would therefore silently open ZERO
windows on a cold first Run while the UI claimed success. The explicit gesture restores a fresh, live
activation for BOTH window.open and requestFullscreen. Everything else in §5 (the three-state matched /
needs-reprompt / unavailable language, the amber fallback banner copy + 3-step list + monitor-setup link, the
colorblind-safe status dots) is honored verbatim, plus one added HONEST state ('blocked') for the pop-up-blocked
case. The executor and UI-checker should treat the Go live control + the 'blocked' banner as PLANNED, not
unplanned, per this note.
</ui_spec_deviation>
