# Phase 95 — UI Design Contract

> Visual and interaction contract for the Run/Control screen + Run entry point. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. This is the **operator surface** a non-technical
> projectionist drives under live-service pressure — every decision below optimizes for calm,
> unmistakable, one-glance control. Match the existing dark-mode Tailwind language (see
> `MonitorSetupView.vue`, `PresentationViewer.vue`, `ServiceEditorView.vue`); do NOT introduce a new
> visual system.

## Spacing Scale

Declared values (all multiples of 4 — matches the app's Tailwind usage):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, kbd-chip inner padding |
| sm | 8px | Compact stacking (status pills, legend chips) |
| md | 16px | Default padding inside rail items, panels, dialog body rhythm |
| lg | 24px | Preview-stage padding, dialog header/footer padding |
| xl | 32px | Gap between the large current preview and the next preview |
| 2xl | 48px | Reserved — not needed on this screen |
| 3xl | 64px | Reserved — not needed on this screen |

Exceptions:
- **Interactive touch targets: 44px minimum** (`min-h-11 min-w-11`). Applies to rail item rows, the
  Exit button, keyboard-nav chrome, and both dialog buttons — the operator may be reaching under
  low-light live conditions. This mirrors `PresentationViewer.vue`'s `min-h-11 min-w-11` exit/nav
  buttons.

## Typography

Exactly 4 sizes, exactly 2 weights (matches app convention). NOTE: the slide **previews** render via
`SlideCanvas` and carry their OWN per-slide typography (`--slide-font-*`) — the rows below govern only
the operator **chrome** around the previews.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display (screen title / service name) | 20px (`text-xl`) | 600 (`font-semibold`) | 1.2 |
| Heading (panel/dialog titles, "Order of Service") | 16px (`text-base`) | 600 (`font-semibold`) | 1.3 |
| Body / rail item label | 14px (`text-sm`) | 400 (`font-normal`); active rail item + status labels 600 | 1.5 |
| Hint / keyboard legend / slide counts | 12px (`text-xs`) | 400 (`font-normal`) | 1.4 |

Weights: **400 regular** and **600 semibold** only. No other weights.

## Color

Dark-mode operator surface. The 60/30/10 split below maps to the app's existing gray/indigo language.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `gray-950` (#030712) page canvas; `gray-900` (#111827) rail & panels | Full-viewport background, order-of-service rail, status/preview panels |
| Secondary (30%) | `gray-800` (#1f2937) borders & secondary buttons; `gray-300/400/500` text ramp | Dividers, secondary/ghost buttons, body/hint text hierarchy |
| Accent (10%) | `indigo-600` (#4f46e5) fills, `indigo-500` (#6366f1) rings/bars | See reserved list below |
| Destructive | `red-600` (#dc2626) | The Escape-exit confirm's primary "Exit run mode" button ONLY |
| Live / on-air status | `red-500` (#ef4444) dot + `green-400` (#4ade80) / `amber-300/400` (#fbbf24) status dots | Semantic **status** signaling only (see note) — never a fill or CTA |

**Accent (indigo) reserved for:** the Run entry button (primary CTA), the active order-of-service item's
left-border bar + tinted background, the ring framing the **current** (live) preview pane, and focus
rings (`focus:ring-indigo-500`). NOT used for the next-preview frame, not for body text, not for
generic hover.

**Live / on-air status note (deliberate second red usage — flag to checker, justified):** the screen
uses red in TWO distinct, non-overlapping roles: (1) a small **on-air `LIVE` badge** — a `red-500` dot
plus the literal text "LIVE" on a `gray-900/80` pill pinned to the current preview (broadcast
convention; communicates R266 "what you see large IS on the projector now"), and (2) the **destructive
`red-600` confirm button** in the Escape-exit dialog. Both are intentional and separated by role. The
LIVE badge NEVER carries meaning by color alone — the word "LIVE" is always present (colorblind-safe).
Output-status dots reuse Phase 92's semantics: **green-400 = ready/matched**, **amber-300/400 =
fallback/needs-attention**, never red (an un-placed output is a calm amber fallback, not an error).

## Layout & Component Contract

> This section is the prescriptive layout the planner/executor implement. It is the heart of the
> contract; the checker validates copy/color/spacing/typography against it.

### 0. Surface shell

- `RunControlView.vue` at `/run/:serviceId` renders a **full-viewport, standalone dark surface** —
  **NOT** wrapped in `AppShell`. Rationale: R261 mandates a "dedicated standalone screen (not the
  service editor)"; the operator needs a calm, single-purpose surface with no app nav to fat-finger
  mid-service. The ONLY way out is the Exit affordance → confirm (R265).
- Root: `class="fixed inset-0 flex flex-col bg-gray-950 text-gray-100"`.
- Three horizontal bands: **top bar** (fixed height `h-14`), **main region** (`flex-1 min-h-0`),
  **bottom legend strip** (`h-9`). An optional **fallback banner** slots between top bar and main
  region when outputs are un-placed (see §5).

### 1. Top bar (`h-14`, `bg-gray-900`, `border-b border-gray-800`, `px-6 flex items-center gap-4`)

- **Left:** service name / date (`text-xl font-semibold text-gray-100`, truncate).
- **Center-right (`ml-auto`):** the **output status cluster** (§5 happy-path pills).
- **Far right:** the **Exit button** — a ghost icon button (X glyph, `min-h-11 min-w-11`,
  `text-gray-300 hover:text-white`, `aria-label="Exit run mode (Esc)"`). Click → opens the Exit confirm
  dialog (§4), identical to pressing Escape. It is ALWAYS visible (never opacity-faded — unlike
  PresentationViewer, this is a lit control room, not a projection).

### 2. Order-of-service rail (R262 / R263) — left column of the main region

- Container: `w-80 flex-none h-full overflow-y-auto bg-gray-900 border-r border-gray-800`.
- Sticky header inside: **Order of Service** (`text-base font-semibold text-gray-100`, `px-4 py-3
  border-b border-gray-800`).
- Data source: `sortedSlotsWithIndex(service)` (Phase 91) — the SAME ordering the assembler uses.
- **Each item is a full-width row button**, `w-full text-left px-3 py-2.5 min-h-11 rounded-md flex
  items-start gap-3`, showing: section label (`text-xs text-gray-500`) above the item title
  (`text-sm text-gray-300`), with a right-aligned **slide count** (`text-xs text-gray-500`).
- **Item states (three, explicit):**
  1. **Default (has slides, not current):** `text-gray-300`, `hover:bg-gray-800/60`,
     `cursor-pointer`. Whole row is the click affordance → jumps live output to that item's first
     assembled slide via `firstAssembledIndexBySlot(slides).get(slotIndex)`.
  2. **Active ("you are here" — the item whose `slot` index === `currentSlide.slotIndex`):**
     `bg-indigo-600/15`, a **`border-l-2 border-indigo-500`** accent bar, title promoted to
     `text-gray-100 font-semibold`, plus a small `indigo-400` filled dot / `▸` marker before the
     title. This is the R262 "you are here" highlight — unmistakable at a glance, driven by
     `currentSlide.slotIndex`, and it MUST auto-scroll into view when the current slide changes
     (`scrollIntoView({ block: 'nearest' })`).
  3. **No assembled slides (absent from `firstAssembledIndexBySlot`):** rendered as a **non-interactive
     `<div>` (not a button)**, `text-gray-600`, `cursor-default`, no hover, secondary line **No
     slides**, `aria-disabled="true"`. Clicking is a no-op. It reads visibly dimmer than a live item.
- Rail empty state (locked service, zero assembled slides anywhere): the empty-state heading + body
  from the Copywriting Contract, centered in the rail, `text-gray-400`.

### 3. Dual preview stage (R264 / R266) — flex-1 center/right of the main region

- Container: `flex-1 min-w-0 h-full p-6 lg:p-8 flex flex-col`.
- **Proportion / placement:** the **current** preview is dominant. Use a responsive grid:
  `grid grid-cols-1 lg:grid-cols-3 gap-8 items-start`, where the **current** pane spans
  `lg:col-span-2` and the **next** pane spans `lg:col-span-1`. Below `lg`, they stack (current on top,
  next beneath). Each pane is a fixed **16:9** box (`aspect-video`) so it mirrors the audience
  projector exactly.
- **Current preview (dominant):**
  - Label row above the pane: the **LIVE** on-air pill — `red-500` dot + the word `LIVE`
    (`text-xs font-semibold`) on a `gray-900/80` `rounded-full px-2.5 py-1` pill. This is the R266
    "you are live" indicator: it makes it visually obvious the pane IS the projector, so there is NO
    "push to live" button anywhere on the screen.
  - The pane: `<SlideCanvas :slide="currentSlide" :interactive="false" />` inside a
    `rounded-lg overflow-hidden ring-2 ring-indigo-500` frame (the indigo ring = "this is the active,
    selected, live pane"). Backgrounds ARE shown (operator fidelity to the audience output).
  - `current = slides[index]`. If assembly is still loading → the `PresentationViewer` spinner +
    "Loading slideshow…".
- **Next preview (subordinate):**
  - Label above: **Next up** (`text-xs font-semibold text-gray-400`).
  - The pane: `<SlideCanvas :slide="nextSlide" :interactive="false" />`, `rounded-lg overflow-hidden
    ring-1 ring-gray-800` (NO accent ring — reinforces it is NOT live). Visibly smaller (the
    col-span-1 vs col-span-2 does this).
  - `next = slides[index+1] ?? null`. When null, render a `gray-900` placeholder pane with centered
    **End of service** (`text-sm text-gray-500`).
- The size + accent-ring asymmetry (large ringed LIVE current vs small un-ringed Next) is the whole
  point: single-selection is legible without any button or instruction.

### 4. Escape-exit confirmation dialog (R265)

- Reuse the confirm-dialog **shell verbatim** from `DeactivateOrgConfirmDialog.vue` (Teleport,
  backdrop `bg-black/60 z-40`, panel `z-50 max-w-md bg-gray-900 rounded-xl border border-gray-800
  shadow-2xl`, hand-rolled focus trap, focus-on-open lands on **Cancel**, `confirming`-guarded
  dismissal). Copy: heading **Exit run mode?**, body + buttons per the Copywriting Contract.
- **Cancel is the safe default and is focused on open.** The confirm button is `bg-red-600
  hover:bg-red-500` (destructive styling — tearing down a live service is consequential).
- **Escape-key behavior is dual-layered and MUST be correct:** pressing Escape on the control screen
  OPENS this dialog (it does NOT exit). Pressing Escape **while the dialog is already open** cancels
  the dialog (per the shell's own `onKeydown`) — it does NOT confirm. This guarantees a stray/double
  Escape can never tear down the service. Navigation keys (§6) MUST NOT fire while the dialog is open
  or while any input/dialog has focus.
- On confirm: close both output windows, `runChannel.close()`, and `router` back to the service view.

### 5. Output-open + monitor status (the integration seam)

Mirror Phase 92's three-state language (matched / needs-reprompt / unavailable) as **first-class**
states — a fallback is calm, never an error.

- **Happy path (matched):** compact status cluster in the top bar — a green-400 dot + **Displays
  ready**, with two subordinate `text-xs text-gray-400` lines/pills: `Audience → {label}` and
  `Confidence → {label}`. Calm, confirmatory, no call to action.
- **Opening (transient):** **Opening displays…** with the `PresentationViewer` spinner glyph at
  `text-indigo-400`.
- **Fallback (needs-reprompt OR denied/unavailable):** a persistent **amber banner** slotted between
  the top bar and the main region — reuse the `ServiceEditorView.vue` lock-banner idiom
  (`border border-amber-800 bg-amber-950 rounded-md px-4 py-3`, amber warning glyph, `text-amber-200`)
  hosting `MonitorFallbackPanel`'s copy: heading **Finish setting up your displays**, the 3-step
  ordered list (windows opened → drag each to its screen → click Enter fullscreen in each), and an
  **Open monitor setup** link (`text-amber-200 underline` → `/monitor-setup`). The un-positioned
  pop-outs still open; the operator leans on each output window's OWN "Enter fullscreen" affordance
  (Phases 93/94). Amber, never red — this is a supported path, not a failure.
- Status dots are colorblind-safe: every dot is paired with a text label (Ready / Opening / the amber
  banner heading), never color-only.

### 6. Keyboard legend + navigation (R265)

- **Always-visible legend strip** at the bottom (`h-9 bg-gray-900 border-t border-gray-800 px-6 flex
  items-center gap-4 text-xs text-gray-500`). Render each key as a small kbd chip
  (`bg-gray-800 text-gray-300 rounded px-1.5 py-0.5 font-mono text-[11px]`) followed by its action
  label: `→ / Space` Next · `←` Previous · `↑ / ↓` Item · `Esc` Exit. Subtle but permanent — the
  non-technical operator never has to remember the map.
- Key map (match `PresentationViewer.vue`'s `handleKeydown` structure, add/remove listener on
  mount/unmount): **ArrowRight / Space → next slide**; **ArrowLeft → previous slide**;
  **ArrowDown → next order item's first slide**; **ArrowUp → previous order item's first slide**;
  **Escape → open Exit confirm** (§4). Every slide/item change immediately `postState`s with a
  strictly increasing `seq` (R266 single-selection — no push step). Keys are inert while the confirm
  dialog or any input is focused.
- Reserve a UI slot + the `B` key for a FUTURE blackout affordance (per REQUIREMENTS Out-of-Scope
  note) — build NO blackout logic now; just do not bind `B` to anything else.

### 7. Run entry button (R261 / R275)

- Home: the **locked read-only view of `ServiceEditorView.vue`** (primary). Secondary acceptable: the
  services list row. Absent/disabled on a draft (`status === 'draft'`).
- Gate on **org membership (`orgId`), editor OR viewer** — NOT `isEditor`/`canEditService`. Running is
  presentation-only (R275). This is a deliberate divergence from every other action in that view,
  which gate on `canEditService`.
- Appearance: **primary CTA** — `bg-indigo-600 hover:bg-indigo-500 text-white rounded-md px-4 py-2
  text-sm font-medium inline-flex items-center gap-2` with a play ▶ icon and the label **Run**. This
  is the app's established primary-button idiom (`MonitorSetupView.vue`'s Detect/Save buttons). It
  should read as the prominent, welcoming action on a locked service — placed near the service header,
  visually distinct from the amber lock banner's "Reopen for editing" (which only editors see).

## UI Considerations

Applicable state considerations resolved: 6 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | order-of-service rail (locked service, zero assembled slides) | ✅ covered | Rail renders the documented "Nothing to present yet" heading + body; no live item exists so no accent bar shows |
| empty | next-slide preview at the last slide | ✅ covered | Next pane renders the "End of service" placeholder when `slides[index+1]` is null |
| loading | preview panes before assembly completes | ✅ covered | Reuses `PresentationViewer` spinner + "Loading slideshow…" until slides resolve |
| loading | output windows opening / placing | ✅ covered | Status cluster shows "Opening displays…" with the spinner glyph during the open+place gesture |
| error | service fails to load / subscribe | 🧪 backstop | Renders the documented error copy with a refresh path; verified via a UI-state test forcing the load-failure branch |
| error | monitor mapping doesn't match or permission unavailable | ✅ covered | First-class amber fallback banner (needs-reprompt / denied / unavailable) with drag+fullscreen steps and the monitor-setup link — never a dead end (mirrors Phase 92) |
| overflow | long service (many order items) in the rail | ✅ covered | Rail is `overflow-y-auto`; the active item auto-scrolls into view (`scrollIntoView block:'nearest'`) on every navigation |
| long-text | long song/scripture titles in a rail item | 🧪 backstop | Item title truncates/wraps within the fixed `w-80` rail without pushing the slide count off-row; verified via a visual UI-state test with an overflowing title |
