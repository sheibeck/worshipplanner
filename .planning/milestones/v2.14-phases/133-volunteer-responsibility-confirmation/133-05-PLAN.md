<objective>
Add unconfirmed-only recipient targeting for reminder nudges (R413, per D-R413), reusing the
existing v1.7 volunteer-messaging send pipeline as a recipient-filter change — NOT a new send
primitive. A new `unconfirmedOnly` flag narrows the resolved recipient set to people with at least
one unconfirmed (or needs-reconfirmation) assignment for the service, applied identically in the
client preview and the authoritative server re-resolver.

Purpose: A planner nudges only those who haven't confirmed, without dunning people who already
did. The server MUST re-resolve from the confirmations subcollection (this codebase's law: never
trust the client's computed recipient list — "Anti-Pattern 1" in sendQueuedMessageHandler).
Output: `unconfirmedOnly` on the client + server selector types, both resolvers, the composer
toggle, and the server confirmations read + filter.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client-declared recipient intent -> server | the client sends a selector (who-to-resolve), never a final email list; the server re-resolves authoritatively |
| confirmations state -> send list | the server reads confirmations via Admin SDK (bypasses rules) and must scope reads to this org/service only |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-133-16 | Tampering | client forges a pre-filtered recipient list to bypass targeting | high | mitigate | server never accepts a client id list; sendQueuedMessageHandler re-resolves from scratch and re-derives the confirmed-key set from the confirmations subcollection (Anti-Pattern 1) |
| T-133-17 | Information Disclosure | Admin-SDK confirmations read scope | low | mitigate | read is serviceRef.collection('confirmations') where serviceRef is orgRef/services/{serviceId}, orgId already validated by the handler's existing scoping — no cross-service/tenant read |
| T-133-18 | Denial of Service | nudge bypassing quota/kill-switch | medium | mitigate | unconfirmedOnly reuses the existing queueServiceMessage/sendQueuedMessage pair; no parallel quota/kill-switch code added, so ORG_MAX_EMAILS_PER_DAY / MESSAGE_MAX_RECIPIENTS / kill-switch still apply |
