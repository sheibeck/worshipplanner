<objective>
Establish the confirmation data model, the volunteer scoped-write Firestore rule, and its
12 ALLOW/DENY rules tests — the load-bearing security foundation every other Phase 133 plan
depends on. Introduces one new subcollection (`services/{serviceId}/confirmations/{roleId}_{emailLower}`)
governed by its OWN rule block, plus two new denormalized fields on the existing
`rehearseAccess` projection so both the rule check and downstream diffs can reason about a
volunteer's roles without ever reading `personId` or re-implementing role resolution in rules.

Purpose: A volunteer confirming an assignment is a NEW scoped-WRITE by a non-org-member. This
plan makes that write possible AND proves it cannot become a cross-tenant, cross-service,
self-escalation, or plan-mutation vector (the v2.8 SEC-S-01 lesson). It must land before any UI.
Output: `src/utils/confirmations.ts` (pure model + helpers), two new `rehearseAccess` fields,
the `confirmations` rule block, and 12 emulator rules tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| magic-link volunteer -> Firestore | A non-org-member (no membership doc, no org claim) issues a scoped WRITE to a service subcollection — the phase's central new attack surface |
| client-supplied doc fields -> rule | roleId/emailLower/status arrive as untrusted request.resource.data and must be validated against the editor-trusted rehearseAccess projection |
| org A actor -> org B data | cross-tenant isolation, structurally enforced by path-derived orgId |
