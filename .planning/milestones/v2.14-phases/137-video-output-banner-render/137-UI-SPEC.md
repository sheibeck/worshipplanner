# Phase 137 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Two surfaces, two rule sets, zero redesign.** (1) The **authoring control** — a per-item Banner/Full-screen
choice in `SlidesTab.vue` — is a UI chrome element and follows the app's existing dark gray-950 control
language verbatim (the `SlotLoopControl.vue` pill precedent). (2) The **render** — the lower-third banner on
the Video output — is a live-stream compositing surface, not app chrome; it is machine-consumed by
OBS/vMix, so its "design system" is legibility-over-video + title-safe, not the app's typography/color
tokens. Full-screen mode (Phase 136) is byte-identical and untouched. No backing-bar/drop-shadow contrast
treatment this phase (explicitly deferred — REQUIREMENTS.md, `## Out of Scope`) — banner legibility comes
from title-safe inset + a large default text size only.

## Spacing Scale

Declared values (must be multiples of 4) — all already in use in the files this phase touches:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps in the toggle |
| sm | 8px | Segmented-toggle internal padding, gap between control and caption |
| md | 16px | Key-color card padding (`p-4`), gaps between card rows |
| lg | 24px | (inherited page-level rhythm, unchanged by this phase) |

Exceptions: the banner render itself is NOT built on the 8-point app scale — its layout is expressed as
**ratios of the 1280×720 reference stage** (title-safe insets below), because it must letterbox correctly
at arbitrary capture resolutions, not just app-chrome breakpoints. This is the same exception model
`SlideCanvas.vue`'s existing full-screen inset already uses (`calc(100% - 160px)` against the 1280×720
stage), extended to a second, smaller reference frame for the band.

### Render — banner text (live-stream surface, its own rule: legibility over video, not the app's chrome scale)

The banner reuses `SlideCanvas.vue`'s existing per-slide shrink-to-fit sizing **unchanged** — no new font
logic. The only new variable is the FRAME it fits into (smaller than the full 1280×720 stage), which
naturally yields smaller rendered text for the same font-size input. No minimum-size floor is added this
phase (Claude's Discretion, resolved: reusing the existing auto-fit exactly, rather than forking a
banner-specific minimum, keeps this phase additive and matches "reuse SlideCanvas, do not redesign it").

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#030712` gray-950 (`bg-gray-950`) | App chrome background (SlidesTab, Monitor Setup) — unchanged |
| Secondary (30%) | gray-900/gray-800 (`bg-gray-900` cards, `border-gray-800`/`border-gray-700` hairlines) | Segmented-toggle inactive state, key-color setting card |
| Accent (10%) | indigo-600/500 (`bg-indigo-600`, `focus:ring-indigo-500`) | The ACTIVE segment of the Banner/Full-screen toggle only, and the key-color toggle's active/checked tint (reused `SlotLoopControl.vue` recipe: `border-indigo-600 bg-indigo-950/40 text-indigo-200`) |
| Destructive | not applicable | No destructive actions in this phase |

Accent reserved for: the selected segment of the per-item Banner/Full-screen toggle, and the "use solid key
color" checkbox's active tint. Never used anywhere in the RENDER itself (the render has no app-brand color
vocabulary — see below).

**The RENDER's color contract is separate and load-bearing (R427):**

| Mode | Region | Value |
|------|--------|-------|
| Transparent (default) | Everywhere outside the slide content, both above the band and any letterbox bars inside the band | `background: transparent` (CSS, not `bg-black`) — an actual alpha channel for a Browser-Source-style software compositor |
| Key-color (opt-in) | Same regions as above | A single configurable solid color, `<input type="color">`, **default `#FF00FF`** (saturated magenta — REQUIREMENTS.md R427, CONTEXT.md, NOT the green ARCHITECTURE.md floated as an alternative — magenta is the locked default) |
| Banner text | Slide content inside the band | Whatever `SlideCanvas.vue` already renders for that slide (its own text/background resolution, unchanged) — the banner does not recolor or restyle the slide's own content |

Full-screen mode (unconfigured or `mode: 'fullscreen'`) is **unchanged from Phase 136**: pure black root,
opaque full-bleed slide. Transparent/key-color backgrounds apply ONLY when the current item's
`videoOutput.mode === 'banner'` on the Video output.

## Layout & Contracts

### Surface 1 — Authoring control (R425), `SlidesTab.vue` / `SlideGrid.vue`

**New component:** `SlotVideoOutputControl.vue`, a sibling of `SlotLoopControl.vue` in
`src/components/slides/`, following the identical prop/emit shape:

```
props: { slot: ServiceSlot, editable: boolean }
emits: { change: [videoOutput: NonNullable<ServiceSlot['videoOutput']>] }
```

**Placement:** inside `SlideGrid.vue`'s existing `slide-grid-group-media-panel` row (`mx-6 mt-3 flex
flex-wrap items-start gap-x-3 gap-y-2 rounded-md border border-gray-800 bg-gray-900 px-3 py-2`) — the SAME
row `SlotLoopControl` already occupies, sitting beside it (not below it) when both are visible. Add this
control's own presence to that row's `v-if` disjunction (`showGroupMusicControl || ... || canLoopSlot ||
true` — see scope note below) so the panel still renders even for slot kinds that have no Loop control.

**Scope (Claude's Discretion, resolved):** unlike `loop` (MISC/ANNOUNCEMENTS only, an explicit existing
restriction — `isLoopableSlot`), `videoOutput` is declared on the BASE `MediaAttachableSlot` with no
kind restriction in REQUIREMENTS.md/CONTEXT.md. Show this control for **every** slot kind (Song, Scripture,
Message, Misc, Announcements, Hymn, Imported) — a lower-third is just as meaningful for a scripture
reference or a song title as for an announcement. Do not replicate `isLoopableSlot`'s gate for this control.

**Visual — a two-segment pill toggle** (distinct from Loop's checkbox+select, because this is a pure
either/or choice with no secondary parameter, not an enable/configure pair):

```html
<div class="flex flex-col gap-1" data-testid="slot-video-output-row">
  <div
    class="inline-flex rounded-md border border-gray-700 overflow-hidden text-xs font-medium"
    role="radiogroup"
    aria-label="Video output display mode"
  >
    <button
      type="button"
      role="radio"
      :aria-checked="mode === 'fullscreen'"
      data-testid="slot-video-output-fullscreen-btn"
      class="px-2.5 py-1.5 transition-colors"
      :class="mode === 'fullscreen' ? 'bg-indigo-600 text-white' : 'bg-gray-800 text-gray-300 hover:bg-gray-700'"
    >Full-screen</button>
    <button
      type="button"
      role="radio"
      :aria-checked="mode === 'banner'"
      data-testid="slot-video-output-banner-btn"
      class="border-l border-gray-700 px-2.5 py-1.5 transition-colors"
      :class="mode === 'banner' ? 'bg-indigo-600 text-white' : 'bg-gray-800 text-gray-300 hover:bg-gray-700'"
    >Banner</button>
  </div>
  <span class="text-[11px] text-gray-500" data-testid="slot-video-output-caption">Video output only</span>
</div>
```

- Default rendered state (no `slot.videoOutput` or `mode: 'fullscreen'`): "Full-screen" segment active
  (indigo), matching the schema default (R425's "absent = full-screen").
- `!editable` (locked service): both segments render but are non-interactive — reuse `SlotLoopControl`'s
  `:disabled` precedent (`disabled` attribute + no hover state), not a hidden control (a planner should
  still SEE the current setting on a locked service, only not change it).
- Clicking the already-active segment is a no-op (does not re-emit `change`) — mirrors radio-group
  semantics, avoids a spurious autosave write.

### Surface 2 — Render, `FullscreenSlideOutput.vue` (extends the Phase 136 shared render)

**Branch condition:** `props.role === 'video' && currentSlideVideoOutputMode.value === 'banner'`, resolved
the same way `useRunControl`'s `currentLoopSlot()` resolves `loop` — via
`localService.slots[currentSlide.slotIndex]?.videoOutput?.mode` (ARCHITECTURE.md's documented resolution
path; no new wiring). Full-screen (the `else` branch, including the "no flag at all" default) renders
**exactly** the existing template — no new markup, no new condition inserted into that path.

**Reference geometry** — a SECOND, smaller `useContainScale` region alongside the existing full-stage one:

```
BANNER_REFERENCE_WIDTH  = 1280   // matches REFERENCE_WIDTH — same aspect discipline
BANNER_REFERENCE_HEIGHT = 200    // ≈ 28% of the 720 full-stage reference height
```

```
┌─────────────────────────────────────────────────────────┐  ← video picture (live camera behind, if transparent)
│                                                           │
│                    (transparent / key-color)              │
│                                                           │
│  ┌─────────────────────────────────────────────────────┐ │  ← band top = 72% down the frame
│  │ ░░ 64px ░░  [ SlideCanvas content, fit-to-band ]  ░░ │ │  ← title-safe inset: 64px each side (5% of 1280)
│  │ ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │ │     16px top / 12px bottom (band-relative)
│  └─────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────┘  ← frame bottom = band bottom (flush, no bottom margin outside the band)
```

- The band is anchored to the BOTTOM of the output frame, height = 28% of the frame's rendered height
  (mirrors the reference ratio, so it holds at any capture resolution — 1080p, 720p, etc.).
- `SlideCanvas` mounts inside the band's own `useContainScale({ refW: 1280, refH: 200 })` region exactly as
  it already mounts inside the full-stage one — same component, same auto-fit, smaller box. If the band's
  live aspect ratio (viewport-width : 28%-viewport-height) doesn't exactly match 1280:200, `useContainScale`
  letterboxes inside the band (never stretches) — those letterbox bars ARE the "banner's own non-content
  region" the key-color fill targets (CONTEXT.md's explicit phrasing).
- Title-safe inset inside the 1280×200 band reference: **64px horizontal each side (5%)**, **16px top / 12px
  bottom** — reuses the same "content is fit to an inset safe box, not the raw frame edge" principle as
  `SlideCanvas.vue`'s existing full-stage inset, scaled down for the smaller box. This is the ENTIRE
  legibility treatment this phase ships (no backing bar, no drop shadow — explicitly deferred).

**Background resolution** (replaces `FullscreenSlideOutput.vue`'s hardcoded `bg-black` for this one branch
only):

| Condition | Root background |
|-----------|-----------------|
| `role !== 'video'`, OR `role === 'video'` and mode is fullscreen/absent | `bg-black` (Tailwind class) — UNCHANGED |
| `role === 'video'` and mode is `banner`, key-color OFF (default) | inline `style="background: transparent"` |
| `role === 'video'` and mode is `banner`, key-color ON | inline `style="background: {keyColorHex}"` (reads the localStorage setting below) |

### Surface 3 — Key-color setting, `MonitorSetupView.vue`

**Visibility:** render as its OWN card, directly below the monitor grid (state B/B3, same level as the
existing "Your displays" section), **only when at least one live monitor currently has role `'video'`
assigned** (`Object.values(roleByFingerprint).includes('video')`) — a setting for an output that isn't
assigned to any screen is dead chrome (same "don't render an empty/irrelevant control" discipline the
`SlideGrid.vue` group-media-panel comment already documents for this codebase).

```html
<div class="mt-4 rounded-lg bg-gray-900 border border-gray-800 p-4" data-testid="video-key-color-card">
  <h2 class="text-sm font-semibold text-gray-100">Video output background</h2>
  <p class="text-xs text-gray-400 mt-1">
    Controls what's behind the banner on the Video output. Leave this off for a transparent
    background — works with most software compositors (OBS, vMix Browser Source).
  </p>
  <label class="mt-3 flex items-center gap-2 text-sm text-gray-300">
    <input type="checkbox" data-testid="video-key-color-toggle" class="h-4 w-4 rounded border-gray-600 bg-gray-800 text-indigo-600 focus:ring-indigo-500 focus:ring-offset-gray-900" />
    Use a solid key color instead of transparent
  </label>
  <div v-if="keyColorEnabled" class="mt-2 flex items-center gap-2">
    <input type="color" data-testid="video-key-color-picker" value="#FF00FF" class="h-8 w-8 rounded border border-gray-700 bg-gray-800 p-0" aria-label="Key color" />
    <span class="text-xs text-gray-400 font-mono">#FF00FF</span>
  </div>
</div>
```

**Storage (Claude's Discretion, resolved):** device-scoped `localStorage`, sibling of
`MONITOR_CONFIG_STORAGE_KEY` in `src/utils/monitorConfig.ts` — new key `wp:videoKeyColor:v1`, value
`{ enabled: boolean, colorHex: string }`, default `{ enabled: false, colorHex: '#FF00FF' }`. Per-device
(not per-org): key-color is a property of the physical video room's compositor setup, exactly the same
reasoning `monitorConfig.ts`'s header comment already gives for keeping monitor role mappings device-local
rather than in Firestore. The common path (transparent, the default) needs zero configuration — this card
only needs to be touched by a church whose downstream tool requires chroma-key.

## Responsive Behavior

- Authoring control: the segmented toggle + caption fit within the existing `slide-grid-group-media-panel`
  row's `flex-wrap` behavior — on narrow viewports it wraps onto its own line exactly as
  `SlotLoopControl`/`BackgroundControl` already do; no new breakpoint logic needed.
- Key-color card: full-width block inside `MonitorSetupView`'s existing `max-w-4xl` page container —
  stacks correctly at any width, no internal grid to break.
- Render (Surface 2): governed by output-window/display geometry, not app breakpoints — the band's 28%
  height ratio and the reference-frame letterboxing already handle arbitrary capture resolutions (this is
  the entire point of expressing the band in reference-frame ratios rather than fixed pixels).

## Accessibility

- **Authoring control:** `role="radiogroup"`/`role="radio"` + `aria-checked` communicate the two-state
  choice to assistive tech (not a bare pair of unlabelled buttons). Visible text labels ("Full-screen" /
  "Banner") — never icon-only. Focus ring: reuse the app's standard `focus:outline-none focus:ring-2
  focus:ring-indigo-500` on each segment button (matches every other interactive control in this file's
  precedent set). Color is never the only signal of which segment is active — the active segment also
  changes background AND is the one carrying `aria-checked="true"`.
- **Key-color card:** standard `<label>`-wrapped checkbox (native semantics, no ARIA needed) +
  `aria-label="Key color"` on the bare `<input type="color">` (which has no visible text label of its own).
- **The RENDER's "accessibility" is legibility over live video, not WCAG chrome contrast** (CONTEXT.md/
  REQUIREMENTS.md framing): the only two guarantees this phase makes are (1) a title-safe inset so text
  never sits at the literal frame edge where capture/broadcast crop can clip it, and (2) reuse of
  `SlideCanvas`'s existing auto-fit sizing so text always fits its box without manual tuning per slide. No
  contrast guarantee is made against arbitrary live video content behind a transparent banner — that
  is the explicitly deferred backing-bar/drop-shadow treatment (backlog), not a gap in THIS spec.
