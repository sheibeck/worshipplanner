<objective>
Fix R428: a multi-church member who opens a nav link in a new browser tab (right-click -> open in new tab) or follows a deep link into a fresh tab is bounced to /select-church because the active org is persisted only in sessionStorage, which a genuinely-new tab does not inherit.

The fix is additive-only and lives entirely inside `src/stores/auth.ts`'s three private storage helpers plus their existing logout clear call: add a uid-scoped `localStorage` fallback tier (per the locked "Two-tier storage" decision for R428). sessionStorage stays the primary; localStorage is consulted only when sessionStorage is empty; both tiers are written together and cleared together. No changes to `loadOrgContext`, `needsOrgSelection`, `requiresOrgSelection`, or the router guard (locked decision: "needs zero changes to loadOrgContext, needsOrgSelection, or the router guard").

Purpose: restore intended-destination navigation for multi-church members across new tabs/deep links while preserving all three sessionStorage-era guarantees (stale-membership re-validation, sign-out cleanup, per-tab isolation with NO cross-tab live sync).

Output: the two-tier storage helpers in auth.ts and their unit coverage in auth.test.ts.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser tab -> browser storage | The tab reads a persisted org id from sessionStorage/localStorage. This value is untrusted UI state, never an access-control decision. |
| client -> Firestore/Storage rules | The authoritative multi-tenant org-isolation boundary. Unchanged by this phase — no rules edits. The client persistence is a convenience only; server-side rules keyed on the user's real auth claims remain the security boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-138-01 | Elevation of Privilege / Tampering | persisted org id in localStorage (readRememberedOrg) | high | mitigate | The persisted id is honored only when it passes `loadOrgContext`'s `ids.includes(remembered)` re-validation against the user's live memberships (preserved verbatim, auth.ts:527) AND the helper's own `parsed.uid === uid` check. A stale/forged localStorage value is rejected before it becomes the active org; the router guard and Firestore/Storage rules would reject it downstream regardless. Defense-in-depth already in place — this phase must not remove it. |
| T-138-02 | Information Disclosure | shared/kiosk computer cross-account org leak | medium | mitigate | `clearRememberedOrg()` clears BOTH tiers on sign-out (locked R428 decision), and the value is uid-scoped so `readRememberedOrg(uidB)` rejects user A's `{uid: uidA, ...}` even if cleanup were somehow skipped. Leak is limited to an org *name* hint, never data access (rules enforce that). |
| T-138-SC | Tampering (supply chain) | npm installs | low | accept | No new dependencies are installed this phase (browser storage APIs only); no supply-chain surface added. |
</threat_model>
