<objective>
Establish the data-and-security foundation My Schedule reads from. Add the constrained collection-group `list` capability to the existing `rehearseAccess` firestore rule, provision the composite index the query requires, prove the new list read path with the FIRST constrained-list rules-emulator tests (the phase's KEY RISK — the current suite tests only `get` by id), and extend the Phase 125 projection with the one field My Schedule genuinely needs that it does not yet carry: per-email role names.

Purpose: My Schedule's sole data query is a `collectionGroup('rehearseAccess')` list (a magic-link volunteer holds no orgId claim). Phase 125 proved `get`-by-id and proved an UNFILTERED list is denied, but never proved that a properly `array-contains`-constrained list SUCCEEDS. That is unproven, not proven, in this codebase — closing it is the gate for the whole feature.

Output: an explicit `allow list` arm on `rehearseAccess`, a COLLECTION_GROUP composite index, a new R378 rules describe block, and `rolesByEmailLower` on `RehearseAccessDoc`.
</objective>
