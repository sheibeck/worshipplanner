Build `useVolunteerServiceDoc.ts` — the composable that resolves `orgId` for the standalone `/volunteer/service/:serviceId` route (which carries no orgId) and fetches the extended `rehearseAccess` doc. Output: One composable + its unit test.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| route input (serviceId only) → Firestore path construction | The route carries only serviceId; orgId MUST come from the volunteer's own server-filtered mySchedule result, not from any client-suppliable value. |
| volunteer client → rehearseAccess get arm | The fresh getDoc is the live R377 re-check (parentIsPlanned + assigned-email + email_verified) enforced server-side. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-127-02 | Spoofing | orgId path construction | high | mitigate | Resolve orgId only from mySchedule.docs (server-enforced by the collectionGroup list rule's assignedEmailsLower filter); never read orgId from a route param/query; unit-assert the source. |
| T-127-05 | Information Disclosure | serviceId enumeration | high | mitigate | The fresh getDoc is gated server-side by the existing get arm; a guessed serviceId for another org resolves no store match (access-denied, no getDoc) or is denied by the rule (mapped to access-denied) — the client never leaks whether the doc exists. |
| T-127-03 | Tampering (staleness) | stale cached list-arm doc | medium | mitigate | Re-fetch via a fresh getDoc (live parentIsPlanned re-check) rather than rendering the possibly-stale mySchedule cached doc, closing the reopen-staleness gap on the read side. |

No new trust boundary beyond the inherited Phase 125 get arm. No package installs.
