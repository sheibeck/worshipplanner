# Phase 127 — UI Design Contract: Volunteer Service View (Rehearse, Order of Service & Stage Layout)

> Visual and interaction contract for R384–R393. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker. Governs the standalone, read-only per-service view a volunteer reaches by tapping
> a service card on My Schedule (Phase 126) — **replacing** the build-safe
> `VolunteerServicePlaceholderView.vue` at `/volunteer/service/:serviceId`. This is **not** the
> planner's `ServiceEditorView` — a volunteer never sees drafts, editing chrome, or messaging.

Design reference: the owner's **`Rehearsal.dc.html`** mock (Turn 9, Nocturne palette). Its
**3-column layout, grouping, and player anatomy are authoritative**; its color values are **not** —
remapped to the app's existing dark gray-950/indigo Tailwind tokens using the **identical remap
method 126-UI-SPEC.md used** (verified against live source of `SongFilesTab.vue`,
`SongFilePreviewModal.vue`, `ShareView.vue`, `StageLayoutView.vue`, `MyScheduleView.vue`,
`ServiceEditorView.vue`'s tablist, and `rehearseAccess.ts`). App-fidelity, not a Nocturne clone.

## Data Dependencies (read before implementing — governs what the contract can render)

**Current `RehearseAccessDoc`/`RehearseSong`** (`src/utils/rehearseAccess.ts`, Phase 125) carries, per
song: `id`, `title`, `keyOrArrangement?`, `attachments[]` (`id`/`name`/`kind`/`downloadUrl?`/`href?`).
It carries **no** order-of-service items and **no** stage layout — both must be added this phase
(CONTEXT's explicit instruction) mirroring `buildServiceSnapshot`/`toPublicServiceSnapshot`'s
existing PII-safe allowlist pattern (`src/stores/services.ts`) rather than inventing a new one:

- **Order of Service tab needs:** an ordered list of `{ position, kind, sectionLabel?, title/detail
  fields per kind }` — the exact per-kind field set `buildServiceSnapshot`'s `slotsWithBpm` already
  produces (song title+key+bpm, scripture ref, hymn name+number+verses, prayer/message/announcements/
  misc labels) **minus** any per-slot free-text (`notes`/`body` — already dropped unconditionally by
  `buildServiceSnapshot`, R346/SEC-S-04) — plus the existing `roleAssignments` allowlist (`roleName`
  + `personNames[]`, no ids). This is a straight reuse of the SAME allowlist `ServiceSnapshot` already
  defines; no new PII surface.
- **Stage Layout tab needs:** `stageLayout.elements: PublicStageMarker[]` — `id`/`label`/`kind?`/
  `zone`/`xPct`/`yPct`/`roleName?`/`personName?`/`withVocal?` — **identical** to what
  `toPublicServiceSnapshot()` already strips down to for the public share link (drops the free-text
  `note` field). Reuse that exact allowlist.
- **Recommendation:** extend `buildRehearseAccess` to call the same slot/role/stage-projection helpers
  `buildServiceSnapshot` already calls (or factor a shared allowlist function both call), rather than
  re-deriving the PII rules from scratch — this is the planner's call per CONTEXT's "Claude's
  Discretion," but re-deriving the same rules twice is a drift risk worth flagging.

**Fields the mock shows that do NOT exist in the data model today** — each flagged `⚠ unresolved`
below and in UI Considerations, with the omit-gracefully behavior specified so the executor never
renders `undefined`/`NaN`/an invented placeholder:

| Mock field | Exists today? | Contract behavior |
|---|---|---|
| Song **key** | ✅ `RehearseSong.keyOrArrangement` (from `SongSlot.songKey`) | render `font-mono`, omit the whole token if absent |
| Song **bpm** | ⚠ exists on `Arrangement.bpm`, but `RehearseSong` doesn't carry it yet — needs a small `buildRehearseAccess` addition (resolve via `slot.songKey` → matching `Arrangement`, same resolution `buildServiceSnapshot`'s `slotsWithBpm` already does) | omit from the meta line if the projection isn't extended this phase; do not block the phase on it |
| **Time signature** | ❌ not modeled anywhere (`Arrangement`/`Song`/`Service` — confirmed by direct type read) | omit permanently — no source of truth exists to add cheaply; not a should-extend-projection case like bpm |
| **CCLI** | ✅ `Song.ccliNumber` | include in the meta line as `"CCLI {ccliNumber}"`, omitted when the string is empty (existing songs frequently have `''`) |
| PDF **"N pages"** | ❌ not modeled — no PDF page-count library in the stack (SongFilesTab's own `metaLine()` comment confirms: "never a pages/duration field") | omit permanently — do not add a new dependency to get it (SEED-003 no-new-deps precedent) |
| **"added by {name}"** | ⚠ `SongAttachment.createdBy` is a raw uid, not a resolved display name, and the volunteer session isn't authorized to read the full roster to resolve it (R377 isolation) | omit the "added by" clause; keep the existing `metaLine()` pattern of `{type} · {size} · {date}` instead — the date already conveys recency without a new PII-adjacent read |
| Per-song **"Note from {leader}"** | ❌ no field on `Song`/`SongAttachment` for a rehearsal-specific note | per CONTEXT: render nothing (no card at all) unless the planner adds the field to the projection this phase — this is an explicit "may extend, may omit" call, not a silent drop |
| **Order of Service** items | ❌ not yet in `RehearseAccessDoc` | must be added this phase (see above) — not optional, R392 requires it |
| **Stage Layout** elements | ❌ not yet in `RehearseAccessDoc` | must be added this phase (see above) — not optional, R393 requires it |

**PDF page navigation feasibility (R387, flagged for the planner, not a data-model gap):** the mock's
"Page X of Y, prev/next" chrome implies a custom PDF renderer. The app has **no `pdf.js` (or
equivalent) dependency** — `SongFilePreviewModal.vue`'s existing PDF preview is a plain
`<iframe :src="downloadUrl">` that defers entirely to the browser's own built-in PDF viewer (which
already supplies its own page indicator/scroll on Chrome/Edge/Firefox). **Recommendation:** do NOT
add a new PDF-rendering dependency to build a custom paginator — let the native in-iframe viewer
supply page navigation, and treat the mock's page-nav row as decorative chrome the native viewer
already provides. This is flagged `⚠ unresolved` in UI Considerations for the planner to confirm.

|------|------|--------|-------------|
| Display | 20px (`text-xl`) | 600 (semibold) | 1.2 — service name in the service header only |
| Heading | 16px (`text-base`) | 600 (semibold) | 1.3 — song title (list row + detail panel), tab-panel section headers |

identical mono-for-numerals precedent as 126-UI-SPEC's "big mono day number."

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-gray-950` | page background, Column 1/3 background |

**Accent reserved for** (explicit — never "all interactive elements"):
- The **active tab**'s underline + label — `text-indigo-300 border-indigo-500 bg-gray-900` (identical
  formula to `ServiceEditorView.vue`'s existing tab classes, reused verbatim for cross-surface
  consistency).
- The **selected song row** (Column 1) — `bg-indigo-950/30 border-l-2 border-indigo-500`, title
  `text-white` (vs. `text-gray-100` for unselected rows).
- The **"Playing" indicator** on a song row whose track is active — `text-indigo-400` dot + label.
- The bottom player's **round play/pause button** fill — `bg-indigo-600 hover:bg-indigo-500`.
- The **seek bar** fill/thumb — native `<input type="range" class="accent-indigo-500">` (Tailwind's
  `accent-color` utility drives both the filled track and the thumb in every evergreen browser with
  zero custom drag logic to build/maintain).
- The **Loop toggle**, only when active — `text-indigo-400` icon + `bg-indigo-950/40` pill background;
  inactive state is plain `text-gray-400`.
- Focus rings — `focus:ring-2 focus:ring-indigo-500 focus:ring-offset-2 focus:ring-offset-gray-950` on
  every interactive control (song rows, tab buttons, player controls, Print/Download buttons).
- Top-bar user-chip avatar fill — `bg-indigo-600`, reused verbatim from `MyScheduleView.vue`.

**Explicitly NOT accent-colored:** the speed-cycle button (neutral `bg-gray-800 text-gray-200
border-gray-700` at every speed value — cycling through speeds is not a "success" state), PDF/MP3
count badges in Column 1 rows (`text-gray-500`), Print/Download icon buttons (`text-gray-400
hover:text-gray-200` — informational actions, not the primary path), the Order of Service and Stage
Layout tab bodies (fully neutral — read-only reference material, no accent needed there since nothing
is selectable).

### 3. Mobile reflow (R391 — critical)

Below `sm:` (640px), the Rehearse tab becomes a **drill-down stack of three screens** inside the tab
panel — the 3 columns cannot sit side-by-side on a phone:

**Screen A — Song list** (full width, same row anatomy as Column 1, just `w-full` instead of
`w-[300px]`). Tapping a row advances to Screen B.

**Screen B — Song detail** (full width, same content as Column 2), with a `‹ Songs` back button
(chevron-left + label, `text-sm text-indigo-400`) at the top. Tapping a PDF row advances to Screen C;
tapping a Play toggle activates the pinned bottom player (see below) **without leaving Screen B** —
listening and reading are independent actions on mobile, matching desktop's independent
column2/column3 split.

**Screen C — PDF reader, link-first (R391 hard requirement)**: **no inline `<iframe>`** on mobile —
mobile browsers frequently fail to render an embedded PDF reliably (v2.7 research finding, restated
in CONTEXT). Instead:
```
‹ Way Maker
Way Maker.pdf

[ Open PDF ]        ← primary, bg-indigo-600, opens attachment.downloadUrl in a new tab
[ Download ]        ← secondary, outline, same fetch-blob download as SongFilesTab.vue
```
- `‹ {song title}` back button returns to Screen B.
- "Open PDF" (`w-full bg-indigo-600 hover:bg-indigo-500 text-white rounded-md py-3 text-sm
  font-medium`) is the primary action — `window.open(downloadUrl, '_blank', 'noopener,noreferrer')`,

### 7. Whole-view states (loading / access-denied / error / empty)

- **Loading** (rehearseAccess doc fetch in flight): `flex flex-col items-center gap-3 py-16

  Check your connection and try again."` + Retry (`text-sm text-indigo-400`) — identical phrasing
  formula to 126-UI-SPEC's My Schedule error state, for cross-surface consistency.
- **Empty song list** (a Planned service with zero SONG slots — rare, but must not crash Column 1):
  `"No songs in this service yet."` (`text-sm text-gray-500 py-8 text-center`) in place of the row
  list; Columns 2/3 show their own "select a song" empty states, which naturally read fine with

### 8. Accessibility

- Tabs: `role="tablist"` / `role="tab"` / `aria-selected` / `aria-controls` / roving `tabindex` +
  arrow-key navigation — reused verbatim from `ServiceEditorView.vue`'s existing `handleTabKeydown`
  pattern (do not reinvent tab keyboard behavior).
- Song list rows: real `<button>` elements (never a `<div>` with a click handler), `aria-current`
  reflects selection in addition to the visual accent border.
- Bottom player: play/pause `aria-label` toggles between `"Play {track}"`/`"Pause {track}"`; seek
  `<input type="range" aria-label="Seek">` gets native keyboard support for free; speed button
  `aria-label="Playback speed, {n}×. Press to change."`; loop toggle is a real `aria-pressed` button,
  not a styled `<div>`.
- PDF iframe: `tabindex="-1"` (identical to `SongFilePreviewModal.vue` — a cross-origin browsing
  context the keyboard trap logic cannot see inside); Print/Download remain real, focusable,
  labeled controls outside the iframe.
- Mobile drill-down back buttons: real elements with descriptive `aria-label`s (e.g. `"Back to song
  list"`, not an icon-only chevron with no accessible name).
- Color contrast: reuses the exact indigo-400/300-on-gray-900/950 combinations already verified
  across Phases 121/126 on this same palette — no new contrast risk introduced by this phase.
