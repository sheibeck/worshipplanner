<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Super-admin operator → `DeleteOrgConfirmDialog`/`OrganizationsTab` | A human's click/typed input crosses into a call that triggers an irreversible cross-tenant cascade delete |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-77-09 | Tampering | Client-side type-to-confirm gate | low | accept | This gate is pure UX (prevents a mis-click, not a malicious actor) — a super-admin who bypasses the dialog and calls `deleteOrganization` directly with an arbitrary `confirmName` is still independently checked server-side against the stored org name (T-77-02, Plan 01); this component adds no new server trust, so a client-side bypass gains nothing an authorized super-admin could not already do legitimately |
| T-77-10 | Information Disclosure | Confirm-dialog echo (member/pending counts) | low | accept | The dialog only displays `memberCount`/`pendingCount` already visible in the same Organizations row the super-admin is looking at — no new data is exposed beyond what `listOrganizations` (super-admin-gated) already returned to this same client |
| T-77-11 | Repudiation | Row removal after delete | low | accept | The durable audit trail (who deleted what) is Plan 01's server-side log line (T-77-05) and the returned summary, not this component; the client only reflects that outcome, it does not need its own independent record |

No high/critical-severity threats originate in this plan — the enforcement boundary is Plan 01's server-side
callable and `firestore.rules`; this plan is UI convenience on top of an already-safe backend.
</threat_model>
