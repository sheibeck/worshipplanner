<objective>
Add a super-admin cross-tenant access arm to `firestore.rules` and `storage.rules` (R225) so a super-admin
can read and write ANY organization's content without a membership document, while keeping Phase 77's
org-doc delete DENY and the Phase 76 lifecycle-field guard absolute for every client, super-admin included.

that, left unaudited, would silently reopen the exact CR-01/T-76-10 lifecycle-field bypass Phase 76 closed
for ordinary editors — this plan closes both the widening and its downstream hazard in the same task.

Purpose: R225 — the security boundary that makes "step into any church for support" possible without
falsifying membership records or weakening deletion/lifecycle protections.
Output: `firestore.rules` and `storage.rules` with the new super-admin arm; `src/rules.test.ts` and
`src/storage.rules.test.ts` with a genuine emulator ALLOW/DENY suite proving the arm, its DENY boundary, and
the two adjacent guards (delete, lifecycle fields) it must not disturb.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client (browser, any authenticated user) → `firestore.rules` | Untrusted read/write requests; the ONLY enforcement point for cross-tenant Firestore isolation |
| Client (browser, any authenticated user) → `storage.rules` | Untrusted Storage read/write requests, claim-based (no cross-service Firestore lookup — the documented deny-everyone incident this repo already suffered) |
| Custom `superAdmin` claim → both rules files | The claim itself is the trust boundary: only the owner-controlled `syncSuperAdminClaim` Cloud Function (Admin SDK, Phase 68) can set it, off writes to `superAdmins/{uid}` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-78-01 | Elevation of Privilege | `isOrgMember`/`isOrgEditor` (firestore.rules), `isOrgMemberByClaim` (storage.rules) | critical | mitigate | The super-admin arm is claim-only (`request.auth.token.superAdmin == true`), zero cross-document lookup, so it cannot be forged via a planted document; the claim is settable only by the Admin-SDK `syncSuperAdminClaim` trigger off `superAdmins/{uid}` doc writes, which are themselves gated to existing super-admins in rules and re-checked server-side by `setSuperAdminClaim` (Phase 68). Proven by emulator ALLOW (super-admin, no membership doc) + DENY (non-member, non-super-admin) tests (R225, both files). |
| T-78-02 | Elevation of Privilege / Tampering | `organizations/{orgId}` `allow update` (lifecycle fields) | critical | mitigate | Composition hazard: widening `isOrgEditor` to include super-admins would otherwise reopen `preservesLifecycleFields() || isSuperAdmin()` into an unconditional super-admin lifecycle-field bypass (the CR-01/T-76-10 class of bug). Closed in the SAME task by deleting the `|| isSuperAdmin()` disjunct — lifecycle fields (`active`/`deactivatedAt`/`deactivatedBy`/`reactivatedAt`/`reactivatedBy`) are now Admin-SDK-only (`setOrgActive`) for literally everyone. Proven by an emulator DENY on a super-admin client `updateDoc({active:false})`. |
| T-78-03 | Tampering / Elevation of Privilege | `organizations/{orgId}/members/{uid}` `allow write` | low | accept | `allow write: if isOrgEditor(orgId)` legally includes `create` (Firestore `write` = create+update+delete, OR-evaluated against every other matching `allow` clause); once super-admins inherit `isOrgEditor` for every org, the RULES layer alone does not prevent a super-admin's client from creating its own member doc — R226's "no member doc" guarantee is therefore a CLIENT-CODE CONTRACT (`78-02-PLAN.md`'s `enterOrgAsSuperAdmin` never calls `setDoc`/`writeBatch`), not a rules-enforced invariant. Pre-existing gap (an ordinary editor already has this power for their own org today), only widened in SCOPE by this phase (every super-admin, every org). Not closed here — tightening `members/{uid}`'s `allow write` to exclude `create` would need its own regression tests against TeamView's role-toggle/remove flows (unrelated scope creep for R224-R227); mitigated instead by `78-02-PLAN.md`'s unit test asserting the enter flow never writes. Flagged as a candidate future hardening phase. |
| T-78-04 | Tampering | `organizations/{orgId}` `allow delete` | high | mitigate | Phase 77's `allow delete: if false;` (line 147) is unconditional, with no `isOrgEditor`/`isOrgMember` reference the Pattern-1 widening could reach — diff review confirms zero changes to that line. The existing emulator DENY (`src/rules.test.ts:496-501`, a super-admin client SDK delete) is re-run unmodified as part of this task's verify, proving no regression. |

All high/critical-severity threats above are mitigated, not accepted. T-78-03 is the sole accepted
(low-severity) residual, documented and test-covered — not silently dropped.
</threat_model>
