<objective>
Implement the server-side enforcement half of church deactivation/reactivation: a super-admin-gated
`setOrgActive({orgId, active})` callable that persists the org's lifecycle status and fans out the
`deactivatedOrgs` custom-claim key to every member, plus the `firestore.rules`/`storage.rules` changes
that independently deny a deactivated org's ordinary members while exempting a super-admin.

Per 76-RESEARCH.md's Option 2 recommendation: `deactivatedOrgs: Record<string, true>` is an ADDITIVE
custom-claim key, never replacing or filtering the existing `orgs` map or legacy `orgId`/`role` keys.
Zero changes to the already-shipped Phase 73 claim-computation code
(`computeOrgsClaimForUid`/`buildOrgsMapClaim`/`decideMembershipClaim`).

**Super-admin exemption scope is NARROW (76-CONTEXT.md/76-RESEARCH.md Open Question 1, deliberate):**
this phase's exemption only waives the *active* check for a super-admin who already has a genuine
membership doc under the org. It does NOT let a super-admin without a membership doc enter an org at
all — `isOrgMember`'s `exists()` requirement and `isOrgMemberByClaim`'s membership arms are untouched.
Full membership-doc-less "enter any church" is Phase 78's explicit deliverable (R225) — do not build
any part of it here.

Purpose: this is the rules-enforced security boundary (R213) — the client-side login-block in
76-02-PLAN.md is UX only and must never be treated as the actual access control.
Output: a deployable (but UNDEPLOYED) `setOrgActive` Cloud Function, two rules-file diffs, and genuine
emulator ALLOW/DENY test coverage for both.
</objective>
