<objective>
Remediate the two Phase 112 firestore.rules findings that share the same two files, in one owner:
- **SEC-S-01 (Critical, live in prod):** `shareTokens` (~:341), `quarterShares` (~:388), and
  `serviceShares` (~:405) use the unsplit `allow read: if true`, which grants `list` as well as `get`.
  Any unauthenticated caller can `getDocs(collection(...))` and enumerate every org's shared service
  plans and volunteer names. Fix: split each into `allow get: if true; allow list: if false;` — the
  narrowest change that preserves the shipped `getDoc`-by-id flow while closing enumeration.
- **SEC-ISO-01 (High):** the legacy client-side org self-provisioning path is still rule-live — the
  `organizations/{orgId}` `allow create` (~:129-130) and the `members/{uid}` Flow-1 org-creation
  disjunct (~:150-159) let any signed-in user self-provision orgs and squat slugs/names, bypassing the
  deployed, super-admin-gated `onboardOrganization` Admin-SDK path. Fix: remove both legacy branches
  outright; invite-acceptance Flow-2 is untouched.

Each fix carries a REAL emulator test per R323 — DENY-case list tests (the SEC-S-01 regression proof),
the preserved get-by-id ALLOW tests, an assertFails for the removed founder path, and the preserved
Flow-2 invite-acceptance ALLOW.

Purpose: close a proven live cross-tenant data leak and a duplicate unprotected provisioning route.
Output: modified `firestore.rules` + extended `src/rules.test.ts`, built/tested/committed, UNDEPLOYED.

**This plan performs NO deploy.** The orchestrator handles any production deploy AFTER phase
verification, with an explicit per-deploy owner confirmation. No task here runs `firebase deploy` or
`gcloud`.
</objective>
