## Flagged assumptions

- **The existing `rehearsalDefaults` harness cannot prove AC-RHD-51 or AC-RHD-52.** Its `runTransaction` stub passes a
  `tx.get` that returns undefined, so `ensureShareLink` throws into `createService`'s soft-fail catch and `setDoc` never
  runs. Its `onSnapshot` never fires, so `services.value` stays empty and `maybeRefreshShareLink` returns early. A "no
  marker in the written payload" test there would pass with nothing written. Both criteria live in the new file, which
  must first assert that the documents exist.
- **Ordering alone does not prove the new page exists.** `writeSharePayload` catches its own memorable-URL failure, and
  `maybeRefreshShareLink` catches everything else, so both return normally when the page was not written. The helper
  must read the new doc. This is what research's plain "do it after the refresh" missed.
- **`onSave` will send `date` on every save once Plan 05 lands**, so `typeof data.date === 'string'` alone would run the
  removal path on every autosave. The comparison with the old date is what keeps a normal save at zero extra reads.
- **The old date comes from `services.value`, with one fallback read.** `services.value` holds the pre-write state, per
  the comment in `maybeRefreshShareLink`, so take it before `updateDoc`, because latency compensation can update it
  straight after. A miss falls back to one direct read, following `markAsPlanned` at lines 667-671, but placed before the
  write: afterward the stored doc already holds the new date. It runs only for a write with a `date` and a cache miss.
  Once Plan 05 adds `date` to every `onSave` payload, that is one extra read per autosave on a cache miss, which the
  org-wide subscription makes rare. A warm cache adds no read.
- **A cold cache usually leaves the old page in place, and that is safe.** `maybeRefreshShareLink` returns early when
  `services.value` has no such service (line 1272), so no new page is written and `retireOldServiceShare` stops at its
  new-page check (AC-RHD-58). The fallback changes the outcome only when the new date's page already exists and records
  this service. Do not widen `maybeRefreshShareLink` to cover this; it has its own contract and tests.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client store → public documents | The client writes and removes `serviceShares` and `shareTokens`, which anyone can `get` |
| one service → another on the same date | `serviceShares` is keyed by slug and date alone, so two services can share a document |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-147-15 | Denial of service | `retireOldServiceShare` on a date two services share | low | accept | Moving the service the page records leaves the other with no date page until its next save. The owner accepted this on 2026-11-06 (AC-RHD-68), and that service's token link is unaffected |
