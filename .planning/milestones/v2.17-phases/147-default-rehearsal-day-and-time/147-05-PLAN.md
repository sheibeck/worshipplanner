## Owner decisions

Settled on 2026-11-06 and recorded in CONTEXT. These are not assumptions, so do not reopen them.

- **Undo restores the marker.** ADR-0249 (i). Undo means the edit never happened, so it restores the whole snapshot, marker
  included. The rule that an edit ends auto-moving for good covers setting a value back by hand, which AC-RHD-29 tests.
  AC-RHD-64 and AC-RHD-65 pin Undo.
- **No extra code in `onUndo`.** `date` and `rehearsals` sit in the same `previousService` clone, and the one following
  save sends both. The risk AC-RHD-64 and AC-RHD-65 guard is `date` missing from the payload, in which case Undo would put
  the rows back and leave the date behind in Firestore.

## Flagged assumptions

- **Do not warm up before a date-change test.** Research says the first mutation is swallowed and a test needs two. That
  was checked at planning with the real harness and is wrong for this flow: one `onDateChange` straight after mount gave
  one `updateService` call. A warm-up touch would mask a real swallow of the most common flow, which is open a service,
  change only the date, and leave. AC-RHD-37 and AC-RHD-38 use a single mutation. The warm-up comments elsewhere in the
  suite are left alone.
- **Six criteria pass at RED by design:** 11, 26, 31 (view citation), 32, 36 and 39. They are regression guards for behaviour
  that must not change. Every other new test must fail at RED.
- **`mockUpdateService` is a mock here,** so these tests cannot see old-page removal. Plan 03 proves that against stored
  documents. The real-app check is the `<human-check>` in Task 3.
