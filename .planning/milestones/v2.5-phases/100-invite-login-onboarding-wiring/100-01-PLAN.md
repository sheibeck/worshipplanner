<objective>
Wire Phase 99's `sendInviteOnboardingEmail` Cloud Function into the app so an in-app invite
actually sends the correct onboarding email, and make the login screen usable for an invited
person — without changing any existing sign-in or invite-acceptance behavior.

Three cohesive, small changes in one plan (coarse granularity — no wave dependency between them):
1. TeamView.onInvite calls the callable (best-effort) after writing the authoritative invite docs,
   and shows honest, result-driven success copy (R288, R294).
2. LoginView gains a discoverable set/reset-password hint and a real `auth/operation-not-allowed`
   error message (R292).
3. Tests: a new mounted describe block in TeamView.test.ts covering the three copy states + the
   best-effort resilience guarantee, and a new LoginView.test.ts covering the error map + hint (R288/R292/R294).

Purpose: Close the gap the debug surfaced — the in-app invite only wrote Firestore docs and never
sent an email, and a disabled email/password provider produced a useless generic error.
Output: Extended TeamView.vue + LoginView.vue, extended TeamView.test.ts, new LoginView.test.ts.
</objective>

|----------|-------------|

This plan is client wiring only. |
| client (LoginView) → Firebase Auth SDK | Standard SDK auth; this plan only maps an existing error code to copy — no new privilege. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-100-01 | Tampering / Denial | TeamView.onInvite | medium | mitigate | Callable is invoked AFTER `batch.commit()` inside its OWN nested try/catch that only logs; it never rethrows, never sets `inviteError`, never reverts the committed invite/lookup docs; `isInviting` clears in `finally`. A disabled/undeployed/rejected callable can never block or revert the authoritative membership write (R294). Task 3 test #3 proves this. |
| T-100-02 | Repudiation / Info disclosure | TeamView copy branch | low | mitigate | Success copy strictly branches on `emailSent === true`; the disabled, failed (null result), and any-other-kind paths use honest "added — let them know to sign in with this address" copy, so the UI never falsely claims an email was sent when it was not (R288). |
| T-100-03 | Info disclosure | client bundle | low | accept | No secrets touch the client. The client passes only `{ orgId, email }`; RESEND_API_KEY and all provisioning live in the Phase 99 function (bound via `onCall({ secrets: [RESEND_API_KEY] })`, never shipped to the browser). Nothing new added here. |
| T-100-04 | Spoofing / Elevation of privilege | callable invocation with attacker-chosen orgId/email | medium | transfer | Enforced server-side by Phase 99: auth-presence gate, independent org-editor re-check on the caller's member doc, and CR-01 (the send is bound to a real pending invite doc). TeamView writes that authoritative invite doc with identical `trim().toLowerCase()` normalization BEFORE calling, so the existence gate passes only for genuine invites. No client-side control can weaken these. |
