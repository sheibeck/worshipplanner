# Milestone v2.6: Per-Org Bible API Toggle & Manual Fallback

**Status:** ✅ SHIPPED & DEPLOYED TO PRODUCTION 2026-08-31
**Phases:** 101-103
**Total Plans:** 6
**Tag:** `v2.6`

## Overview

Put Bible API access behind a per-organization on/off switch controlled from the Owner Console, and when
it is off give that org a zero-cost manual path (BibleGateway deep-link, plain-scripture reference-only,
congregational reading composed in the existing reading textarea) so scripture and congregational-reading
features always work without passing pay-only, non-commercial API costs to users.

**Requirements:** R295–R301 (7 mapped, 100% coverage) — see [v2.6-REQUIREMENTS.md](v2.6-REQUIREMENTS.md).

**Key context:** Promoted from backlog 999.3. Mirrors the v2.2 per-org AI enablement pattern
(`aiMasterEnabled`/`setOrgAiEnabled`) — a super-admin master field on `Organization`, written only by a
super-admin-gated Cloud Function, mirrored into `authStore`, and gated in `firestore.rules`. Default OFF,
no data migration — the manual fallback makes an OFF org fully functional, not broken. There was no
existing single Bible-fetch choke point before this milestone (fetching was split across
`src/utils/esvApi.ts` and `src/utils/nltApi.ts`, with ESV/NLT version dispatch duplicated inline in
`src/components/ScriptureInput.vue` and `src/components/CongregationalEditor.vue`) — this milestone
introduced one (`src/utils/scriptureApi.ts`). The BibleGateway link builder already existed in
`src/utils/scripture.ts` (`scriptureWebLink`/`nltLink`).

## Phases

### Phase 101: Per-Org Bible API Toggle — Owner Console Infrastructure

**Goal**: A super-admin can enable or disable Bible API access per organization from the Owner Console,
mirroring the proven per-org AI enablement pattern, with every org defaulting to OFF and no client able to
flip the field directly.
**Depends on**: Nothing (first phase of v2.6)
**Requirements**: R295, R301
**Success Criteria** (what must be TRUE):

  1. A super-admin can enable/disable Bible API access for a specific organization from the Owner Console's
     Organizations tab (`OrgConfigDrawer`), persisted via a new super-admin-gated Cloud Function
     (`setOrgBibleEnabled`) that writes a master field on the `Organization` document (R295).
  2. `firestore.rules` denies any direct client write to that master field — only the Cloud Function can
     set it (R295).
  3. A newly onboarded org and every existing org (including Berean) start with Bible API disabled, with no
     data migration performed (R295).
  4. The Owner Console's Organizations list shows each org's current Bible API on/off state at a glance,
     mirroring the existing AI-enablement row/drawer treatment (R301).

**Plans**: 2/2 plans executed

- [x] 101-01-PLAN.md — Backend: Organization.bibleApiEnabled field + super-admin-gated setOrgBibleEnabled
      Cloud Function + listOrganizations echo + firestore.rules deny (R295, R301)
- [x] 101-02-PLAN.md — Frontend: authStore bibleApiEnabled/isBibleApiEnabled mirror + OrgConfigDrawer
      checkbox + OrganizationsTab onToggleBible + per-row at-a-glance state (R295, R301)

**UI hint**: yes

### Phase 102: Gated Scripture Fetch Dispatcher

**Goal**: Every ESV/NLT scripture fetch — client and server — passes through one per-org gate, so a
disabled org makes zero proxy requests while an enabled org's experience is unchanged.
**Depends on**: Phase 101 (needs the org master field + `authStore` mirror to gate against)
**Requirements**: R296, R297
**Success Criteria** (what must be TRUE):

  1. When Bible API is enabled for an org, ESV/NLT passage preview and the LLM-assisted
     congregational-reading auto-fetch continue to work exactly as they do today, with no observable
     regression (R296).
  2. A new single dispatcher (`src/utils/scriptureApi.ts`, the `isAiEnabled()` analog) is the only path
     `ScriptureInput.vue` and `CongregationalEditor.vue` use to fetch passage text — neither calls
     `esvApi.ts`/`nltApi.ts` directly anymore (R297).
  3. When Bible API is disabled for an org, the app makes no ESV/NLT proxy request for that org, and
     scripture-text-dependent UI degrades gracefully rather than erroring (R297).
  4. The server `api` proxy's `esv` and `nlt` branches independently enforce the same per-org gate
     (defense-in-depth), rejecting a fetch for a disabled org even if a client bypassed the dispatcher
     (R297).

**Plans**: 2/2 plans executed

- [x] 102-01-PLAN.md — Client `scriptureApi.ts` dispatcher (single gated choke point) + route
      ScriptureInput.vue/CongregationalEditor.vue through it; enabled=passthrough (R296),
      disabled=graceful no-op (R297)
- [x] 102-02-PLAN.md — Server defense-in-depth: `checkOrgBibleEnablement` mirroring
      `checkOrgAiEnablement`, applied to the esv/nlt proxy branches (R297)

**Details:** A code-review round on this phase caught and fixed a live bypass in
`planningCenterApi.ts`'s scripture-push branch (CR-01, a Planning-Center-export gate bypass) plus warning
findings, before the phase's verification passed.

### Phase 103: Manual Fallback When Bible API Is Off

**Goal**: An organization with Bible API disabled has a fully functional, zero-cost path for scripture
selection and congregational readings — a BibleGateway deep-link plus manual entry — so being OFF never
breaks the workflow.
**Depends on**: Phase 102 (the fallback UI is conditioned on the gate reporting OFF)
**Requirements**: R298, R299, R300
**Success Criteria** (what must be TRUE):

  1. When disabled, scripture selection and congregational-reading UI offer an "Open in BibleGateway"
     deep-link for the entered reference in the desired version — any version, not just ESV/NLT — reusing
     the existing link builder in `src/utils/scripture.ts` (R298).
  2. When disabled, a user can manually enter passage text so it becomes the slide/reading content, for any
     version (R299).
  3. The LLM congregational split continues to operate on manually entered text when Bible API is off,
     still subject to the independent AI gate (R299).
  4. When disabled for an org, the "Bible Translation" selector is hidden in that org's Settings
     (`SettingsView.vue`), mirroring how the "AI Features" card hides when the AI master gate is off (R300).

**Plans**: 2/2 plans executed

- [x] 103-01-PLAN.md — bibleGatewayLink deep-link builder (R298) + hide the Settings "Bible Translation"
      card when off (R300)
- [x] 103-02-PLAN.md — Bible-API-off fallback UI in both editors: deep-link + text entry, congregational
      split on entered text under the independent AI gate (R298, R299)

**Details:** A code-review round on this phase caught and fixed two data-loss bugs (CR-01: pasted text
silently erased by a reference edit or the still-visible Preview button; CR-02: paste-box keystrokes
clobbering an AI split or manual edit) before the phase's verification passed.

**Owner refinement (2026-08-31, post-Phase-103):** the separate "Paste the passage text" textarea and the
off-state message were **removed** by owner direction. A plain scripture slide has no text-entry
affordance when the API is off — only the BibleGateway look-up deep-link; its slide is just the reference.
A congregational reading is composed directly in the existing bottom reading/format textarea, and the
AI split runs on that text via `hasPassageToSplit`/`onAiSplit`'s fallback to the textarea content.
R299 was updated in place to record this refinement rather than tracked as a separate item.

## Milestone Summary

**Key Decisions:**

- Single super-admin master gate (`Organization.bibleApiEnabled`), no church-editable leaf toggle —
  mirrors the v2.2 per-org AI-enablement pattern exactly (`aiMasterEnabled`/`setOrgAiEnabled`); sufficient
  for the cost-control goal, deferred a leaf toggle to Future Requirements.
- Default OFF for every org, including the existing production org (Berean), with no data migration — the
  manual fallback is what makes an OFF org fully functional rather than broken.
- One new choke point, `src/utils/scriptureApi.ts` (the `isAiEnabled()` analog), replacing the previously
  split `esvApi.ts`/`nltApi.ts` direct-call pattern in both `ScriptureInput.vue` and
  `CongregationalEditor.vue` — with an independent server-side `checkOrgBibleEnablement` gate on the `api`
  proxy's `esv`/`nlt` branches as defense-in-depth.
- Fallback = BibleGateway deep-link (any version) plus manual text entry — but the manual-entry shape was
  refined post-build by owner direction: the separate paste textarea and off-state message were removed.
  Plain scripture is now reference-only (deep-link only) when off, and congregational reading is composed
  directly in the existing bottom reading textarea (no new input surface), with AI split still running on
  that text under the independent AI gate.
- Settings' "Bible Translation" card hides when the Bible API is off for the org, mirroring the existing
  "AI Features" card hide-when-off treatment.

**Issues Resolved:**

- Two code-review rounds caught and fixed real defects before ship: Phase 102's review caught a live gate
  bypass in `planningCenterApi.ts`'s scripture-push branch (a Planning-Center-export path that reached
  ESV/NLT without going through the new per-org gate); Phase 103's review caught two fallback data-loss
  bugs — pasted text silently erased by a reference edit or the still-visible Preview button, and paste-box
  keystrokes clobbering an AI split or a manual edit.
- Milestone audit (`.planning/v2.6-MILESTONE-AUDIT.md`) independently re-ran all three test/type gates
  (type-check clean; app suite 175/177 files with only the two pre-existing baseline failures; functions
  suite 636/636) and traced the full toggle → dispatcher gate → fallback UI path end to end against live
  source, not narrative — PASSED 7/7 requirements, 5/5 integration seams WIRED, zero blocking gaps.

**Issues Deferred / Tech Debt:**

- **Batched human/visual UAT** — per explicit owner instruction for this autonomous run, every phase's
  browser/visual click-through was deferred into one owner-run round at milestone end
  (`.planning/v2.6-DEFERRED-UAT.md`), matching the v1.4–v2.5 owner-attributed precedent. All underlying
  logic is proven by automated tests; this is a documented, intentional deferral.
- **103 WR-3 (fallback-UI dedup, skipped)** — the near-verbatim "Open in BibleGateway" block is duplicated
  between `ScriptureInput.vue` and `CongregationalEditor.vue`. Explicitly triaged and skipped in
  `103-REVIEW-FIX.md` as a maintainability-only concern (both blocks are independently correct and
  independently tested); a future-phase candidate (e.g. `BibleApiOffFallback.vue`), not a correctness risk.
- **`src/stores/appConfig.test.ts` baseline failure** — pre-existing, inherited from a v2.5-era commit
  (`b365a1b9`), unrelated to v2.6's scripture/Bible-API work; confirmed by independent re-run during audit
  to be the same failure mode (dot-path-payload assertion), not something v2.6 introduced or worsened.
- **`src/storage.rules.test.ts`** — long-standing, documented Storage-emulator `firestore.exists()`
  cross-service limitation (see CLAUDE.md); not a v2.6 regression.
- **Owner post-deploy action:** because the default is OFF, every production org — including Berean —
  must be explicitly enabled for the Bible API via the Owner Console after deploy, or that org's ESV/NLT
  auto-fetch stops working and it falls back to the manual/BibleGateway path. Phase 102's own sequencing
  note: deploying `functions:api` (the server esv/nlt gate) denies esv/nlt for every org not yet enabled,
  so enabling Berean (and any other org that needs the live API) must be sequenced with, or immediately
  before/after, that deploy.

**Deploy:** Shipped and deployed to production 2026-08-31 (rules + `functions:api`/`setOrgBibleEnabled`/
`listOrganizations` + hosting). Tag `v2.6` (pre-existing, not created by this archival).
