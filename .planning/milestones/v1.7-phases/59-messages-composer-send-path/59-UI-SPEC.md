# Phase 59 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope & Precedent (read first)

Phase 59 ships the **first live send surface** in v1.7: one new component,
`src/components/MessageComposer.vue` — a centered modal opened by a ✉ **Messages** action wired into
`ServiceEditorView.vue`'s `buildActionBarItems`. Everything the composer needs already exists: the
recipient resolver (`src/utils/messagingRecipients.ts::resolveRecipients` + `MESSAGING_TEAM_LABELS`,
Phase 58), the kill-switch gate (`src/utils/messaging.ts::isMessagingEnabled()`, Phase 58), and a
proven modal shell idiom (`src/components/PptxImportModal.vue` / `NewServiceDialog.vue`). This spec is a
**contract** (component inventory, states, interaction/validation, accessibility, responsive, and
empty/disabled/error states) — it prescribes reuse of those existing idioms and invents no new visual
language.

**Visual reference:** `.planning/research/DESIGN-messaging.md` § **5a — Composer: "Message the team"**
is the authoritative layout. Where the mockup's hex values differ from the app, the app's dark theme
(`gray-950` body, `gray-900` cards, `indigo` accent) wins — as stated at the top of that design file.
This spec swaps the mockup's "violet" for the app's shipped **`indigo`** accent (the color every
existing modal/button in `src/components/` already uses), so the composer matches its siblings rather
than the mockup's palette.

**What is NOT in this phase (per `59-CONTEXT.md` boundary):** no delivery-history panel, no bounce
"Fix email" affordance, no lock/re-lock diff modal, no "opened" counts anywhere. Schedule-for-later
renders and persists intent, but the composer builds no scheduling-dispatch UI (Phase 61 cron dispatches).

**Focal point (visual hierarchy):** the eye lands first on the **SEND TO** team-chip wrap at the top of
the body — recipients are the composer's teams-first thesis (R136) and every downstream control (the
live "Reaches N" count, the enabled/disabled Send button) depends on that selection. The **Send now**
primary button in the footer is the secondary anchor (the only `indigo` fill in the footer).

### Accepted deviations — app-wide consistency (matched to Phase 58, do NOT re-flag)

Phase 58's UI-SPEC recorded three items the generic `gsd-ui-checker` rubric flags but which are
**deliberate app-wide conventions** already shipped across every sibling surface. Phase 59 inherits the
exact same conventions and records them here for the same reason — changing them would make the composer
the single inconsistent surface in the app. Accepted under the v1.7 autonomous grant's "pick the
reasonable default, state it" clause:

1. **Third font weight `font-medium` / 500 (Typography → ACCEPTED).** Every existing modal button
   (`PptxImportModal`, `NewServiceDialog`, `CsvImportModal`) uses `text-sm font-medium` on its
   primary/secondary CTAs, and `TeamTagPill` uses `font-medium` on chips. The composer's buttons and
   team chips inherit this app-wide chrome weight; it introduces no new weight. Collapsing only the
   composer to two weights would visibly mismatch every other modal.
2. **`12px` spacing (`gap-3`/`px-3`/`space-y-3`) (Spacing → ACCEPTED).** `12px` is a load-bearing
   app-wide token (`gap-3` between footer buttons, `px-3` input padding, `space-y-3` field stacks) used
   in every existing modal and Settings card. It is a multiple of 4 and the de-facto scale here;
   re-spacing only the composer would misalign it against its siblings.
3. **CTA verbs are action-specific, not a fixed noun phrase (Copywriting → ACCEPTED).** The primary CTA
   label is dynamic — **`Send now`** vs **`Schedule send`** (see Copywriting Contract). This mirrors the
   app's existing modals, whose primary buttons name their concrete action (`Import`, `Create service`)
   rather than a generic verb+noun. Not a divergence — the established modal-CTA convention.

Net: no new tokens, no new component library, no new copy pattern — the composer is idiom-consistent
with `PptxImportModal.vue` and the Phase 58 Messaging surfaces. A future project-wide design-system pass
is the correct venue for the rubric ideals, not this component.

## Component Inventory

**Count: 11 sub-components** within the single new `MessageComposer.vue` (plus 1 action-bar entry point
wired in `ServiceEditorView.vue`). Enumerated 1–11 below; entry point listed as 0.

### 0. ✉ Messages action-bar entry point (`ServiceEditorView.vue::buildActionBarItems`)

A ✉ **Messages** item added to the service action bar, positioned to the **left of `⇱ Share`,
separated by the existing thin divider** (per DESIGN § "Service header entry point"). Uses the same
action-bar item shape every other service action uses. Two-part gate:

- **Hidden/disabled when `isMessagingEnabled()` is false** (the Phase 58 kill-switch choke point). Per
  `59-CONTEXT.md` + DESIGN, a messaging-off org shows **no live send surface**. **Default resolved
  (autonomy grant): DISABLED, not hidden** — render the ✉ item greyed (`opacity-50
  cursor-not-allowed`, `aria-disabled="true"`, `title="Turn on Messaging in Settings to email
  volunteers"`) rather than omitting it, so an editor can discover the feature exists and where to
  enable it. Rationale: a silently-absent button is undiscoverable; the disabled+tooltip form is the
  app's existing pattern for gated actions and teaches the path to Settings. (If the checker prefers
  hidden, that is a one-line flip — but disabled is the stated default.)
- **Editor-gated:** the item is only present for `authStore.isEditor`. A viewer never sees it (matches
  every other mutating action-bar item).

Clicking (when enabled) opens `MessageComposer.vue` with `open = true`, passing the current
`service`, `quarters`, `roles`, `people`, and the resolved org/service messaging context.

### 1. Modal shell (reused verbatim from `PptxImportModal.vue`)

`<Teleport to="body">` → `bg-black/60` backdrop (`z-40`, fade `Transition`) + centered container
(`z-50 fixed inset-0 flex items-center justify-center p-4`) holding:

```html
<div class="w-full max-w-2xl max-h-[90vh] bg-gray-900 rounded-xl border border-gray-700 shadow-2xl flex flex-col">
```

Note the composer widens to **`max-w-2xl`** (vs the importer's `max-w-lg`) — it carries more form density
(recipients + type + subject + body + options). Three flex regions: fixed header (`shrink-0`),
scrollable body (`flex-1 overflow-y-auto`), fixed footer (`shrink-0`). Enter/leave `Transition` classes
copied verbatim (opacity+scale). **Dismissal:** ✕ close button, backdrop click, and **Escape key** all
call `onCancel` (Escape via a `@keydown.esc` listener while `open` — matches app modal expectations;
add if not already inherited from the shell).

### 2. Header (`px-6 py-4 border-b border-gray-800`)

Left: `h2` **"Message the team"** (`text-base font-semibold text-gray-100`) + a `text-xs text-gray-400
mt-0.5` service-date subline (e.g. `Sunday, August 16 · 9:00 AM`, formatted from the service date).
Right: the icon-only ✕ close button (`p-1.5 rounded-md text-gray-500 hover:text-gray-300
hover:bg-gray-800`, `aria-label="Close"`, inline-svg glyph — verbatim from `PptxImportModal.vue`).

### 3. SEND TO — team chips (R136, primary selector)

Section label `SEND TO` (`text-xs font-semibold uppercase tracking-wide text-gray-400 mb-2`). Below, a
`flex flex-wrap gap-2` of **team chips**, teams first, driven by `MESSAGING_TEAM_LABELS`
(Worship/Tech/Vocals/Hosts) + an **"Everyone on this service"** chip. Each chip is a `<button
type="button" role="checkbox" :aria-checked>` rendering `{label} · {count}` where `count` is that
selection's resolved reachable count from `resolveRecipients`. Chip idiom (from `TeamTagPill.vue`,
`inline-flex items-center px-2 py-0.5 rounded-full text-xs font-medium border`):

- **Selected:** `bg-indigo-600 border-indigo-500 text-white`.
- **Unselected:** `bg-gray-800 border-gray-700 text-gray-300 hover:border-gray-600`.
- Multi-select. Selecting **Everyone** sets `includeEveryone = true` and visually supersedes the four
  team chips (they render selected-but-implied / dimmed while Everyone is on — a `title` explains
  "Everyone is selected"). Toggling a specific team off Everyone clears `includeEveryone` and keeps the
  remaining explicit teams. Selection writes the `{ teams, individualPersonIds, includeEveryone }` shape.

### 4. Individuals panel (R136, secondary selector)

An inset panel (`rounded-lg bg-gray-800/60 border border-gray-700 p-3 mt-3`). Label **"Individuals"**
(`text-xs text-gray-400`) with a right-aligned **`＋ Add someone`** link (`text-xs text-indigo-400
hover:text-indigo-300`) that opens a person picker (reuse the app's existing person-select idiom; a
searchable `<select>`/typeahead over `people` — implementer discretion, but must exclude already-added
ids). Selected individuals render as **removable pills** in a `flex flex-wrap gap-2` row: `{name} ✕`
(`inline-flex items-center gap-1 px-2 py-0.5 rounded-full text-xs bg-gray-700 text-gray-200`, the ✕ a
`hover:text-red-300` remove button with `aria-label="Remove {name}"`). Adding a person pushes to
`individualPersonIds`; removing splices it.

### 5. Unreachable / open-roles helper line (R135 surfacing, muted)

Directly under the recipient block, a muted line (`text-xs text-gray-500 mt-2`): when the current
selection's `unreachableCount > 0`, show **"{unreachableCount} selected {people|person} {have|has} no
email"**; independently, when the service has open (unfilled) roles, append/show **"Unassigned roles
have no email — {N} roles on this service are still open."** (per DESIGN § 5a). This is informational,
never an error color. If both counts are zero, the line is omitted.

### 6. MESSAGE TYPE — segmented control (R137)

Section label `MESSAGE TYPE`. A 3-way segmented control (`inline-flex rounded-md border border-gray-700
overflow-hidden`, each segment a `<button type="button" role="radio" :aria-checked>` with
`px-3 py-1.5 text-sm`): **One-off message** | **Reminder** | **Share service link**. Selected segment
`bg-indigo-600 text-white`; unselected `bg-gray-800 text-gray-300 hover:bg-gray-750`. Maps to
`messages.type` `'oneoff' | 'reminder' | 'share-link'`. **Selecting a type seeds subject/body defaults**
(e.g. Share-service-link pre-inserts the `{{service_link}}` token into the body and a link-centric
subject; Reminder seeds a reminder-toned default). **Default-selected: One-off** on open. Seeding only
overwrites subject/body **if the user has not yet edited them** (a dirty-flag guard so switching types
after typing does not silently destroy the draft — resolved default under autonomy grant).

### 7. Subject field (R138)

Label **"Subject"** (`text-xs text-gray-400 mb-1`) + single-line `<input type="text">`
(`w-full bg-gray-800 border border-gray-700 rounded-md px-3 py-2 text-sm text-gray-100
placeholder-gray-500 focus:outline-none focus:ring-2 focus:ring-indigo-500`). Placeholder e.g.
`Rehearsal moved to 8:15 this Sunday`. Bound to `messages.subject` (raw, un-rendered — may contain
tokens).

### 8. Message body + token palette (R138)

Label **"Message"**. Multi-line `<textarea>` (`min-h-[132px]`, same control classes as the subject,
`resize-y`), bound to `messages.body` storing the **raw token template** (never pre-rendered — R139
requires per-recipient render at send time). Below the textarea, a `flex flex-wrap gap-2` row of
**insert-token chips**: `＋ Service date`, `＋ Service link`, `＋ Their roles`, `＋ Song list`
(`inline-flex items-center gap-1 px-2 py-1 rounded-md text-xs bg-gray-800 border border-gray-700
text-gray-300 hover:border-indigo-500 hover:text-indigo-300`). Clicking a chip **inserts the token at
the current cursor position** (`{{service_date}}`, `{{service_link}}`, `{{their_roles}}`,
`{{song_list}}`) into the textarea and restores focus + caret after the inserted token. A `text-xs
text-gray-500` helper: "Tokens fill in per person when the email sends."

### 9. Sample preview (R138, clearly-labelled sample)

A collapsible/inline preview box (`rounded-lg bg-gray-800/60 border border-gray-700 p-3 mt-3`) opened by
a **`Preview`** affordance (a footer button, see #11, or an inline toggle — implementer discretion; the
footer `Preview` button is the DESIGN reference). Header row: a small badge **"SAMPLE"** (`text-[10px]
uppercase tracking-wide bg-gray-700 text-gray-300 px-1.5 py-0.5 rounded`) + muted caption **"Rendered
for {sampleRecipientName} — the actual email personalizes each person's roles."** Body: the subject +
body with tokens resolved against a **representative sample recipient** (the first reachable recipient,
else the current user), per `59-CONTEXT.md`. This is explicitly NOT the final per-person text — the
caption says so. If there are zero reachable recipients, the preview renders against the current user
and the caption notes "no recipients selected yet."

### 10. Options card (R141)

An inset "Options" card (`rounded-lg bg-gray-800/60 border border-gray-700 p-3 mt-4`, `space-y-3`), each
row a native `<input type="checkbox" class="accent-indigo-600">` + `text-sm text-gray-200` label:

- **`Attach the service order as a link`** → `options.attachServiceLink` (appends the public share link
  / enables `{{service_link}}`). **Default: checked** (the common case for volunteer mail; resolved
  default).
- **`Send me a copy`** → `options.sendCopyToSelf`. **Default: unchecked.**
- **`Schedule for later`** → toggles a reveal (`v-if`) of a **datetime input** (`<input
  type="datetime-local">`, same control classes, `mt-2`). When checked, `scheduledFor` is required and
  drives the send-mode (see validation). **Default: unchecked** (send-now is the default path). A muted
  `text-xs text-gray-500` note when scheduled: "Scheduled messages are sent by a daily job — this
  message won't leave until then." (honest about the Phase 61 dependency without exposing the internals).

### 11. Footer (`px-6 py-4 border-t border-gray-800 flex items-center justify-between gap-3 shrink-0`)

- **Left — live recipient summary (R140):** `text-xs text-gray-400`, **"Reaches {reachable.length}
  {people|person}"**, and when `unreachableCount > 0` a muted appended span **" · {unreachableCount}
  {have|has} no email"** (`text-gray-500`). Optionally a compact selection descriptor
  ("Worship, Tech, +2 individuals") per DESIGN, space permitting. **Recomputes on every selection
  change** via `resolveRecipients(service, quarters, roles, people, selection)`.
- **Right — button group (`flex items-center gap-3`):**
  - **`Preview`** (secondary: `px-4 py-2 rounded-md text-sm font-medium text-gray-300 bg-gray-800
    hover:bg-gray-700 border border-gray-700`) — toggles the #9 preview.
  - **`Cancel`** (same secondary idiom) — calls `onCancel` (closes, discards draft; if the draft is
    dirty, an inline "Discard message?" confirm is at implementer discretion — not required this phase).
  - **Primary Send button** (`px-4 py-2 rounded-md text-sm font-medium text-white bg-indigo-600
    hover:bg-indigo-500 transition-colors disabled:opacity-50 disabled:cursor-not-allowed`): label is
    **dynamic** — **`Send now`** when schedule-for-later is off, **`Schedule send`** when it is on
    (reflects send-now vs scheduled, R141). Calls the `queueServiceMessage` client wrapper. Disabled
    per the validation rules below.

## Interaction & Validation Behavior

| Trigger | Behavior |
|---------|----------|
| Open composer | Fetch/receive `service, quarters, roles, people`; default type = One-off; recompute "Reaches N"; focus the first team chip (or Subject) for keyboard users. |
| Toggle any team / Everyone / add/remove individual | Update selection shape; **immediately recompute** `resolveRecipients`; update every per-chip count, the "Reaches N" footer, the unreachable helper, and the Send button enabled-state. |
| Select message type | Seed subject/body defaults **only if not user-edited** (dirty guard); mark type as `messages.type`. |
| Click a token chip | Insert `{{token}}` at textarea caret; restore focus + caret. |
| Toggle "Schedule for later" | Reveal/hide the `datetime-local`; flip primary button label `Send now`↔`Schedule send`. |
| Click primary Send | Guard (below) → set button to a loading/disabled state ("Sending…" / "Scheduling…") → call `queueServiceMessage` → on success close modal + surface a toast via the existing `ToastHost` ("Message queued to {N} people" / "Message scheduled"); on failure show the inline error (below) and re-enable the button. |
| Escape / backdrop / ✕ | `onCancel` — close and discard the in-memory draft. |

**Send button disabled (`disabled` + `disabled:opacity-50 cursor-not-allowed`) when ANY:**

1. **Zero reachable recipients** — `resolveRecipients(...).reachable.length === 0`. The button carries a
   `title="Select at least one team or person with an email"` so hovering explains the block. This is
   the required **zero-reachable-recipients disabled-Send state**.
2. **Empty subject AND empty body** — nothing to send. (A blank subject alone with a body is allowed;
   discretion — but at least one of subject/body must be non-empty. Resolved default.)
3. **Schedule-for-later on but `scheduledFor` empty or in the past** — an inline `text-xs text-red-400`
   note under the datetime input: "Pick a future date and time." blocks send.
4. **A send is already in flight** (button shows loading state).

**Kill-switch defense in depth:** even though the entry-point (#0) is disabled when messaging is off,
`queueServiceMessage` **re-checks the kill-switch server-side** (per `59-CONTEXT.md`) — the UI gate is a
convenience, not the security boundary. If a queued send is server-rejected because messaging was turned
off between open and send, the composer shows the generic send-failure error (below).

## Accessibility

- **Dialog semantics:** modal container `role="dialog" aria-modal="true" aria-labelledby="{title-id}"`.
  Focus is trapped within the modal while open; on close, focus returns to the ✉ action-bar item.
- **Keyboard:** Escape closes; Tab cycles all controls in DOM order (chips → individuals → type →
  subject → body → token chips → options → footer buttons); token chips and team chips are real
  `<button>`s (Space/Enter activate). The datetime input is a native control (fully keyboard-operable).
- **Roles/state:** team chips `role="checkbox" aria-checked`; message-type segments
  `role="radio"` within a `role="radiogroup" aria-label="Message type"`; the disabled Send button uses
  `disabled` (not just styling) so it is announced and skipped; remove-pill ✕ buttons carry
  `aria-label="Remove {name}"`; the close button `aria-label="Close"`.
- **Live region:** the footer "Reaches N people" line is `aria-live="polite"` so screen-reader users
  hear the count update as they change the selection.
- **Contrast:** all text meets the app's existing dark-theme contrast (`text-gray-100/200/300` on
  `gray-900/800`); the muted `text-gray-500` unreachable note is informational, paired with the visible
  count, never the sole carrier of a blocking condition.

## Responsive Behavior

Single modal, `w-full max-w-2xl max-h-[90vh]` with an internal `overflow-y-auto` body — the shell is
inherently responsive (the `p-4` outer padding keeps it off the viewport edges on small screens).

- **Mobile (`< sm`):** the modal is effectively full-width (minus `p-4`); team chips and token chips
  `flex-wrap` naturally onto multiple rows; the footer switches to allow the recipient summary to wrap
  above the button group if space is tight (`flex-col sm:flex-row` on the footer, buttons full-width
  stacked on the narrowest widths is acceptable — implementer discretion within the reused footer idiom).
- **Desktop (`≥ sm`):** the DESIGN § 5a single-column layout — recipient summary left, buttons right in
  the footer; body scrolls internally if content exceeds `90vh`.
- No separate tablet breakpoint is introduced; the app uses only the `sm:` boundary here (consistent
  with the existing modals).
