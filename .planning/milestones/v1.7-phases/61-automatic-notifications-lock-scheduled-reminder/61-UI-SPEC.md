# Phase 61 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope & Precedent (read first)

Phase 61 is **overwhelmingly automatic** — R144 (auto-email on first lock) is a client hook on an existing
lifecycle action, and R145 (scheduled reminder) is a **backend `onSchedule` cron with NO interactive UI at
all**. The net-new UI is therefore **exactly one small affordance**: a **lock-time confirmation** the planner
sees when a *first* lock auto-enqueues a lock-notification email. Everything else this phase touches is
**reused, not rebuilt** (see § Reused, not rebuilt below).

**The one net-new surface:** a subordinate **confirmation line inside the existing amber lock banner**
(`ServiceEditorView.vue:308`, `data-testid="service-lock-banner"`). That banner already renders
`v-if="authStore.isEditor && isLocked"` — i.e. it appears *exactly* on the draft→locked transition that R144
hooks — so it is the least-surprising, zero-new-component host for "who just got emailed." One `v-if` line is
added beneath the banner's existing copy, mirroring the `lifecycleError` line already hosted there
(`ServiceEditorView.vue:337`). No new component, no modal, no new store, no shared-component edit.

**Feedback-idiom decision (STATED — the load-bearing choice of this spec).** The app has **no success-toast
idiom**. `src/stores/toasts.ts` + `src/components/ToastHost.vue` are a *failure-only* stack by deliberate
design (R041): `ToastHost` hardcodes a red card (`border-red-800 bg-red-950 text-red-400`), a warning-triangle
glyph, and a literal **`Save failed.`** prefix on every message. Pushing a success string to it renders as
"**Save failed.** Notified 5 volunteers" — wrong. (Phase 59's `toasts.push('Message queued to N people')` is a
latent misrender for the same reason; **out of scope to fix here**, flagged for a later pass.) The lock action's
own success feedback today is purely the **visual status-pill flip** + the appearance of the amber lock banner;
its *failure* feedback is the inline `lifecycleError` line in that banner. **Resolved default (v1.7 autonomy
grant): the lock-notification confirmation is an inline, transient, informational line hosted in the lock
banner — NOT the failure toast, and NOT a shared-component refactor.** Rationale: it is the app-consistent
success-feedback surface (co-located with the state the planner just created), it reuses the banner's existing
amber/informational palette, and it keeps a small phase small. Refactoring `ToastHost` to support success
variants is the correct venue for a future project-wide pass, not this phase.

**First lock is automatic, not a prompt (per `61-CONTEXT.md`).** There is **no confirm-before-lock dialog** —
R144/SC1 is "can automatically email," governed by the Phase 58 default. So the affordance is a **post-lock
confirmation** ("Notified N…"), never a pre-lock "Locking will notify N…" prompt. (The confirm-with-diff prompt
is Phase 62's re-lock scope, explicitly out of this phase.)

**What is NOT net-new UI in this phase** (all reused — see § Reused, not rebuilt): the Settings Messaging card
(kill-switch + `lockNotifyDefault` / `reminderEnabled` / `reminderDaysBefore` / `timezone`), the per-service
messaging-defaults panel (per-service overrides), and the delivery-history panel (which already lists sent
`reminder` / `lock-notification` rows). The scheduled reminder (R145) has **zero interactive UI**.

**Focal point (visual hierarchy):** the lock banner's primary elements are unchanged — its lock message
(`lockBannerLead` + `lockBannerBody`) and the **Reopen for editing** button remain the banner's anchors. The
new confirmation line is **deliberately subordinate** — a secondary, informational row beneath the copy, in the
same subordinate slot the `lifecycleError` line uses. It must not compete with the lock message or the Reopen
action.

### Accepted deviations — app-wide consistency (matched to Phase 58/59/60, do NOT re-flag)

Inherited verbatim from `59-UI-SPEC.md` / `60-UI-SPEC.md` § Accepted deviations. Changing them here would make
this surface the single inconsistent messaging affordance. Accepted under the v1.7 autonomous grant's "pick the
reasonable default, state it" clause:

1. **Third font weight `font-medium` / 500 (Typography → ACCEPTED).** The lock banner's lead
   (`ServiceEditorView.vue:319`) and its Reopen button already use `font-medium`; the confirmation line's
   emphasis inherits this app-wide chrome weight. No new weight introduced. Same ruling as Phase 58/59/60.
2. **`12px` spacing (`gap-3` / `px-4 py-3`) (Spacing → ACCEPTED).** The lock banner is `gap-3 px-4 py-3`; the
   confirmation line lives inside it and inherits those load-bearing app-wide tokens. Multiple of 4, de-facto
   scale here. Re-spacing only this line would misalign it inside its own banner.
3. **CTA verbs are action-specific, not a fixed noun phrase (Copywriting → ACCEPTED).** The one link this phase
   can surface (in the error state) is **`Open Messages`** — an action-specific verb+noun matching the app's
   modal-CTA convention, not a generic label. Same ruling as Phase 59 deviation #3.

**One phase-specific palette note (NOT a deviation):** this surface is **amber-toned**, because it lives inside
the existing amber lock banner — it inherits `text-amber-200` / `text-amber-300` informational tones, not the
messaging surfaces' `indigo` accent. `indigo` remains reserved for the *messaging action* surfaces (composer,
history links) and `red` for genuine failures; neither is introduced here. This is inheriting the host banner's
established color context, not a new token.

## Component Inventory

**Count: 1 net-new sub-element** (enumerated 0–1) — a single confirmation line added inside the existing
`service-lock-banner` in `ServiceEditorView.vue`. No new component file; the shape below is added markup +
minimal state.

### 0. Lock hook state (the trigger — `ServiceEditorView.vue::onMarkAsPlanned`, `services.ts`)

Not a visual element; the state the line reads. After `serviceStore.markAsPlanned` succeeds and
`applyTransitionLocally('planned')` runs (`ServiceEditorView.vue:2778-2779`), and **only on the first
draft→locked transition** (no prior `lockSnapshots/current`), the hook:

1. writes `lockSnapshots/current` (for Phase 62's future diff — every lock), then
2. **iff** `isMessagingEnabled()` **and** the effective lock-notify default resolves ON, resolves the
   assigned recipients client-side (the same `resolveRecipients(...)` the composer uses, `messagingRecipients.ts`)
   to get **N = reachable count**, enqueues the `type:'lock-notification'` message via `queueServiceMessage`, and
   sets a local UI ref that drives the line below.

**Critical non-blocking rule (mirrors the app's existing `bumpScheduledSongsLastUsed` pattern,
`ServiceEditorView.vue:2800-2804`):** the enqueue runs in **its own try/catch AFTER the transition has already
succeeded and is on screen**, and its failure is **never re-raised into `lifecycleError`**. Reporting "Couldn't
mark this service as Planned" when the lock in fact succeeded would be a lie (the exact defect class that
comment block guards against). A failed enqueue instead drives the line's **error state** (§ #1, informational
amber), not the red lock-failure line.

The local UI state is a small ref, e.g.:
```ts
// null → render nothing. Discriminated by kind.
const lockNotify = ref<
  | null
  | { kind: 'sent'; count: number }
  | { kind: 'none-reachable' }
  | { kind: 'error' }
>(null)
```
Set on the first-lock path; left `null` when messaging is off, when the default is OFF, or when it is not a
first lock (re-lock is Phase 62). **Cleared** on Reopen, on navigating away, and — mirroring the app's 6000ms
toast auto-dismiss (`toasts.ts:27`) — optionally auto-cleared after ~6s so the confirmation reads as a transient
courtesy, not permanent banner furniture. (Persist-until-Reopen is an acceptable alternative at implementer
discretion; transient is the stated default for parity with the toast timing.)

### 1. Confirmation line (net-new markup, inside `service-lock-banner`)

Added beneath the banner's copy `<p>` (`:318-321`), in the same subordinate `basis-full` slot the
`lifecycleError` line occupies (`:337-341`), rendered `v-if="lockNotify"` with a branch per state:

```html
<!-- lives inside the existing service-lock-banner div -->
<p
  v-if="lockNotify"
  class="basis-full text-sm"
  :class="lockNotify.kind === 'sent' ? 'text-amber-200' : 'text-amber-300'"
  aria-live="polite"
  data-testid="lock-notify-confirmation"
>
  <template v-if="lockNotify.kind === 'sent'">
    Notified <span class="font-medium">{{ lockNotify.count }}</span>
    assigned {{ lockNotify.count === 1 ? 'volunteer' : 'volunteers' }}.
  </template>
  <template v-else-if="lockNotify.kind === 'none-reachable'">
    No assigned volunteers have an email — no one was notified.
  </template>
  <template v-else>
    Locked — but the notification couldn’t be sent.
    <button type="button" class="font-medium text-amber-100 underline hover:text-white"
            @click="openMessageComposer">Open Messages</button>
    to send it.
  </template>
</p>
```

- **`sent` (success):** `text-amber-200`, "Notified {N} assigned {volunteer|volunteers}." — the R144 happy path.
  N is the client-resolved *reachable* count. The **authoritative** sent/bounced tally is the Phase 60 history
  panel; this line is the immediate courtesy confirmation (parity with the composer's "Message queued to N
  people" intent, minus the toast's failure styling).
- **`none-reachable`:** `text-amber-300` (muted), shown when the default is ON + messaging on but the resolver
  returns zero reachable recipients (everyone assigned lacks an email, or no one is assigned). No false "Notified
  0." Mirrors the composer's unreachable messaging tone (informational, never error).
- **`error`:** `text-amber-300` (muted), shown when the post-lock enqueue throws. **Not red** — the lock
  succeeded; only the secondary email failed. Offers the manual path via an `Open Messages` link that opens the
  Phase 59 composer (`messageComposerOpen = true`). This is the phase's only interactive net-new element.
- **`null` (no line):** messaging off, default OFF, or not a first lock → the banner shows **only** its normal
  locked message. Correct neutral no-op — no email means no feedback (SC2 posture).

**`aria-live="polite"`** is set on THIS line (the parent banner is deliberately *not* a live region — persistent
furniture, `:299-302`), so a screen-reader user hears the confirmation once on lock without re-announcing the
whole banner.

## Interaction & Behavior

| Trigger | Behavior |
|---------|----------|
| Planner clicks **Mark as Planned** on a **draft** service (first lock), messaging ON, effective lock-notify default ON, ≥1 reachable recipient | Transition succeeds (existing) → banner appears → **`lockNotify = { kind:'sent', count:N }`** → line reads "Notified N assigned volunteers." (`aria-live` announces once). The `lock-notification` message also lands in the Phase 60 history panel with real counts. |
| Same, but **0 reachable** recipients | Enqueue is a no-op (server re-resolves to nobody) → **`kind:'none-reachable'`** → muted "No assigned volunteers have an email — no one was notified." |
| Same, but messaging OFF **or** effective default OFF | **No enqueue, `lockNotify = null`** → banner shows only its normal locked copy. No email, no feedback (SC2). |
| First lock succeeds but the **enqueue call throws** (network / callable error) | Lock stays succeeded (never re-raised into `lifecycleError`) → **`kind:'error'`** → muted "Locked — but the notification couldn’t be sent. Open Messages to send it." The `Open Messages` link opens the Phase 59 composer. |
| **Re-lock** (a `lockSnapshots/current` already existed) | **No auto-enqueue, `lockNotify = null`** — re-lock notification is Phase 62's prompt-with-diff, out of this phase. Banner shows normal locked copy. |
| Click **Reopen for editing** / navigate away | `lockNotify = null` (line clears with the state it described). |
| ~6s elapse after a `sent`/`none-reachable`/`error` line appears (optional, stated default) | Auto-clear to `null` (parity with the 6000ms toast timeout), so the confirmation is transient, not permanent banner furniture. |

**Server defense in depth (unchanged, noted):** even when the client gate passes, `queueServiceMessage`
re-checks the kill-switch server-side (Phase 59). If messaging was turned off between draft and lock, the
enqueue is server-rejected → the client lands in the **`error`** branch (lock already succeeded), which is the
correct, honest surface. The UI gate is a convenience, not the security boundary.

## UI Considerations

Applicable state considerations resolved: 4 covered, 1 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| populated | Lock-notification confirmation line (success) | ✅ covered | `kind:'sent'` renders "Notified N assigned volunteers." in the lock banner, `aria-live="polite"`. Copy in Copywriting Contract; the durable record is the reused Phase 60 history panel. |
| empty | No email was sent (messaging/default off, or re-lock) | ✅ covered | `lockNotify = null` → **no line**. Deliberate neutral no-op (SC2: never signals a send that didn't happen). Not a collection empty-state — a rendered-nothing branch. |
| partial | Some/all assigned volunteers unreachable (0 reachable) | ✅ covered | `kind:'none-reachable'` → muted "No assigned volunteers have an email — no one was notified." Mirrors the composer's unreachable-recipient tone; never claims "Notified 0." |
| error | Post-lock enqueue failure (incl. server kill-switch reject) | ✅ covered | `kind:'error'` → muted amber line + `Open Messages` link; **never** re-raised as the red lock-failure line (the transition succeeded — mirrors `bumpScheduledSongsLastUsed`'s non-blocking pattern). Copy in Copywriting Contract. |
| zero-one-many | "Notified N assigned volunteer(s)" pluralization | 🧪 backstop | The count copy must pluralize at 1 vs many (`1 volunteer` / `2 volunteers`) and the count must equal the resolver's reachable length. Verified via a UI-state test over the branch — no single human eyeball guarantees both plural forms, so held as a backstop. |

Notes on non-applicable categories: **loading** — the enqueue is fire-after-transition and non-blocking; the
banner is already on screen, so there is no spinner state to design (the line simply appears when the enqueue
resolves). **long-text** — the line is fixed template copy plus an integer; no free-text overflow. **disabled**
— there is no new interactive control except the error-state `Open Messages` link, which is only rendered in the
error branch (never a disabled state). The scheduled reminder (R145) has **no UI**, so no state applies to it —
its output is covered by the reused Phase 60 panel's already-specified states.
