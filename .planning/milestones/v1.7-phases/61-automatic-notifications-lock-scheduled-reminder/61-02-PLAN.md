<objective>
Ship the R145 reminder engine: a NEW `sendScheduledReminders` daily `onSchedule` Cloud Function (built and
tested against the MOCKED provider, UNDEPLOYED) that auto-enqueues the shared service link to everyone assigned
N days before a service, reckoned in the org's local timezone, exactly once. It mirrors the shipped
`cleanupOrphanRendersHandler` (`functions/src/index.ts:729-817`) EXACTLY — broad `collectionGroup` scan, org
recovered from the parent chain, per-item try/catch so one bad service never aborts the run, handler exported
separately for unit test, offset to its own `04:00` UTC slot.

Purpose: R145 (auto-send N days before, default 7, configurable, org-local timezone via R133) and its two hard
SC4 rules — never on a draft, never twice. This is the load-bearing plan of the phase: the timezone date
boundary and the `reminderSentAt` idempotency are the assertions the whole reminder feature stands on.

DECISIONS (locked, from 61-RESEARCH.md):
- Read org messaging from `org.settings.messaging.*` and the org zone from `org.settings.timezone` — NOT
  `org.messaging.*` (research Pitfall 2; the `queueServiceMessageHandler` shape at `:1024-1027`).
- Idempotency ordering: set `messaging.reminderSentAt` AFTER a successful enqueue (research § Idempotency,
  CONTEXT wording). The crash-between window is a rare single double-send at daily cadence, not a lost reminder;
  document this and the transactional claim-first upgrade path in the SUMMARY (research A5 / Open Question 1).
- NO new Firestore index: the `status in [...]` collection-group scan is the same class as the shipped
  `pptxRenders` scan that needs none (research § Firestore Indexes). The ~30-day lookahead is a CODE filter.

Output: `sendScheduledRemindersHandler` + the `sendScheduledReminders` onSchedule wrapper in
`functions/src/index.ts`, and its `describe` block in `functions/src/index.test.ts`. Nothing deployed; no secret.
