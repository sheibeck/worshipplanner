# Phase 62 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope & Precedent (read first)

Phase 62 is the **final, highest-complexity v1.7 phase**. Its one net-new client surface is a **dedicated
re-lock notify modal** — `src/components/ReLockNotifyPrompt.vue` — opened when a planner **re-locks** a
service (unlock → edit → re-lock) whose typed change diff is **non-empty**. It reuses, and does not
reinvent, every idiom Phases 58–61 shipped:

- **Modal shell** — the `<Teleport to="body">` → `bg-black/60` backdrop + centered
  `bg-gray-900 rounded-xl border border-gray-700 shadow-2xl flex flex-col` container copied verbatim from
  `PptxImportModal.vue:1-49` (the same shell `MessageComposer.vue` uses). Same fade/scale `Transition`,
  same three flex regions (header `shrink-0` / body `flex-1 overflow-y-auto` / footer `shrink-0`), same
  ✕ close glyph (`PptxImportModal.vue:45-47`).
- **Recipient choice + "Reaches N"** — the exact idiom from `MessageComposer.vue` (Phase 59 § SEND TO,
  Reaches-N footer), driven by `resolveRecipients(service, quarters, roles, people, selection)` +
  `MESSAGING_TEAM_LABELS` (`src/utils/messagingRecipients.ts`, Phase 58).
- **Type badge** — the muted pill idiom from `60-UI-SPEC.md` § Component #5
  (`inline-flex items-center px-2 py-0.5 rounded-full text-xs font-medium border`), reused per ChangeEntry
  row to tag its SONG / ORDER / ROLE / NOTES / SLIDES type.
- **Team-tag chip** — the `TeamTagPill.vue` chip recipe, reused read-only per row for `affectedTeams`.
- **Checkbox** — the shipped `h-4 w-4 rounded border-gray-600 bg-gray-800 text-indigo-600
  focus:ring-indigo-500 focus:ring-offset-gray-900` native checkbox (`ServiceEditorView.vue:510-514`)
  inside a `flex items-center gap-2` `<label>` (`:505-517`).
- **Kill-switch gate** — `isMessagingEnabled()` (Phase 58): messaging OFF → the modal **never opens**
  (re-lock overwrites the snapshot silently). Same choke point the composer/history use.
- **Send path** — `queueServiceMessage` with `type:'relock-notification'` + `changeDiff` (Phase 59
  wrapper, extended this phase). No new send surface.

**This is a CONTRACT**, not an implementation — component inventory, the check/uncheck → Reaches-N
interaction, the affected-vs-everyone recipient choice, every state (incl. Lock-quietly-always-available
and messaging-off-no-modal), accessibility of the checkable list + modal focus trap, and responsive.
Illustrative markup snippets are grounding, not the `.vue`.

**Visual reference:** no dedicated DESIGN-messaging.md section exists for the re-lock modal (it post-dates
§5a/§5b). The authoritative visual basis is therefore the **composer** (`59-UI-SPEC.md` § SEND TO / footer)
for the recipient half and the **history type-badge** (`60-UI-SPEC.md` §5) for the row half — this spec
composes those two shipped idioms inside the `PptxImportModal` shell. Where any generic-rubric ideal
conflicts with a shipped idiom, the shipped idiom wins (see § Accepted deviations), exactly as Phases
58–61 ruled.

**Focal point (visual hierarchy):** the eye lands first on the **checkable change-diff list** at the top
of the modal body — the diff *is* the notice content (R146), and every downstream control (the live
"Reaches N", the enabled/disabled "Send notice") recomputes from which rows are checked. The **primary
"Send notice"** button in the footer is the secondary anchor (the only `indigo` fill in the footer);
**"Lock quietly"** sits beside it as an always-available, secondary-styled escape (SC3).

**Success-criteria trace:** SC1 → the modal opens with the typed checkable diff (Component #3–4); SC2 →
the affected-vs-everyone choice + live Reaches-N (Component #5–6); SC3 → "Lock quietly" always enabled
(Component #7); SC4 → BOTH actions overwrite `lockSnapshots/current` (§ Interaction, stated for the
modal's contract even though the write itself is the lock hook's job).

### Accepted deviations — app-wide consistency (matched to Phase 58/59/60/61, do NOT re-flag)

Inherited verbatim from `59-UI-SPEC.md` / `60-UI-SPEC.md` § Accepted deviations. Changing them here would
make this modal the single inconsistent messaging surface. Accepted under the v1.7 autonomous grant's
"pick the reasonable default, state it" clause:

1. **Third font weight `font-medium` / 500 (Typography → ACCEPTED).** Every existing modal CTA
   (`PptxImportModal`, `MessageComposer`), the `TeamTagPill` chip, and the Phase 60 type badge use
   `text-sm`/`text-xs font-medium`. This modal's buttons, checkbox-row emphasis, type badges, and team
   chips inherit that app-wide chrome weight; it introduces no new weight. Same ruling as Phase 58/59/60/61.
2. **`12px` spacing (`gap-3` / `px-3` / `space-y-3` / `p-3`) (Spacing → ACCEPTED).** `12px` is the
   load-bearing app-wide token — the composer footer's `gap-3`, its `space-y-3` field stacks, the
   `messaging-defaults-panel`'s `p-3`. This modal reuses it for the footer button group, the row list, and
   inset panels. Multiple of 4, de-facto scale here; re-spacing only this modal would misalign it against
   its siblings.
3. **CTA verbs are action-specific, not a fixed noun phrase (Copywriting → ACCEPTED).** The primary CTA is
   **`Send notice`** and the secondary escape is **`Lock quietly`** — action-specific verb phrases matching
   the app's modal-CTA convention (`Import`, `Create service`, `Send now`), not a generic label. Same
   ruling as Phase 59 deviation #3. Additionally the primary label goes **dynamic** — `Send notice` →
   `Send to everyone` is NOT introduced (kept single-label for clarity); the composer's dynamic-label
   precedent (`Send now`/`Schedule send`) is cited only to justify action-specific verbs, not a second
   label here.

Net: no new tokens, no new component library, no new copy pattern — the modal is idiom-consistent with
`PptxImportModal.vue` + `MessageComposer.vue` + the Phase 60 badges. A future project-wide design-system
pass is the correct venue for the rubric ideals, not this component.

## Component Inventory

**Count: 9 sub-components** (enumerated 0–8) within the single new `ReLockNotifyPrompt.vue` (plus the
lock-hook trigger that owns whether the modal opens at all). Enumerated below; the lock-hook branch is #0.

### 0. Lock-hook trigger (NOT a visual element — `ServiceEditorView.vue::onMarkAsPlanned`)

Not markup; the state that decides whether the modal opens. On the **re-lock** path (a prior
`lockSnapshots/current` exists), the hook reads the prior snapshot + fingerprint, computes the current
ones, and runs `diffServiceSnapshots(...) → ChangeEntry[]`. Gating (all stated, no questions):

- **Messaging OFF (`isMessagingEnabled()` false) → modal NEVER opens.** Re-lock overwrites
  `lockSnapshots/current` silently (there is nowhere to send). This DIFFERS from the composer's
  disabled-but-visible entry point deliberately: there is no standing affordance here — the modal is an
  event-driven prompt, so "no prompt" is the correct messaging-off behavior (SC-consistent with Phase 61's
  "no email → no feedback"). **Stated default.**
- **Empty diff (`ChangeEntry[]` length 0) → modal NEVER opens.** A re-lock with nothing material changed
  overwrites `lockSnapshots/current` silently, no prompt (per `62-CONTEXT.md` re-lock branch). **Stated.**
- **Non-empty diff AND messaging ON → open `ReLockNotifyPrompt.vue`** with `open = true`, passing the
  computed `ChangeEntry[]`, the `service`, `quarters`, `roles`, `people`, and the resolved messaging
  context. `lockSnapshots/current` is **NOT overwritten yet** — the overwrite is deferred to modal confirm
  (SC4; overwriting earlier would destroy the diff basis, per `62-CONTEXT.md`).

**Critical:** the service is **ALREADY locked** by the time this modal opens — the lock transition
succeeded and is on screen (amber lock banner visible). This modal is a **follow-up notification choice**,
never the lock action itself. The header (#2) makes that explicit so a planner never reads "Send notice"
as "and then lock."

### 1. Modal shell (reused verbatim from `PptxImportModal.vue`)

`<Teleport to="body">` → `bg-black/60` backdrop (`z-40`, fade `Transition`) + centered container
(`z-50 fixed inset-0 flex items-center justify-center p-4`) holding:

```html
<div class="w-full max-w-lg max-h-[90vh] bg-gray-900 rounded-xl border border-gray-700 shadow-2xl flex flex-col">
```

`max-w-lg` (the importer's width, not the composer's wider `max-w-2xl`) — the re-lock modal is a scoped
review + choice, lower form density than the composer. Three flex regions: fixed header (`shrink-0`),
scrollable body (`flex-1 overflow-y-auto`), fixed footer (`shrink-0`). Enter/leave `Transition` classes
copied verbatim (opacity + scale). **Dismissal:** ✕ close, backdrop click, and **Escape** all call
`onCancel`. **Dismiss semantics (STATED):** dismissing via ✕/backdrop/Escape is equivalent to **Lock
quietly** for the snapshot — the service is already locked, so a dismissed prompt must STILL overwrite
`lockSnapshots/current` (SC4: the next re-lock diffs against the new state regardless of how this prompt
closed). It sends no message. This is the safe default and is stated so the executor does not leave the
snapshot stale on dismiss.

### 2. Header (`px-6 py-4 border-b border-gray-800 shrink-0`)

Left: `h2` **"Notify about these changes?"** (`text-base font-semibold text-gray-100`) + a subordinate
**already-locked subline** on its own row: the amber lock glyph (reused from `service-lock-banner`) +
`text-xs text-amber-300` **"This service is already locked — choose who to tell about your edits."** This
subline is the load-bearing clarity affordance (the modal is a follow-up, not the lock). Right: the
icon-only ✕ close button (`p-1.5 rounded-md text-gray-500 hover:text-gray-300 hover:bg-gray-800`,
`aria-label="Close"`, inline-svg glyph — verbatim from `PptxImportModal.vue:45-47`).

### 3. Change-diff list container (R146 — the focal point)

Section, no loud label needed (the header names it). A `<ul role="list" class="mt-1 divide-y
divide-gray-800">` (or `space-y-2`) holding one **checkable row (#4)** per `ChangeEntry`, in the order the
diff returns them. A **"Select all / none"** convenience is at implementer discretion (not required; all
rows default checked so the common path needs no bulk control). Above the list, a muted `text-xs
text-gray-500` count line: **"{N} {change|changes} since the last lock"** (pluralization-safe). If the
diff is non-empty (the only case this modal opens), the list always renders ≥1 row — there is **no
empty-list state inside the modal** (empty diff never opens it, #0).

### 4. ChangeEntry row (checkable — per `ChangeEntry`)

A `<label class="flex items-start gap-2 py-2 cursor-pointer">` (the shipped checkbox-row idiom,
`ServiceEditorView.vue:505-517`) containing:

- **Checkbox** (`<input type="checkbox" v-model=… class="h-4 w-4 mt-0.5 rounded border-gray-600
  bg-gray-800 text-indigo-600 focus:ring-indigo-500 focus:ring-offset-gray-900">`) — **default checked**
  (every change is included until the planner unchecks it). Toggling recomputes Reaches-N (#6) and the
  audit `changeDiff` payload live.
- **Type badge** (`inline-flex items-center px-2 py-0.5 rounded-full text-xs font-medium border
  bg-gray-800 text-gray-300 border-gray-700`, muted — the Phase 60 §5 badge idiom, NOT accent). Label maps
  `ChangeEntry.type`: **SONG** · **ORDER** · **ROLE** · **NOTES** · **SLIDES**. (Optional per-type hue at
  implementer discretion within the app-wide `bg-{hue}-900/50 text-{hue}-300 border-{hue}-800` recipe;
  the muted-gray default is least-surprising and stated as the baseline.)
- **Human description** (`text-sm text-gray-200`) — the `ChangeEntry.description` string (e.g. "Song in
  slot 2 changed to 'Great Are You Lord'", "Notes updated", "Slides changed"). Wraps freely; no
  truncation (matches the app's free-text convention).
- **Affected-team tags** (`flex flex-wrap gap-1 mt-1`): one read-only `TeamTagPill`-recipe chip per
  `ChangeEntry.affectedTeams` group, labelled via `MESSAGING_TEAM_LABELS`
  (band→Worship / tech→Tech / vocals→Vocals / other→Hosts). A **ROLE** entry renders exactly one chip
  (that role's group, R147); every other type renders the broad set. These chips are informational — they
  explain *why* a team is reachable, and they visibly update the affected-teams union the recipient choice
  (#5) defaults to.

### 5. Recipient choice (R147, SC2 — affected vs everyone)

An inset card (`rounded-lg bg-gray-800/60 border border-gray-700 p-3 mt-4 space-y-2`) with a `text-xs
font-semibold uppercase tracking-wide text-gray-400` label **"NOTIFY"** and **two mutually-exclusive
options** rendered as a segmented pair of `<button type="button" role="radio" :aria-checked>` (the
composer's segmented-control idiom; a native radio group is an acceptable equivalent at implementer
discretion):

- **"Affected teams"** — **DEFAULT selected.** Resolves to the **union of `affectedTeams` across the
  CHECKED entries** (recomputes as rows are checked/unchecked). A muted `text-xs text-gray-500` descriptor
  lists the current union (e.g. "Worship, Vocals"). If the checked set's union is empty (all rows
  unchecked, or only rows with no resolvable team), this option resolves to zero teams → drives the
  zero-reachable disabled state (#7 / § States).
- **"Everyone on this service"** — sets `includeEveryone = true` (the resolver ignores the team filter and
  resolves every assigned role). Independent of which rows are checked (it reaches everyone regardless),
  though the checked entries still define the audit `changeDiff`.

**Affected-vs-everyone DEFAULT decision (STATED):** **"Affected teams" is the default** — it is R147's
stated primary intent (tell the people a change actually touches), the least-noisy choice, and mirrors the
composer's teams-first thesis (R136). "Everyone" is the deliberate opt-up for a planner who wants the
whole service informed. Selecting an option writes the `{ teams, individualPersonIds: [], includeEveryone }`
selection shape `resolveRecipients` consumes (no individual-person picker in this modal — the notice
targets teams/everyone only, per `62-CONTEXT.md`; `individualPersonIds` is always `[]`).

### 6. Live "Reaches N" line (R147/SC2 — the recompute anchor)

Directly under the recipient choice (and mirrored in the footer summary), a `text-xs text-gray-400`
`aria-live="polite"` line: **"Reaches {reachable.length} {person|people}"**, and when the current
selection's `unreachableCount > 0` a muted appended span **" · {unreachableCount} {has|have} no email"**
(`text-gray-500`, informational, never error). **Recomputes on EVERY change** to (a) which ChangeEntry
rows are checked (which changes the affected-teams union), or (b) the affected-vs-everyone choice — via
`resolveRecipients(service, quarters, roles, people, selection)`. This is the same count idiom the
composer footer uses (Phase 59 § Component #11 left side); it is the single live readout that ties the
checkable list to the recipient outcome.

### 7. Footer (`px-6 py-4 border-t border-gray-800 flex items-center justify-between gap-3 shrink-0`)

- **Left — live recipient summary (mirrors #6):** `text-xs text-gray-400` **"Reaches {N} {person|people}"**
  (+ the muted no-email span). `aria-live="polite"`. Recomputes with every selection change.
- **Right — button group (`flex items-center gap-3`):**
  - **`Lock quietly`** (secondary: `px-4 py-2 rounded-md text-sm font-medium text-gray-300 bg-gray-800
    hover:bg-gray-700 border border-gray-700`) — **ALWAYS enabled (SC3)**, regardless of checked rows,
    recipient choice, or reachable count. Sends **no** message; overwrites `lockSnapshots/current` (SC4)
    and closes. This is the always-available escape and must never be disabled.
  - **Primary `Send notice`** (`px-4 py-2 rounded-md text-sm font-medium text-white bg-indigo-600
    hover:bg-indigo-500 transition-colors disabled:opacity-50 disabled:cursor-not-allowed`) — calls
    `queueServiceMessage` with `type:'relock-notification'`, `recipientSelector` = the chosen selection,
    `changeDiff` = the **checked** entries (audit), `options.attachServiceLink: true`, subject/body
    auto-generated from the checked entries. Then overwrites `lockSnapshots/current` (SC4) and closes.
    **Disabled** per the rules in § States (zero reachable, or zero checked entries, or a send in flight).
    On disable it carries a `title` explaining the block. There is deliberately **no `Cancel`** distinct
    from `Lock quietly` — since the service is already locked, "cancel the prompt" and "lock quietly" are
    the same outcome; collapsing them to one clearly-labelled `Lock quietly` avoids a "does Cancel leave it
    unlocked?" ambiguity. (✕/backdrop/Escape also resolve to Lock-quietly semantics, #1.)

### 8. Inline send-failure error (conditional)

On a `queueServiceMessage` rejection, a `text-red-400 text-sm mt-2` line in the footer area:
**"Couldn't send the notice. The service is still locked — try again or Lock quietly."** The **Send
notice** button re-enables (draft/selection preserved so the planner can retry), and **Lock quietly**
remains available. **Safe-behavior decision (STATED):** on send failure the service **stays locked** and
`lockSnapshots/current` is **NOT overwritten by the failed send** — the overwrite is coupled to a
*successful* confirm (send success OR an explicit Lock-quietly). Rationale: if the send failed, keeping
the OLD snapshot means a retry (or a later Lock-quietly) still diffs against the true pre-edit basis, so
the change list is not silently lost. The lock transition itself already succeeded independently (Phase 61
non-blocking pattern), so the failure is amber/red-informational at the notice level, never a re-raised
lock failure. Server kill-switch reject (messaging turned off between open and send) lands here too, with
copy: **"Messaging is turned off for your organization — Lock quietly to finish."**

## Interaction & Behavior

| Trigger | Behavior |
|---------|----------|
| Re-lock a service with a **non-empty** diff, messaging ON | Lock transition succeeds (banner shows) → `ReLockNotifyPrompt` opens with all ChangeEntry rows **checked**, recipient = **Affected teams**, Reaches-N computed from the checked-union. `lockSnapshots/current` NOT yet overwritten. |
| Re-lock with an **empty** diff, or **messaging OFF** | **No modal.** `lockSnapshots/current` overwritten silently. (SC-consistent no-op.) |
| Check / uncheck a ChangeEntry row | Update the checked set → recompute the affected-teams union → **immediately recompute** `resolveRecipients` → update the Reaches-N line (#6 + footer), the recipient descriptor, and the **Send notice** enabled-state. The `changeDiff` audit payload = the currently-checked entries. |
| Switch recipient choice (Affected teams ↔ Everyone) | Rewrite the `{ teams, includeEveryone }` selection → recompute Reaches-N + Send enabled-state. Checked rows still define `changeDiff`. |
| Click **Send notice** (enabled) | Disable + set loading ("Sending…") → `queueServiceMessage(type:'relock-notification', changeDiff, recipientSelector, options.attachServiceLink:true)` → on success: overwrite `lockSnapshots/current`, close, surface the app's existing confirmation posture (see note); on failure: show #8 inline error, re-enable, keep snapshot as-was (safe). |
| Click **Lock quietly** (always enabled, SC3) | No send → overwrite `lockSnapshots/current` (SC4) → close. |
| ✕ / backdrop / Escape | Same as Lock quietly for the snapshot (dismiss = quiet lock): overwrite `lockSnapshots/current`, no send, close (#1). |

**Success-feedback note (inherited constraint, NOT re-litigated):** per `61-UI-SPEC.md`, `ToastHost.vue`
is a **failure-only** stack (hardcoded `Save failed.` prefix), so pushing a success string misrenders. The
re-lock modal therefore surfaces send success by **closing on success** (the service is already locked;
the Phase 60 history panel is the durable "was it sent" record — a `relock-notification` row lands there
with real counts). No success toast is introduced. This matches Phase 61's routing-around decision and
avoids the latent `ToastHost` misrender; a success/info toast variant remains a future project-wide pass.

**Server defense in depth (unchanged, noted):** even though #0 gates on `isMessagingEnabled()` client-side,
`queueServiceMessage` re-checks the kill-switch server-side (Phase 59). A between-open-and-send disable →
the #8 server-reject error branch (lock already succeeded; snapshot untouched by the failed send). The UI
gate is a convenience, not the security boundary.

## Accessibility

- **Dialog semantics:** modal container `role="dialog" aria-modal="true"
  aria-labelledby="{title-id}" aria-describedby="{already-locked-subline-id}"`. Focus is **trapped** within
  the modal while open (Tab/Shift-Tab cycle stays inside); on close, focus returns to the control that
  triggered the re-lock (the Mark-as-Planned / Re-lock action, or the service action bar). Initial focus
  lands on the **first ChangeEntry checkbox** (or the modal container) so a keyboard user starts at the
  diff, not the destructive-looking primary.
- **Checkable list:** each row is a native `<label>` wrapping a native `<input type="checkbox">`, so the
  full description + badge is a click/tap target and Space toggles it; the list is `role="list"`, rows are
  implicit list items. Checkbox state is native (announced as checked/unchecked) — never carried by color
  alone. The type badge and team chips are `aria-hidden` decoration relative to the description OR are
  included in the accessible name via visible text (implementer discretion) — the description text is the
  authoritative label.
- **Recipient choice:** the two options are `role="radio"` within a `role="radiogroup"
  aria-label="Who to notify"`; `aria-checked` reflects selection; arrow keys move between them (native
  radios) or Space/Enter activate (button-radios). Never color-only.
- **Live region:** the **Reaches N** line(s) are `aria-live="polite"`, so a screen-reader user hears the
  count update as they check/uncheck rows or switch the recipient choice.
- **Buttons:** the disabled **Send notice** uses the real `disabled` attribute (announced + skipped) with a
  `title`; **Lock quietly** is never disabled; the ✕ close carries `aria-label="Close"`.
- **Keyboard:** Escape closes (= Lock-quietly semantics); Tab order is DOM order (checkboxes → recipient
  radios → footer: Lock quietly → Send notice). All controls are native/`<button>` — fully operable.
- **Contrast:** all text meets the app's dark-theme contrast (`text-gray-100/200/300` on `gray-900/800`);
  the muted `text-gray-500` no-email note is informational, paired with the visible count, never the sole
  carrier of a blocking condition; the red error line matches the app's existing red-on-gray error contrast.

## Responsive Behavior

Single modal, `w-full max-w-lg max-h-[90vh]` with an internal `overflow-y-auto` body — the shell is
inherently responsive (the `p-4` outer padding keeps it off the viewport edges on small screens); a long
change list scrolls within the body while header/footer stay fixed.

- **Mobile (`< sm`):** effectively full-width (minus `p-4`). ChangeEntry rows keep the checkbox +
  description on the first line and let the type badge + team chips `flex-wrap` onto the next; the footer
  switches to `flex-col sm:flex-row` so the Reaches-N summary wraps above the button group, and the two
  buttons may go full-width stacked on the narrowest widths (Lock quietly above Send notice, or side by
  side — implementer discretion within the reused footer idiom).
- **Desktop (`≥ sm`):** recipient summary left, buttons right in the footer; body scrolls internally if the
  diff list exceeds `90vh`.
- No separate tablet breakpoint — the app uses only the `sm:` boundary here (consistent with every existing
  modal).
