# Phase 64 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope & Precedent (read first)

Phase 64 is a **refinement pass over two SHIPPED components** — `src/components/MessageComposer.vue`
(the Phase 59 send surface) and `src/components/ServiceMessageHistory.vue` (the Phase 60/63 history
card). **It invents no new component, no new visual language, and no new tokens.** Every change below is
an *edit to existing markup* that already carries the app's dark-theme idioms. The authoritative visual
contract is `59-UI-SPEC.md` (all 11 sub-components, states, a11y, responsive) — this spec **inherits it
wholesale** and overrides only the six specific spots R151–R156 touch.

**Grounding:** Vue 3 `<script setup>` + Tailwind v4 hand-rolled dark theme. No design system —
`components.json` absent, no shadcn/shadcn-vue in the repo. shadcn gate: **N/A** (not initialized, no
third-party registries). Native `input`/`textarea`/`select`/`checkbox`/`button` + inline `<svg>` glyphs,
Inter 400. Reuse the composer's existing idioms and `ServiceMessageHistory`'s status-pill recipe
verbatim.

**No questions asked** (owner away, v1.8 autonomous grant). Every grey area is resolved to the
app-consistent default and **stated** in-line below.

### Accepted deviations — inherited from `59-UI-SPEC.md`, do NOT re-flag

Phase 59 recorded three deliberate app-wide conventions the generic checker rubric flags. Phase 64 edits
the same markup and inherits them unchanged. **These are not divergences and must not be re-raised:**

1. **Third font weight `font-medium` / 500** on interactive chrome (buttons, chips) — app-wide across
   every modal and `TeamTagPill`. The Send button, team chips, token chips, and history status pills all
   carry it. (59 Accepted deviation #1.)
2. **`12px` spacing (`gap-3` / `px-3` / `space-y-3` / `py-1.5`)** — load-bearing app-wide token, a
   multiple of 4, used in the composer footer, control padding, and the segmented control. (59 Accepted
   deviation #2.)
3. **Action-specific dynamic CTA verbs** — the primary button reads `Send now` / `Schedule send` (and
   now `Sending…` / `Scheduling…` in-flight), not a fixed noun phrase. Mirrors the app's `Import` /
   `Create service` modal-CTA convention. (59 Accepted deviation #3.)

**New for this phase (recorded, not flagged):** the token palette drops from 4 to 4 chips (swap
`Song list` → `Name`); the footer button group drops from 3 buttons to 2 (the `Preview` button is
deleted — preview is now always live). Both reduce surface area; neither adds a token or pattern.

## Change Contract (the six refinements)

Each entry is an **edit to existing markup**, with the current line references and the exact resolved
behavior. Line numbers are the shipped file at spec time (approximate — match the markup, not the number).

### R151 — Team-chip labels → Band / Vocals / Tech / Other

- **Where:** `src/utils/messagingRecipients.ts::MESSAGING_TEAM_LABELS` (L17-22). Currently
  `band→'Worship'`, `tech→'Tech'`, `vocals→'Vocals'`, `other→'Hosts'`. **Change to** `band→'Band'`,
  `tech→'Tech'`, `vocals→'Vocals'`, `other→'Other'` — the raw RoleGroup names, matching Volunteer Roles.
- **Composer markup: NO per-chip change.** The team chips already render `{{ team.label }} · {{ team.count }}`
  (MessageComposer.vue L78) where `team.label` is read from `MESSAGING_TEAM_LABELS[group]` in the
  `teamChips` computed (L396-400). Changing the one constant re-labels the chips everywhere it feeds —
  the composer chips **and** `ReLockNotifyPrompt.vue`'s team tags — with zero component edits. **Confirmed:
  the UI needs no per-chip change.**
- Note for the executor (not a UI concern): update any test that hard-codes `"Worship"` / `"Hosts"`.

### R152 — "+ Add someone" becomes a clear, working add affordance

- **Current (broken affordance):** MessageComposer.vue L97-107 wraps a native `<select>` inside a
  `<label class="text-xs text-indigo-400 …">＋ Add someone</label>`. The add happens only on the select's
  `@change="onAddIndividual"`; **clicking the "＋ Add someone" text merely focuses the hidden select**, so
  it reads as "does nothing / just highlights the dropdown." `addablePeople` (L412) filters on `p.active`.
- **Decision (resolved default): a visible, labeled person picker — a real form `<select>`, not a
  link-disguised control.** Restructure the Individuals-panel header row so the picker is an obvious
  dropdown the user selects a name from; the selection adds a removable pill and bumps "Reaches N".
  Concretely:
  - Keep the panel's left-hand **"Individuals"** label (L96). Replace the `<label>`-wrapped select
    (L97-107) with a **standalone `<select data-testid="add-someone-select">`** styled as the app's
    other selects (`bg-gray-800 border border-gray-700 rounded-md px-2 py-1 text-xs text-gray-100
    focus:outline-none focus:ring-2 focus:ring-indigo-500`), right-aligned in the header row.
  - **First option is a disabled placeholder** `＋ Add someone…` (`value=""`, `disabled` so it can't be
    re-selected but reads as the affordance label). Remaining options are `addablePeople` by name.
  - **Behavior (unchanged handler, keep `onAddIndividual` L449-454):** on `@change`, push the chosen id
    into `selection.individualPersonIds` and **reset the select back to the placeholder** (`el.value = ''`
    — already done). The person appears as a removable pill (pills already work, L109-125), and the live
    "Reaches N" (footer `reachableCount`, driven by the `resolved` computed L384) reflects them
    automatically — no extra wiring.
  - **Keyboard-accessible:** it is a native `<select>` (Tab to focus, arrow/Enter to choose) — inherent.
- **`active`-filter risk — resolved:** `Person.active` is a **real, reliably-set boolean** (roster.ts
  L19: "soft-delete inverse; inactive people drop out of proposals + pickers"). Keeping
  `p.active && !alreadySelected` is the *intended* behavior — inactive volunteers **should** be excluded.
  The "empty dropdown" perception in CONTEXT was root-cause (a) the label affordance, **not** (b) the
  filter. **Keep the `active` filter.** Fallback, stated for the executor: *if* verification shows real
  roster people carrying a falsy/absent `active`, relax the filter to exclude **only already-selected
  ids** (`!selection.individualPersonIds.includes(p.id)`) so the picker is never wrongly empty.
- **No typeahead** — small rosters (per CONTEXT deferred). A plain `<select>` suffices.
- **Empty add-picker state:** when `addablePeople` is empty (everyone reachable is already added, or the
  roster has no other active people), the select shows a **disabled** placeholder reading **`No one left
  to add`** and is itself `disabled` (`disabled:opacity-50 cursor-not-allowed`) — a quiet, honest
  resting state, not an error.

### R153 — Live preview (remove the click-to-preview gate)

- **Current:** the `sample-preview` block is gated `v-if="showPreview"` (L194) and toggled by a footer
  **`Preview`** button (L241-246) bound to a `showPreview` ref (L351, reset L629).
- **Decision:** **Remove the `showPreview` gate, the `Preview` button, and the `showPreview` ref.** The
  Sample-preview block **renders always** and updates live as subject/body change — `samplePreview` is
  already a reactive computed (L526-529), so it recomputes on every keystroke with no new logic.
- **Position: unchanged** — the preview stays exactly where it is in the scroll body (after the message
  body + token palette, before the Options card, L193-201). It is clearly a **representative render**:
  keep the existing `SAMPLE` badge (L196) and the muted caption (L197, `sampleCaption`) that says
  "Rendered for {name} — the actual email personalizes each person's roles." / the no-recipients variant.
- **Footer consequence:** the button group (L240-261) drops to **`Cancel` + primary Send** only. `gap-3`
  and `justify-between` are unchanged; removing one secondary button leaves the footer visually balanced.

### R154 — Tokens: drop `{{song_list}}`, add `{{name}}`

- **Palette (client `tokenChips`, L362-367):** **remove** `{ token: 'song_list', label: 'Song list' }`;
  **add** `{ token: 'name', label: 'Name' }`. **Final chip set, in order:**
  **`＋ Service date` · `＋ Service link` · `＋ Their roles` · `＋ Name`** (still 4 chips; same
  `flex flex-wrap gap-2` row, same chip idiom L181-188, no markup change beyond the array).
- **Sample render (`renderSample`, L518-524):** stop offering `song_list`; **render `{{name}}`** as the
  sample recipient's own name — `fillToken(out, 'name', sampleRecipient.value?.name ?? '[name]')`,
  following the `their_roles` precedent (L521). (The `songList` computed L504-510 may be removed if now
  unused.) The always-on preview thus shows the real recipient name live.
- **Server (`functions/src/index.ts renderMessageTokens`):** add `{{name}}` → the recipient's own `name`,
  per-recipient like `{{their_roles}}`; **keep `{{song_list}}` supported server-side** (harmless legacy)
  — it simply leaves the palette. This is a functions change; ships built/tested/**UNDEPLOYED**. Not a UI
  surface, noted for completeness.

### R155 — Sending state (in-button spinner) + kill the perpetual "Sending…"

**Composer — Send button (L253-260):**

- The button already shows a dynamic label (`sendLabel`: `Sending…` / `Scheduling…` while `sending`,
  L559-562) and `sendDisabled` already includes `sending` (L547-553). **Add a VISIBLE in-progress
  spinner** inside the button: when `sending`, render, before the label, an app-standard CSS spinner
  `<span class="inline-block h-4 w-4 border-2 border-white/70 border-t-transparent rounded-full
  animate-spin" aria-hidden="true"></span>` with the button content in an `inline-flex items-center
  gap-2`. The button stays `disabled` while sending (unchanged). Matches the history card's spinner recipe
  (ServiceMessageHistory.vue L86-89) recolored white for the indigo fill.
- **Disable Cancel during send:** `onCancel` already no-ops while `sending` (L608-609); **also disable it
  visually** — add `:disabled="sending"` + `disabled:opacity-50 disabled:cursor-not-allowed` to the
  Cancel button (L247-252) so the whole footer reads inert during the async action (matches
  `PptxImportModal`'s in-progress footer).
- **Remove the misleading success toast:** delete the `toasts.push(...)` success call (L592-596). The
  composer already `emit('sent', …)` (L597) and the parent closes it; the Phase 60/63 history panel shows
  the sent message. **Rationale (owner-disclosed defect):** `ToastHost.vue` hard-codes a red "Save
  failed." prefix, so a success toast renders "Save failed. Message queued…". Dropping the push removes
  the misrender. **Leave the error path untouched** — `sendError` still renders inline
  (`text-red-400`, footer, L238). Resolves the Phase 59 PENDING-VERIFICATION defect.

**History — `ServiceMessageHistory.vue` failed/stuck affordance:**

- **Current:** `statusPill` (L211-225) maps `queued`/`sending` → `{ label: 'Sending…', spinner: true,
  grey classes }` **with no age check**, and `sendTimeLabel` (L241-255) likewise returns `'Sending…'` for
  those statuses — so a message whose send trigger never flipped the status spins **forever**.
- **Decision (resolved default): an aged-queued/sending row surfaces as a red "Failed to send" pill
  instead of a perpetual spinner.**
  - **Threshold:** `createdAt` older than **5 minutes** (`ServiceMessageDoc.createdAt: Timestamp | null`
    exists, L61 of the store — use `createdAt.toMillis()`; if `createdAt` is null, fall back to treating
    the row as *not yet* aged, i.e. keep "Sending…"). A row `queued`/`sending` **and** `createdAt` older
    than `5 * 60 * 1000` ms → **stuck**.
  - **Presentation of a stuck row:** reuse the existing **`failed` pill recipe verbatim** —
    `bg-red-900/50 text-red-300 border-red-800`, **no spinner** — with label **`Failed to send`**. The
    already-`failed` status keeps its existing red `Failed` pill (L217-218). A genuinely recent
    `queued`/`sending` row (< 5 min) keeps the grey **`Sending…`** spinner pill (a legitimate in-flight
    state).
  - **`sendTimeLabel`** for a stuck row returns **`Failed to send`** (red is carried by the pill; the
    time line just stops lying with "Sending…"). Recent in-flight rows still read `Sending…`.
- **No retry write path** — this is a **read-only presentation change** (surfacing only). An actual
  resend-from-history action is explicitly deferred (CONTEXT). Copy stays `Failed to send` (not
  "Stuck — retry") since no retry affordance is offered yet.

### R156 — Message types seed distinct content (preview now proves it)

- **Segmented control markup: unchanged** (L134-152). The "types do nothing" perception was the hidden
  preview (fixed by R153) plus subtle/misaligned seeds — fixed here in `TYPE_DEFAULTS` + `selectType`.
- **Align `TYPE_DEFAULTS` (L371-381)** to the CONTEXT-agreed content (raw token templates — the
  authoritative per-recipient render is server-side):
  - **One-off** (`oneoff`): `subject: ''`, `body: ''` — a blank compose.
  - **Reminder** (`reminder`): `subject: 'Reminder: {{service_date}}'`, body seeded with the service link
    (and `{{name}}` / `{{their_roles}}` as apt), e.g. `Hi {{name}} — a reminder you're scheduled to serve
    on {{service_date}}. Here's the plan: {{service_link}}`.
  - **Share service link** (`share-link`): `subject: 'Service plan for {{service_date}}'`,
    `body: '{{service_link}}'` — **link-only**.
- **Keep the dirty guard** (`selectType`, L462-467): re-seed `subject`/`body` **only when
  `!subjectDirty` / `!bodyDirty`** — switching type after typing never clobbers the draft.
- **Reminder additionally defaults recipients to Everyone assigned:** add a new **`recipientDirty`** ref,
  set `true` whenever the user changes team/individual/everyone selection (`toggleTeam`, `toggleEveryone`,
  `onAddIndividual`, `removeIndividual`). In `selectType('reminder')`, if `!recipientDirty`, set
  `selection.includeEveryone = true` (and clear `selection.teams`, mirroring `toggleEveryone`). **One-off
  and Share leave recipients as-is** (owner spec focuses on Reminder; do not auto-set recipients for the
  other two). Reset `recipientDirty=false` in `resetComposer` (L614-630).
- With R153's always-live preview, switching type now **visibly** rewrites the rendered subject/body (and,
  for Reminder, bumps "Reaches N" to everyone) — closing the "does nothing" gap.
