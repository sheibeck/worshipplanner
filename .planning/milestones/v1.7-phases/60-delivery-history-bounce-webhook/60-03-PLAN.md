<objective>
Ship the read-only client surface: a per-service "Sent on this service" delivery-history card (R142) that lists
each `messages/{id}` with type / recipient count / send time and surfaces hard bounces per message (R143) with a
"Fix email →" deep-link to the volunteer's roster edit. The card mounts inline in the Service Order tab of
`ServiceEditorView.vue`, directly below the `messaging-defaults-panel`, and is hidden when messaging is off.

Purpose: R142 (the history listing — ROADMAP success criterion 1) and R143 (hard-bounce surfacing + fix
affordance — success criterion 2). The panel merely READS what 60-02's webhook wrote (`status:'bounced'`,
`bounceReason`, `bouncedAt`, `deliveryCounts.bounced`); it has no write path of its own and needs NO new Firestore
rule — nested-path `messages`/`recipients` reads run under the Phase 58 `isOrgMember` rules already deployed
(60-UI-SPEC.md § Panel Placement; 60-CONTEXT.md § Firestore rules). The panel is idiom-consistent with the
`messaging-defaults-panel` card, the `LyricVersionHistory.vue` row/badge list, and the `PptxImportModal.vue`
spinner — it invents no new visual language (60-UI-SPEC.md is the authoritative contract).

This plan is independent of 60-01/60-02 (Wave 1): a missing `deliveryCounts.bounced` is treated as 0, so the panel
renders correctly against today's Phase-59 docs even before the webhook is deployed.

Output: a small `src/stores/serviceMessages.ts` store (nested subscribe + lazy bounced-recipients read), the new
`ServiceMessageHistory.vue` panel, its mount + gate in `ServiceEditorView.vue`, the RosterView `?edit=` deep-link
handler, and the four new/extended test files.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (history panel) → Firestore (nested reads) | The panel reads services/{id}/messages + messages/{id}/recipients under the Phase 58 isOrgMember rules; it is READ-only and issues no writes |
| isMessagingEnabled() UI gate | The messaging-off HIDDEN gate is a client convenience; the server kill-switch (Phase 58) and the isOrgMember read rules are the real boundary |
| ?edit={personId} deep-link → RosterView edit | The query param only pre-opens an existing edit form for a person the org member can already edit; the roster write path (Phase 58 rules) is unchanged |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-60-03a | Tampering | a client forging bounce state via the panel | high | mitigate | The panel is READ-only; recipients `allow write: if false` and messages `allow update,delete: if false` (firestore.rules :152,:144) — only 60-02's Admin-SDK webhook writes bounce state. |
| T-60-03b | Information Disclosure | a non-member reading another org's message history | medium | mitigate | Nested-path reads run under the Phase 58 isOrgMember rules (firestore.rules :142,:151); NO client collectionGroup read is introduced (which would need a new rule + ALLOW-case test — 60-CONTEXT.md § Firestore rules). |

| T-60-SC | Tampering | npm/pip/cargo installs | low | accept | ZERO packages installed this plan — the panel reuses shipped Phase-58/59 utils + firebase/firestore + vue-router already present. |
