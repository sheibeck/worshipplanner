# Phase 60 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope & Precedent (read first)

Phase 60 ships **one new read-only client surface**: the per-service **"Sent on this service"** delivery-history
panel (R142) with **per-message hard-bounce surfacing** (R143). The other Phase 60 deliverable — the
`messageWebhook` HTTP Function — has **no UI** and is out of this contract entirely (it is a Cloud Function
that writes `recipients/{id}.status='bounced'`, `bounceReason`, `bouncedAt`, and increments
`messages/{id}.deliveryCounts.bounced`; the panel merely *reads* what it wrote).

This panel is a **sibling of the Phase 59 composer** and reuses the exact same hand-rolled Tailwind dark-theme
idioms. It invents no new visual language. Everything it needs already exists:

- The **card shell** idiom — `rounded-lg bg-gray-900 border border-gray-800 p-3` — is copied verbatim from
  the existing per-service **`messaging-defaults-panel`** (`ServiceEditorView.vue:811`, Phase 58), directly
  above which this panel mounts.
- The **pill/badge** idiom — `inline-flex items-center px-2 py-0.5 rounded-full text-xs font-medium border`
  with the tint recipe `bg-{hue}-900/50 text-{hue}-300 border-{hue}-800` — is the app-wide status-pill recipe
  already shipped in `RosterView.vue` (emerald Active pill, line 368) and `TeamTagPill.vue` (teal/pink
  variants). Phase 60 instantiates that same recipe in new hues (red, amber, indigo, gray) — not a new token
  family.
- The **kill-switch gate** `isMessagingEnabled()` (Phase 58) gates the panel like it gates the composer.
- The **spinner** idiom (`h-8 w-8 border-2 border-indigo-500 border-t-transparent rounded-full animate-spin`)
  is copied verbatim from `PptxImportModal.vue:103`.
- The **✉ New message** link reopens the existing `MessageComposer.vue` (`messageComposerOpen = true`, Phase 59)
  — no new composer, no new open path.

**Visual reference:** `.planning/research/DESIGN-messaging.md` § **5b — "Sent on this service" history** is the
authoritative layout (card header "Sent on this service" + `✉ New message` link; each row = type badge +
subject + counts + timestamp; a `[BOUNCED]` row with a `→ Fix email` affordance). Two DESIGN reconciliations
apply and are enforced here: (1) **omit the "N opened" figure everywhere** — v1.7 tracks *sent + hard bounces
only* (locked decision, DESIGN scope-reconciliation note); (2) the mockup's "violet" becomes the app's shipped
**`indigo`** accent (same swap Phase 59 made).

**What is NOT in this phase:** no retry/resend of a bounced message from the panel (deferred), no soft-bounce or
complaint or open surfacing, no write path of any kind from the panel (roster edit is the only mutation, and it
happens on a *different* view the "Fix email" link routes to). The panel is **read-only**.

**Focal point (visual hierarchy):** in the resting/populated state the eye lands first on the **most-recent
message row at the top** (newest-first is R142's ordering). When any message has bounced, the **red bounce
indicator** is the deliberate second focal point — it is the single loud color in an otherwise-muted list, so a
planner sees a bad address immediately (R143's whole purpose). Everything else (type badges, counts, timestamps)
is intentionally muted so the bounce cannot be missed.

### Accepted deviations — app-wide consistency (matched to Phase 58/59, do NOT re-flag)

Inherited verbatim from `59-UI-SPEC.md` § Accepted deviations. Changing them here would make this panel the
single inconsistent messaging surface. Accepted under the v1.7 autonomous grant's "pick the reasonable default,
state it" clause:

1. **Third font weight `font-medium` / 500 (Typography → ACCEPTED).** Every existing pill (`TeamTagPill`,
   RosterView's Active pill) and every modal CTA uses `font-medium`. The type/status/bounce badges inherit this
   app-wide chrome weight; it introduces no new weight. Same ruling as Phase 58/59.
2. **`12px` spacing (`gap-3` / `px-3` / `space-y-3` / `p-3`) (Spacing → ACCEPTED).** `12px` is the load-bearing
   app-wide token — the `messaging-defaults-panel` card this panel sits beside is `p-3`, and its field stacks are
   `space-y-3`. Re-spacing only this panel would misalign it against its immediate sibling. Multiple of 4, de-facto
   scale here.
3. **Same tint recipe, new hues (Color → ACCEPTED).** The status-pill recipe `bg-{hue}-900/50 text-{hue}-300
   border-{hue}-800` is already app-wide (emerald, teal, pink). Instantiating it in red / amber / indigo / gray for
   message-status semantics is a reuse of the established recipe, not a new palette. Only `indigo` and `red` carry
   *interactive/semantic* meaning (accent + destructive); amber/gray are purely informational status tints.

Net: no new tokens, no new component library, no new copy pattern — the panel is idiom-consistent with the
`messaging-defaults-panel` card and `PptxImportModal.vue`.

## Panel Placement Decision (STATED)

**Decision: a "Sent on this service" card rendered inline in the Service Order tab of `ServiceEditorView.vue`,
directly BELOW the existing `messaging-defaults-panel` card (`ServiceEditorView.vue:811`).** Not a new tab, not a
modal.

Rationale (least-surprising, app-consistent):
- **Co-location:** the `messaging-defaults-panel` (per-service messaging config) already lives at the top of the
  Service Order tab. Placing the *history of what those settings produced* immediately below it groups every
  per-service messaging surface in one place — the same tab where the composer's context (`service`, `quarters`,
  `roles`, `people`) already lives.
- **Not a tab:** the editor deliberately has exactly three tabs (Service Order / Slides / Roles). Adding a fourth
  "Messages" tab for a read-only list would be tab proliferation the app has resisted; the card idiom scales here
  without it.
- **Not a modal:** history is *reference* content a planner scans, not a task flow. Modals in this app
  (`PptxImportModal`, `MessageComposer`, `NewServiceDialog`) are all *task* surfaces. A read-only list belongs
  inline.
- Uses the identical card shell as its neighbor: `rounded-lg bg-gray-900 border border-gray-800 p-3` with a
  `mt-3` gap below the defaults panel.

The panel reads the service's **`services/{id}/messages`** subcollection (nested-path read, `isOrgMember` rule,
already deployed in Phase 58) via a new subscription in `src/stores/services.ts`; bounced-recipient detail reads
each bounced message's **`messages/{id}/recipients`** subcollection (also `isOrgMember`, Phase 58) lazily on
expand. No `collectionGroup` client read is introduced, so **no new Firestore rule this phase** (per
`60-CONTEXT.md` § Firestore rules — the preferred nested-path path).

## Component Inventory

**Count: 13 sub-components** (enumerated 0–12) — one new `ServiceDeliveryHistory.vue`-style card mounted in
`ServiceEditorView.vue`'s Service Order tab, plus the store read. (Whether it is a standalone
`ServiceDeliveryHistory.vue` component or an inline card block is at implementer discretion — the
`messaging-defaults-panel` is inline, so inline is the least-surprising default; the contract below is
component-shape-agnostic.)

### 0. Mount point + store read (`ServiceEditorView.vue` Service Order tab + `src/stores/services.ts`)

The card renders inside `<div v-show="activeTab === 'service-order'">`, `mt-3` below the
`messaging-defaults-panel` (`ServiceEditorView.vue:811`). Two gates, both matching the app's existing patterns:

- **Messaging-off gate — HIDDEN (stated default, DIFFERS from the composer entry point, deliberately).** When
  `isMessagingEnabled()` is false the entire card is **omitted** (`v-if`). Rationale: per `60-CONTEXT.md`
  ("a fresh org with messaging off shows no history surface") a messaging-off org has *no messages* — a disabled
  empty card would teach nothing. Discoverability is NOT lost: the Phase 59 ✉ action-bar item already renders
  *disabled-with-tooltip* ("Turn on Messaging in Settings…") when messaging is off, so the feature's existence
  and the path to enable it are already surfaced there. This is the correct place for the disabled-hint
  affordance; the history card is a reference surface, so hidden is right. (Contrast Phase 59 #0, which chose
  disabled-not-hidden *for the action affordance* — a considered, surface-specific difference, not an
  inconsistency.)
- **Editor gate:** the card renders only for `authStore.isEditor` (matches the `messaging-defaults-panel`'s
  `canEditService`/editor branches and every other mutating-adjacent surface). A viewer never sees it.

The store adds a subscription/read for `services/{id}/messages` ordered **newest-first** (by `createdAt`/`sentAt`
desc), exposing `{ sent, failed, bounced }` with a **missing `bounced` treated as 0** (older docs, per
`60-CONTEXT.md`). Bounced-recipient detail is fetched lazily per message on expand from `messages/{id}/recipients`
where `status === 'bounced'`.

### 1. Card shell + header (`rounded-lg bg-gray-900 border border-gray-800 p-3 mt-3`)

Header row (`flex items-center justify-between`): left, `<h2 class="text-xs font-semibold text-gray-400
uppercase tracking-wider">Sent on this service</h2>` (verbatim class from the neighbor); right, the
`✉ New message` link (#2).

### 2. `✉ New message` link (header affordance)

A `<button type="button" class="text-xs font-medium text-indigo-400 hover:text-indigo-300">✉ New message</button>`
that sets `messageComposerOpen = true` — reopening the **existing** `MessageComposer.vue` (Phase 59). This is a
convenience mirror of the action-bar ✉ item, not a second composer. Rendered only when `isMessagingEnabled()` (the
whole card already is). DESIGN § 5b specifies this link.

### 3. History list container

A `<div class="mt-3 divide-y divide-gray-800">` (or `space-y-2`) holding one row (#4) per `messages/{id}`,
**newest first**. When empty → the empty state (#10); while loading → the loading state (#11); on read failure →
the error state (#12).

### 4. Message row (per `messages/{id}`)

A row (`py-2 flex items-start gap-3`, wrapping on mobile). Left cluster: the **type badge** (#5) + a `text-sm
text-gray-200` **primary label** = the message `subject` (fallback to a type-derived label like
"Service link — goes out to everyone assigned" when `subject` is empty, per DESIGN § 5b). Right cluster
(`ml-auto text-right`): the **counts + timestamp** (#6) and, on their own line, the **status pill** (#7) and/or
the **bounce indicator** (#8). When a bounce indicator is present the row is expandable (#8 owns the toggle).

### 5. Type badge (pill idiom)

`inline-flex items-center px-2 py-0.5 rounded-full text-xs font-medium border bg-gray-800 text-gray-300
border-gray-700` (muted, neutral — never accent). Label maps `messages.type`:

| `type` | Badge label |
|--------|-------------|
| `oneoff` | **One-off** |
| `reminder` | **Reminder** |
| `share-link` | **Share link** |
| `lock-notification` / `relock-notification` / any future auto type | **Automatic** |

When a message is `status:'scheduled'` the badge still shows the type; the **Scheduled** *status* pill (#7)
carries the scheduled state, and the timestamp cluster shows "Scheduled for …" (#6). (This matches DESIGN § 5b's
separate `[SCHEDULED]` framing while keeping type and status on distinct badges.)

### 6. Counts + timestamp cluster (`text-xs text-gray-500`)

Recipient count + send time, newest-first ordering already applied by the store. Copy (pluralized 0/1/many):

- **Sent messages:** `{deliveryCounts.sent} sent` (e.g. `14 sent`). When `deliveryCounts.bounced > 0`, this line
  is accompanied by the bounce indicator (#8) — the count line itself stays muted; the red pill does the
  flagging. The "opened" figure from the mockup is **omitted** (out of scope).
- **Scheduled messages** (`status:'scheduled'`): `{recipientCount} recipients` where the count is the resolved
  selector size (or, if not yet resolved, omitted) + a separate **"Scheduled for {date}"** line — using
  `scheduledFor` formatted in the org timezone (Phase 58's timezone; reuse the app's existing date formatter).
- **Send time:** `sentAt` formatted like the composer's service-date subline (e.g. `Aug 9, 4:12 PM`). While
  `sending`/`queued`, show a muted "Sending…" in place of the timestamp.

### 7. Status pill (conditional)

Rendered per the § Color status-pill table. **Omitted for a clean `sent` message** (no pill — the count carries
it), so the list stays quiet and the bounce indicator is the only loud element. `Scheduled` = indigo; `Partial`
= amber; `Failed` = red; `Sending…` = gray + the verbatim spinner glyph
(`inline-block h-3 w-3 border-2 border-gray-500 border-t-transparent rounded-full animate-spin`, sized down from
`PptxImportModal.vue:103`).

### 8. Bounce indicator + expand toggle (R143 — the focal point)

When `deliveryCounts.bounced > 0`, render a **red pill button**:
`<button type="button" :aria-expanded="expanded" class="inline-flex items-center gap-1 px-2 py-0.5 rounded-full
text-xs font-medium border bg-red-900/50 text-red-300 border-red-800 hover:bg-red-900/70">` with label
**"{N} bounced"** + a `▸`/`▾` chevron glyph that rotates on expand. This is the single loud element in the list.
Clicking toggles the per-message bounced-recipients sublist (#9). Only messages with `bounced > 0` are
expandable; all other rows are static (read-only, no chevron).

### 9. Bounced-recipients sublist (expanded, read-only)

Revealed under the row (`v-if="expanded"`, `mt-2 pl-3 border-l-2 border-red-800/50 space-y-2`). Lazily reads
`messages/{id}/recipients` where `status === 'bounced'`. Each entry (`text-xs`):

- **`{recipient.name}`** (`text-gray-200`) + their **`{recipient.email}`** (`text-gray-500`) — the address that
  bounced.
- **Bounce reason** (`text-red-400`): the `bounceReason` string from the webhook (e.g. "address rejected"). When
  `bounceReason` is null/empty, fall back to the copy **"Address rejected"** (DESIGN § 5b: "Micah T. — address
  rejected").
- The **Fix email** affordance (#10 — numbering: see #9→ router-link below).

While this sublist is loading its recipients, show a compact muted "Loading…" line (single async read, no
skeleton needed — matches the app's button-local loading pattern).

### 10. `Fix email` affordance (the R143 "fix the bad address" link)

**Default resolved (autonomy grant): a deep-link to the volunteer's roster edit** — the durable fix, since the
roster `Person.email` is the source of truth (`60-CONTEXT.md`). Rendered as a
`<router-link class="text-xs font-medium text-indigo-400 hover:text-indigo-300" :to="{ name: 'volunteers',
query: { edit: recipient.personId } }" title="Update this volunteer's email in the roster">Fix email →</router-link>`.

Contract note for the executor: the roster view is `RosterView.vue` at route **`/volunteers`** (name
`volunteers`), which today opens a person's edit form via local `editingPersonId` state and does **not** yet read
a route query. Honoring `?edit={personId}` requires a **small additive enhancement to `RosterView.vue`** (on
mount / on query change, set `editingPersonId` to `query.edit` and open the edit form). This is the least-surprising
default (it lands the planner *on the exact broken record*); the fallback, if that enhancement is descoped, is a
plain link to `/volunteers` with no query (the planner finds the person manually). Prefer the deep-link. Either
way this is the panel's ONLY navigation and it triggers **no write from the panel itself** — the fix happens on
the roster view.

### 11. Empty state ("Nothing sent yet")

When the org has messaging on but this service has zero `messages/{id}` docs: a centered muted block inside the
card (`py-6 text-center`): a `text-sm text-gray-300` heading **"Nothing sent yet"** + a `text-xs text-gray-500
mt-1` body **"Messages you send for this service will appear here."** The `✉ New message` header link remains the
next step. No illustration (matches the app's text-only empty states).

### 12. Loading state

While the `messages` subscription is resolving its first snapshot: the verbatim spinner
(`h-8 w-8 border-2 border-indigo-500 border-t-transparent rounded-full animate-spin`, from
`PptxImportModal.vue:103`) centered in a `py-6` block, with an `aria-live="polite"` `text-xs text-gray-500`
"Loading message history…". Subsequent live updates (a new send, a bounce landing) patch in without a full
re-spinner — the list is reactive.

### 13. Error state (load failure)

If the `messages` read fails (permission/network): a `text-red-400 text-sm py-4` line
**"Couldn't load message history. Please refresh."** — mirroring the neighboring panel's
`text-red-400 text-sm` error line (`ServiceEditorView.vue:868`) and Phase 59's send-failure tone. No retry
button (a page refresh re-subscribes; matches the app's other read surfaces).

| Trigger | Behavior |
|---------|----------|
| Open the Service Order tab (messaging on, editor) | Subscribe to `services/{id}/messages` (newest-first). Show loading (#12) → populated list (#4 rows) / empty (#11) / error (#13). |
| A new message is queued (via the composer) | The reactive subscription patches the new row in at the top — no manual refresh. |
| A bounce webhook lands (server writes `status='bounced'` + `deliveryCounts.bounced`) | The reactive subscription flips the affected row's counts and renders the red bounce indicator (#8) live. |
| Click the bounce indicator (`N bounced`) | Toggle `aria-expanded`; lazily read that message's bounced `recipients` and reveal the sublist (#9). Re-click collapses. |

| Message still `scheduled` | Row shows the **Scheduled** pill + "Scheduled for {date}"; no counts-sent line until it sends. |
| Message `partial` / `failed` | Row shows the amber **Partial** / red **Failed** pill; `{sent} sent` reflects the partial tally; a `failed` message with `bounced>0` shows the bounce indicator too. |

**Read-only guarantee:** the panel issues no Firestore writes. Every mutation a user reaches from it (fixing an
email) happens on `RosterView.vue`. This keeps the Phase 58 read rules (`isOrgMember`) sufficient and adds no new
client-facing rule (`60-CONTEXT.md` § Firestore rules).

## Accessibility

- **List semantics:** the history list is a `role="list"`; each message row `role="listitem"`. The card title
  `<h2>` labels the region (`aria-labelledby` off the title id).
- **Expand/collapse:** the bounce indicator is a real `<button>` with `aria-expanded` reflecting the sublist
  state and `aria-controls` pointing at the sublist region; the chevron is decorative (`aria-hidden`). Only
  bounced rows are interactive — non-bounced rows are static text (no misleading affordance).
- **Live region:** the loading line and the list container are `aria-live="polite"` so a screen-reader user hears
  "Loading message history…" and, when a bounce lands live, the updated row — the bounce is never carried by
  color alone (the red pill has the visible text "N bounced").
- **Color independence:** every status is carried by a **text label** in its pill (Scheduled/Partial/Failed/
  N bounced), never by hue alone — WCAG 1.4.1. The bounce reason is literal red-text *plus* the word "bounced" on
  the pill.
- **Keyboard:** the `✉ New message` button, each bounce toggle, and each `Fix email` link are all natively
  focusable and in DOM order (row → toggle → sublist links). `Fix email` is a `router-link` (real anchor,
  Enter-activates).
- **Contrast:** all text meets the app's dark-theme contrast (`text-gray-200/300` on `gray-900`); muted meta is
  `text-gray-500` but always paired with a labelled badge, never the sole carrier of a blocking condition. The
