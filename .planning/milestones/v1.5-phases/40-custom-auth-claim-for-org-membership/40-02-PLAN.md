**`buildOrgMembershipClaim(orgId, role)`** — returns the claim object in the exact locked shape from
D-01/D-02/D-03: two readable top-level keys, `{ orgId, role }`, and nothing else. Normalise a legacy
`role` of `'admin'` to `'editor'` so the claim matches what `loadOrgContext` already shows the user

backfill and any future consumer reference the key names from one place rather than string literals.

**`decideMembershipClaim(params)`** — the single shared decision function (DISC-02), taking
`{ uid, orgId, role }` where `role` is `undefined` for a delete. It returns a discriminated union:
`{ action: 'set', claims }`, `{ action: 'clear' }`, or `{ action: 'skip', reason }` with reason
`'not-primary-org' | 'no-user-doc' | 'already-current'`. Logic, in order:

1. Read `users/{uid}` via `getFirestore()`. If the document does not exist, or its `orgIds` is absent or
   empty, return skip/no-user-doc. **Never** fall back to trusting the event's `orgId` param — this is
   `parsePptxHandler`'s "independently re-verify, never trust the caller-declared value" rule, and it is
   the control for threat T-40-05.
2. If `orgIds[0]` is not equal to the passed `orgId`, return skip/not-primary-org. This holds for
   deletes too: removing a non-primary membership must not clear the primary claim. `orgIds` is a
   `string[]` and `noUncheckedIndexedAccess` is on in the app tsconfig — narrow the index access
   explicitly rather than asserting non-null.
3. If `role` is undefined (delete of the primary membership) return `{ action: 'clear' }`. Comment that
   this deliberately clears rather than recomputing a new primary: `TeamView.vue`'s client-side
   `deleteDoc` does not update `users/{uid}.orgIds`, so `orgIds[0]` is itself stale at this moment and
   recomputing from it would produce a claim for an org the user just left.
4. Otherwise build the claim, read the user's existing claims via `getAuth().getUser(uid)`, and if they
   already match on both keys return skip/already-current. This makes the trigger idempotent and gives
   the backfill (plan 40-04) its D-11 skip-if-already-matching behaviour from the same code.

Add a prominent block comment on this function recording the **known limitation from D-01/D-04**: the

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Firestore members document | An org editor can write `role` on a members document via `TeamView.vue`; that value is untrusted input to the trigger. |
| trigger → Firebase Auth custom claims | Only the Admin SDK crosses this boundary; the claim it writes becomes an authorization signal in `storage.rules`. |
| event params → claim decision | `event.params.orgId` is supplied by the trigger path and must not be the sole authority for which org the claim names. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-40-05 | Elevation of Privilege | `decideMembershipClaim` primary-org resolution | high | mitigate | The handler independently re-derives the primary org from `users/{uid}.orgIds[0]` in Firestore and skips any write whose `orgId` does not match, rather than trusting `event.params.orgId`. Mirrors `parsePptxHandler`'s existing never-trust-the-caller pattern. Proven by the non-primary-org skip tests (both write and delete). |
| T-40-04 | Elevation of Privilege (stale grant) | claim lifetime after membership removal | medium | accept | Deleting a primary membership calls `setCustomUserClaims(uid, null)` immediately, but an ID token already issued keeps its claim until it expires — Firebase's ID token lifetime is a fixed 1 hour and cannot be shortened. Today removal takes effect at once via the Firestore arm; after the owner's deploy 2 there is a bounded ≤1h window. Accepted and **must be recorded in `functions/DEPLOY-ORG-CLAIMS.md`** (plan 40-04), with `revokeRefreshTokens(uid)` named as the escalation path if an immediate lockout is ever required. |
| T-40-03 | Spoofing | claim authorship | high | mitigate | Custom claims are writable only through the Admin SDK inside a trusted Cloud Functions runtime. The client SDK has no claim-writing API, so a user cannot mint `{ orgId, role }` for an org they do not belong to. The trigger is the only code path in this repository that calls `setCustomUserClaims` besides the owner-run backfill. |
| T-40-08 | Denial of Service | trigger retry storm | low | mitigate | The handler catches its own errors and resolves with a failure outcome rather than throwing, so a transient Auth API failure cannot turn into an unbounded Cloud Functions retry loop against `setCustomUserClaims`. Logged via the established `console.error('[module] operation:', err)` convention. |
| T-40-SC | Tampering | npm/pip/cargo installs | high | accept | **No package-manager install occurs in this plan or anywhere in phase 40.** `firebase-admin@^13.10.0` and `firebase-functions@^7.2.5` are already installed and were verified against their own type definitions during research; `40-RESEARCH.md` § Package Legitimacy Audit records this as not-applicable. An acceptance criterion asserts `git diff functions/package.json functions/package-lock.json` is empty. |
</threat_model>
