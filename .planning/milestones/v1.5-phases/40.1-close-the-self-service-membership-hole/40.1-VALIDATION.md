# Phase 40.1 — Validation Strategy

> Derived from `40.1-RESEARCH.md` § Validation Architecture.

---

## ★ The discipline that makes this phase real

**The DENY test must be confirmed to FAIL against the CURRENT, unfixed rule — before the fix lands.**

A deny-test written after the fix and never run against the vulnerable rule proves nothing; it might
pass for an unrelated reason. Phase 40's executor did exactly this correctly, mutating the rule to
`&&` to prove its guard test could fail. Do the same here in reverse: run the new deny-test against
today's `allow create: if isSignedIn() && request.auth.uid == uid` and watch it fail.

**The inverse risk of Phase 40 is live here.** Phase 40's danger was a rule that denies everyone,
visible as all-allows-failing. This phase's danger is a rule that **allows** everyone — which looks
green if you only test the happy path.

## Per-Criterion Verification Map

Every case here is **behaviourally testable** — `firestore.rules` uses same-service
`exists()`/`get()`, which firebase-js-sdk#6803 does not affect. **No structural source assertions as
a substitute.**

| Criterion | Behavior | Test Type | Must first fail against the unfixed rule? |
|---|---|---|---|
| 1 | **DENY** — signed-in user with no invite self-creates membership in an arbitrary org | Firestore-emulator DENY | ✅ **YES — mandatory.** This is the vulnerability. If it passes against today's rule, the test is wrong. |
| 2 | **ALLOW** — user accepting a genuine outstanding invite | Firestore-emulator ALLOW | No — should pass both before and after |
| 3 | **ALLOW** — founder creating their own first membership in a brand-new org | Firestore-emulator ALLOW | No — should pass both before and after. **This is the trap:** a fix considering only the invite path breaks it, and nothing in the existing suite would catch that. |
| 4 | **DENY** — user with a genuine invite submits an escalated role | Firestore-emulator DENY | ✅ **YES** — today the body is unconstrained, so this must fail before the fix |
| 5 | `firestore.rules` modified, **NOT deployed** | Inspection | `git log` shows no deploy; the change is handed to the owner |

## The `get()` vs `getAfter()` question — the emulator is the arbiter

Research is **MEDIUM confidence** on one point and said so plainly: whether `get()` truly ignores
earlier-same-batch writes while `getAfter()` sees post-batch state. Official docs confirm
`getAfter()`'s purpose but not the exact ordering direction verbatim.

**Do not resolve this by reading more documentation. Resolve it by running the criterion-3 ALLOW
test.** Expected shape:

- Org creation branch → **`getAfter()`** on the org doc (the org doc is written in the same batch)
- Invite branch → plain **`get()`/`exists()`** (the invite predates the batch and is deleted within it)

If the criterion-3 test fails with that arrangement, swap which branch uses which and re-run. The
research document records this contingency explicitly; treat a swap as an expected outcome, not a
plan defect.

## Out of Scope — recorded, not fixed

Research found two further over-permissive rules while tracing. **Do not fix them in this phase** —
record only:

1. `organizations/{orgId}`'s unrestricted `isOrgEditor` write lets an editor rewrite `createdBy`.
   Grants no new capability today (editors already have full member-write access), but it weakens
   the org-creation branch's predicate if that branch relies on `createdBy`.
2. `inviteLookup/{email}`'s `allow create: if isSignedIn()` — a structurally distinct self-invite
   vector. It does **not** defeat this phase's fix, because the fix reads the org-scoped
   `invites/{email}` document, not `inviteLookup`.

Both belong to a future phase.
