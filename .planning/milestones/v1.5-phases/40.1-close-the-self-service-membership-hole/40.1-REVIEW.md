# Phase 40.1: Code Review Report

**Reviewed:** 2026-08-07T02:10:00Z
**Depth:** standard (security-critical single-rule change, reviewed with elevated scrutiny)
**Files Reviewed:** 2 (`firestore.rules`, `src/rules.test.ts`)
**Status:** findings

## Summary

The stated goal of R104 — stop an arbitrary signed-in user from self-joining an arbitrary org with a
client-chosen role — is achieved. Verified by re-reading `organizations/{orgId}` (its `allow create`
requires `createdBy == request.auth.uid` and only fires when the org doc does not already exist, so
an attacker cannot forge `createdBy` on a pre-existing *victim* org they don't already administer),
by re-running `src/rules.test.ts` against the live emulator (94/94 green, including all four new
R104 tests), and by tracing both legitimate call sites in `ensureUserDocument` (`src/stores/auth.ts:264-350`)
against the new predicate.

However, the org-creation branch's `getAfter()` check is broader than intended: it authorizes on
"does the org doc's `createdBy` field currently equal my uid," not "was this org just created, by me,
in this exact operation." Those are different claims, and the gap between them is a real, provable
authorization bypass — see CR-01. The rule's own inline comment (`firestore.rules:46-52`) asserts the
narrower claim is true; it isn't, and `40.1-RESEARCH.md`'s "Why an attacker cannot forge this branch"
paragraph makes the same unproven leap. This is exactly the kind of gap the phase's own Pitfall-4
discipline ("run the DENY case against the real thing, don't trust the doc") was meant to catch, and
it wasn't run for this specific case because the case itself wasn't in CONTEXT.md's four mandated
tests.

The four new tests (`src/rules.test.ts:147-249`) are non-vacuous: Tests B and C use a real
`writeBatch` mirroring `ensureUserDocument`'s exact operation order (not `seedDoc`, which bypasses
rules), and each of the four tests would fail against a rule missing the specific mechanism it's
proving (no-invite denial, `getAfter()` vs `get()`, role-forcing, role-matching). Re-running the
suite against the emulator confirms all pass. The only real gap is that the four mandated cases don't
include the scenario CR-01 depends on, so the suite is green while CR-01 remains open.

## Critical Issues

### CR-01: Org-creation branch grants a permanent "founder" backdoor that survives explicit member removal

**File:** `firestore.rules:53-54` (predicate), `firestore.rules:45-69` (full `allow create` block)

**Issue:**

```javascript
(getAfter(/databases/$(database)/documents/organizations/$(orgId)).data.createdBy == request.auth.uid
  && request.resource.data.role == 'editor')
```

`getAfter()` on a path that the current write operation does *not* itself touch simply reflects the
document's **current, already-committed state** — it is not scoped to "within this same batch,"
contrary to the rule's own comment ("the org doc is created in the SAME atomic batch as this write")
and `40.1-RESEARCH.md`'s claim that this branch can only be true "if the attacker is, in this same
request, legitimately creating that exact org." Neither of those is enforced by the code as written;
they describe the *intended* use, not what the predicate actually checks.

Consequence: `organizations/{orgId}.createdBy` is set once at org creation and never cleared. Any
user who is (or ever was) that value can re-create their own `members/{uid}` document with
`role: 'editor'` **at any later time**, via a single ordinary `setDoc` — no batch, no invite, no
relationship to the org's *current* membership required. Concretely:

1. A church's founder creates the org (legitimate, `createdBy = founderUid`).
2. A second editor later removes the founder via the existing "Remove member" feature
   (`src/views/TeamView.vue:345-370`, `deleteDoc(...members/{uid})`) — e.g. the founder leaves the
   church, is fired, or their account is suspected compromised. The removal succeeds; the founder has
   no membership doc and, per `isOrgMember`/`isOrgEditor`, no access.
3. At any point afterward, the removed founder calls
   `setDoc(doc(db, 'organizations', orgId, 'members', founderUid), { role: 'editor', ... })` directly.
   `getAfter()` on the (untouched) org doc still reports `createdBy == founderUid` — because that
   field was never modified by removal — so the predicate is satisfied and the write is **allowed**.
   The founder silently regains full editor access, undoing the removal.

This directly contradicts R104's own wording — "the creator of a **brand-new** organization" — and
the requirement's stated purpose (member removal should be effective). It is also **compounded** by
the recorded-but-out-of-scope finding that `organizations/{orgId}`'s `allow write: if isOrgEditor(orgId)`
is field-unrestricted (`firestore.rules:31`, `40.1-RESEARCH.md` "Other Over-Permissive Findings"): any
*current* editor can rewrite `createdBy` to an **arbitrary uid** (not just their own), planting a
backdoor for a third party who has never been a member of the org at all, and who can claim it even
after the planting editor is themselves removed. Per this review's scope instructions, that
out-of-scope finding is flagged here specifically because it widens CR-01's blast radius from "a
former founder can walk back in" to "any editor can grant a durable, invisible standing invitation to
anyone, redeemable indefinitely" — it defeats this fix's stated goal (no self-service, uninvited
membership).

None of the four new tests exercise this path — all three ALLOW/DENY-adjacent org-creation tests seed
no pre-existing org for the target uid (Test C is explicitly "nothing seeded"), so the suite is green
without ever probing "org already exists, `createdBy` matches, but the org was not created in this
operation."

**Fix:** Require that the org did not exist *before* this operation — i.e. that it is genuinely being
created in the same batch, not merely that its `createdBy` field happens to match. `exists()` (unlike
`getAfter()`) reflects pre-batch-start state, so combining both closes the gap while preserving both
legitimate flows unchanged:

```javascript
(!exists(/databases/$(database)/documents/organizations/$(orgId))
  && getAfter(/databases/$(database)/documents/organizations/$(orgId)).data.createdBy == request.auth.uid
  && request.resource.data.role == 'editor')
```

Add a regression test proving the specific bypass this closes:

```typescript
it('DENIES a removed former founder from recreating their own editor membership', async () => {
  // Org exists, createdBy == the very user attempting to (re)join. No member doc exists for
  // them (simulating TeamView's "Remove member" having already run). This must be denied —
  // "creator of a brand-new org" (R104) is not the same claim as "createdBy currently == me."
  await seedDoc('organizations/orgA', { name: "Founder's Church", createdBy: 'founder' })
  const context = testEnv.authenticatedContext('founder', { email: 'founder@example.com' })
  const db = context.firestore()
  await assertFails(
    setDoc(doc(db, 'organizations', 'orgA', 'members', 'founder'), {
      role: 'editor',
      joinedAt: new Date(),
    }),
  )
})
```

Run this test against the **current** (unfixed) predicate first to confirm it fails (proving the
bypass is real, per this phase's own Pitfall-4 discipline), then apply the `!exists()` fix and confirm
it passes alongside the existing four.

**Resolution: FIXED — commit `bda074d`.**

Applied the recommended `!exists()` guard exactly as suggested: `firestore.rules`'s org-creation
branch now reads `!exists(org) && getAfter(org).data.createdBy == request.auth.uid && ...`. Added the
regression test verbatim (adapted only in placement — appended inside the existing `describe('Members
create — R104 self-service membership hole')` block rather than a new block, since it exercises the
same predicate as the other four R104 tests).

Sequencing followed Pitfall-4 discipline exactly: ran the new test alone against the **unmodified**
rule first — `assertFails(...)` itself threw with "Expected request to fail, but it succeeded," proving
the write the test describes actually succeeded against the vulnerable rule. Only then applied the
`!exists()` fix and re-ran the full suite: **108/108 passing** (was 107/107; net +1 new test, zero
regressions). Both legitimate flows (Test B invite-acceptance, Test C org-creation via real
`writeBatch`) still pass unchanged, confirming the fix does not break onboarding or invite acceptance.

Also verified the compounding concern the finding raised: the recorded-but-out-of-scope
`organizations/{orgId}` unrestricted-editor-write finding no longer defeats R104 after this fix. An
editor rewriting `createdBy` on an **existing** org cannot satisfy the new predicate, because
`!exists(org)` is false for any org that already exists — the `!exists()` guard closes that
compounding path along with the primary one, with no change to the `organizations/{orgId}` rule
itself (left untouched, per scope).

## Warnings

### WR-01: Rule's own security-invariant comment is unproven and, per CR-01, false as written

**File:** `firestore.rules:46-52`
**Issue:** The comment states the org-creation branch is checked "in the SAME atomic batch as this
write," presenting the same-batch relationship as an enforced invariant. As shown in CR-01, nothing in
the predicate enforces that; the comment describes the intended/legitimate use, not what the code
actually restricts. A future maintainer reading only this comment (as `40.1-RESEARCH.md`'s "Why an
attacker cannot forge this branch" section did) will reasonably conclude the predicate is
same-batch-scoped when it is not.
**Fix:** Once CR-01's `!exists()` guard is added, update the comment to state the actual mechanism:
"`!exists()` proves the org did not exist before this operation; `getAfter()` proves it does, with the
right `createdBy`, immediately after — together they prove genuine same-batch creation, not merely a
`createdBy` field match."

**Resolution: FIXED — commit `bda074d`** (folded into CR-01's commit, not a separate cosmetic change,
per the fix instructions). The Flow 1 comment block in `firestore.rules:46-58` no longer asserts an
unenforced same-batch invariant; it now states the actual mechanism — that `!exists()` proves pre-batch
absence and `getAfter()` proves the post-batch value, and that only their combination proves genuine
same-batch creation. A future maintainer reading only the comment will no longer reach the same wrong
conclusion `40.1-RESEARCH.md`'s "Why an attacker cannot forge this branch" section reached.

## Info

### IN-01: Invite-branch email normalization relies on an unverified assumption about token claims

**File:** `firestore.rules:66-68`
**Issue:** The invite match compares `request.auth.token.email.lower()` against the invite doc ID,
which the client normalizes as `email.trim().toLowerCase()` (`TeamView.vue`). `40.1-RESEARCH.md`
itself flags this as Assumption A2 (MEDIUM confidence, not independently verified this session): that
Firebase Auth's `token.email` is always whitespace-free and case-normalizes identically to JS
`.toLowerCase()` for every sign-in method this app might ever add. Today's two providers
(Google, email/password) make this safe in practice, and the guard fails closed (denies) rather than
erroring into an allow if the assumption ever breaks — so this is not a live vulnerability, just an
undertested assumption worth a comment noting the dependency if a new auth provider is ever added.
**Fix:** No action required now; if a future phase adds a sign-in method with looser email
normalization (e.g. SAML/OIDC providers that can preserve casing or trailing whitespace), add a test
using `authenticatedContext` with a deliberately-off-normalized email to confirm the fail-closed
behavior still holds.

**Resolution: NO ACTION TAKEN — matches the finding's own recommendation.** This is explicitly not a
live vulnerability (fails closed, not open) and the finding's own Fix section says no action is
required until a new sign-in method is added. Nothing to fix today; left as a documented dependency
for a future phase that touches auth providers.
