### CR-01 (Critical, code review) — independently confirmed fixed

Code review (`40.1-REVIEW.md`) found that the org-creation branch's original `getAfter()`-only
predicate proved only "createdBy CURRENTLY equals my uid," not "this org was just created, by me, in
this batch" — meaning any past founder, even one explicitly removed from the org, could re-grant
themselves `role: 'editor'` at any later time with a bare `setDoc`.

Verified independently by reading the current `firestore.rules` (lines 45-76): the org-creation
branch now reads `!exists(org) && getAfter(org).data.createdBy == request.auth.uid && ... role ==
'editor'`. `!exists()` reflects state as of the *start* of the operation and therefore cannot be
satisfied for an org that already existed before the write — this closes the exact gap CR-01
identified. A regression test (`src/rules.test.ts:257-267`, "DENIES a removed former founder from
recreating their own editor membership") seeds an existing org with `createdBy` already equal to the
attacking uid and asserts the write fails; independently re-run, it passes as part of the 108/108
suite. `40.1-REVIEW-FIX.md` records this test was first run against the pre-`!exists()` rule and
observed to genuinely fail, matching the phase's own Pitfall-4 discipline.

Also confirmed the review's claim that CR-01's fix retroactively closes the compounding out-of-scope
finding: an editor rewriting `createdBy` on an org they already administer (the recorded,
still-unfixed `organizations/{orgId}` unrestricted-write finding) cannot satisfy `!exists()` for that
already-existing org, so it can no longer be used to plant a durable backdoor via this predicate.
