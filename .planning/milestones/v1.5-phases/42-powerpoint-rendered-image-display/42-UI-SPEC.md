# Phase 42 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note (repeated from the orchestrator prompt, load-bearing for every section below):** this is not a
new screen. It adds exactly three visual states — **ready** (rendered PNG), **pending**, **failed** — to two
existing surfaces: the slide grid (`SlideCard.vue` inside `SlideGrid.vue`) and the presenter
(`PresentationViewer.vue`). A fourth condition — **no `renderImportId`** — is explicitly *not* a new state:
it is the existing, untouched parsed-text path and must render byte-identical to today.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — custom Vue 3 `<script setup>` SFCs, no headless-UI dependency |
| Icon library | none — inline hand-drawn SVG paths, matching every existing icon in `PresentationViewer.vue` (spinner, chevrons, exit X) and `SlideCard.vue` (drag-handle dots) |
| Font | unset / browser default sans stack — global slide typography is Phase 46's scope (R093/R094), explicitly out of scope here; this phase inherits whatever renders today |

**Why `Tool: none` rather than initializing shadcn:** `components.json` does not exist anywhere in the repo
(confirmed by directory scan). This is a mature Vue 3 + Tailwind v4 codebase with an established, working,
hand-rolled component convention documented in `.planning/codebase/CONVENTIONS.md` ("Tailwind CSS utility
classes only, no scoped CSS; static class maps to prevent dynamic class purging"). shadcn is a React-first
tool; bolting it on now, for a phase that adds three state branches to two existing components, would be an
unrelated wholesale styling-system change with no requirement asking for it. Under the standing autonomy
grant this is the defensible default — recorded as a decision, not asked as a question.

**Design source check (per the phase prompt's explicit instruction to say so, not invent provenance):**
`docs/design/slides-tab.dc.html` was grepped for `imported`/`pptx`/`deck`/`pending`/`failed`/`render`. It
covers the plan rail's "SLIDE DECK" badge and the drop-target copy ("Drop PPTX, images, video") — it does
**not** cover any pending/failed/rendered-image state for an imported deck's own slide tiles. This UI-SPEC
is original design work for those three states, not a transcription of an existing wireframe.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 11px | 400 (regular) | 1.2, uppercase, tracking-wide |
| Body | 13px | 400 (regular) | 1.5 (Tailwind `leading-normal`) |
| Heading | 36px (`text-4xl`) | 600 (semibold) | 1.2 |
| Display | not used this phase | — | — |

**Provenance, not invention:**
- **Label** (11px/400) reproduces `SlideCard.vue`'s existing `slide-card-content-label` class verbatim
  (`text-[10px] uppercase tracking-wide` is 10px there; this phase's grid-state labels use the sibling
  `slide-card-kind-badge` size of `text-[11px]` — 11px is chosen because these new labels sit at the same
  visual weight as the kind badge, not the smaller corner eyebrow).
- **Body** (13px/400/1.5) reproduces `SlideCard.vue`'s `slide-card-body` class verbatim
  (`text-[13px] leading-normal`).
- **Heading** (36px/600/1.2) reproduces `PresentationViewer.vue`'s existing `isLoadingState`/`isEmptyState`
  headings verbatim (`text-4xl font-semibold` / `text-4xl font-semibold text-gray-400`) — the presenter's
  two new per-slide states reuse this exact size so a congregation never perceives one state as visually
  "louder" or more alarming than another already-shipped state.
- **Display** is not used: the presenter's pending/failed states are a single centered heading plus one
  optional smaller caption line (using the Body size), not a display-scale moment — declared "not used"
  rather than inventing an unused fifth size.

**Weight budget (2 max, per contract):** 400 and 600 only, for the elements this phase adds. Pre-existing
chrome this phase does not touch (e.g. the kind-badge chip's `font-medium`/500) is inherited from Phase 25/33
and outside this budget — noted so the checker does not flag it as a violation introduced here.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-gray-900` (card) / `bg-black` (presenter root) | Existing surface colors, unchanged |
| Secondary (30%) | `bg-gray-950/40` (grid preview box), `border-gray-800` | Existing card/tile chrome, unchanged |
| Accent (10%) | indigo (`indigo-400`/`indigo-300`) | **Pending** state only — spinner and "Rendering…" label, on both the grid tile and the presenter, reusing the exact indigo spinner already shipped in `PresentationViewer.vue`'s `isLoadingState` and `SlideGrid.vue`'s `mediaUploadProgress` text |
| Destructive (grid) | `red-400` icon / `red-300` text / `bg-red-950/20` tile tint | **Failed** state, grid only — reuses the exact red family already shipped in `PptxImportModal.vue`'s error banner (`text-red-400` icon, `text-red-300` text) and `SlideGrid.vue`'s `mediaUploadError`/`reorderError` (`text-red-400`) |
| Failed (presenter) | `amber-300` icon, `gray-100` heading, `gray-400` caption — **not red** | See discretionary decision below |

Accent reserved for: the pending-state spinner and its label text, on both surfaces. Nowhere else in this
phase's new elements.

### Discretionary decision — presenter failed state uses amber, not red

**This is a deliberate divergence from the grid's red, recorded per the autonomous-mode instruction to
state defaults explicitly with rationale.** 42-CONTEXT.md is explicit: *"the presenter is seen by a
congregation, not just the operator, so its failure state must be dignified on a projection screen rather
than looking like a crash."* A full centered `red-300`/`red-400` treatment on the one thing a congregation
is looking at reads as an error page, not a dignified pause. `PresentationViewer.vue` already has exactly
this soft-caution vocabulary shipped and working: `videoMutedPlaying`'s "Playing muted — tap to unmute" chip
uses `bg-amber-900/40 text-amber-300` for a "something's not quite right, no cause for alarm" signal, while
the component's actual hard problems (a broken media URL, `onMediaError`) render as a barely-there
`text-gray-500` caption, not red. The failed-render state follows that established amber-for-soft-signal
precedent: a small amber icon plus a same-size, same-weight heading as the pending state (never escalating
visual loudness slide-to-slide), with the mapped failure sentence as a muted `text-gray-400` caption below.
Red stays reserved for the grid, where the audience is the operator and "this needs your attention" is the
correct signal.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | None — this phase adds no call-to-action. Retry/re-render UI is explicitly deferred (42-CONTEXT.md § Deferred Ideas); the failed state is informational only |
| Empty state heading | Not applicable — an `ImportedDeck` always has ≥1 parsed slide (import validation already guarantees this); no zero-slide empty state exists for this phase to design |
| Empty state body | Not applicable, same reason |
| Error state (grid) | "Render failed" (label, 11px/400) + the mapped failure sentence below it (13px/400, see table below) |
| Error state (presenter) | "This slide couldn't be rendered." (heading, 36px/600) + the mapped failure sentence below it (13px/400, `text-gray-400`) |
| Destructive confirmation | Not applicable — this phase performs no destructive action |
| **Grid — pending** | "Rendering…" (label, 11px/400, `text-gray-300`) |
| **Presenter — pending** | "This slide is still rendering." (heading, 36px/600, `text-gray-100`) |

### `failureReason` → human sentence (mandatory mapping — never render the raw slug)

Per the codebase pointers: `functions/src/index.ts`'s `PptxRenderDoc.failureReason` is a short machine-ish
string (`missing-render-doc`, `missing-storage-path`, etc.) — **not** user-facing prose. Displaying it
verbatim would put a slug like `missing-render-doc` in front of an operator or, worse, a congregation. A
static lookup table (following the exact precedent of `KIND_BADGE_CLASSES` in `slideDisplay.ts` — a
fully-spelled-out `Record`, never string-templated) maps each known reason to a short sentence, with a
generic fallback for any value the client doesn't recognize (including reasons added to the backend after
this phase ships):

| `failureReason` value | Displayed sentence |
|---|---|
| `missing-render-doc` | "This deck's render record is missing." |
| `missing-storage-path` | "The rendered file couldn't be located." |
| `undefined` / unrecognized / any future value | "This slide couldn't be rendered." |

This table is copywriting guidance for the plan/executor to implement as a `Record<string, string>` with a
default-arm fallback (the same shape as `KIND_BADGE_CLASSES`'s `default` backstop in `slideActionMenuItems`)
— it is not exhaustive of every string the backend might ever write, by design; the fallback exists precisely
so an unmapped value never surfaces raw text.

## Phase-Specific Component Contracts

The six cells this phase must specify. Each row states the visual treatment, the state trigger, and the
testid convention (new testids only where no existing one already covers the case).

### Grid tile (`SlideCard.vue`, inside its existing `h-[140px] overflow-hidden rounded-md bg-gray-950/40` preview box)

| State | Trigger | Visual treatment | testid |
|---|---|---|---|
| **Ready** | `pptxRenders/{importId}.status === 'ready'` and this tile's slide has a resolved rendered-image URL | The rendered PNG fills the box via `<img class="h-full w-full object-contain" />` — **byte-identical treatment to the existing `ImageSlide` path** (`isImage` branch, line 36-42 of `SlideCard.vue` today). Parsed text is never drawn once a render is ready. The existing top-left content-label and top-right slide-number overlay badges stay layered on top, unchanged | Reuse `slide-card-image` (no new testid — visually and structurally the same element the `ImageSlide` branch already renders) |
| **Pending** | Deck has a `renderImportId` and `pptxRenders/{importId}.status === 'pending'` (or the doc doesn't exist yet — see Edge below) | Box background stays `bg-gray-950/40` (no tint). Centered: a 16px indigo-400 `animate-spin` spinner (the exact SVG already shipped in `PresentationViewer.vue`'s `isLoadingState`, scaled down) with 8px gap above the "Rendering…" label (11px/400, `text-gray-300`). Existing content-label/number overlay badges stay visible on top, unaffected | `slide-card-render-pending` (new) |
| **Failed** | `pptxRenders/{importId}.status === 'failed'` | Box background tints `bg-red-950/20 border border-red-900/40` (contained to this tile only — never bleeds into the card's outer border or the grid background). Centered: a small `red-400` warning icon, 8px gap, "Render failed" (11px/400, `text-red-300`), then the mapped failure sentence (13px/400, `text-red-400/80`-equivalent muted red) below. Existing overlay badges stay visible | `slide-card-render-failed` (new) |

**Edge — no `renderImportId`:** zero new code path. The tile renders through the existing parsed-`TextSlide`
(body-text) or `ImageSlide` (already-uploaded image) branches exactly as today. This case must never enter
the pending or failed branches above — there is no render to be pending or failed *about*.

**Edge — render doc doesn't exist yet:** the render trigger writes the `pptxRenders` doc asynchronously
after the parse call returns (per `functions/src/index.ts`'s documented "queue-write is best-effort,
non-blocking" comment). A deck can therefore have a `renderImportId` for a brief window before the doc
exists. Treat "doc absent" identically to `status: 'pending'` — never as failed, and never by falling through
to the parsed-text path (that would be the exact "misleadingly-stale" outcome R080 forbids).

### Presenter (`PresentationViewer.vue`, inside its existing black full-bleed canvas, `data-testid="presentation-slide"`)

| State | Trigger | Visual treatment | testid |
|---|---|---|---|
| **Ready** | Same condition as the grid's ready row | `<img class="max-h-[80vh] max-w-full object-contain" />` — byte-identical treatment to the existing `image` slide-kind branch (line ~182-187 today) | Reuse `presentation-image` (no new testid) |
| **Pending** | Same condition as the grid's pending row, evaluated for whichever slide is currently on screen | Centered content block, same layout family as the existing `isLoadingState`/`isEmptyState` blocks (`flex flex-col items-center gap-4`): the same 40px indigo-400 spinner already used for `isLoadingState`, then "This slide is still rendering." (36px/600, `text-gray-100`) | `presentation-render-pending` (new) |
| **Failed** | Same condition as the grid's failed row, evaluated for whichever slide is currently on screen | Centered content block, **same size and layout as Pending** (never visually louder): a small `amber-300` icon (not red — see Discretionary Decision above), 8px gap, "This slide couldn't be rendered." (36px/600, `text-gray-100`), 16px gap, the mapped failure sentence as a caption (13px/400, `text-gray-400`) | `presentation-render-failed` (new) |

**Non-negotiable, quoted from 42-CONTEXT.md:** *"the presenter must never silently show nothing, and must
never skip a pending/failed slide — skipping changes the deck's length mid-service."* Concretely: the
pending/failed slide **occupies its normal position** in `props.slides` and in `progressLabel`'s `n / m`
count, navigable with prev/next exactly like any other slide. It is never filtered out of the assembled
slideshow array, and the "N / M" progress pill counts it like any other slide.

**Bottom chrome (exit button, prev/next, progress pill) stays exactly as-is** on a pending/failed slide —
this phase does not touch `hasSlides`, `atFirst`, `atLast`, or the auto-hide chrome timer. An operator can
navigate past a pending/failed slide exactly as they can any other slide.

### Aspect ratio — one rule for both surfaces

PowerPoint decks are typically 16:9 or 4:3, and a service's slide grid can mix decks (or even mix
16:9 and 4:3 slides if a source deck itself mixed them). **`object-contain`, never `object-cover`, on both
surfaces, for the ready state:**
- **Grid:** the tile keeps its existing **fixed height** (`h-[140px]`) with **fluid width** (CSS grid
  `auto-fill, minmax(200px,1fr)`, unchanged). A 4:3 render is simply narrower within its own cell than a
  16:9 render — no letterboxing bars are drawn (the box background `bg-gray-950/40` peeks through instead,
  which is the exact behavior `ImageSlide` already produces today for a non-16:9 uploaded image).
- **Presenter:** `max-h-[80vh] max-w-full object-contain`, unchanged from the existing `ImageSlide`
  treatment — a 4:3 render pillarboxes against the black canvas background rather than cropping or
  stretching.

**Why not `object-cover`:** a PowerPoint slide's content (text, logos, chart labels) frequently sits close
to its edges. Cropping to fill the tile/canvas would cut off content the user actually authored and saw in
PowerPoint — directly contradicting the owner's framing that this phase exists to show slides "the way they
natively looked."
