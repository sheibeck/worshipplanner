  <behavior>
    - progressionVwTypeSequence('1-2-2-3') returns [1, 2, 2, 3, 3]; progressionVwTypeSequence('1-2-3-3') returns [1, 2, 3, 3, 3] (position-sorted values of PROGRESSION_SLOT_TYPES, read as an ordered sequence, NOT a position lookup)
    - buildSlotsFromTemplate([], true) returns [] (empty template → zero slots)
    - buildSlotsFromTemplate of 3 SONG entries with VW on → the SONG slots' requiredVwType are the FIRST THREE of the sequence in order (1, 2, 2), indexed by song ordinal not array position
    - buildSlotsFromTemplate of a mixed template (e.g. SONG, SCRIPTURE, SONG, PRAYER, SONG) with VW on → only SONG slots consume sequence entries, in order (1, 2, 2); non-song kinds are untouched and interleaved at their array positions
    - buildSlotsFromTemplate of 7 SONG entries with VW on → the 6th and 7th songs cycle via modulo (sequence[5 % 5]=1, sequence[6 % 5]=2) — the disclosed modulo-cycle default for templates longer than the 5-entry canonical sequence
    - buildSlotsFromTemplate with VW OFF → SONG slots carry createSlot's own default requiredVwType (no ordinal-derived value applied; the ordinal sequence is not consulted at all)
    - Output slots have contiguous positions 0..n-1 (reindexSlots applied), and kind/section preserved from each entry
    - An entry whose kind is not a recognized SlotKind is skipped/ignored (defensive integrity guard, threat T-44-03) rather than producing an undefined-kind slot
  </behavior>
  <action>
Add two new exports in `slotTypes.ts`, composing the existing `PROGRESSION_SLOT_TYPES`, `createSlot`, and `reindexSlots` — do not duplicate their logic (RESEARCH "Don't Hand-Roll").

`progressionVwTypeSequence(progression: Progression): VWType[]` — take `PROGRESSION_SLOT_TYPES[progression]`, sort its numeric keys ascending, and map to their values, yielding the ordered VW-type sequence. This is the fix for Pitfall #2: `PROGRESSION_SLOT_TYPES` is keyed by ABSOLUTE position (0,2,5,6,8) which only means anything against buildSlots' fixed 9-slot shape; an arbitrary template must read it as an ordinal sequence walked by each SONG's ordinal index, never indexed by array position.

`buildSlotsFromTemplate(entries: ServiceTemplateEntry[], vwModeEnabled: boolean, progression: Progression = '1-2-2-3'): ServiceSlot[]` — derive the sequence once; keep a running `songOrdinal` counter starting at 0; map each entry to `createSlot(entry.kind, vwType, entry.section)` where `vwType` is set ONLY when `entry.kind === 'SONG'` AND `vwModeEnabled` (index `sequence[songOrdinal % sequence.length]`, then increment `songOrdinal`); for all other cases pass `vwType` as `undefined` so `createSlot`'s own `?? 2` default applies (VW mode off → plain SONG per Area 3). Skip any entry whose `kind` is not one of the known `SlotKind` values (defensive guard — do not pass an unknown kind into `createSlot`'s exhaustive switch, which would return `undefined`). Return `reindexSlots(slots)` so positions are contiguous. Import `ServiceTemplateEntry` from `@/types/organization`.

DISCLOSE the modulo-cycle choice as a deliberate discretionary decision (Open Question 1 / Assumption A1): for a template with more SONG entries than the 5-entry canonical sequence, VW types cycle (modulo) rather than clamping to the last value. Note the alternative (clamp-to-last) in a code comment so the owner can see the chosen behavior at verification time.

Extend `slotTypes.test.ts` with a `describe('buildSlotsFromTemplate', ...)` block covering every case in the behavior list above (empty, fewer-than-5 songs, more-than-5 songs cycling, mixed kinds, VW off, position contiguity, unknown-kind skip). Pitfall #2's warning: a suite that only exercises the canonical 9-slot "Reset" shape will NOT catch the ordinal bug — the fewer/more-than-5-song cases are mandatory.
  </action>
