<objective>
Extract the two decisions R078 turns on — "which of several already-circulated tokens is the one to
adopt" and "what a freshly-minted token looks like" — into a dependency-free module so they can be
proven exhaustively without a Firestore mock, and so the production-only failure mode the research
pass found cannot creep back in.

Purpose: the obvious implementation of "adopt the most recent existing token" is
`where('serviceId','==',id)` plus `orderBy('createdAt','desc')`. That query needs a composite index;
this project's `firestore.indexes.json` is empty; and **the Firestore emulator does not enforce
composite-index requirements**, so that query passes every local test and then throws
`FAILED_PRECONDITION` in production on exactly the services R078 exists to rescue. Moving the
ordering into a pure client-side function removes the temptation and makes the ordering itself —
ties, missing timestamps, foreign orgs — directly testable.

Output: `src/utils/shareTokens.ts` and its test file. No Firestore, no Pinia, no mock.

This plan is Wave 1 and runs in parallel with Plan 01; its file set is new and touches nothing else.
</objective>

Create `src/utils/shareTokens.ts`. Head the file with a doc comment naming R078, naming the
composite-index trap it exists to avoid, and stating that the module is deliberately free of
Firestore and Pinia imports.

Export a structural type `ShareTokenCandidate` with a required `id: string` and optional
`orgId?: unknown` and `createdAt?: unknown`. `unknown` on the two optional fields is deliberate:
these values arrive from `d.data()` on a Firestore snapshot, which is untyped, and pretending
otherwise is how a runtime shape surprise becomes a crash inside a soft-fail catch where nobody
sees it.

Export `mintShareToken(): string`. Allocate `new Uint8Array(18)`, fill it via `crypto.getRandomValues`,
and join each byte as two lowercase hex digits with `padStart(2, '0')` — the exact generator at
`services.ts:354-357`, unchanged, 144 bits of entropy, 36 characters.

Export `shareTokenCreatedAtMillis(value: unknown): number`. It must total-order every timestamp shape
a `shareTokens` document can actually carry in this codebase, and never throw:
- an object exposing a callable `toMillis` (a server-resolved Firestore `Timestamp`) → the result of
  calling it, coerced through `Number`;
- an object with numeric `seconds` (and optionally numeric `nanoseconds`) — the shape
  `services.test.ts`'s `serverTimestamp` mock produces, and the shape a raw REST read gives — →
  `seconds * 1000` plus `nanoseconds / 1e6` when present;
- a `Date` → `getTime()`;
- a finite number → itself;
- anything else, including `null`, `undefined`, a non-finite number, and a `serverTimestamp()` that
  has not yet round-tripped from the server → `0`.
Guard every branch with a typeof/instanceof check before dereferencing, and return `0` rather than
`NaN` from any branch that would otherwise produce `NaN`; a `NaN` leaking into a comparator silently
destroys the sort order rather than failing loudly.

Export `pickAdoptableToken(candidates: ShareTokenCandidate[], orgId: string): string | null`.
Three steps, in this order:
1. **Filter** to candidates whose `orgId` is a string strictly equal to the `orgId` argument
   (T-41-07). The Firestore query that produces these candidates filters on `serviceId` only, so it
   is not org-scoped; without this filter an adoption could latch onto a document belonging to
   another organisation.
2. **Sort** a copy of the filtered array — never mutate the input — over a total order:
   `shareTokenCreatedAtMillis(b.createdAt)` minus the same for `a` (descending), and when that
   difference is exactly zero, `b.id.localeCompare(a.id)` so the lexicographically greatest document
   id wins. Document in a comment that the tiebreak exists because Firestore query iteration order is
   not a guarantee, and that a locally-pending `serverTimestamp()` reads as `null`, coerces to `0`,
   and therefore sorts last deterministically instead of throwing.
3. **Return** the first element's `id`, or `null` when the filtered list is empty.

Add a comment stating explicitly that the caller must NOT add a server-side sort clause to the query
that produces these candidates, and why: an equality filter combined with a server-side sort on a
different field requires a composite index, `firestore.indexes.json` has none, and the emulator does
not enforce the requirement — so the failure would first appear in production. Write that comment in
prose. **Do not name the Firestore sort operator anywhere in this file, not even inside a comment** —
the acceptance criterion for this task is a whole-file grep for that identifier returning zero, and a
comment mentioning it would invalidate its own check.

| Boundary | Description |
|----------|-------------|
| Firestore query results → adoption logic | The adoption query filters on `serviceId` only, so its result set is NOT org-scoped. Documents from any organisation that happen to reference this `serviceId` reach this module. |
