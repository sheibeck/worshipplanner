<objective>
Close R077: make an already-shared service's public view follow the plan automatically. Hook the
share-payload refresh onto the three — and only the three — write paths that actually change what
`ShareView` renders, behind a per-session cache so an unshared service pays nothing, and behind the
WR-06 soft-fail so a share hiccup can never fail a user's save.

the payload rewritable; this plan is what actually keeps the payload current. It is the second half
of the single root cause behind both reported symptoms.

Output: an internal `maybeRefreshShareLink` hook and its three call sites, plus the tests that prove
the payload follows the plan, that nothing writes back to the service document, and that the PII
guard holds on the refresh path too.

**Read Plan 03's SUMMARY first** for the exact `writeSharePayload` and `shareLinkCache` shapes.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Service edit (private) → `shareTokens/{token}` (world-readable) | The refresh is the mechanism that carries private editing state across into a public document. Everything `buildServiceSnapshot` emits becomes visible to anyone holding the URL, on every save. |
| Share write → `services/{docId}` | The reverse direction must remain closed. `services/{docId}` feeds the only `onSnapshot` in the store, which feeds the editor's remote-merge watcher and autosave; a write-back would close a trigger loop. |
| Browser → Firestore | `firestore.rules` is the only authorization tier. Until the owner deploys Plan 01's rules every refresh is denied server-side. |
