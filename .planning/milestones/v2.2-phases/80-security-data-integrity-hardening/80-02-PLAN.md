<objective>
Close R234: `deleteService` currently deletes only the service doc, leaving every public share artifact live — a deleted service's share URL keeps resolving (stale-authorization / information-disclosure defect). Extend `deleteService` to revoke all three artifact types the service can accumulate — `shareTokens` (query by serviceId, possibly several), `serviceShareLinks/{id}` (direct-keyed), and `serviceShares/{slug}__service-{date}` (slug+date-keyed) — before deleting the service doc, reusing the `deleteQuarter` guarded-delete precedent adapted for query-based lookup.

Purpose: A live, unauthenticated share URL for a deleted service serves stale content indefinitely (PENDING-VERIFICATION C5). Client-only — the `allow delete` rules for all three collections already exist; NO rules change.

Output: A revocation block in `src/stores/services.ts` `deleteService`, plus unit tests in `src/stores/__tests__/services.test.ts` proving all three artifact types are revoked (including the multi-`shareTokens` case) and that a never-shared service deletes without throwing.
</objective>

  <action>
Per R234, extend `deleteService(id)` in `src/stores/services.ts` (currently ~lines 403-412: it only calls `deleteDoc` on the service doc then `shareLinkCache.delete(id)`). All needed Firestore helpers are already imported in this file (`collection`, `query`, `where`, `getDocs`, `getDoc`, `deleteDoc`, `doc`). Mirror the `deleteQuarter` revocation structure (`src/stores/quarters.ts` ~lines 460-483: revoke public share docs FIRST, each existence-guarded, then delete the parent LAST), adapting to these three key shapes documented in RESEARCH:

  1. Look up the service object from the store's in-memory cache BEFORE any delete — `services.value.find((s) => s.id === id)` — because the `serviceShares` key needs `service.date`, and after the service doc is deleted the date is unrecoverable (Pitfall 4). `deleteQuarter` does the analogous `getQuarter(quarterId)` at the top of its own function.
  2. shareTokens (QUERY-based — a service can accumulate more than one via adoption/re-share): `getDocs(query(collection(db, 'shareTokens'), where('serviceId', '==', id)))` and `deleteDoc` each returned doc's ref. This mirrors `ensureShareLink`'s own adoption query shape. No existence pre-check needed — a query result set is already known to exist.
  3. serviceShareLinks/{id} (direct-keyed identity doc): `getDoc(doc(db, 'serviceShareLinks', id))`; only `deleteDoc` when `.exists()`.
  4. serviceShares/{slug}__service-{date}: read the org's slug via `getDoc(doc(db, 'organizations', orgId.value))` -> `slug`; if slug and the service object are present, build `doc(db, 'serviceShares', slug + '__service-' + service.date)`, `getDoc` it, and only `deleteDoc` when `.exists()`.
  5. Delete the service doc LAST (existing `deleteDoc(doc(db,'organizations',orgId.value,'services',id))`), then keep the existing `shareLinkCache.delete(id)` (WR-03) unchanged.

CRITICAL (Pitfall 3): each of steps 3 and 4 MUST be existence-guarded with `getDoc().exists()` before `deleteDoc`. An unconditional `deleteDoc` against a never-created doc evaluates the delete rule against a null `resource`, whose `resource.data.orgId` dereference errors — Firestore treats an erroring rule as DENY, not a no-op. Skipping the guard turns "this service was never shared" (the common case) into a hard permission-denied. Unlike `deleteQuarter`, there is NO single outer `if (shareToken)` gate here — each of the three artifact types is independently possibly-present, so check/query each one independently rather than gating the whole block behind one flag.

Add tests inside the existing `describe('deleteService', ...)` block in `src/stores/__tests__/services.test.ts` (~line 773), following that file's established `vi.mocked(getDoc/getDocs/setDoc/deleteDoc)` mocking conventions and `triggerSnapshot([...])` fixture setup. Cover the five behaviors above. For the multi-token case, mock `getDocs` to return two token docs and assert both refs are passed to `deleteDoc`. For the absent cases, mock `getDoc` to return `{ exists: () => false }` and assert `deleteDoc` is NOT called for that path and the call does not reject. Keep the two existing deleteService tests (the plain `deleteDoc` call and the WR-03 stale-cache test) green.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated public reader -> Firestore public share docs | Anyone holding a share URL reads `shareTokens`/`serviceShares`/`serviceShareLinks`; these must not outlive the resource they expose |
| org editor -> Firestore (service deletion) | An editor deletes a service; the client-authored cascade must revoke every derived public-access artifact, not just the service doc |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-80-04 | Information Disclosure | Stale public share URL after service deletion (`shareTokens`/`serviceShares`/`serviceShareLinks`) | high | mitigate | `deleteService` revokes all three artifact types (query-based for shareTokens) before deleting the service doc (R234), mirroring the shipped `deleteQuarter` precedent; proven by unit tests that a leftover artifact no longer exists after delete |
| T-80-05 | Denial of Service | `deleteService` on a never-shared service (rules DENY on null resource) | medium | mitigate | Existence-guard (`getDoc().exists()`) every direct-keyed delete so the common never-shared case does not hit permission-denied (Pitfall 3); proven by the absent-artifact no-throw tests |
| T-80-SC | Tampering | npm/pip/cargo installs | low | accept | No new package installs this phase (RESEARCH Package Legitimacy Audit: N/A — reuses already-installed firebase/pinia) |
