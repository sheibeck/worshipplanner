<objective>
Prove the lock and close the phase (R045, R048's removal gate).

Purpose: R045's order half is largely a consequence of Phase 29 having made the slots
array section-major at every mutation site, and its membership half is a consequence of a
single existing cascade delete. Neither needs a new mechanism — adding a second ordering
key (a stored order field on the group document) would create exactly the drift this
phase exists to eliminate. What they DO need is proof, because the bug class is "some
particular arrangement desyncs", which example-based tests systematically miss.

There is no property-testing style anywhere in this codebase and `fast-check` is not
installed. This phase establishes the pattern with a plain generated-permutation loop,
consistent with the existing "iterate over test cases" convention — a generated case list
instead of a hand-written one. Do not add a property-testing dependency for one
narrow-domain invariant.

One thing the executor must know before writing the order test: `assembleSlideshow` sorts
slots by their `position` field while `AssembledSlide.slotIndex` carries the ARRAY index.
Those two agree only because every mutation site and the load path compose
`reindexSlots(orderSlotsBySection(slots))`, which sets `position` to the array index. The
permutation suite must assert BOTH halves of that chain, so a future change that reorders
the array without reindexing is caught here rather than at rehearsal. Do NOT "simplify"
the assembler's sort away as part of this plan — that is a behavior change outside this
phase's decided scope; assert the invariant instead.

Output: a proven order-and-membership lock, a clean removal gate, and one human
confirmation of the exact symptom that started this phase.
</objective>
