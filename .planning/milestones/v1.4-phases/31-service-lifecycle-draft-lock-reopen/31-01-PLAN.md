<objective>
Make the Firestore rules layer actually enforce the draft lock on the `services`
collection (R036), and close the wildcard that currently makes any such rule a no-op.

**★ Why this plan is first and cannot be reordered.** `31-RESEARCH.md` proved by
EXECUTION against the emulator that `firestore.rules:71-73`'s
`match /{collection}/{docId}` also matches `/organizations/{orgId}/services/{docId}`,
and Firestore rules are OR-evaluated. A rules file whose `/services` block read
literally `allow write: if false` **still permitted an editor's write**. Until the
catch-all excludes `services`, every other layer of this phase is decorative — the
store guard and the UI gate would both be bypassable by anyone with a browser console.

**Deliberately NOT in this plan:** the `slideGroups` rule. It cannot ship without the
`canWrite` narrowing that goes with it (see 31-02), because the materialization watcher
writes on service LOAD and would start throwing permission-denied on every locked
service. Keep them together in wave 2.
</objective>

## Task 1 — Close the catch-all bypass

`firestore.rules:71-73` currently reads:

```javascript
      match /{collection}/{docId} {
        allow read, write: if isOrgEditor(orgId);
      }
```

Add **only** `&& collection != 'services'` to the write clause.

**★ Do NOT add the `slideGroups` exclusion here.** There is no `/slideGroups` block in
`firestore.rules` — this wildcard is the ONLY rule granting write to
`/organizations/{orgId}/slideGroups/*`. Excluding it now would drop every slide-group
write through to the global deny, including load-time materialization on **draft**
services, and nothing in this wave would detect it (`src/rules.test.ts` has zero
`slideGroups` coverage). That exclusion belongs in wave 2, in the same commit as the
`/slideGroups` block that replaces it.

Add a comment stating why the exclusion exists, because a future reader deleting it
would silently disable this entire phase.

## Task 2 — The /services rule

Replace `firestore.rules:51-54` with this, verbatim:

```javascript
      // Services — viewers read; editors write only while the STORED status is
      // draft, with two explicit carve-outs (reopen, Planning Center export).
      //
      // Note the read is of `resource.data.status` (STORED), never
      // `request.resource.data.status` (INCOMING) — reading the incoming value
      // would let any write that also sets `status: 'draft'` edit a locked
      // service, which is precisely the payload an attacker would send.
      match /services/{docId} {
        function storedStatus() { return resource.data.get('status', 'draft'); }
        function keys() { return request.resource.data.diff(resource.data).affectedKeys(); }

        allow read:   if isOrgMember(orgId);
        allow create: if isOrgEditor(orgId) && request.resource.data.status == 'draft';
        allow delete: if isOrgEditor(orgId);
        allow update: if isOrgEditor(orgId) && (
          // 1. Ordinary editing — allowed only while the STORED status is draft.
          //    This also covers the draft -> planned transition (D-02).
          storedStatus() == 'draft'

          // 2. D-09 — the Planning Center export write. planned -> exported,
          //    carrying real export evidence. `hasAll(['pcExportedAt'])` (not
          //    pcPlanId) because affectedKeys() only reports CHANGED keys and a
          //    re-export to the same plan writes an unchanged pcPlanId.
          || (storedStatus() == 'planned'
              && request.resource.data.status == 'exported'
              && keys().hasOnly(['status','pcExportedAt','pcPlanId','updatedAt'])
              && keys().hasAll(['pcExportedAt'])
              && request.resource.data.pcPlanId is string)

          // 3. R037 — Reopen. The ONLY status-reverting write. hasOnly() is what
          //    stops "reopen" being used to smuggle a slots rewrite alongside the
          //    status change. D-11's pcExportedAt/pcPlanId are untouched by design.
          || (request.resource.data.status == 'draft'
              && keys().hasOnly(['status','updatedAt']))
        );
      }
```

**Three things you must not "fix":**

1. **`hasAll(['pcExportedAt'])` and NOT `hasAll(['pcPlanId'])`.** `affectedKeys()`
   reports only keys whose VALUE changed. A re-export to the same Planning Center plan
   rewrites an identical `pcPlanId`, which never appears in the diff — so requiring it
   denies the legitimate re-export that D-11 exists to enable. Research's probe D3
   failed on the naive version and passed on this one. `pcExportedAt` is safe to require
   because the client always writes a fresh `serverTimestamp()`.
2. **`create` is split out and does not reference `resource.data`.** On a create,
   `resource.data` is null and referencing it produces an evaluation error.
3. **`delete` is unconditional beyond the editor check** — D-15. Do not add a status
   condition; the UI warns instead.

**Verification:** Task 3's tests.

## Task 3 — Emulator-backed rules tests

Add a describe block to `src/rules.test.ts` covering every scenario below. Follow the
existing file's conventions — `assertFails` for denials (37 existing uses), and `seedDoc`
to plant a `planned`/`exported` service directly, since it bypasses rules.

| Scenario | Expect |
|---|---|
| draft service, full field save | ALLOW |
| draft -> planned | ALLOW |
| planned service, ordinary field edit | DENY |
| exported service, ordinary field edit | DENY |
| exported -> draft, `status` + `updatedAt` only (Reopen) | ALLOW |
| planned -> draft (Reopen) | ALLOW |
| reopen payload that ALSO edits another field | DENY |
| planned -> exported + `pcExportedAt` + `pcPlanId` (D-09) | ALLOW |
| **re-export to the SAME `pcPlanId`** (D-11) | ALLOW |
| `create` with `status:'exported'` / with `status:'draft'` | DENY / ALLOW |
| legacy doc with NO `status` field, ordinary edit | ALLOW (treated as draft) |
| `roleAssignmentOverrides.{roleId}` dot-path write, planned / draft | DENY / ALLOW |
| delete a locked service | ALLOW |
| viewer read / viewer write | ALLOW / DENY |

**★ The re-export case and the dot-path case are the two that matter most.** The
re-export case is the one reasoning got wrong. The dot-path case is how the Roles tab
gets covered at the rules layer — the Roles tab writes
`roleAssignmentOverrides.{roleId}` via a scoped update, which surfaces in
`affectedKeys()` as `roleAssignmentOverrides`, which is in neither carve-out's
`hasOnly` list and is therefore denied on a locked service without any Roles-specific
rule.
