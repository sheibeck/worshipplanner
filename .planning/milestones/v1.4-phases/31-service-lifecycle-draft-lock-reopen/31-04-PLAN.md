<tasks>

## Task 1 — The computeds

Add `isLocked` (stored status is not draft) and `canEditService`
(`authStore.isEditor && !isLocked`) to `ServiceEditorView.vue`. Rename or retire
`isExportedLocked` (`:1288`) — it fires only at `exported` and never at `planned`, which is
half the requirement. Leaving a similarly-named computed alongside the new one invites a
future edit to use the wrong one.

## Task 2 — Service Order tab: apply the five-class migration

Work the table line by line. For each site, state in your SUMMARY which class you applied.
If a site does not match its stated class when you read it, STOP and report rather than
guessing — a wrong class inverts the lock at that site.

Also in scope: `canReorder` (`:1392`) currently omits `isExportedLocked` entirely, so
**drag-reorder works on an exported service today**. That is a live defect this plan
closes.

## Task 3 — Slides tab

- Add a `serviceLocked` prop to `SlidesTab.vue`, distinct from `isEditor`, so the drawer
  can tell "you are a viewer" from "the service is locked" (31-UI-SPEC.md requires
  different copy for each). Default it `false` so existing test fixtures keep working.
- Compose the lifecycle lock with Phase 30's `canMutate` (`EditSlideDrawer.vue:432`) and
  `canReorder` (`SlideGrid.vue:596`) rather than adding a parallel mechanism.
- The drawer still OPENS when locked, read-only — it is the only surface showing a slide at
  size.
- Drawer notice: use the **dynamic `:data-testid`** from 31-UI-SPEC.md `:651`
  (`drawer-song-readonly-notice` for a song group, `drawer-service-locked-notice` for a
  locked non-song group). This keeps both existing assertions at
  `EditSlideDrawer.test.ts:1432` and `:1439` green with zero test churn — do not rename.
- Gate `SlideGroupMusicControl`'s wrapper: with no bed audio and no add affordance it
  renders an empty bordered box, which locked services hit constantly.

## Task 4 — Roles tab

Assignments render as names, no checkboxes. Note the Roles tab writes
`roleAssignmentOverrides.{roleId}` through the store directly, bypassing
`localService`/autosave — so a template-only gate leaves the write path open. Gate the
handler too. (The rules layer already denies this write on a locked service; the UI must
not offer it.)

`31-UI-SPEC.md`'s claim that the Roles tab is "editor-only entirely" is true of the tab
BUTTON (`:410`) but not the panel — a viewer branch exists at `:934-936`. Do not delete it.

## Task 5 — ★ Dead-instruction copy, and Sortable teardown

**Four empty states tell a locked user to do something they cannot.** Replacing the copy is
required, not optional — hiding the control while leaving the instruction is worse than
either:
- `ServiceEditorView.vue:564-569` — the Phase 29 section placeholder ("Drag an item here…")
- `SlideGrid.vue:130-137` — "Add a slide, or drop a file below."
- `SlidePlanRail.vue:22-25` — "Add songs… on the Service Order tab"
- `ServiceEditorView.vue:940` — Roles' "assign roles manually below"

**Sortable teardown.** Hiding drag handles leaves the Sortable instances attached. Destroy
them when the gate closes and re-create when it opens — the five per-section instances AND
`SlideGrid`'s. Without this, **reopening a service leaves the tab undraggable**, which is a
new defect introduced by the fix.

## Task 6 — Tests

- Each tab renders read-only at `planned` AND at `exported` (not just `exported` — that
  asymmetry is the bug being fixed).
- Export to PC, Present, Print, Share remain enabled while locked.
- One banner on screen; switching tabs does not add a second.
- A viewer sees no banner.
- **Reopen → drag works again without remounting** (the Sortable teardown regression).
- No rendered empty state contains the four dead instructions while locked.
- Handler-level guards: call each gated handler directly and assert it no-ops when locked,
  not merely that the template hides it.
