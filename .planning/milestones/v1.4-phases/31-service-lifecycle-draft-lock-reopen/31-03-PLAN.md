<objective>
Replace the blind three-way status cycle with explicit named transitions, add the store's
draft-only write guard (the middle enforcement layer), and give a failed transition
somewhere to be seen (R036, R037).

**What is being deleted and why.** `ServiceEditorView.vue:1796`'s `toggleStatus` cycles
draft → planned → exported → draft on a badge click. It is the source of two live defects:
a user can mark a service "Exported" without ever exporting it (leaving `pcExportedAt` and
`pcPlanId` unset), and reopening an exported service is an unlabelled click with no
warning. D-01 deletes it outright.

**Deliberately NOT in this plan:** the tab-by-tab gate migration and the lock banner's
read-only renderings (31-04), and R038's Sunday default (31-05). This plan owns the
*transitions*; 31-04 owns what the tabs look like once locked.
</objective>

## Task 1 — Store: transition actions + the draft-only guard

In `src/stores/services.ts`:

- Add explicit transition actions rather than a generic status setter — one for
  draft → planned, one for reopen (→ draft). The reopen action writes ONLY `status` and
  `updatedAt`, because the rules layer's `hasOnly(['status','updatedAt'])` will reject
  anything else. **Do not include `pcExportedAt`/`pcPlanId` in the reopen payload even to
  re-write their existing values** — that would surface in `affectedKeys()` and be denied.
- Add a guard on the ordinary update path that refuses a write when the stored status is
  not draft, EXCEPT for the two legal carve-outs (the export write, and delete). Mirror the
  rules layer's shape; do not invent different policy. Per `31-PATTERNS.md` there is no
  existing guard precedent in this store — the closest shape is
  `useSlideshowAssembly`'s `canWrite` short-circuit, so follow that idiom.
- **★ `updateService` is not the only write path.** The Roles tab goes through
  `setRoleOverride` (`services.ts:155-158`) and `clearRoleOverride` (`:165-169`), each with
  its own `updateDoc`. Guard BOTH. Without them the store layer simply does not cover
  Roles, and "three-layer enforcement" would be false for that tab — the rules layer denies
  those writes and wave 4 gates the handler, so R036 still lands, but at two layers, not
  three.
- The guard is defence-in-depth, not the primary enforcement. It exists so a client-side
  bug surfaces as a clear local error rather than an opaque Firestore rejection.

**Verification:** store tests — a draft write passes, a planned/exported write is refused
locally, the export write passes, delete passes at any status, reopen passes.

## Task 2 — The status pill and the two transition actions

In `ServiceEditorView.vue`:

- Delete `toggleStatus` (`:1796`) entirely. Delete the clickable `<button>` badge at
  `:57-71`; keep the `<span>` at **`:72`** — per 31-UI-SPEC.md `:290-293` the span is
  already the correct non-interactive pill and its `px-2 py-0.5` is pre-existing, not new
  markup.
- `:134` is `:disabled="!hasSermonContext || aiSuggestingAll || isExportedLocked"` —
  **compound. Drop ONLY the `isExportedLocked` term**, leaving
  `:disabled="!hasSermonContext || aiSuggestingAll"`. Its button gains
  `v-if="canEditService"` in wave 4. Deleting the whole binding would make "Suggest All
  Songs" clickable with no sermon context and re-clickable while a request is in flight.
  (`31-UI-SPEC.md:92` has this right; `:871`'s summary line had it wrong and is corrected.)
- Delete the stale `:title` at `:135` — `'Service is exported — cycle badge back to Draft
  to edit'` instructs the user to operate the control you just removed.
- Add **Mark as Planned** (draft only) and **Reopen for editing** (locked only), per
  31-UI-SPEC.md's placement.
- Add a single `hasPcExportEvidence` computed: true when `pcExportedAt` or `pcPlanId` is
  present. **This one computed drives both** the reopen confirm's Planning Center warning
  and Task 4's delete-confirm sentence. Do not write two.

**★ D-04 — the warning gates on EVIDENCE, not on the status string.** Live data may hold
services sitting at `exported` that were set by hand through the old cycle and never
exported. Warning them that "Planning Center holds the previously exported version" would
be false, and a warning users learn is sometimes false is one they learn to click through.

## Task 3 — Reopen: confirm dialog and the no-optimistic-flip contract

- Reopening a `planned` service: one click, no dialog (D-10 — friction only where there
  are consequences).
- Reopening with `hasPcExportEvidence`: open a confirm dialog carrying the Planning Center
  warning. Copy is specified in 31-UI-SPEC.md `:493-509`. Reuse the `:211-237` Teleport
  shell.
- **★ Status must NOT flip optimistically.** Await the store action. On rejection the pill,
  the banner and every gate keep showing the OLD status, and `lifecycleError` renders. A UI
  showing `Draft` while the store still holds `planned` is exactly the "it didn't save"
  defect class this milestone exists to close — do not reintroduce it in the phase that is
  supposed to tighten correctness.
- `lifecycleError` copy, verbatim from 31-UI-SPEC.md `:226-227`:
  - failed Reopen: `Couldn't reopen this service. Check your connection and try again.`
  - failed Mark as Planned: `Couldn't mark this service as Planned. Check your connection and try again.`
- Two surfaces: inside the lock banner while locked; inline in the header Save area while
  draft. The autosave error line at `:100-106` is NOT available while locked — 31-04
  removes it there — which is why the banner has to host it.

## Task 4 — Delete confirm gains the evidence-gated sentence (D-15)

Extend the existing delete confirm body (`:216`) with one sentence, shown only when
`hasPcExportEvidence`: *"This service was exported to Planning Center. Deleting it here
does not remove that plan."*

Delete itself stays available at every status — the owner decided this explicitly. Delete
is the only irreversible action in this view, and for an exported service it silently
orphans a live Planning Center plan and destroys the audit trail D-11 preserves. Warning is
the mitigation; locking is not.
