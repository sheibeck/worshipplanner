<objective>
Deliver the pure ordering contract the rest of the phase is built on: a section-major grouping of
slots that is total (every slot lands somewhere, including legacy slots with no `section`), stable
(relative order preserved within a bucket), and driven only by `SERVICE_SECTIONS`.

Isolating this in `src/utils/` is what makes the section-order guarantee testable without mounting a
2,900-line view, and what lets Plan 05 add a fifth section by touching one type file.

Purpose: one source of truth for "what order are the slots in", shared by the rendered grouping and
by the array that gets persisted — so the editor view and the array print/export/assembly read can
never diverge again.
Output: three exported pure functions plus tests; no component or view touched.
</objective>

  <name>Task 1: groupBySection / flattenBySection / orderSlotsBySection in slotTypes.ts</name>
  <files>src/utils/slotTypes.ts, src/utils/__tests__/slotTypes.test.ts</files>
  <behavior>
    - groupBySection over four sectioned slots in scrambled order returns each slot under its own section key, in SERVICE_SECTIONS order, with within-bucket relative order preserved.
    - groupBySection over slots that all lack a section returns five empty section buckets and every slot in the trailing legacy bucket, in input order.
    - groupBySection over a mixed input puts section-less slots in the legacy bucket and leaves the sectioned ones untouched.
    - flattenBySection concatenates the section buckets in SERVICE_SECTIONS order then the legacy bucket last.
    - orderSlotsBySection on an interleaved array (worship, sending, worship, message) returns section-major order by id.
    - orderSlotsBySection on an already-section-major array returns the SAME array reference (identity, not a copy).
    - orderSlotsBySection never adds, drops, mutates, or re-mints a slot — output ids are a permutation of input ids and every slot object is the same reference.
  </behavior>
  <action>
Add to `src/utils/slotTypes.ts`, following the file's existing JSDoc-on-every-export convention and
its `(D-XX)` design-reference comment style:

- `export function groupBySection<T>(items: readonly T[], getSection: (item: T) => ServiceSection | undefined): { sections: Record<ServiceSection, T[]>; legacy: T[] }`
  Generic on purpose: the view groups `{ slot, index }` pairs while the reorder handler groups bare
  `ServiceSlot`s, and both must use the identical bucketing rule. Initialise every
  `SERVICE_SECTIONS` key to an empty array up front so empty sections are always present as keys
  (this is what lets the view render an empty section unconditionally, R043). Anything whose
  `getSection` returns `undefined` — or returns a value not in `SERVICE_SECTIONS` — goes to `legacy`.

- `export function flattenBySection<T>(grouped: { sections: Record<ServiceSection, T[]>; legacy: T[] }): T[]`
  Concatenate in `SERVICE_SECTIONS` order, then `legacy` last. Trailing placement for section-less
  members deliberately mirrors `useSlideshowAssembly.ts:555-559`, which already ships section-less
  slides as a trailing "Ungrouped" group — do not invent a second rule.

- `export function orderSlotsBySection(slots: ServiceSlot[]): ServiceSlot[]`
  Composition of the two above over `(s) => s.section`. Identity-preserving: when the flattened
  result is element-for-element reference-equal to the input, return the ORIGINAL `slots` array,
  not the new one. Document why in the JSDoc — the same reason `backfillSlotIds` (lines 101-120)
  returns the original service reference: a fresh array reference in an autosave-watched view
  manufactures a false `isDirty` and, on the load path's remote-merge branch, a comparison that
  never converges.

Do NOT call `reindexSlots` from inside `orderSlotsBySection` — keep ordering and position-renumbering
separate concerns; callers compose `reindexSlots(orderSlotsBySection(slots))`.

Nothing here may reference a section name as a string literal. `SERVICE_SECTIONS` is the only
enumeration source (D005) — that is what makes Plan 05's fifth member free.
  </action>

  </verify>

All three helpers exported with JSDoc and covered by the seven behaviours above; the identity-return
