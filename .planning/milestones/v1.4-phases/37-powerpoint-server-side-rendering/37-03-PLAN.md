<objective>
Lay the bridging function's foundation: the IAM-authenticated invoker seam, and the durable Firestore
queue entry that decouples the slow render from the fast user-facing `parsePptx` call.

Purpose: R062 requires the render to be invoked asynchronously over service-to-service IAM auth.
`parsePptx` is an `onCall` the user watches a spinner for; it must not block. This plan adds the
invoker (isolated so the completeness-check handler can mock one function rather than the auth library)
and the queue write, without changing a single observable behaviour of `parsePptxHandler`.

Output: `functions/src/renderInvoker.ts` + tests, and one additive Firestore write in
`functions/src/index.ts` with regression tests proving nothing else moved.

**Nothing is deployed.** The IAM binding this code depends on is handed to the owner in plan 37-06.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Bridging Cloud Function → private Cloud Run service | A Google-managed identity crosses into another service; the ID-token audience is the whole access decision |
| `parsePptx` caller → Firestore `pptxRenders` | An authenticated app user's request causes a server-side write to a new collection |
| npm registry → `functions/node_modules` | A new third-party dependency enters an already-shipping Cloud Functions project |
