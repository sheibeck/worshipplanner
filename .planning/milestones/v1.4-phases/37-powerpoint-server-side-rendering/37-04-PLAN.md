<objective>
Build the completeness check — the one piece of logic standing between a failed render and a broken
Sunday morning.

Purpose: R062's success criterion is that a deck flips to "ready" **only** once every expected image is
confirmed uploaded. This is fully testable without a container, and 37-CONTEXT.md asks for it to be
tested hard. It is also where this phase's sharpest correctness trap lives.

Output: `requestPptxRenderHandler` and its `onDocumentCreated` trigger in `functions/src/index.ts`, plus
an exhaustive test suite in `functions/src/index.test.ts`.

★ **Trap 1, restated because it is easy to get backwards:** the expected page count must NEVER come from
`parsePptxBuffer`'s `MappedSlide[]` length. `mapAstToSlides` (`functions/src/pptxParser.ts:86-135`)
*skips* slides with neither substantial text nor images (line 131) and emits *one entry per image* on a
multi-image slide (lines 115-128). Its length is structurally decoupled from the deck's real page count
— a 6-slide deck can yield 4 entries. Using it would make this check silently wrong in both directions.

**Nothing is deployed.** The service URL param defaults to empty and the unconfigured branch is a tested
behaviour, not a placeholder.
</objective>

    Export `interface RenderOutcome { status: PptxRenderStatus; renderedCount: number; failureReason?:
    string }` and `export async function requestPptxRenderHandler(params: { orgId: string; importId:
    string }): Promise<RenderOutcome>`:

    1. Read the render doc at `pptxRenderDocRef(orgId, importId)`. If it does not exist, log and return
       a failed outcome without writing — there is nothing to update.
    2. Take `storagePath` from the doc. If it is missing or not a string, write `status: "failed"` with
       `failureReason: "missing-storage-path"` and return.
    3. `const renderServiceUrl = PPTX_RENDER_SERVICE_URL.value().trim()`. If empty, write
       `status: "failed"`, `renderedCount: 0`, `failureReason: "render-service-not-configured"`, and
       return **without calling `invokeRenderService` at all**. Comment that this is the expected state
       until the owner runs `render-service/DEPLOY.md`'s deploy command, and that an unconfigured
       service must never be able to produce a ready flip.
    4. Call `invokeRenderService({ orgId, importId, storagePath, renderServiceUrl })` inside a
       try/catch. On rejection, log, write `status: "failed"`, `renderedCount: 0`,
       `failureReason: "render-service-error"`, and return. Capture `reportedCount` from the response.
    5. ★ **Independent recount.** `const [files] = await getStorage().bucket().getFiles({ prefix:
       renderedPrefixFor(orgId, importId) })`. For each file, take the object name's final path segment
       and match it against `RENDERED_OBJECT_NAME`; discard non-matching objects so a stray upload can
       never inflate the count. Parse the captured digits into page numbers and sort ascending.
       Comment that this mirrors `parsePptxHandler`'s own "never trust the client-declared value alone,
       independently re-verify" pattern at lines 172-181.
    6. ★ **The gate.** Compute `actualCount` as the number of matching objects and derive
       `contiguous` as: `pageNumbers` has length `actualCount` and equals exactly `[1, 2, … actualCount]`
       with no gaps. Then
       `const complete = actualCount > 0 && actualCount === reportedCount && contiguous;`
       Comment each conjunct: `actualCount > 0` is the empty-render guard (a deck that rendered nothing
       must be `failed`, never `ready`, and its parsed text layer stays usable either way);
       `actualCount === reportedCount` is the self-report cross-check; `contiguous` catches the partial
       render that count alone misses — pages 1, 2 and 4 uploaded against a reported count of 3 would
       otherwise pass.
    7. Merge-write `{ status: complete ? "ready" : "failed", renderedCount: actualCount, updatedAt:
       FieldValue.serverTimestamp() }` plus, when incomplete, `failureReason: "incomplete-render"`, and
       return the outcome.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Cloud Run response → bridging function | A self-reported `renderedCount` crosses from another service and must not be trusted alone |
| Cloud Storage listing → the ready decision | Object names determine whether a deck is presentable on Sunday |
| Firestore trigger → the handler | An automatically-fired event carries `orgId`/`importId` path params |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-37-13 | Tampering | A partial render reported as complete | critical | mitigate | The ready flip requires three independent agreements — a positive count, reported-equals-actual, and a contiguous 1..N page sequence — with the recount derived from an independent Storage listing, never from the response alone. Tests 1-4, 8 and 11 cover every disagreement. |
| T-37-14 | Repudiation | A ready deck with no evidence of what was counted | medium | mitigate | Every outcome merges `renderedCount` and, on failure, an explicit `failureReason` (`incomplete-render`, `render-service-error`, `render-service-not-configured`, `missing-storage-path`) onto the render doc, so a later investigation can distinguish the causes. |
