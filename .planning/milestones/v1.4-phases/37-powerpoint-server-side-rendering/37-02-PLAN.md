<objective>
Implement the render service itself: the LibreOffice → PDF → PNG pipeline, its org-prefix guard, its
page-ordering contract, and the single HTTP route Cloud Run will expose.

Purpose: this is the code that produces R062's true-fidelity images. Every seam in it is testable
without a container — the argv passed to `soffice` and `pdftoppm`, the storage-path guard, the page
ordering, and the destination naming. 37-VALIDATION.md's deploy-boundary table lists all of these in
the "verifiable now (and must be)" column.

Output: `render-service/src/render.ts`, `server.ts`, `main.ts` and their test files.

**`execFile` is mocked in every test. The real `soffice` binary is never invoked, no container is
built, and nothing is deployed.**
</objective>

    Export the contract first: `interface RenderRequest { orgId: string; importId: string; storagePath:
    string }` and `interface RenderResult { renderedCount: number; pageNumbers: number[] }`.

    Export constants: `RENDER_DPI = 150`, `SOFFICE_TIMEOUT_MS = 180_000`, `PDFTOPPM_TIMEOUT_MS =
    120_000`, `RENDERED_PAGE_PAD = 4`, and `PPTX_IMPORT_PATH_GUARD = /^orgs\/[^/]+\/pptx-imports\/[^/]+\//`.

    Export `renderedPrefix(orgId, importId)` returning `orgs/{orgId}/pptx-imports/{importId}/rendered/`.

    ★ Export `renderedObjectName(pageNumber: number): string` returning `page-` followed by the page
    number left-padded with zeros to `RENDERED_PAGE_PAD` digits, then `.png` — so page 2 becomes
    `page-0002.png` and page 10 becomes `page-0010.png`. This is load-bearing, not cosmetic: the
    bridging function recounts by listing Storage, and an unpadded name set sorts `page-1, page-10,
    page-2` under lexical collation, which would corrupt both the ordering and the recount. Document
    that reason in a comment on the constant.

    ★ Export `pageNumberFromOutputName(name: string): number | null` which matches pdftoppm's own output
    filenames against `/^page-0*(\d+)\.png$/` and returns the parsed integer, or `null` for anything
    else. pdftoppm zero-pads its own output to the width of the last page, so both `page-2.png` and
    `page-02.png` must parse to 2. Never derive ordering from the raw filename string.

    Export `async function renderPptxToImages(req: RenderRequest): Promise<RenderResult>`:

    1. Guard: reject unless `storagePath` starts with `orgs/{orgId}/pptx-imports/` AND matches
       `PPTX_IMPORT_PATH_GUARD`. Throw an `Error` naming the violation. Comment that Cloud Run's IAM
       already authenticated WHO called but never validated WHAT they asked to read — this is the
       independent payload check, mirroring `functions/src/index.ts:168`.
    2. `mkdtemp` a working directory under `os.tmpdir()` with prefix `pptx-`. Derive the LibreOffice
       profile directory as a path INSIDE that working directory, so it is unique per request —
       LibreOffice's own lock file makes a shared profile unreliable under concurrency (Pitfall 3).
    3. Wrap steps 4–8 in `try` with a `finally` that `rm`s the working directory recursively and
       forcefully. This `rm` targets only the process-local temp directory; it is never a Storage delete.
    4. Download the source object to `source.pptx` inside the working directory via
       `storage.bucket().file(storagePath).download({ destination })`.
    5. Run `soffice` with `--headless`, `--norestore`, `--nolockcheck`, `--nodefault`, an
       `-env:UserInstallation=file://` argument pointing at the per-request profile directory,
       `--convert-to pdf`, `--outdir` set to the working directory, and the pptx path — with
       `{ timeout: SOFFICE_TIMEOUT_MS }`. The timeout is the DoS bound from Pitfall 5.
    6. Run `pdftoppm` with `-png`, `-r`, `String(RENDER_DPI)`, the produced `source.pdf` path and a
       page-name prefix of `page` inside the working directory — with `{ timeout: PDFTOPPM_TIMEOUT_MS }`.
    7. `readdir` the working directory, map each entry through `pageNumberFromOutputName`, drop nulls,
       and sort **numerically ascending by the parsed page number** — never by filename string. If the
       resulting list is empty, throw an `Error` stating the render produced no pages. A zero-page
       render must surface as a failure, never as a successful render of zero pages.
    8. Upload each page with `bucket.upload(sourceFilePath, { destination: renderedPrefix(orgId,
       importId) + renderedObjectName(pageNumber) })`, where `pageNumber` is the parsed page number from
       the source filename — not the array index. Set `metadata.metadata.createdAt` to an ISO timestamp,
       matching the convention `src/utils/pptxUpload.ts` already uses for every uploaded object.
    9. Return `{ renderedCount: pages.length, pageNumbers }` with `pageNumbers` in ascending order.

    Instantiate `Storage` lazily inside the function (or via a module-scope const) so a test that mocks
    `@google-cloud/storage` controls it. Do not import `firebase-admin` here.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Bridging Cloud Function → Cloud Run `/render` | IAM-authenticated caller, but an unvalidated JSON payload crosses here |
| Uploaded `.pptx` → LibreOffice | Adversarial or malformed document content enters a conversion engine |
| Render service → Cloud Storage `rendered/` | The service writes objects the completeness check will later count |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-37-04 | Tampering | `storagePath` in the `/render` payload | high | mitigate | `renderPptxToImages` re-checks the `orgs/{orgId}/pptx-imports/` prefix and `PPTX_IMPORT_PATH_GUARD` independently; two tests cover wrong-prefix and cross-org paths and assert `execFile` is never reached. |
| T-37-05 | Denial of Service | Adversarial `.pptx` (zip bomb, pathological embeds) | high | mitigate | Explicit `timeout: 180000` on `soffice` and `timeout: 120000` on `pdftoppm`; Cloud Run `--timeout=300` and `--memory=2Gi` in the deploy handoff bound the rest; the existing 25MB `storage.rules` upload cap already bounds the input. |
| T-37-06 | Denial of Service | Shared LibreOffice profile lock under concurrency | medium | mitigate | A per-request-unique `UserInstallation` profile inside the request's own `mkdtemp` directory, asserted by the soffice-argv test; `--concurrency=1` in the deploy handoff removes the class entirely. |
| T-37-07 | Information Disclosure | Error responses from `/render` | low | mitigate | `handleRenderRequest` returns generic `invalid request` / `render failed` bodies and logs detail only server-side; a test asserts the 500 body contains no substring of the thrown error. |
| T-37-08 | Tampering | Rendered page ordering | high | mitigate | Destination names are 4-digit zero-padded and derived from the parsed page number, never from listing order or array index; the lexical-hostile 12-page test pins it. |
</threat_model>
