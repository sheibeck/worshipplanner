<objective>
Roll the shared status indicator out to the other three autosaving surfaces —
`CongregationalEditor.vue`, `ScriptureSlideEditor.vue` and `SongLyricEditor.vue` — retiring the
three per-status handles each of them duplicates today, and resolve the surface-id lifecycle

satisfy it, and these three are the cheap wins — they are already on `useAutoSave`, so the change

assertions moved onto the new handles.
</objective>

<breaking_rename>
## ★ The three per-status handles are retired — this is deliberate, not incidental

Each of the three editors currently exposes three separate per-status test handles: one on a
colour-only yellow dot for pending, one on the saving text, one on the saved text. All nine
occurrences are retired. `SaveStatusIndicator` exposes one stable handle across all four
surfaces, plus a second one for the failure branch.

32-UI-SPEC.md § 5 calls this out explicitly and asks the plan to name it so it does not surface
as unexplained test breakage. Every assertion in the three component test files that targets a
retired handle must be rewritten in this plan, not left to fail. Record the before and after
`it(` counts per file in the SUMMARY — the counts must not drop.

Accessibility note worth stating plainly: the retired handles carried no ARIA role of their own
beyond a `title` attribute on the pending dot, which is not reliably announced. The new text
inside a polite live region is a strict improvement, not a like-for-like swap.
</breaking_rename>

    phase's UI layer and it is genuinely reachable in both of these components. The record id
    starts null and is assigned only inside the fetch handler, which sets the composable's watch
    source BEFORE the awaited create resolves and populates the id. A surface id read reactively
    at render time can therefore transition from a null-suffixed key to a real-id key while a save
    armed by that same mutation is still pending.

    Resolve it by capturing the id once: hold a separate ref that is assigned the first time the
    record id becomes non-null and is never re-derived while the component stays mounted. Build
    the surface id from that captured ref, prefixed per 32-UI-SPEC.md § 5. While it is unresolved,
    register nothing in the store at all and bind the indicator to an empty string — the store
    returns a fresh idle entry for an unknown key, so the indicator renders nothing. That single
    decision resolves both the E4 partial backstop and the E4 loading backstop: with no entry
    registered, there is nothing to inherit from a previously-open record.

    Report status into the store from one watcher over the composable's status, keyed by the
    captured surface id, skipping entirely while it is unresolved. Set the saved timestamp only on
    the transition into saved. Set the failure text to the generic sentence from
    32-UI-SPEC.md § Copywriting Contract, verbatim — these components have no reorder concept, so
    they never use the reorder variant. Never assign a caught error's message as the failure text;
    raw Firestore error text must not reach user-facing copy.

    Clear the entry on unmount, inside the existing unmount hook, next to the existing composable
    cleanup call. Without this a surface's last-known entry outlives its component.

    Leave both `useAutoSave` call sites exactly as they are. The composable is not rewritten in
    this phase; only the reporting and the rendering change. Do not pass a debounce override — 800
    milliseconds is the app's one constant and both files already rely on the default.

    These two components are currently unmounted dead weight pending Phase 34, so the risk above
    is not reachable in production today. Handle it correctly anyway: Phase 34 mounts them, and a
    latent attribution bug is cheaper to prevent than to diagnose later.
