## ★ REVISED 2026-08-03 by owner decision — the mount seam is the SLIDE, not the Service Order row

The previous version of this plan put the affordance on the **Service Order SCRIPTURE row**. Owner UAT
finding F1 (`34-UAT.md`) is that the owner reaches for scripture editing **from the slide** — the
3-dot action menu and the drawer — and that both currently dead-end:

- `slideDisplay.ts:308-312` — a `scripture` entry's menu offers `edit-details` + `edit-in-scripture`,
  and `edit-in-scripture` lands on `handleNavigateToScriptureEditor` (`ServiceEditorView.vue:1499-1506`),
  which is a tab switch plus `scrollIntoView`. It opens no editor.
- `EditSlideDrawer.vue:155-161` — the `scripture` branch renders `scripturePassageText` read-only under
  `SCRIPTURE_TEXT_CAPTION` (`:678`), with no route out. Worse, the R047 ripple recorded at `:648-656`
  means a reference-only scripture slide always resolves with empty `text`, so that block shows the
  user nothing but the reference back.

**The owner's decision, made with the D-13/D-15 tension on the table:** the scripture slide's edit
route opens `CongregationalEditor`. Fetch the passage, split it into Leader/Congregation, and that
text lands on the slide — real text on the slide, via the sanctioned R064 path. **There is no
free-text scripture override in scope and none may be built.** D-13/D-15 route scripture read-only to
its canonical source precisely to stop a shadow copy of scripture from diverging; a fetched-then-split
passage is not a shadow copy, a hand-typed one is.

## The relay is REUSED; the handler body is deliberately REPLACED

Stated plainly because the brief requires it: **the wiring is reused, the handler body is replaced.**

Reused, unchanged: `SlidesTab.requestEditInScripture()` (`:426-429`), its
`navigate-to-scripture-editor` emit (`:177`), the parent binding
(`ServiceEditorView.vue:1222`), the handler's name and seat, and the WR-04 unsaved-drawer guard
`confirmLeavingOpenDrawer()` (`SlidesTab.vue:456-462`).

Replaced: the BODY of `handleNavigateToScriptureEditor`. It stops switching tabs and scrolling and
starts opening the editor for that slot. The tab switch existed only because R047 had deleted the
panel this relay used to reveal; restoring a destination makes the scroll obsolete, and keeping it
would drag a user off the Slides tab they are working in — the disorientation that made F1 read as
"it opens nothing". The existing `[data-scripture-slot-index="1"]` tests assert the OLD destination;
they are rewritten against the new one, explicitly, not deleted.

**One editor surface, two routes.** The drawer's new control emits up to `SlidesTab`, which calls the
SAME `requestEditInScripture()` the menu path calls. Both therefore arrive at one mount. Do not add a
second `CongregationalEditor` anywhere — an acceptance criterion counts the mounts.

## Why a modal, and why the save status rides along

The editor mounts as a `Teleport`ed modal owned by `ServiceEditorView` — the same shape as the
existing Planning Center export dialog (`:363-366`), so this is an established pattern in this file,
not a new one. `ServiceEditorView` is also the only place that can host it: it owns `localService`,
`canEditService` and the one `useAutoSave` over `localService`. A modal keeps the user on the Slides
tab where they started.

Consequence that must be handled rather than absorbed: `ServiceEditorView`'s sticky save-status bar
(`:235-241`) sits **behind** a modal, so R041's "a user always sees whether their work is saved" would
silently degrade for exactly the writes this panel produces. 34-06 removed the editor's own
`SaveStatusIndicator` (correctly — it no longer persists). The fix is neither of those: the **modal
header** renders the shared `SaveStatusIndicator` bound to the SAME `service:{serviceId}` surface id
the page already uses. One aggregator, one save path, one surface id, status visible while editing.

### ...which creates a second live region, so this plan closes that too

A `Teleport`ed modal does not unmount the page behind it, and 34-10 keeps the page's status region
mounted at idle rather than `v-if`-ing it away (that plan's whole point is preserving announcement
fidelity). So without a further change, opening this modal would leave **two** `aria-live="polite"`
regions mounted on `service:{serviceId}`. Their CONTENT always agrees — same surface id, same
aggregator — so this is not the two-disagreeing-fields defect. The two real costs are that polite
regions with identical text can double-announce, and that `find('[data-testid="save-status"]')`
resolves to whichever node comes first in the document, which would let a future test silently assert
against the wrong one.

**Resolution: the page's bar is suppressed while this modal is open.** The modal owns the status while
it is up, and there is exactly one region on that surface id at any moment. Task 2 makes the change
and pins the selector ambiguity with a count assertion, so "exactly one" is enforced rather than
assumed. Closing the modal restores the page bar; if a save is still in flight at that moment the
region does remount once, which is the same single-transition cost 34-10 already analysed and is
strictly smaller than leaving two regions live for the whole editing session.

## The WR-04 contract is non-negotiable and gets its own task

`CongregationalEditor.vue` seeds its editable state ONCE at setup and is deliberately not reactive to
later prop changes (34-06 preserves this; the original contract comment lived at
`CongregationalEditor.vue:357-376`, addressed by name to Phase 34, and is restated in full in
`PENDING-VERIFICATION.md` item 34.2). A parent that swaps which slot the panel is showing without
forcing a fresh instance will silently misattribute saves to the first slot the instance ever saw. The
mount is keyed on `slot.id` — the stable slot identity minted by Phase 24 D-01, already the anchor
every `slideGroups/{slotId}` document uses — and Task 3 proves the swap really does produce a new
instance. A comment asserting the key is present is not evidence; a swap test is.
