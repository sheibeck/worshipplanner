<objective>
Find out why Export to PC did not appear, then fix what is actually broken — which is not what the

## ★ The owner's diagnosis is incorrect. The symptom is real.

The owner reported: *"You removed the Export to PC functionality. Now all I have is a Copy to PC
button."* Verified against live source — **it was not removed**:

- `ServiceEditorView.vue:165-196` still carries the **Export to PC** button with its spinner,
  exported-check and upload icons, `data-testid="export-pc-btn"` and its `onExportToPC` handler. The
  full Planning Center export modal is still there too (`:363-465`).
- It is gated `v-if="authStore.hasPcCredentials"`. **Copy for PC** at `:198` is that `v-if`'s
  `v-else` — its own comment says *"shown when NO credentials OR service is draft"*.
- `auth.ts:51-57` — `hasPcCredentials` requires `pcAppId` and `pcSecret` to be non-null **and**
  non-empty. `auth.ts:107-108` loads both from the org document (`orgData.pcAppId` /
  `orgData.pcSecret`).

So the export path is intact and the observed behaviour means **`hasPcCredentials` evaluated false for
this org**. Two candidate causes, and this is a diagnosis task before it is a fix task:

1. The org document genuinely has no PC credentials — never set, cleared, or written under different
   field names.
2. A load-order/reactivity regression leaves `pcAppId`/`pcSecret` null at render time even though the
   org document has them.

Cause 2 is not far-fetched here: the `/services/:id` route carries only `meta: { requiresAuth: true }`
(`router/index.ts:59-63`), **not** `requiresEditor`, so the guard never awaits `waitForRole()` for this
view — and `waitForRole()` is the only thing that indirectly waits for `loadOrgContext`, since the
member `onSnapshot` that sets `userRole` is registered after the org-document read. This view can
therefore render before the credential refs are populated. Whether that self-heals through reactivity
or leaves them null is exactly what Task 1 settles.

## Two hard constraints, both non-negotiable

**⑴ Do NOT ungate the button.** Surfacing an export that cannot authenticate is worse than the current
state — the user gets a failure at the Planning Center API instead of an honest "not configured".

**⑵ Do not read, print, log, or write credential values.** `pcSecret` is a live secret. Every
assertion in this plan is about presence, absence, or the value of `hasPcCredentials` — never about
the credential itself. Test fixtures use obviously-synthetic placeholder strings and assert only that
`hasPcCredentials` flips; no real value goes into a fixture, a snapshot, a log line or a commit.

## The real defect, whichever cause it is

Silently swapping to a differently-named button is what made this read as a deletion. An editor whose
organization has no Planning Center credentials deserves to be **told that**, with a route to set them
— not handed a different button and left to infer that a feature was removed. That is a genuine UX
defect regardless of which cause Task 1 finds, and it has no requirement covering it, which is why
Task 2 writes one.

### The proposed requirement, verbatim

> **R071** (quality-attribute): An editor who cannot export to Planning Center is told why, with a
> route to fix it. When Planning Center credentials are not configured for the organization, the
> service editor says so plainly beside the copy-for-Planning-Center fallback and links to Settings,
> instead of silently substituting a differently-named button. The export affordance itself stays
> gated — an export that cannot authenticate is never offered.
> *(Added 2026-08-03 from owner UAT finding F5, where the silent substitution read as the export
> feature having been deleted.)* `[FEAT]`
