<objective>
Stop rendering an empty bordered box at the top of the Service Editor — without giving up a single
save-status announcement to do it.

**This is not R064 work.** It is owner UAT finding F4 from the 2026-08-03 hands-on session
(`34-UAT.md`), a Phase 32 defect planned here because it surfaced in the same session.

Purpose: `ServiceEditorView.vue:235-241` gates the bordered, sticky save-status wrapper on
`v-if="canEditService"` alone, while the `SaveStatusIndicator` inside it renders `<!--v-if-->` when
there is nothing to report (`SaveStatusIndicator.vue:8-16` — idle deliberately has no branch). An
editor with an idle service therefore gets an empty bordered box pinned to the top of the scrollport.
The owner pasted exactly this DOM after marking a service Planned and reopening it.

Output: the box gone, the live region kept, and the exhaustiveness guard actually enforced.

## ★ REVISED — the fix removes the CHROME, not the element

The rule this codebase already established is *"don't render an empty box"*: `SlideGrid.vue:68-73`
gates the group-music wrapper with an explicit comment — *"31-UI-SPEC E5: gate the WRAPPER, not just
the control's contents. With no bed audio and no add affordance the control renders an empty bordered
box"* — and `:84-90` repeats it verbatim for the background row. Both do it with `v-if`, because in
those two cases there is nothing else the wrapper is for.

**Here there is.** This wrapper contains an `aria-live="polite"` region. Assistive technology
announces *mutations* to a region it is already monitoring; it generally does not announce content a
region was created already holding. Unmounting the wrapper at idle would therefore cost the first
"Saving soon…" of every session — a real R041 regression traded for a cosmetic fix.

A third option is strictly better than either:

| | empty box gone | first transition announced |
|---|---|---|
| `v-if` on the wrapper | yes | **no** |
| indicator always renders something | **no** | yes |
| **chrome-only gate (this plan)** | **yes** | **yes** |

The "box" IS the chrome — `sticky top-0 z-10 mb-3 flex items-center gap-2 rounded-md border
border-gray-800 bg-gray-900 px-4 py-2`. Strip all of it at idle and what remains is an empty block
element containing an empty block element: **zero height** (an empty block box generates no line
boxes, so `text-xs`'s line-height contributes nothing), zero border, zero background, zero margin, no
sticky positioning — nothing pinned, nothing visible, and no layout shift when it later fills. The
owner's complaint is fully answered and the live region survives.

This diverges *mechanically* from `SlideGrid`'s `v-if` while honoring the same rule, and the code
comment must say so plainly rather than implying the two are identical — a future reader who greps for
the E5 pattern needs to find the reason this one is different sitting right there.

## One predicate, exhaustively proven to agree

The gate needs to answer "will the indicator render anything?", and the naive version of that answer
is a second copy of the indicator's branch list living in a different file — the two-disagreeing-fields
shape this codebase keeps getting bitten by (Phase 28's two competing order fields; Phase 33's
partially-applied cascade).

So the predicate is **exported from `src/stores/saveStatus.ts`**, beside the `SaveStatusEntry` type it
reads and the `GENERIC_ERROR_TEXT` constant that already lives there for exactly this reason (WR-01,
32-REVIEW: *"module-level so both the toast fallback AND SaveStatusIndicator's inline-error fallback
share the identical string"*). Agreement is then asserted across **every** member of `AutoSaveStatus`
(`useAutoSave.ts:3` — `'idle' | 'pending' | 'saving' | 'saved' | 'error'`, five members, confirmed by
direct read).

### ★ The enumeration must be compiler-enforced, and a typed array is NOT that

`const statuses: AutoSaveStatus[] = ['idle', 'pending', 'saving', 'saved', 'error']` constrains each
ELEMENT to be a union member. **It does not require the array to contain every member.** That
annotation compiles today and keeps compiling after a sixth status is added and omitted here — the
test would go on passing while the guard it exists to provide quietly stopped existing. That is the
same class of false green `34-VERIFICATION.md` had to correct in this very phase.

The enforceable mechanism is a **total record keyed by the union**, which is already this codebase's
idiom: `slideDisplay.ts:41` (`KIND_BADGE_CLASSES: Record<SlotKind, string>`) and `:232`
(`MENU_ITEM_LABELS: Record<MenuItemKey, string>`) both use it, and both genuinely fail to compile when
a union member has no key. Task 1 builds `ALL_SAVE_STATUSES` the same way and derives the iterable
from its keys. TypeScript here is `~5.9.3`, so either a `Record<AutoSaveStatus, true>` annotation or a
`satisfies Record<AutoSaveStatus, true>` check works; both are missing-key-checked.

And the guard is **demonstrated, not asserted**: the executor temporarily deletes one key, runs the
type gate, records the actual compiler error, and restores it. A pattern that is merely present is
worth less than a pattern observed to bite.

## Forward note — plan 34-07 owns the duplicate-region case

`SaveStatusIndicator` on the SAME `service:{serviceId}` surface id. Because this plan keeps the page's

suppressing this bar while the modal is open, and pins the resulting test-selector ambiguity. Nothing
about that belongs here — this plan runs in wave 1 and `congregationalSlotIndex` does not exist yet —
but the coupling is recorded so neither plan is read in isolation.
