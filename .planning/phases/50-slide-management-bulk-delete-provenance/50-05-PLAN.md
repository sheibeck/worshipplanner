The exact ready-mode resolution ORDER `importedEntryContent` must apply (a strict extension of the
ec217aa logic, not a rewrite):
1. If `innerSlideId` is a synthetic `rendered-page-N` (renderedPageNumberFromIdentity ≠ null) → use N.
   (This is the IMPORTED-slot materializer's own entries; unchanged.)
2. Else if a `renderedPage` reference was supplied (the 50-03 field on a hand-added entry) → use it.
3. Else if `deck.slides.length === resolution.entryCount` (1:1) → the ec217aa positional fallback:
   `idx = deck.slides.findIndex(s => s.id === innerSlideId); pageNumber = idx + 1`. (Legacy entries.)
4. Else → leave pending (no reliable pairing — the multi-image legacy case that this phase can only
   fix for entries re-added after 50-03).
Then `url = renderedUrls?.[pageNumber - 1]`; a still-resolving URL stays a pending placeholder, never
a broken `<img>`. All non-ready modes (parsed/pending/failed) are unchanged.

Legacy-entry decision (50-CONTEXT.md — planner's call): FALLBACK, no migration. Justification: a
one-time migration cannot reliably re-key legacy MULTI-image entries — the very pairing that is
impossible is why they were broken (Fact 1). Single-image legacy entries already resolve via the
positional fallback and keep doing so. Legacy multi-image entries have never worked, so keeping them
on the fallback is no regression; the owner re-adds them (now with R106's bulk remove + re-import) to
get a renderedPage. Keep the positional fallback in place — do not delete it.
