<objective>
R109 — a production deploy is visible to users without a manual cache-clear. Add a `headers`
entry under `hosting` in `firebase.json` so `index.html` is served with a no-cache/revalidate
policy; leave hashed `assets/*` on their existing immutable cache. Confirm no service worker
caches the shell.

Purpose: On 2026-08-10 a production deploy cost real debugging time because browsers ran the
old bundle from a cached `index.html`. A no-cache shell means the browser always re-fetches the
current document, which references the current hashed bundle.

Output: An updated `firebase.json` and an automated test that guards the header (the change is
deploy-gated per the standing NO-DEPLOYS grant, so the test is the in-repo proof).

## Artifacts this plan produces
- `firebase.json` → `hosting.headers` array containing an entry that serves the shell document
  with `Cache-Control: no-cache, no-store, must-revalidate` (or `max-age=0, must-revalidate`).
- `src/__tests__/firebaseHostingHeaders.test.ts` — parses `firebase.json` and asserts the shell
  no-cache header exists and that no header narrows `assets/*`.
</objective>

<task type="auto">
  <name>Task 1: Serve index.html no-cache in firebase.json</name>
  <files>firebase.json</files>
  <read_first>firebase.json (the whole `hosting` block: `public: dist`, the `/api/**` function rewrite, and the `**` → `/index.html` SPA rewrite)</read_first>
  <action>
    Add a `headers` array to the `hosting` object (a sibling of `public`, `ignore`, and `rewrites`)
    per R109 (50-CONTEXT.md LOCKED decision). Add one entry whose `source` targets the served shell
    document and whose `headers` set `Cache-Control` to `no-cache, no-store, must-revalidate` (a
    stricter, valid superset of the PRD's `max-age=0, must-revalidate` — either satisfies R109).

    Use `source: "/index.html"` for the shell entry. Do NOT add any header entry that narrows the
    cache of `assets/**` or other hashed build output — the LOCKED decision is that hashed assets
    keep their existing long/immutable cache, so leaving them unlisted is deliberate, not an
    omission. Keep the existing `public`, `ignore`, and `rewrites` untouched and keep the file valid
    JSON (no trailing commas). The `**` → `/index.html` SPA rewrite stays exactly as is.

    Note for the executor: Firebase evaluates `headers` `source` globs against the incoming request
    path. The `/index.html` entry covers direct loads of the shell. Deep SPA routes (e.g.
    `/services/123`) rewrite to index.html but are matched by the header layer on their own request
    path, not `/index.html`; that behavioral nuance is a deploy-time / human-verify concern captured
    in the phase verification, not a blocker for this config change. Do NOT add a catch-all `**`
    no-cache header to compensate — that would also strip the immutable cache off hashed assets,
    violating the LOCKED decision.
  </action>
  <verify>
    <automated>node -e "const c=require('./firebase.json'); const h=(c.hosting.headers||[]).find(e=>String(e.source).includes('index.html')); if(!h) throw new Error('no index.html headers entry'); const cc=h.headers.find(x=>x.key.toLowerCase()==='cache-control'); if(!cc||!/no-cache|max-age=0/.test(cc.value)) throw new Error('index.html not served no-cache'); const bad=(c.hosting.headers||[]).some(e=>/assets/.test(String(e.source))&&e.headers.some(x=>x.key.toLowerCase()==='cache-control'&&/no-cache|max-age=0/.test(x.value))); if(bad) throw new Error('assets narrowed'); console.log('ok')"</automated>
  </verify>
  <done>firebase.json is valid JSON; hosting.headers has an index.html entry with a no-cache/revalidate Cache-Control; no header narrows assets/* to no-cache.</done>
</task>
