<objective>
Build the super-admin-gated `deleteOrganization` callable that permanently and completely removes a
deactivated church — every Firestore subcollection (via `recursiveDelete`), every cross-collection
reference (`orgNames`, `inviteLookup`, `users/{uid}.orgIds`, and the 5 orgId-keyed top-level collections
`shareTokens`/`serviceShareLinks`/`orgSlugs`/`quarterShares`/`serviceShares`), and every Storage object
under `orgs/{orgId}/…` — and close the `firestore.rules` gap that currently lets a client delete an org
document directly.

Purpose: This is the milestone's highest-risk, irreversible operation (R215-R219, R221). A missed
subcollection or cross-reference leaves permanently orphaned tenant data; a missed rules gap lets a client
bypass the re-verifying callable entirely. Both failure modes are closed here, proven by test.
Output: `functions/src/orgDeletion.ts` (new callable + handler), widened exports in `orgProvisioning.ts`,
`functions/src/index.ts` registering the deployed Function, an unconditional `firestore.rules` delete DENY
on `organizations/{orgId}`, and the accompanying unit + emulator test coverage.
</objective>

  <action>
    In `firestore.rules`'s `match /organizations/{orgId} { ... }` block, the existing line
    `allow write: if isOrgEditor(orgId) && (preservesLifecycleFields() || isSuperAdmin());` currently grants
    an ordinary editor DELETE access to the org doc: `write` bundles create+update+delete, and
    `preservesLifecycleFields()` short-circuits to `true` specifically on delete (`request.resource == null`
    — its own comment reads "Delete: nothing being written, nothing to restrict"). A bare new
    `allow delete: if false;` added alongside this `write` rule would NOT actually deny anything — Firestore
    evaluates every matching `allow` clause for an operation with OR semantics, so `write`'s existing grant
    for delete would still win. The fix is to narrow scope, not just add a rule:

    1. Change that line from `allow write: ...` to `allow update: ...` (identical condition body, only the
       operation keyword changes) — this removes delete from that rule's coverage entirely. `updateDoc`
       calls map exactly to Firestore's `update` operation, so every existing test exercising this line via
       `updateDoc(...)` (the T-76-10/T-76-06 lifecycle-field guard tests) is unaffected.
    2. Immediately after the existing `allow create: ...` rule in the same block, add a new, deliberately
       UNCONDITIONAL rule: `allow delete: if false;` — no `isSuperAdmin()` exemption (77-RESEARCH.md
       Pitfall 5: the only legitimate deletion path is the Admin-SDK `deleteOrganization` callable, which
       bypasses rules entirely and needs no exemption). Add a short comment above it explaining both why it
       is unconditional AND why the `write`→`update` narrowing above was necessary for this line to have any
       effect at all (the load-bearing reason, for future maintainers).

    Confirm no client code path anywhere in `src/` calls `deleteDoc` on `organizations/{orgId}` itself
    (only on its subcollections, which have their own independent rule blocks and are unaffected) — this

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → `deleteOrganization` callable | Untrusted `orgId`/`confirmName` input crosses into Admin-SDK-privileged, cross-tenant-capable code |
| Client → `firestore.rules organizations/{orgId}` | Untrusted client attempts a direct document delete, bypassing the re-verifying callable entirely |
| `deleteOrganizationHandler` → Firestore/Storage Admin SDK | Privileged calls that bypass `firestore.rules`/`storage.rules` entirely once inside the handler |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-77-01 | Elevation of Privilege | `deleteOrganizationHandler` caller gate | critical | mitigate | `assertSuperAdminCaller` (claim check + independent `superAdmins/{uid}` Firestore re-read) runs FIRST, before any org data is read — identical gate to the 4 existing callables, never forked |
| T-77-02 | Tampering | `confirmName` verification | high | mitigate | Server independently re-reads `organizations/{orgId}.name` and compares against the caller-declared `confirmName` with strict `===` — the client's echo alone proves nothing; closes "delete the wrong org via a mis-click or a scripted call with a guessed name" |
| T-77-03 | Tampering / Denial of Service (orphaned tenant data) | Cascade read/delete ordering | high | mitigate | Read-before-delete ordering (members, `inviteLookup`, `orgNames` guard, and the 5 extra collections all captured BEFORE `deleteFiles`/`recursiveDelete` fire) — proven by a unit test asserting call order via a shared spy sequence |
| T-77-04 | Tampering | `firestore.rules organizations/{orgId}` client delete | critical | mitigate | Unconditional `allow delete: if false;` with the `write`→`update` narrowing fix (Task 2) so no other rule implicitly grants delete — proven by emulator DENY for both an ordinary editor and a super-admin client context |
| T-77-05 | Repudiation | `deleteOrganizationHandler` | medium | mitigate | A single audit log line records `orgId`, org `name`, and `callerUid` before the destructive cascade begins (step 6); the returned summary is the durable, UI-surfaced record of what was removed (a dedicated audit-log collection is deferred per REQUIREMENTS Future) |
| T-77-06 | Tampering (deactivate/delete race) | `active` eligibility gate | high | mitigate | The handler reads `organizations/{orgId}.active` fresh at the START of every call (never a stale client snapshot); a reactivate landing between dialog-open and callable execution is caught by this live read, mirroring `setOrgActiveHandler`'s same-state-aware fresh read |
| T-77-07 | Information Disclosure (orphaned public share docs) | `shareTokens`/`serviceShareLinks`/`orgSlugs`/`quarterShares`/`serviceShares` | medium | mitigate | The cascade explicitly queries-and-deletes all 5 orgId-keyed top-level collections rather than leaving them as an accepted residual risk — closes 77-RESEARCH.md Pitfall 2 / Open Question 1 per the owner's "everything associated with it" framing |
| T-77-08 | Tampering / Denial of Service (cross-tenant orphan on retry) | `arrayRemove` + orgId-scoped queries | high | mitigate | Every write is scoped to the captured `orgId` and its own member uids; `arrayRemove(orgId)` (never an overwrite) on `users/{uid}.orgIds` preserves other memberships; every cross-reference query filters `where('orgId','==',orgId)` so a retry can never touch another org's data — proven by the idempotent-retry unit test |
| T-77-SC | Tampering | npm/pip/cargo installs | n/a | accept | No new packages introduced this phase (77-RESEARCH.md Package Legitimacy Audit: not applicable — `firebase-admin`/`@google-cloud/storage` already installed and used elsewhere) |

All high/critical-severity threats above are mitigated, not accepted — none are deferred.
