## Layout

Extend `src/views/OwnerConsoleView.vue` in place. Do not create a new route or a new shell.

```
<AppShell>
  <div class="px-6 py-8 max-w-4xl">
    [existing] Page header — "Owner Console"
    [existing] Super-admins roster card (Phase 68 — untouched by this phase)

    "Platform configuration" section (REPLACES the Phase 68 dashed placeholder card):
      - Section heading + single global provenance stamp (see Provenance below)
      - Cleanup card
      - AI Proxy card
      - Messaging card
      - Sender card
      - Deploy-time settings note (small, dashed, informational — see below)
  </div>
</AppShell>
```

- Each config card reuses the exact card shell already used by every `SettingsView.vue` section:
  `rounded-lg bg-gray-900 border border-gray-800 p-4 mt-6` (first card in the group may use `mb-6`
  before it if directly following the roster card — mirror the existing `mt-6` cadence between
  cards).
- Card header: `<h2 class="text-sm font-semibold text-gray-300 mb-3">{Area}</h2>`.
- Every card leads with one short explanatory paragraph (`text-xs text-gray-400 mb-3`) BEFORE its
  fields — mirrors the "AI Features" / "Messaging" cards in `SettingsView.vue`, which explain before
  offering the control. Owners are not developers; every knob gets one plain-English sentence.
- Field order within each card follows the order these knobs are declared in `AppConfig`
  (`functions/src/appConfig.ts`) — see Component Inventory below for the exact per-card field list.

### Section-level provenance (resolved design decision)

`AppConfig` (functions/src/appConfig.ts) carries exactly **one** top-level `updatedBy`/`updatedAt`
pair — not one per area. Rendering a stamp on all four cards would either require a functions/type
change (out of scope — Phase 69 is closed) or show the identical value four times, falsely implying
per-area granularity that does not exist. Resolution: show **one** global stamp, once, directly under
the "Platform configuration" heading and above the four cards:

```html
<p v-if="appConfig.updatedBy" class="text-xs text-gray-500 mb-4">
  Last changed by {{ appConfig.updatedBy }} at {{ formatStamp(appConfig.updatedAt) }}
</p>
```

- If `appConfig/global` has never been saved through this console (`updatedBy`/`updatedAt` absent),
  render **nothing** — no placeholder text, no "—". A fresh/never-touched doc is a safe, expected
  state (R182); inventing a stamp for it would be misleading.
- `updatedBy` is written as the saving super-admin's **email** (`authStore.user?.email`), not their
  uid — cheap (already in the client session, per CONTEXT.md's "resolve uid → display name/email
  where cheap"), no extra lookup required.
- `updatedAt` renders as `toLocaleString('en-US', { month: 'short', day: 'numeric', year: 'numeric',
  hour: 'numeric', minute: '2-digit' })` — e.g. `Aug 20, 2026, 3:45 PM`. This extends (does not
  replace) the date-only `formatDate` helper already in `OwnerConsoleView.vue`, which is used
  unchanged for the roster's "Granted" column.
- Every save action (any field, any card) overwrites this single stamp with the current user/time —
  expected "last write wins" behavior, consistent with this app's rejection of real-time
  collaborative editing elsewhere (FEATURES.md Anti-Features).

## Component Inventory

### Cleanup card

Intro copy: *"These control the four scheduled data-cleanup jobs (media, PPTX renders, backgrounds,
PPTX sources). Turning a cleanup ON uses a dry-run safety flow — coming in a future release. Below you
can adjust how long each type of data is kept and the most it can delete in one run."*

| Field | AppConfig path | Control | Editable this phase? |
|-------|----------------|---------|----------------------|
| Delete media after inactivity | `cleanup.mediaEnabled` | read-only toggle | **No** |
| Delete orphaned PPTX renders | `cleanup.pptxRenderEnabled` | read-only toggle | **No** |
| Delete orphaned backgrounds | `cleanup.backgroundEnabled` | read-only toggle | **No** |
| Delete orphaned PPTX sources | `cleanup.pptxSourceEnabled` | read-only toggle | **No** |
| Media retention (days) | `retention.mediaDays` | number, explicit Save | Yes |
| Orphan render staleness (hours) | `retention.orphanRenderStaleHours` | number, explicit Save | Yes |
| Background retention (days) | `retention.backgroundDays` | number, explicit Save | Yes |
| PPTX source retention (days) | `retention.pptxSourceDays` | number, explicit Save | Yes |
| Max deletions per run | `deleteCapPerRun` | number, explicit Save | Yes |

The four read-only toggles render as a visually distinct sub-block, grouped together first (before
the retention numbers), each a disabled checkbox reflecting its live effective value:

```html
<label class="flex items-center gap-3 opacity-60 cursor-not-allowed">
  <input type="checkbox" :checked="config.cleanup.mediaEnabled" disabled
    class="h-4 w-4 rounded border-gray-700 bg-gray-800 text-indigo-600" />
  <span class="text-sm text-gray-200">Delete media after inactivity</span>
  <span class="text-xs text-gray-500 italic">(read-only)</span>
</label>
```

One shared note beneath all four (not repeated per-toggle):

> *"Enabling a cleanup requires a dry-run preview and a confirm step, coming in a future release.
> These switches reflect the current state but can't be changed here."*

### AI Proxy card

Intro copy: *"Rate limits and the allowed AI models for song suggestions, scripture discovery, and
congregational-reading-split features, across every organization."*

| Field | AppConfig path | Control |
|-------|----------------|---------|
| Requests per minute | `aiProxy.rateLimitPerMin` | number, explicit Save |
| Requests per day | `aiProxy.rateLimitPerDay` | number, explicit Save |
| Allowed models | `aiProxy.allowedModels` | comma-separated text, explicit Save (resolved decision — see below) |
| Max tokens per request | `aiProxy.maxTokensCeiling` | number, explicit Save |

**Resolved decision — `allowedModels` is a `string[]`, not covered by CONTEXT.md's boolean/number/
text bucketing.** No new list-editor UI is introduced (zero new dependencies). It renders as one text
input holding a comma-separated list (e.g. `claude-haiku-4-5-20251001, claude-sonnet-4-5`); on save,
split on `,`, trim each entry, drop empties, and require at least one non-blank entry remains
(client-side `required`, mirroring `coerceAllowedModels`'s fail-closed default-list fallback). The
effective-value display for this field wraps normally (no truncation) — a long model list is fully
visible while editing (`long-text` / `overflow` coverage, see UI Considerations).

### Messaging card

Intro copy: *"The scheduled reminder job and the send-volume limits for volunteer email, across every
organization."*

| Field | AppConfig path | Control |
|-------|----------------|---------|
| Run the scheduled messaging cron | `messaging.scheduledCronEnabled` | toggle, saves on change |
| Max recipients per message | `messaging.maxRecipients` | number, explicit Save |
| Max emails per org per day | `messaging.orgDailyEmailQuota` | number, explicit Save |

This is the ONE editable boolean in the whole surface (the other four booleans are the read-only
cleanup flags). It follows the same immediate-save-on-change pattern as `aiEnabled`/`pcEnabled` in
`SettingsView.vue` — no explicit Save button, just the checkbox + inline `Saved!`/error line.

### Sender card

Intro copy: *"The email address volunteer notifications send from. It must belong to a domain
verified in Resend — this app can't verify a domain for you."*

| Field | AppConfig path | Control |
|-------|----------------|---------|
| Display name | `sender.fromName` | text, explicit Save, optional |
| From address | `sender.fromAddress` | text, explicit Save, required, format-validated |

- **No secret field ever appears here** (R192) — `RESEND_API_KEY` is never entered, displayed, or
  fetched by this view. There is nothing to redact because nothing secret is ever requested.
- `fromAddress` format check reuses the SAME lax shape check already established by
  `OwnerConsoleView.vue`'s own `isValidEmailFormat` (contains `@`, contains `.`, non-empty, no
  whitespace) — deliberately not a new/stricter regex, for consistency with the one email-format
  check this codebase already has in this exact file.
- **Resend-verified-domain warning (non-blocking):** after format validation passes, check the
  address's host against a small deny-list of known-unverifiable Firebase-managed hosts:
  `/\.web\.app$/i` and `/\.firebaseapp\.com$/i` (the two Firebase Hosting default domains named in
  `functions/src/index.ts`'s own comment and R192). If matched, show — do not block Save —
  `⚠ This domain can't be verified in Resend (Firebase-managed, no DNS access). Emails from it will
  fail to send until you configure a custom domain.` in amber/yellow text (`text-yellow-500`, the
  only new-ish color usage in this contract — see Color below), directly under the input.
  This is deliberately narrow (only the two named unverifiable hosts) rather than guessing at every
  free-mail provider — matching R192's explicit scope.

## Deploy-time settings note (R185 display — included, per CONTEXT's "include if cheap and clear")

**Resolved design decision:** this note does **not** attempt to show live current values. `AI_PROXY_
MAX_INSTANCES`, `GLOBAL_MAX_INSTANCES`, and the render-service caps are read from `process.env` at
Cloud Functions module load — there is no client-reachable path to their live value without new
plumbing (a new callable), which is explicitly out of scope this phase (zero new dependencies). Showing
a *stale hardcoded* number would be actively misleading — worse than not showing one. The note is
therefore purely informational, with no data binding:

```html
<div class="rounded-lg bg-gray-900 border border-gray-800 border-dashed p-4 mt-6">
  <h2 class="text-sm font-semibold text-gray-500">Deploy-time settings (requires redeploy)</h2>
  <p class="text-xs text-gray-600 mt-1">
    Function instance limits (AI proxy, global, and render-service concurrency caps) are set in
    deploy-time environment configuration, not here. Changing them requires a redeploy — see
    functions/.env and render-service deploy config.
  </p>
</div>
```

Reuses the exact dashed-border/muted-text visual language `OwnerConsoleView.vue` already used for its
Phase 68 placeholder card — signals "not interactive" using an established pattern rather than a new one.

## States & Interactions

### Page-level (config load)

| State | Trigger | Rendering |
|-------|---------|-----------|
| Loading | Before the first `appConfig/global` `onSnapshot` callback fires | The four cards render `Loading configuration...` (mirrors `OwnerConsoleView.vue`'s existing `Loading roster...` text/placement) instead of fields |
| Load error | `onSnapshot`'s error callback fires (permission-denied, network) | Cards replaced with `Couldn't load platform configuration. Refresh the page and try again.` — page stays otherwise usable (roster card unaffected) |
| Loaded, doc missing | Snapshot resolves, `exists()` is `false` | Not an error — every field renders its DEFAULT_APP_CONFIG value labeled `(default)`, per R182. This is the expected first-ever-visit state. |
| Loaded, doc present | Snapshot resolves with data | Deep-merge per leaf; each field shows its resolved value, `(default)` badge only on leaves absent from the raw doc |

### Per-field (editable number/text fields)

Mirrors `SettingsView.vue`'s org-name/slug pattern exactly — an explicit Save button, not autosave
(autosave-on-keystroke is unsafe for a field with min/max validation, since intermediate keystrokes
are transiently invalid):

1. Input is pre-filled with the current EFFECTIVE value on load (and re-synced via a `watch` if the
   store's resolved config changes from elsewhere, matching every existing `watch(() =>
   authStore.settings.X, ...)` re-sync block in `SettingsView.vue`).
2. `(default)` badge shown next to the label while the RAW leaf is absent from the doc; disappears the
   moment that leaf is explicitly saved (see "`(default)` badge" note below).
3. Save button: `bg-indigo-600 hover:bg-indigo-500 disabled:opacity-60 ... px-4 py-2 text-sm font-medium`
   (identical classes to every existing Save button). Disabled until (a) the input passes its
   min/max/required validation AND (b) the value differs from the current effective value (dirty
   check) — identical `isSaveDisabled` shape to `onSave`/`onSaveSlug`.
4. Button label cycles `Save` → `Saving...` → `Saved!` (2s, `setTimeout`) → `Save`, identical triad to
   every existing field in this codebase.
5. Inline validation error (red, `text-red-400 text-sm mt-2`) appears the moment the input fails
   bounds — shown even before Save is clicked, so an owner sees why Save is disabled, not just that it
   is.
6. Save failure (network/rules): `text-red-400 text-sm mt-2`, generic `Failed to save. Please try
   again.` — identical copy already used by every save handler in `SettingsView.vue`.

### `(default)` badge — precise semantics (implementation-facing)

The badge reflects whether the **raw Firestore leaf is present**, not whether the resolved value
happens to numerically equal the default. Comparing resolved-value-equality would mislabel a
deliberate "set it back to 30" as still-default, which is dishonest provenance. The client must check
presence in the pre-merge raw doc snapshot for each leaf, not the post-merge resolved value.

### Per-field (editable toggle — `messaging.scheduledCronEnabled` only)

Immediate save on change, identical to `aiEnabled`/`pcEnabled`/`messagingEnabled` in `SettingsView.vue`:
checkbox `@change` fires the write directly (no separate Save button), inline `Saved!`
(`text-green-400`)/error line appears and the `Saved!` line clears after 2s. On save failure, the
checkbox reverts to its prior value (`= !newValue`), matching every existing toggle handler.

### Read-only cleanup toggles

No interaction at all — `disabled`, `opacity-60 cursor-not-allowed`, no click handler, no save state.
Always reflects the live effective value (read path only).

### Data-write mechanics (implementation-facing pitfall — resolved here, not left for the executor to discover)

`organizations/{orgId}` (what every existing `SettingsView.vue` write targets) is guaranteed to exist —
created at signup — so every existing write uses `updateDoc`. **`appConfig/global` has no such
guarantee** (R182: an absent doc is a valid, safe, expected state). `updateDoc` throws `not-found` on a
document that doesn't exist yet. Every write in this phase MUST use `setDoc(doc(db, 'appConfig',
'global'), { ...dotPathFields }, { merge: true })`, not `updateDoc` — otherwise the very first save any
super-admin ever makes throws. Dot-path leaf keys (e.g. `'retention.mediaDays'`) work identically under
`setDoc(..., { merge: true })` as they do under `updateDoc`, so no other part of the established
mirror-write pattern changes.

## Accessibility

- Every input has a visible `<label>` (`text-xs text-gray-400 mb-1`) — no placeholder-as-label
  pattern, matching every existing field in `SettingsView.vue`.
- Every toggle (read-only cleanup flags and the one editable `scheduledCronEnabled` checkbox) is
  wrapped in a full-row `<label class="flex items-center gap-3 ...">` so the clickable/tappable area
  extends across the whole label row, not just the 16px visual checkbox box — identical to every
  existing toggle in this codebase. This is the established mitigation for the visually-small
  (`h-4 w-4`) checkbox control; it is not changed or newly invented for this phase.
- Save buttons and number/text inputs use the SAME `px-4 py-2`/`px-3 py-2` sizing as every existing
  button/input in the app (~36–40px effective height, slightly under the 44px ideal). This is an
  accepted, pre-existing app-wide convention — introducing a larger control size just for this one
  page would create visual inconsistency worse than the minor hit-area shortfall, and would violate
  the "no new design system" constraint. Not a regression introduced by this phase.
- Focus states: `focus:outline-none focus:ring-1 focus:ring-indigo-500` on every input/select,
  identical to the rest of the app — never removed without a replacement indicator.
- The read-only cleanup toggles use native `disabled` (not just visual styling), so they are correctly
  excluded from the tab order and announced as disabled by assistive tech — not a purely-cosmetic
  read-only state.
- Error and warning text (`text-red-400`, `text-yellow-500`) is never the ONLY signal — each is paired
  with a text message (not a color-only indicator), consistent with the rest of the app.

## Resolved Design Decisions (this document)

These were not explicitly answered by `70-CONTEXT.md`/`REQUIREMENTS.md`/`FEATURES.md` and are
resolved here under the v1.9 autonomy grant, each consistent with the existing app:

1. **"Toggle" means the existing checkbox styling**, not a new pill/switch component. `70-CONTEXT.md`
   says "booleans → toggle"; the app has never had a switch component, and introducing one here would
   violate "no new UI library." Every boolean (editable and read-only) uses the identical
   `h-4 w-4 rounded border-gray-700 bg-gray-800 text-indigo-600` checkbox already used throughout
   `SettingsView.vue`.
2. **Global, not per-area, provenance stamp** — forced by `AppConfig`'s single top-level
   `updatedBy`/`updatedAt` pair (see Layout § Section-level provenance).
3. **`allowedModels` (a `string[]`, not covered by CONTEXT's boolean/number/text bucketing) is a
   comma-separated text field** — no new list-editor UI (see Component Inventory § AI Proxy card).
4. **The Deploy-time settings note shows no live values** — no client-reachable data source exists for
   them without new plumbing, which is out of scope; a stale hardcoded number would be worse than an
   honest static note (see Deploy-time settings note section).
5. **`sender.fromAddress` format validation reuses `OwnerConsoleView.vue`'s existing lax
   `isValidEmailFormat` check**, not a new/stricter regex — consistency over strictness, matching the
   one precedent this exact file already set.
6. **Numeric upper bounds** (per Phase 69 review Info-2 — the functions `coerce*` layer has no upper
   bound) are declared explicitly per field:

   | Field | Min | Max | Required | Integer |
   |-------|-----|-----|----------|---------|
   | `retention.mediaDays` | 1 | 365 | yes | yes |
   | `retention.orphanRenderStaleHours` | 1 | 720 | yes | yes |
   | `retention.backgroundDays` | 1 | 365 | yes | yes |
   | `retention.pptxSourceDays` | 1 | 365 | yes | yes |
   | `deleteCapPerRun` | 1 | 5000 | yes | yes |
   | `aiProxy.rateLimitPerMin` | 1 | 1000 | yes | yes |
   | `aiProxy.rateLimitPerDay` | 1 | 100000 | yes | yes (also: must be ≥ `rateLimitPerMin`, inline error `Daily limit must be at least the per-minute limit.` if violated) |
   | `aiProxy.maxTokensCeiling` | 1 | 200000 | yes | yes |
   | `messaging.maxRecipients` | 1 | 5000 | yes | yes |
   | `messaging.orgDailyEmailQuota` | 1 | 50000 | yes | yes |
   | `sender.fromName` | — | 100 chars | no | n/a |
   | `sender.fromAddress` | — | — | yes | n/a (email-shape check instead) |

7. **Write mechanics: `setDoc(..., { merge: true })`, never `updateDoc`**, for `appConfig/global` —
   see States & Interactions § Data-write mechanics. This is the single most load-bearing
   implementation note in this contract; getting it wrong breaks every save on a fresh deploy.
8. **Server-side field-level range validation in `firestore.rules` is NOT added this phase** — per
   `70-CONTEXT.md`'s explicit call: the Phase 69 `coerce*` layer is the authoritative backstop (a
   malformed/out-of-range value can never widen authority), and Phase 68's rules already gate WHO may
   write `appConfig/*` to `isSuperAdmin()`. Client validation (this contract) + the coerce layer is the
   full defense; adding per-field range checks to rules is optional future hardening, not required here.
9. **Component decomposition (recommended, not mandated):** split into `src/components/admin/
   CleanupConfigCard.vue`, `AiProxyConfigCard.vue`, `MessagingConfigCard.vue`, `SenderConfigCard.vue`,
   plus two small reusable field components (`ConfigNumberField.vue`, `ConfigTextField.vue`) to avoid
   repeating the label + `(default)` badge + input + Save-button + status-triad block eleven times.
   `OwnerConsoleView.vue`'s existing roster subscription (component-local, no store) is untouched.
10. **New Pinia store recommended:** `src/stores/appConfig.ts` — `onSnapshot` on `appConfig/global`,
    exposing `config` (the resolved/merged `AppConfig`), `rawDoc` (pre-merge, for the `(default)`
