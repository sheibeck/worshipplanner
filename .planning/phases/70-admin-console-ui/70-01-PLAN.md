<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| super-admin browser -> Firestore `appConfig/global` | The store's `saveField` write crosses here; the client is not the security boundary |
| client value -> Cloud Functions read (Phase 69) | A written value is later read + coerced server-side; the client cannot dictate the trusted shape |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-70-02 | Elevation of Privilege | `store.saveField` write to `appConfig/global` | high | mitigate | Write authority is enforced by Phase 68 `firestore.rules` gating `appConfig/*` to `isSuperAdmin()` (claim-only) — server-side and authoritative; this store is a convenience path only, not re-implementing the gate. No new rules this phase (client-only, per v1.9 grant). |
| T-70-03 | Tampering | numeric/text field values written via `saveField` | high | mitigate | Client min/max/required validation in the field components is UX-only; the Phase 69 `coerce*` layer is the authoritative backstop (enable-flags + model allow-list fail closed, rate limits capped-open), so a value that bypasses the client cannot widen authority at read time. |
| T-70-01 | Information Disclosure | `saveField` payload | medium | mitigate | `saveField` writes only the caller's own `user.email` as `updatedBy` (already in-session, no lookup) and never any secret; the `AppConfig` shape carries no credential field to leak. |
| T-70-SC | Tampering (supply chain) | npm installs | low | accept | No package installs this phase — zero new dependencies (RESEARCH Package Legitimacy Audit: not applicable). |
</threat_model>
