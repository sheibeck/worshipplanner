<objective>
Remediate **SEC-ISO-02 (High):** when an org editor removes a member, Firestore access is cut
immediately, but Storage access is claim-only and survives on the already-issued, unrevoked auth token
for up to ~55 minutes. `syncOrgMembershipClaimHandler`
(`functions/src/orgMembershipClaims.ts:245-319`) updates/clears the claims on member-doc delete but
never forces re-authentication. Fix: add `getAuth().revokeRefreshTokens(uid)` to the handler's "clear"
branch, mirroring the established pattern in `orgProvisioning.ts:461` (try/caught, logged on failure,
never blocking the claim write).

The **primary, emulator-independent proof** is a functions-level unit test asserting
`revokeRefreshTokens` is called with the removed uid on the clear path (mirrors
`orgProvisioning.test.ts`'s `revokeRefreshTokens` assertions). The **secondary** proof is a Storage
ALLOW-case test (a REMAINING member of the same org still has read/write access, proving the revoke
targets only the removed uid) — authored in `src/storage.rules.test.ts` and, if the Storage emulator
(127.0.0.1:9199) is unreachable this session, committed with a clear run-when-available note. The
documented cross-service `exists()` Storage-emulator limitation (CLAUDE.md) MUST NOT block this phase.

Purpose: close the stale-token authz window on member removal. Output: modified
`orgMembershipClaims.ts` + its unit test + an authored Storage ALLOW-case test, built/tested/committed,
UNDEPLOYED.

**This plan performs NO deploy.** The orchestrator handles any production deploy AFTER phase
verification, with an explicit per-deploy owner confirmation. This plan does NOT run `firebase deploy`,
`gcloud`, or `firebase deploy --only functions`. It only rebuilds/tests locally.
</objective>
