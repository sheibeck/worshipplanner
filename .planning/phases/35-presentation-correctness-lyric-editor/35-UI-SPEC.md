# Phase 35 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** this phase does not touch the Service Order tab rebuild or the contextual action bar
(R067/R068 → Phase 36), does not reach Phase 34's unmounted `CongregationalEditor.vue`, and does not add
slide-background rendering to `PresentationViewer.vue` (§6 records this explicitly rather than leaving it
silently unaddressed). Two unrelated clusters: (1) **presentation correctness** — delete one leaking
render line (R059), verify a bracket that already appears to exist on both assembly paths rather than
duplicate it (R060), and thread a start index that already exists in `SlidesTab.vue`'s state through to
`PresentationViewer.vue` (R061); (2) **lyric editor** — convert `LyricPasteDialog.vue` from a
Teleport-modal into an inline region of `SongLyricEditor.vue`, adding a missing-copyright warning that
blocks the paste unless overridden (R065, R066).

**★ This phase has real wireframe backing for R065/R066 — the other three (R059–R061) have none.**
`docs/design/slides-tab.dc.html`'s **Turn 2 — Song lyrics editor** section (lines 358–654, the file's
own "State 1/2/3" sequence) is the specified design for the inline paste treatment — see §4. R059–R061
touch no surface the mockup depicts (a presented slide's chrome, a copyright slide's assembly, a
start-index computation) and are original, minimal design work by this spec, exactly as 33-UI-SPEC
recorded for its own unwireframed surfaces.

**Upstream decisions this spec implements, not re-opens (35-CONTEXT.md):** R059 is a render fix, not a
model change — `sectionLabel` stays on `LyricSlide`, only `PresentationViewer.vue:53`'s render of it is
removed; R060 may already be satisfied on both assembly paths — confirm by test, do not add a second
emission; R061 starts at the highlighted group's first slide when nothing is highlighted, never slide 0
of the whole deck; `LyricPasteDialog.vue`'s CCLI parsing logic is kept, not rewritten; exactly one paste
surface exists once this ships — no modal fallback.

## Phase-Specific Component Contracts

### 1. R059 — `PresentationViewer.vue`'s lyric-slide label

**The fix is a deletion, not a `v-if="false"`.** Remove the entire `<p data-testid="presentation-label">`
block at `:48-54` (the `LyricSlide.sectionLabel` render) from the `slideKind === 'lyric'` template branch
only. The `LyricSlide.sectionLabel` field itself is untouched — `slideDisplay.ts:95,143`'s grid-organization
consumers keep working unchanged, exactly as 35-CONTEXT.md specifies ("labels 'exist only to organize
slides within a group' — describes precisely that surviving use").

**Scoped to the `lyric` branch only.** The scripture branch's `presentation-label` (reference text, `:87-91`)
and the text branch's `presentation-label` (title, `:126-131`) are NOT organizational labels — they are the
slide's actual content — and are out of scope for R059. Do not remove them; R059 targets exactly one line.

> **Superseded in part by quick task `260805-kzd` (2026-08-05, owner-decided).** See
> `.planning/quick/260805-kzd-remove-slide-labels-unify-slide-text-size/260805-kzd-PLAN.md`. The text
> branch's title label was deleted outright under its D2 — the owner reported never using it, so this
> paragraph's "do not remove them" no longer holds for that half. The scripture branch's reference
> SURVIVES, under D1, but as body-treatment content under `data-testid="presentation-scripture-reference"`
> rather than as a label — the assembler builds scripture slides with an empty passage string, so a
> reference-only slide must still project something. The congregational speaker tags were unified to the
> same body treatment in the same pass, under D3, keeping their words and testids.

**Projector legibility note (per the additional context's own framing):** the presented slide is a
projector surface, not app chrome — the remaining lyric body text (`text-5xl`, `:57`) already has no
legibility dependency on the removed label; it was always the dominant visual element on the slide.
Removing the label leaves more, not less, of the frame available to the lyrics themselves.

### 2. R060 — Copyright-slide bracket (verification, not new markup)

### 3. R061 — Present start index (data-threading, no new visual states)

**No new visual affordance.** `SlidesTab.vue` already tracks `selectedSlotId`/`selectedSlideId`
(`:186-187`). The `present` emit (`:19`) gains a computed start-index payload — mapped from whichever
assembled slide corresponds to the current selection, or the selected group's first slide when nothing is
selected within it, or index 0 when no group is selected at all (E3 `error` resolution above).
`ServiceEditorView.vue` threads this through a new prop on `PresentationViewer` (naming and exact
threading mechanism are Claude's Discretion per 35-CONTEXT.md), which seeds `currentIndex` on mount
instead of the current hardcoded `ref(0)` (`PresentationViewer.vue:318`).

**Visually: presenting mid-deck must look identical to presenting from the start.** No "you started
partway through" badge, no distinct entry transition, no altered chrome — the existing progress pill
(`{{ SERVICE_SECTION_LABELS[section] }} · {{ n }} / {{ m }}`, `:266-271`) already communicates position
within the whole deck and needs no augmentation.

then optional warning, then footer) replaces the old dialog's side-by-side `md:flex-row` textarea/preview
split** — that split was only viable at the modal's `max-w-4xl` width; inlined into a 480px panel it
cannot fit, and the wireframe's own narrower panel already shows a stacked flow, not a side-by-side one.

**Header swap** — when paste mode is active, `SongLyricEditor.vue`'s existing header row (`:4-27`,

**Body region** — replaces the song-background row, the section-rows list, and the add-section row (all

  field** — checking it alone flips `canConfirm` from false to true with nothing else required, so the
  paste stays completable in every case.

  `<input type="checkbox" data-testid="paste-copyright-override">`, labelled `Add anyway — I'll enter
  credits later` (the wireframe's own copy, unchanged). Rendered inside the warning card, directly below
  its body text — it only ever appears when the warning card does, since a present CCLI number removes
  the block it exists to lift. `overrideCopyright` is a local `ref(false)`, reset to `false` whenever
  `pasteMode` closes/reopens (same reset timing as `rawText`) and never persisted onto the saved
  document — it only gates this one confirm action.
- **No manual copyright-entry field.** R065 says "detects… and warns," not "offers an inline credits

  transcribed; a user who wants to add credits pastes again with the CCLI block included, or edits the
  song's `copyright-display` block that already exists read-only lower in the normal Sections view
  (`SongLyricEditor.vue:232-248`, unchanged by this phase).
- **`onPasteConfirm`** wraps the existing `onConfirm` logic (parse → `normalizeParsedSections` →

  untouched (E4 `error` backstop) instead of the current implementation's bare `try/finally` with no
  catch. On success, `pasteMode = false` and the normal Sections view re-renders with the new sections —
  identical to today's `onPasteSaved` behavior.
- **`LyricPasteDialog.vue`'s file fate is Claude's Discretion for the plan** — whether its logic is
  inlined into `SongLyricEditor.vue` directly or kept as a child component mounted inline (no Teleport, no
  backdrop, no `fixed`/`z-50` positioning) is an implementation detail this contract does not prescribe;
  what is prescribed is the rendered markup/copy/states above and that exactly one paste surface exists
  afterward (35-CONTEXT.md: "the modal does not survive as a fallback").

### 5. Locked-service behaviour — does not apply to this surface

**`SongLyricEditor.vue` is mounted only from `SongSlideOver.vue`** (the Songs catalog editor), never from
`ServiceEditorView.vue` or any service-scoped route — verified: no `serviceLocked` prop exists anywhere
in `SongSlideOver.vue`'s or `SongLyricEditor.vue`'s prop chain today, and this phase adds none. **The
Phase 31 lock concept ("removed, not disabled-and-explained" on a planned/exported service) does not
apply here at all** — a song's lyrics are canonical catalog data (R054), editable independent of any
individual service's lifecycle status. The paste region (like every other control in this file) is gated
only on `isEditor` (`authStore.isEditor`, `SongLyricEditor.vue:306`), unchanged by this phase. Do not add
a lock banner or lock-aware gating to the paste region — there is no lock state to react to.

### 6. Slide backgrounds in `PresentationViewer.vue` — explicitly OUT OF SCOPE

Phase 33 stores `backgroundImageUrl` at three levels (slide/group/song) and resolves it into
`AssembledSlide.backgroundImageUrl`/`backgroundSource`, but `PresentationViewer.vue` renders no
background layer — correct at the time (Phase 33 scoped presentation out), but this phase's own name is
"Presentation Correctness," so 35-CONTEXT.md requires the decision be made explicitly rather than settled
by omission. **Decision: out of scope for Phase 35.** None of R059/R060/R061/R065/R066 mentions
backgrounds, and adding background compositing here would turn a correctness phase into a rendering
feature with its own contrast/legibility/scrim design work (font-over-image legibility, crop behavior,
video-slide interaction per 33-UI-SPEC §9's own video carve-out) — exactly the kind of scope-widening
33-UI-SPEC's own scope reminder already declined to do. Recorded as a deferred idea in 35-CONTEXT.md;
this UI-SPEC adds no markup, no prop, and no `background-image` CSS to `PresentationViewer.vue`.

## Accessibility Note

- **Paste-mode back link:** a real `<button>` (not a bare `<span>`), so it is keyboard-reachable and
  announced as interactive — matches this codebase's own established preference for real buttons over
  clickable spans wherever the element triggers a state change (33-UI-SPEC §1's own reasoning for why the
  card root became `role="button"` rather than staying a clickable non-interactive element applies in
  spirit here, though this element has no nesting constraint forcing a div substitute).
- **Missing-copyright warning icon:** `aria-hidden="true"` — the adjacent text already states the warning
  in full; the icon is decorative reinforcement, matching the identical pattern at
  `ServiceEditorView.vue:278-281`.
- **Override checkbox:** the `<input type="checkbox">` is wrapped in a `<label>` with its text as a
  direct sibling, so the checkbox and "Add anyway — I'll enter credits later" form one accessible,
  keyboard-reachable, click-anywhere-on-the-row target with no separate `aria-label` needed — the native
  label/input association covers both mouse and screen-reader interaction.
- **Textarea label:** the instructions paragraph immediately precedes the textarea in DOM order and
  functions as its accessible description for sighted and screen-reader users alike, matching the old
  dialog's own `<label>`-then-`<textarea>` adjacency (not re-declared as a formal `aria-describedby` link,
  since the old dialog never had one either — no regression, no new gap introduced).
- **Save-error line:** plain text, no `aria-live` — a discrete confirm-button action's failure is
  discovered by the user looking at the button they just clicked, not something that needs to interrupt
  focus elsewhere; matches this codebase's existing choice not to make the lock banner or provenance
  captions live regions either (31-UI-SPEC's own stated reasoning).
- **R059 removal:** no accessibility regression — the removed label was visually presented text with no
  separate `aria-label`/`aria-describedby` relationship to anything else on the slide; deleting it removes
  exactly the announced content it visually showed, nothing more.
