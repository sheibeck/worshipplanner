# Phase 43 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** this is a narrow phase. Three surfaces change inside the existing
`src/views/ServiceEditorView.vue` "Service Order" tab: (1) the two add-item palettes (per-section
inline chip row + the bottom "add to the service" chip row), (2) a new shared `body` free-text editor
serving MESSAGE / ANNOUNCEMENTS / MISC, and (3) Message's URL/link fields removed from the UI. Nothing
else in the service editor is redesigned. All values below extend the file's existing, already-shipped
Tailwind vocabulary rather than introducing a new one.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — this is a Vue 3 / Vite project, not React/Next; shadcn (Radix-based) does not apply. No `components.json` or `tailwind.config.*` found in the repo root (Tailwind is configured via CSS, per `.planning/codebase/CONVENTIONS.md`). Confirmed by reading `src/views/ServiceEditorView.vue`: every existing control (palette chips, inputs, badges) is a hand-rolled `<button>`/`<input>` with static Tailwind utility classes — no component library import anywhere in the file. |
| Preset | not applicable |
| Component library | none — custom Vue SFCs, hand-rolled Tailwind utilities |
| Icon library | none (npm) — inline hand-authored SVG paths (Heroicons-style `viewBox="0 0 20 20"` / `24 24`), copy-pasted per use site. This phase needs no new icon: the palette chips are plain text buttons, and the shared `body` textarea needs no icon. |
| Font | System default sans-serif stack (no house font yet — Phase 46 introduces one, and explicitly scopes to "slide surfaces" only). The `body` textarea is an editor control, not a slide surface, so it is unaffected by that later phase either way. |

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Kind label ("Announcements" / "Miscellaneous" / "Message") | 12px (`text-xs`) | 600 (`font-semibold`) | 1.2 (Tailwind default for `text-xs`) — rendered uppercase via the `uppercase tracking-wider` utility, exactly like the existing PRAYER/MESSAGE/HYMN labels |

| Palette chip label | 11px (`text-[11px]`) | 500 (`font-medium`) | 1.2 — matches the file's existing `palette-add-*` / `section-add-*` chips verbatim (arbitrary-value size already established there, not a new token) |

Only 3 sizes are actually in play (12 / 14 / 11), matching the file's existing typographic vocabulary
for this row shape — no new size is introduced.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-gray-900` / `border-gray-800` | Slot-item card surface (unchanged — the row wrapping the new textarea is the same `slot-item` card every other kind already uses) |
| Secondary (30%) | `bg-gray-800` / `border-gray-700` | The `body` textarea's own surface, and the palette chip buttons' resting border — identical to every existing input/chip in the file |
| Accent (10%) | `indigo-400` (text) / `indigo-500` (focus ring) | Reserved for: the textarea's `focus:ring-indigo-500` focus state; the existing "＋ Add item" section link and "＋ Add to the service" label text (both already indigo — untouched by this phase); no other element in this phase's scope gets accent color |
| Destructive | `red-400` (hover) | Reserved for: the existing per-row "Remove element" (×) button's `hover:text-red-400` state only — unchanged by this phase, no new destructive control is added |

Accent reserved for: the two "＋ Add item" / "＋ Add to the service" trigger labels (pre-existing,
untouched) and the shared `body` textarea's focus ring. Nothing else in this phase's scope — the new
palette chips (`Announcements`, `Miscellaneous`) use the same neutral `border-gray-700 text-gray-300`
resting state as every other chip (`Song`, `Scripture`, `Prayer`, `Message`), not accent color. A
palette chip is not a primary action; treating one as such would break the existing 5-chip row's visual
parity the moment a 6th and 7th chip are added.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Palette chip labels (both palettes) | `Announcements`, `Miscellaneous` — full words, Title Case, matching the existing un-abbreviated chip set (`Song`, `Scripture`, `Prayer`, `Message`). **Not** `Misc` — `docs/design/slides-tab.dc.html`'s Turn 3 wireframe uses the abbreviation on an aspirational chip row that includes kinds this phase does not build (Sermon, Video, Slide deck, Offering); this phase's actual palette lives beside `Song`/`Scripture`/`Prayer`/`Message`, none of which are abbreviated, so `Miscellaneous` is the internally-consistent choice. |
| Kind label above the shared body editor | Reuses `slotLabel(slot, index)` verbatim — `Message`, `Announcements`, or `Miscellaneous` — the same function every other kind already renders through (`slotLabel()` in `src/utils/slotTypes.ts`), so this phase adds no second source of the display name. |
| Body textarea placeholder — Announcements | `Announcement details…` |
| Body textarea placeholder — Miscellaneous | `Details…` |
| Body textarea placeholder — Message | `Message notes or outline…` (the field that used to hold only a link now holds whatever text a planner wants the team to see — notes, outline, or a plain reminder) |
| Empty state (read-only / locked view, no `body`) | `{Label} — Empty` — e.g. `Announcements — Empty`, `Miscellaneous — Empty`, `Message — Empty`. Matches the exact existing pattern (`Song — Empty`, `Hymn — Empty`, `Imported Slides — Empty`); italic, `text-gray-400`, matching `HymnSlot`'s and `ImportedSlot`'s empty-state class (majority pattern — 2 of 3 existing empty-state rows use `text-gray-400`, not `text-gray-500`). |
| Error state | None introduced. `body` is free text with no format validation — there is no error state for this phase to define. |
| Destructive confirmation (unchanged heading) | `Remove this element from the plan?` — existing `deleteConfirmHeading`, untouched. |
| Destructive confirmation body — new per-kind names | `elementLabel(kind)` in `ServiceEditorView.vue` needs two new cases so the confirm-body sentence names the right thing instead of falling to the generic `'this element'` default: `ANNOUNCEMENTS → 'this announcement'`, `MISC → 'this miscellaneous item'`. Not adding these is not a functional bug (the `default` case already exists and reads correctly), but it is a copywriting gap next to every sibling kind (`'this song'`, `'this hymn'`, `'this message'`, `'this prayer'`) already having a named case — record as a should-have. |
| Section-band empty-state hint | Unchanged — the existing "Drag an item here, or set its Section to {label}." copy already names no specific kind and needs no update for the new kinds. |

## UI Considerations

Applicable state considerations resolved: 6 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Announcements / Miscellaneous / Message body | ✅ covered | A slot with no `body` (or whitespace-only `body`, checked via `.trim()` — the same convention `isSlotPopulated`'s HYMN branch already uses) is a normal, valid state: the editor shows the empty textarea with its placeholder; the locked/non-editor viewer shows the italic `{Label} — Empty` text documented in the Copywriting Contract. Neither view treats an empty `body` as an error. |
| populated | Announcements / Miscellaneous / Message body | ✅ covered | The editor shows the typed text in the textarea; the locked/non-editor viewer renders it read-only via `whitespace-pre-wrap text-sm text-gray-200`, preserving line breaks the same way the textarea displays them while editing. |
| palette exclusivity | Add-item palette (both instances) | ✅ covered | `HYMN` is removed from both palette button rows (the per-section inline chip row and the bottom "add to the service" row) and from nowhere else — `slotLabel()`, `createSlot()`, and the `HYMN` `v-else-if` render block in the slot list all stay byte-identical. The palette enumerates its own kind list rather than mapping over `SlotKind`, so removing a palette entry cannot accidentally remove `HYMN`'s constructibility or its render path. |
| absence-of-regression | Existing HYMN slots (pre-phase-43 data) | 🧪 backstop | "A pre-existing HYMN slot in a saved service still renders, prints, and presents exactly as before the palette change" — this is the harder half of R084 per 43-CONTEXT.md's own framing ("Proof is an absence-of-regression test... asserting only that the palette lost its entry proves the easy half"). No visual diff tool exists in this repo to auto-verify pixel parity, so this is a held-out test assertion, not a design rule — held out for the executor's test suite, not silently assumed to pass. |
| data-retention (no UI) | `MESSAGE.linkUrl` / `linkUrl.linkLabel` after the URL field is removed | ✅ covered | The fields stay in `NonAssignableSlot`'s type and in Firestore; only the editing UI (the two `<input>`s and the "open link" affordance) is deleted from the MESSAGE branch. A service with a pre-existing Message link keeps that value in storage — nothing renders it, and nothing warns the user it "disappeared," because nothing was removed from the data (per 43-CONTEXT.md, explicitly not a migration and explicitly not a notice-worthy event). |
| overflow / long-text | Body textarea (all three kinds) | 🧪 backstop | Design rule: the textarea is `w-full` inside the row's existing `flex-1 min-w-0` container, uses `resize-y` (vertical-only resize) and no `resize-x`, so long text wraps within the fixed-width row and grows the textarea vertically — never triggers horizontal scroll on the row. This is the intended behavior per the spacing/color tokens above; whether real long-paste text actually behaves this way in the rendered DOM is left as a backstop for the executor's test pass rather than assumed correct from the CSS alone. |
| zero-one-many | Multiple Announcements/Misc items in one service | ✅ covered | No new constraint — the palette can be clicked repeatedly exactly as it already can for `Prayer`/`Message`/`Song`; each click appends a fresh slot via the existing `addSlot()` path with no special-casing needed for the two new kinds. |

## Component Contract (phase-specific, in place of a shadcn registry)

Since no component registry is in play, the executor-facing contract is the exact markup/class shape
expected, so the "one shared `body` editor" decision in 43-CONTEXT.md is unambiguous:

**Palette markup (both locations)** — append two chips in this exact order, immediately after the
existing `Message` chip and in place of the removed `Hymn` chip, using the identical class string every
other chip in that row already uses (static, not computed — satisfies the "static class maps" hard
constraint trivially, since no chip's classes vary by kind):

```html
<button type="button" class="rounded-md border border-gray-700 px-2 py-1 text-[11px] font-medium text-gray-300 hover:bg-gray-800 transition-colors" data-testid="palette-add-announcements" @click="addSlot('ANNOUNCEMENTS')">Announcements</button>
<button type="button" class="rounded-md border border-gray-700 px-2 py-1 text-[11px] font-medium text-gray-300 hover:bg-gray-800 transition-colors" data-testid="palette-add-misc" @click="addSlot('MISC')">Miscellaneous</button>
```

(In the per-section inline chip row, the `data-testid` follows the row's existing per-band convention —
`section-add-announcements-${group.key}` / `section-add-misc-${group.key}` — and the click handler
passes `group.key as ServiceSection` and closes the row, exactly as the `Prayer`/`Message` chips already
do. The `Hymn` chip and its `section-add-hymn-${group.key}` testid are deleted from this row only, not
from `createSlot`/`slotLabel`.)

**Shared body block** — combine `MESSAGE`, `ANNOUNCEMENTS`, and `MISC` into **one** `v-else-if` branch in
the slot-content template (replacing today's separate `MESSAGE` block and adding the two new kinds to
it), so there is structurally one editor, not three near-identical copies:

```html
<template v-else-if="slot.kind === 'MESSAGE' || slot.kind === 'ANNOUNCEMENTS' || slot.kind === 'MISC'">
  <div class="flex items-center gap-2 mb-1">
    <p class="text-xs font-semibold text-gray-400 uppercase tracking-wider">{{ slotLabel(slot, index) }}</p>
    <span class="text-xs text-gray-600 italic">No assignment needed</span>
  </div>
  <!-- Editor: CLASS A -->
  <textarea
    v-if="canEditService"
    :value="(slot as NonAssignableSlot).body"
    @input="(slot as NonAssignableSlot).body = ($event.target as HTMLTextAreaElement).value"
    rows="3"
    :placeholder="bodyPlaceholder(slot.kind)"
    class="w-full rounded-md bg-gray-800 border border-gray-700 text-gray-200 text-sm px-3 py-2 focus:outline-none focus:ring-1 focus:ring-indigo-500 placeholder-gray-500 resize-y mt-1"
  ></textarea>
  <!-- Viewer / locked: read-only, preserves line breaks -->
  <p v-else-if="(slot as NonAssignableSlot).body?.trim()" class="text-sm text-gray-200 whitespace-pre-wrap mt-1">{{ (slot as NonAssignableSlot).body }}</p>
  <p v-else class="text-sm text-gray-400 italic mt-1">{{ slotLabel(slot, index) }} — Empty</p>
</template>
```

`bodyPlaceholder(kind)` is a small static lookup (`{ MESSAGE: '...', ANNOUNCEMENTS: '...', MISC: '...' }`)
returning the three placeholder strings from the Copywriting Contract — a static class-map-style object,
consistent with the codebase's existing `badgeClasses`-shaped convention cited in
`.planning/codebase/CONVENTIONS.md`.

**What does NOT change:** the `PRAYER` `v-else-if` block (its own link-field UI stays exactly as-is — out
of scope per 43-CONTEXT.md) and the `HYMN` `v-else-if` block (byte-identical, per R084).
