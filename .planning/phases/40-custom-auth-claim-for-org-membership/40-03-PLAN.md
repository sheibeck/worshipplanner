<objective>
Force the new custom claim onto the active session's ID token when org context loads, and close the
invite-acceptance race with a bounded retry.

Requirement R075 — the rollout never locks out an existing signed-in member. Locked decisions D-06
(force a refresh with `getIdToken(true)`) and D-07 (the refresh fires on org-context load, not sign-in
only, so a member whose claim changes mid-session is not stranded).

Purpose: claims land on a token only at its next mint. Without a forced refresh a member waits up to a
full 1-hour token lifetime for the claim. And research found a **real race the locked decisions do not
close**: `ensureUserDocument`'s invite-acceptance `batch.commit()` returns before the asynchronous
Cloud Functions trigger has necessarily finished setting the claim, so a forced refresh fired on the
very next line can complete *before the claim exists*. Harmless while the Firestore fallback is live
(deploy 1), a genuine hole after the owner's deploy 2 removes it.

Output: a forced refresh on every org-context load, plus a bounded retry scoped to the just-created-
membership path only, so the ordinary path pays no latency.
</objective>

<the_planner_decision_you_must_implement>
**P-01 — the retry is scoped to the just-created-membership path, not to every load.**

The naive form (retry the forced refresh on every `loadOrgContext`) is wrong, and expensively so: for
the entire pre-deploy-1 window, and permanently for a multi-org user whose non-primary org is loaded,
the claim will never match, so every single session start would burn the full retry budget — several
seconds of dead latency on the one code path every authenticated session runs.

Scope it instead to the window where the race actually exists. `ensureUserDocument` knows whether it
just created a `members/{uid}` document — it does so on two paths: the invite-acceptance batch
(`auth.ts:236-241`) and the auto-create-new-org batch (`auth.ts:265-270`). Have it report that fact,
and have `loadOrgContext` retry only when it is true.

- Ordinary load: exactly one forced refresh, no delay, no retry. Latency unchanged.
- Just-joined load: up to `CLAIM_REFRESH_MAX_ATTEMPTS` forced refreshes spaced by
  `CLAIM_REFRESH_DELAY_MS`, stopping the instant the claim matches.

Research's alternative — document the race as accepted risk and keep the Firestore fallback live
forever for new memberships — was considered and **rejected**: it makes the owner's deploy 2
permanently unsafe for new members. The bounded retry closes the hole instead, is client-side only, and
needs no deploy. The residual risk (the trigger takes longer than the whole budget) is recorded, not
eliminated, and plan 40-04 writes it into the runbook.
</the_planner_decision_you_must_implement>

introduces also delays `isReady`. That is acceptable **only** because the retry is scoped to the
just-joined path (P-01). Do not widen it.
</known_test_trap>

  <action>
Add the claim refresh to `src/stores/auth.ts`, per D-06 (force a refresh with `getIdToken(true)`),
D-07 (fire it on org-context load, not sign-in only) and P-01 (bound the retry to the just-joined path).

Export two module-scope constants so the tests can drive timing without magic numbers:
`CLAIM_REFRESH_MAX_ATTEMPTS` (4) and `CLAIM_REFRESH_DELAY_MS` (1500). Four attempts spaced 1.5s gives
roughly a 4.5-second worst case, comfortably inside the few-hundred-milliseconds-to-a-few-seconds band
Cloud Functions triggers typically land in, and it is paid only once, on the load immediately after a
membership is created.

Import `getIdTokenResult` from `firebase/auth`. Prefer it over `getIdToken` because it returns the
decoded `claims` object, which is what lets the retry know whether to stop — `getIdToken` returns only
the raw string and would force a manual JWT decode. The forced-refresh semantics D-06 asks for are
identical: pass `true` as the second argument.

Add an internal helper — `refreshOrgClaim(targetOrgId, awaitClaim)` — that:
- returns immediately if `user.value` is null;
- loops at most once when `awaitClaim` is false, and at most `CLAIM_REFRESH_MAX_ATTEMPTS` times when it
  is true;
- on each pass calls `getIdTokenResult(user.value, true)` and stops as soon as `result.claims.orgId`
  strictly equals `targetOrgId` — a claim naming a *different* org does not count as arrival, so a
  leftover claim from a previous org cannot short-circuit the wait;
- sleeps `CLAIM_REFRESH_DELAY_MS` between attempts but **not after the final one**;
- wraps everything in try/catch, logging `console.error('[auth] refreshOrgClaim:', err)` per the
  established convention, and always resolves. It must never throw: a failed refresh is not a failed
  sign-in, and `storage.rules`' Firestore-membership arm still grants access while the claim is missing.

Call it from `loadOrgContext` after `orgId.value = ids[0]` is set and before, or concurrently with, the
org-document read — but **not** inside the no-organization early-return branch, where there is no claim
to wait for. Give `loadOrgContext` a second optional parameter (defaulting to false) carrying the
just-joined flag, so every existing call site keeps working unchanged.

Change `ensureUserDocument` to report whether it created a members document. Return a small object such
as `{ membershipCreated: boolean }` (it currently returns `void`, so every existing caller that ignores
the value is unaffected — and `loginWithGoogle`, `loginWithEmail` and `registerWithEmail` all do).
Set it true on **both** membership-creating paths: the invite-acceptance batch and the auto-create-new-
org batch. False on the already-a-member path.

In `onAuthStateChanged`, capture that result and pass its `membershipCreated` value into
`loadOrgContext`. Comment the call site with why: this is the invite-acceptance race window — the batch
commit returns before the `syncOrgMembershipClaim` trigger has necessarily run, so the token can be
re-minted before the claim exists.

Add a comment on `refreshOrgClaim` recording the D-01/D-04 known limitation: only the user's primary
org (`orgIds[0]`) is ever carried in the claim, so for a multi-org user the non-primary orgs are served
by the Firestore-membership arm of the dual-read alone, and a claim for a non-primary org will
correctly never arrive.

Then extend `src/stores/__tests__/auth.test.ts`:
- add `getIdTokenResult` to the `firebase/auth` mock factory (see `<known_test_trap>` — omitting it
  breaks the eight existing `loadOrgContext` tests, not just the new ones);
- add a `describe('org claim refresh (R075 / P-01)')` block covering every case in `<behavior>`;
- drive the delays with `vi.useFakeTimers()` and advance them explicitly, so the suite does not spend
  real seconds waiting, and restore real timers in an `afterEach`;
- assert call counts on the mocked `getIdTokenResult`, not just its arguments, since the whole point of
  P-01 is *how many times* it fires.

Do not change `waitForRole`, the member `onSnapshot` handler, the admin-to-editor migration, the R073
settings merge, or the logout reset path.
