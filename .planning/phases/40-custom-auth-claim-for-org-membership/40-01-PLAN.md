<the_trap_read_this_before_task_1>
**Editing `storage.rules` alone will NOT turn the two headline tests green.**

Both currently call `testEnv.authenticatedContext('userA')` with **no token options**, then seed a
Firestore members document. Under the dual-read, a claim-less token fails the claim arm and falls
through to `firestore.exists()`, which is inert in the Storage emulator — so the caller is still
denied and the test still fails.

Turning them green requires **both** halves: the rule gains a claim arm (Task 1) **and** those two
tests supply a claim in the token and drop the now-useless `seedMembershipDoc` call (Task 2). After
the rewrite they prove the **claim** arm. Their **titles must not change** — the phase gate is stated
by test title, and renaming them destroys its checkability.

**Second trap, equally important.** Three existing deny-tests pass *vacuously* today, because a
deny-everyone rule denies everything for the wrong reason:
`denies a member write that exceeds the 25MB size cap`,
`denies a member media upload that exceeds the 50MB media cap`, and
`regression: the media match does not loosen the non-media pptx-imports 25MB cap`.
Each seeds a members doc and sends no claim, so the membership conjunct is false and the size conjunct
is never exercised. Task 3 gives them a valid claim so the **only** false conjunct is the size cap.
Leaving them as-is would ship three assertions that prove nothing — the precise failure mode CLAUDE.md
records.
</the_trap_read_this_before_task_1>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Cloud Storage | Untrusted caller presents a Firebase-signed ID token; `storage.rules` is the only enforcement point. |
| Storage rules → Firestore | Cross-service `firestore.exists()` lookup; inert in the emulator, live in production only since the 2026-08-06 IAM grant. |
| Firebase Auth → ID token payload | Custom claims are written server-side by the Admin SDK and signed into the JWT; the client can read but never author them. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-40-01 | Denial of Service (self-inflicted, against legitimate users) | `storage.rules` membership predicate | high | mitigate | The two predicates are joined by `||`, never `&&`, and the Firestore predicate is never deleted in this phase. | T-40-02 | Elevation of Privilege | `storage.rules` dual-read widening access | high | mitigate | Task 3(a)(b)(c) prove denial still holds for: a claim naming a different org, a claim with no role, and a caller with neither claim nor membership doc — on both the generic and media match blocks. |
| T-40-03 | Spoofing | `request.auth.token.orgId` / `.role` | high | mitigate | Custom claims live inside the Firebase-signed ID token; the client SDK exposes no API to author them, and only the Admin SDK's `setCustomUserClaims` can set them. `authenticatedContext(uid, tokenOptions)` can mint arbitrary claims **only** inside the rules-unit-testing harness, which never runs against production. |
