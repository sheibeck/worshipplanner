# Phase 33 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** this phase does not touch presentation/rendering fidelity (Phase 35 owns how a
background actually composites with text/contrast on a projector), does not move Add-slide/Add-music
into a contextual action bar (R053 → Phase 36), and does not add keyboard drag-reordering (still absent,
still out of scope). It (1) adds three background-image affordances — slide, group, song — resolved
slide → group → song, most-specific-wins; (2) decouples card-click-to-select from edit, replacing it
with an explicit 3-dot `SlideActionMenu.vue` whose item list varies by `sourceRef.kind`; (3) splits
`EditSlideDrawer.vue`'s single body into `mode: 'details' | 'lyrics'`; and (4) deletes the per-slide
audio "whole group" scope option (R058), leaving `SlideGroupMusicControl.vue` as group audio's one
remaining entry point.

**★ No wireframe backing for this phase's core surfaces.** `docs/design/slides-tab.dc.html` (pulled
2026-07-25) has no 3-dot menu, no details/lyrics split, and no background feature anywhere in it — see
33-CONTEXT.md § Specifics for the verified absence table. The 3-dot menu, the two-drawer split, and all
three background affordances are **original design work produced by this spec**, not a wireframe being
transcribed. Where this spec borrows from the mockup, it is borrowing *house visual language only*
(the drawer's scrimless floating-panel behaviour, the app's own already-shipped Tailwind palette) — never
claiming the mockup shows a control it does not contain. The mockup's own hex palette (`#7c5cff` violet,
`#141726` panels) is a **separate, unimplemented Design Canvas prototype** — this spec follows the real
shipped Tailwind palette (`gray-950`/`gray-900`/`indigo-500`) that `SlideCard.vue`, `EditSlideDrawer.vue`
and `SlideGroupMusicControl.vue` already use in production, per the same precedent 31-UI-SPEC and
32-UI-SPEC set.

**Upstream decisions this spec implements, not re-opens (33-CONTEXT.md):** slide → group → song cascade,
most-specific-wins, stated as prose never arrows; video does NOT suppress an inherited background
(deliberate divergence from the audio precedent); provenance is tracked so an override is never
invisible; clicking a slide still selects, never edits; one `SlideActionMenu.vue`, props-driven per
`sourceRef.kind`; song groups get a reduced menu (no "Edit lyrics", no delete); one `EditSlideDrawer.vue`
with a `mode` prop, not two components, not tabs; "Edit lyrics" only for hand-authored text slides;
only one drawer open at a time; `audioScope` deleted outright, no migration, no legacy read path.

## Phase-Specific Component Contracts

### 1. ★ Structural correction to `SlideCard.vue` — the outer element cannot stay a `<button>`

**This is a load-bearing HTML-validity finding, not a style preference.** `SlideCard.vue:2` wraps the
entire card in `<button type="button" ... @click="emit('select', ...)">`. 33-CONTEXT.md requires the
menu trigger to be a real `<button>` with `aria-haspopup="menu"` — but the HTML content model forbids
interactive content (a `<button>`) inside another `<button>`; browsers do not render this predictably
(some auto-close the outer button's tag early, breaking layout; screen readers announce it
inconsistently). The drag handle avoids this today by being a `<span tabindex="0">`, never a real
button (`SlideCard.vue:41-47`) — deliberately, per its own existing comment. A `SlideActionMenu`
trigger cannot use the same workaround, because `aria-haspopup`/`aria-expanded` are meaningful only on
a real button/link per the ARIA spec.

**The fix:** change `SlideCard.vue`'s root element from `<button>` to `<div role="button" tabindex="0">`,
with `@click` and `@keydown.enter`/`@keydown.space` (preventing the space-bar's default page-scroll)
reproducing exactly the activation semantics a native `<button>` gave for free. This is a **mechanical,
behavior-preserving** change — clicking or pressing Enter/Space on the card body still selects, exactly
as today — that exists solely to let `SlideActionMenu`'s trigger legally nest inside it. `data-testid`,
`data-selected`, and every existing class stay unchanged.

### 2. `SlideActionMenu.vue`

```html
<!-- src/components/slides/SlideActionMenu.vue -->
<div class="relative" data-testid="slide-action-menu">
  <button
    type="button"
    class="p-1 rounded-md text-gray-500 hover:text-gray-300 hover:bg-gray-800 transition-colors"
    :aria-haspopup="'menu'"
    :aria-expanded="open ? 'true' : 'false'"
    aria-label="Slide options"
    :data-testid="`slide-action-trigger-${entryId}`"
    @click.stop="onTriggerClick"
  >
    <svg xmlns="http://www.w3.org/2000/svg" class="h-5 w-5" viewBox="0 0 24 24" fill="currentColor">
      <circle cx="12" cy="5" r="1.5" />
      <circle cx="12" cy="12" r="1.5" />
      <circle cx="12" cy="19" r="1.5" />
    </svg>
  </button>

  <div v-if="open" class="fixed inset-0 z-10" @click="close" />

  <Transition
    enter-active-class="transition duration-100 ease-out"
    enter-from-class="opacity-0 scale-95"
    enter-to-class="opacity-100 scale-100"
    leave-active-class="transition duration-75 ease-in"
    leave-from-class="opacity-100 scale-100"
    leave-to-class="opacity-0 scale-95"
  >
    <div
      v-if="open"
      ref="panelRef"
      role="menu"
      class="absolute right-0 top-full mt-1 w-40 origin-top-right rounded-lg border border-gray-700 bg-gray-800 shadow-xl z-20 overflow-hidden"
      :data-testid="`slide-action-panel-${entryId}`"
      @keydown="onPanelKeydown"
    >
      <button
        v-for="item in items"
        :key="item.key"
        type="button"
        role="menuitem"
        class="block w-full px-3 py-2 text-left text-sm transition-colors hover:bg-gray-700"
        :class="item.tone === 'nav' ? 'text-indigo-400 hover:text-indigo-300' : item.tone === 'destructive' ? 'text-red-400 hover:text-red-300' : 'text-gray-200'"
        :data-testid="`slide-action-item-${item.key}`"
        @click="onItemClick(item)"
      >{{ item.label }}</button>
    </div>
  </Transition>
</div>
```

- **`@click.stop` on the trigger** — the exact idiom `SlideCard.vue:47`'s drag grip already established:
  the click must never bubble to the card's own `@click`/`@keydown` select handler, so opening the menu
  never re-fires selection (selection is a harmless no-op if it did, but the click-stop keeps the two
  concerns cleanly separate, matching the grip's own precedent).
- **Click-away backdrop, `z-10`, panel `z-20`** — verbatim reuse of `ServiceEditorView.vue:1100-1109`'s
  existing add-menu dropdown idiom (§ Design System cites no new pattern; this is the second use of an
  already-established one, not an invention).
- **`role="menu"` / `role="menuitem"`, `aria-haspopup`, `aria-expanded`** — the full contract 33-CONTEXT.md
  specifies. **Escape closes and returns focus to the trigger** — `onPanelKeydown` listens for
  `Escape` only; no arrow-key roving-tabindex navigation is implemented (matching this codebase's
  existing, documented gap: the add-menu dropdown it borrows its shell from has none either, and
  33-CONTEXT.md's own citation of "Phase 25 already flagged SortableJS provides no keyboard reordering"
  sets the precedent that this codebase accepts partial keyboard support here rather than retrofitting a
  full roving-tabindex menu for one new control).
- **Panel fixed at `w-40`** (160px) regardless of card width — the narrowest card (200px,
  `SlideGrid.vue:127`) still has room for a `w-40` panel anchored `right-0` without collision (E1
  overflow backstop verifies this at build time).

### 9. ★ The deliberate divergence — video does NOT suppress an inherited background

`slideshowAssembler.ts:204-205` makes a video slide never resolve the group's bed AUDIO
(`resolveEntryMedia` returns `{ audioFromBed: false }` unconditionally for `sourceRef.kind === 'video'`).
**Background extends the SAME function but explicitly does NOT copy this carve-out.** A video slide's
background resolves through the ordinary slide → group → song cascade like any other kind, and its own
`backgroundImageUrl` is settable/clearable in §5 exactly like any other kind's.

**Why, restated for whoever next reads this code:** two audio sources playing simultaneously is an
audible collision with no on-screen indication — a real defect the video carve-out exists to prevent.
Two *visual* layers do not collide the same way: a video slide's own picture already covers whatever is
behind it for the full frame it occupies, so an inherited background is either invisible (video fills
the frame) or visible only in letterboxing the video's own aspect ratio leaves uncovered — in the second
case, showing the background is correct, not a bug. Suppressing background for video would buy nothing
and would surprise a user who set a group background expecting it to show through a narrower video's
letterbox. **This asymmetry is intentional. Do not "fix" it into matching the audio rule for
consistency** — 33-CONTEXT.md records this as a deliberate divergence, not an oversight, and this note
exists so a future reviewer finds the reasoning before "correcting" it.

## Accessibility Note

- **Menu trigger:** real `<button>` (§1's structural correction is what makes this legal), `aria-haspopup="menu"`, `aria-expanded` reflecting open state, `aria-label="Slide options"` since its only visible content is a glyph.
- **Menu panel:** `role="menu"`, each item `role="menuitem"`. **No roving-tabindex arrow-key navigation** — a stated, deliberate gap matching this codebase's existing precedent for its one other dropdown (the add-menu) and for SortableJS's own documented lack of keyboard reordering. Tab order falls through the panel's DOM order (native button focus order), which is sufficient but not optimal — recorded, not silently omitted.
- **Escape closes and returns focus to the trigger** — the one keyboard behaviour 33-CONTEXT.md mandates explicitly; implemented via the panel's own `@keydown.escape` rather than a global listener, so it only fires while the panel actually has focus inside it.
- **Card root (`SlideCard.vue`):** `role="button" tabindex="0"`, `@keydown.enter`/`@keydown.space` reproduce native button activation exactly (§1) — this is a like-for-like semantic swap, not a downgrade; screen readers announce a `role="button"` div identically to a native button for activation purposes, and the change exists solely to make legal HTML nesting for the trigger inside it.
- **Background control file inputs:** `<label>`-wrapped, same pattern `SlideGroupMusicControl.vue:51-63` already ships — the label IS the accessible name, no separate `aria-label` needed.
- **Provenance chips and captions:** plain text, no `aria-live` — these are static descriptive content read in normal document order when a screen reader user reaches that part of the card/drawer, not an announcement-worthy event (matching 31-UI-SPEC's own reasoning for why its lock banner is not a live region either).
- **Removed controls under lock are removed, not `aria-disabled`** (D-05, reused verbatim for this phase's own new controls) — nothing appears in the tab order that cannot be operated.
