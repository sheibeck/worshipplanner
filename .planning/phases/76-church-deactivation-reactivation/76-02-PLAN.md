<objective>
Implement the client-side half of church deactivation/reactivation: a login-block in `loadOrgContext`
that never lets a deactivated org's ordinary member into the app, a church picker that visibly greys
out (rather than silently drops) a deactivated org, and an owner-console control that lets a
super-admin flip an org's status via the `setOrgActive` callable.

**This client check is UX only, never the security boundary** — 76-01-PLAN.md's `firestore.rules`/
`storage.rules` are the enforced boundary. A client bypass (e.g. a modified build calling the Firestore
SDK directly) is denied there regardless of anything built in this plan.

**Correction beyond 76-RESEARCH.md's illustrative snippet:** the research's client-block example reads
`orgSnap.data().active` after a successful `getDoc`, assuming the read always succeeds. Once
76-01-PLAN.md's `firestore.rules` ship, that assumption is FALSE for an ordinary (non-super-admin)
member: `isOrgMember` now composes `isOrgActive(orgId) || isSuperAdmin()`, so a deactivated org's own
member has their read of `organizations/{orgId}` DENIED outright — not merely handed back
`{active:false}` data. The existing `getDoc(orgRef)` call in `loadOrgContext` has NO surrounding
try/catch today; an uncaught rejection there would propagate out of the `onAuthStateChanged` handler,
leave `isReady` never set to `true`, and produce exactly the "blank app" R213 forbids. Task 1 below
wraps that read in a try/catch and treats the denial ITSELF as the deactivation signal — this is more
robust than trusting a client-read boolean, since the read failing is exactly what the rules layer
already proved.

Purpose: deliver the UX layer of R213 (clear messaging, never silent failure) and the UI trigger for
R212/R214, on top of 76-01-PLAN.md's already-enforced rules boundary.
Output: an updated `auth.ts` store, an updated church picker, and a new Deactivate/Reactivate control
on the Organizations tab.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-76-07 | Elevation of Privilege | Client-side login-block (`auth.ts`) | medium | accept | The client check is explicitly UX-only; a bypassed/modified client is independently denied by 76-01-PLAN.md's `firestore.rules`/`storage.rules` regardless of anything built in this plan — documented here so this plan's own scope is never mistaken for the enforcement boundary |
| T-76-08 | Information Disclosure | Membership-list / primary-org `getDoc` failure path | low | mitigate | Every `getDoc` failure for a listed org (deactivation, orphaned membership, or transient error) collapses into the SAME generic id-fallback + the SAME generic deactivation copy; raw Firebase error codes/messages are never surfaced to the end user |
