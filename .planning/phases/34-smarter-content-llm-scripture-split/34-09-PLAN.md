## ★ This is a requirements gap, not a wiring slip — and the record must say so

**R055** ("A background image can be set for all slides in a group") and **R056** ("...on a single
slide, overriding the group's — most specific wins") both describe *setting* a background. **Neither
ever asked for it to render while presenting.** That is why Phase 33's verification passed honestly
with the feature half-delivered: every stated requirement was met.

So this plan does not quietly fold display under R055. It proposes a new requirement, writes it into
`REQUIREMENTS.md` mapped to Phase 34, and only then implements it. Same shape as the open Phase 37
finding that client-side display of rendered images has no owner in the roadmap: **a media cascade
built through authoring, with no requirement covering the surface that was the point of it.**

### The proposed requirement, verbatim

> **R070** (core-capability): A slide's resolved background image is displayed while presenting, not
> only while authoring. The presented slide renders the single background the slide → group → song
> cascade already resolved (R055/R056/R057) — the presentation surface consumes that resolved value and
> never re-derives the cascade — with a legibility treatment so projected text stays readable over the
> image. A video slide's own video takes precedence: no background renders on a video slide.
> *(Added 2026-08-03 from owner UAT finding F3. R055 and R056 both describe SETTING a background and
> neither ever asked for it to render while presenting, which is why Phase 33 verified green with
> authoring and preview complete and display absent.)* `[FEAT]`

## The cascade is NOT re-implemented here

R056 states the precedence as prose deliberately ("most specific wins: a slide's own background beats
its group's, which beats the song's") because arrow notation for it read backwards half the time
during planning. `resolveEntryMedia` already applied it — `slideshowAssembler.ts:236-241` picks
`entry.backgroundImageUrl ?? group.backgroundImageUrl ?? song?.backgroundImageUrl` and records the
winning tier in `backgroundSource`, a deliberate single tri-state field so the url and its provenance
"can never drift apart the way `audioUrl`/`audioFromBed` historically did" (`slide.ts:41-49`).

The viewer therefore reads `slide.backgroundImageUrl` and nothing else. Consuming a second,
independently-derived answer is precisely the two-disagreeing-fields shape this codebase keeps getting
bitten by — Phase 28's two competing order fields, Phase 33's partially-applied cascade — and an
acceptance criterion below asserts the viewer never touches a group or song object.

## Legibility: a fixed scrim, stated concretely

Text over a photograph is the failure mode this feature invites. The treatment is a **scrim**: a
`bg-black/50` layer between the image and the slide content, matching the `bg-black/60` scrim the
export dialog already uses in `ServiceEditorView.vue:365`, so this is an existing in-repo value family
rather than an invented one. Fixed opacity, no per-image analysis, no user control — those are all
things that could be wanted later and none of them is asked for now.

Whether 50% reads correctly on a real projector against a real photograph is a perceptual judgment
jsdom cannot make. It goes to `PENDING-VERIFICATION.md` as an open human check (34-08 Task 2 owns that
file); it is **not** self-approved here.

## Video precedence, stated explicitly

`PresentationViewer.vue:150-164` already renders a video slide's own source, and its comment records
that video "is the video slide's entire visual content — nothing else on a video slide competes with
it for the screen." A background behind a letterboxed video would be exactly that competition. **Video
wins: on a video slide, no background layer renders at all.** Every other slide kind — lyric,
copyright, scripture (both normal and congregational), text, image — renders the background when one
resolved.

## Layer order without restructuring the canvas

The background and scrim mount as siblings inside the viewer root, each `absolute inset-0` with an
inline `zIndex: -1`. The root is `fixed inset-0 z-50`, which already establishes a stacking context,
so negative-z children paint after the root's own black background and **before** all in-flow content
and all positioned siblings. That means the slide canvas, the exit button and the chrome bar all keep
painting above the background with **zero changes to their markup or classes** — no wrapper div around
the per-kind content, no z-index churn on the existing chrome. The inline `zIndex` is used rather than
a Tailwind negative-z utility so the layering cannot depend on whether that utility is generated by
this project's Tailwind config; a background that silently covers the words is the worst possible
failure here.
