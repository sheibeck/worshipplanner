<objective>
Give the SCRIPTURE slot a place to store a congregational reading, and make BOTH slide-materialization
paths carry it onto the slide.

Purpose: this is the data half of Phase 34's reachability gap. `CongregationalEditor.vue` currently
persists to a separate `ScriptureReading` document — the model R047 explicitly rejected (`3da5fe4`
superseded by `5c531b1`) — so sections written today reach no slide. R064's direction is decided:
slot-as-source-of-truth.

Output: `ScriptureSlot.congregationalSections`, one shared derivation helper, and both assembler call
sites reading through it.

## ★ CORRECTED PREMISE — congregational sections do NOT become separate slides

The orchestrator's edge-probe report described congregational sections as materializing into "two
separate scripture slides in stored order". **That is wrong against live source and must not be
built.** Phase 35 already shipped the presentation shape: `PresentationViewer.vue:86-107` iterates
`(currentSlide.slide as ScriptureSlide).sections` on ONE slide, and `isCongregational`
(`PresentationViewer.vue:450-455`) gates on `readingMode === 'congregational' && sections.length > 0`.

The delivered shape is therefore: **one scripture slide per SCRIPTURE slot, carrying ALL sections in
its `sections` array**, rendered as a stacked Leader/Congregation block layout. The edge concerns the
probe raised (never merge same-speaker neighbours, never re-sort, no duplicated or dropped text,
absent/empty behaves exactly as today) are all real and are asserted below — only the "separate
slides" mechanism is corrected. Building N slides would contradict Phase 35's shipped renderer and
would also force `slideGroupMaterializer.ts` to emit N entries, breaking R047's payload-free
single-entry design and its `carryStoredDerivedEntries` id/audio carry-forward.

## ★ Second correction — "exactly one section" is congregational, not normal

The probe folded "holds exactly one section" into the normal-rendering case. That would create a
SECOND predicate disagreeing with `PresentationViewer`'s `sections.length > 0`, which is exactly the
two-disagreeing-fields defect shape this codebase keeps getting bitten by (Phase 28's two competing
order fields; Phase 33's cascade). One predicate: sections present and non-empty means congregational.
Backward compatibility is unaffected — existing production slots have NO sections field at all.
