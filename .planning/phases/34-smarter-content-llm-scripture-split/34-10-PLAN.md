<objective>
Stop rendering an empty bordered box at the top of the Service Editor.

**This is not R064 work.** It is owner UAT finding F4 from the 2026-08-03 hands-on session
(`34-UAT.md`), a Phase 32 defect planned here because it surfaced in the same session.

Purpose: `ServiceEditorView.vue:235-241` gates the bordered, sticky save-status wrapper on
`v-if="canEditService"` alone, while the `SaveStatusIndicator` inside it renders `<!--v-if-->` when
there is nothing to report (`SaveStatusIndicator.vue:8-16` — idle deliberately has no branch). An
editor with an idle service therefore gets an empty bordered box pinned to the top of the scrollport.
The owner pasted exactly this DOM after marking a service Planned and reopening it.

Output: the wrapper gate this codebase already established as the rule, plus the test for the exact
path the owner walked.

## The fix pattern already exists one component away

`SlideGrid.vue:68-73` gates the group-music wrapper on `group?.bedAudioUrl || canWriteGroupMedia` with
an explicit comment: *"31-UI-SPEC E5: gate the WRAPPER, not just the control's contents. With no bed
audio and no add affordance the control renders an empty bordered box."* `SlideGrid.vue:84-90` repeats
it verbatim for the background row. **This bar is missing the guard the codebase already made a rule.**

So the fix is the established one: the wrapper does not render when the indicator has nothing to show.

## What the fix is NOT

Not "make the indicator always render something." Phase 32 deliberately removed the 3s saved→idle fade
and `SaveStatusIndicator.vue:23-26` records that *"idle deliberately has no branch above: rendering
nothing, with no placeholder box and no reserved layout height, is the idle state."* An always-on
status re-introduces exactly the noise that decision dropped, and it would make R041's error state
harder to notice, not easier.

Not "reserve the height so the layout doesn't shift." The same comment already rejects that.

## One predicate, proven to agree — not two that can drift

The gate needs to answer "will the indicator render anything?", and the naive version of that answer
is a second copy of the indicator's branch list living in a different file. That is the
two-disagreeing-fields shape this codebase keeps getting bitten by (Phase 28's two competing order
fields; Phase 33's partially-applied cascade).

So the predicate is **exported from `src/stores/saveStatus.ts`**, next to the `SaveStatusEntry` type it
reads and the `GENERIC_ERROR_TEXT` constant that already lives there for precisely this
single-source-of-truth reason (WR-01, 32-REVIEW: *"module-level so both the toast fallback AND
SaveStatusIndicator's inline-error fallback share the identical string"*). And Task 1 asserts agreement
**exhaustively over the `AutoSaveStatus` union** (`useAutoSave.ts:3` — `idle | pending | saving | saved
| error`) rather than spot-checking, so adding a sixth status later fails the test instead of silently
producing a bar that renders empty again.

## The accessibility consequence, stated rather than absorbed

Gating the wrapper unmounts the `aria-live` region at idle, so the very first transition **into**
`pending` inserts the region with its text already present — a live region generally does not announce
content it was created holding. Every subsequent transition (`pending → saving → saved`, and any
`→ error`) mutates a region that is already mounted and monitored, and is announced normally.

The cost is therefore one missed announcement of "Saving soon…", once, on the first edit of a session;
the benefit is that the region is not permanently present announcing nothing. Phase 32 also removed
the saved→idle fade, so after that first edit the bar stays mounted for the rest of the session. This
is recorded here rather than discovered later, and Task 2 asserts the in-place-mutation half of it.
