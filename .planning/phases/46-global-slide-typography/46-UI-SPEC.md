## Typography

Two typography systems are declared here, deliberately kept separate: **(A)** the Settings-card UI chrome (labels, headings, helper text) — unchanged, uses the existing app-wide Tailwind text scale — and **(B)** the **slide typography contract** this phase actually ships, which is a runtime CSS-variable system layered over the app's existing fixed slide-text classes, not a replacement for them.

### (A) Settings card UI chrome (unchanged, for reference only)

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Card heading | 14px (`text-sm`) | 600 (`font-semibold`) | default |
| Body/help text | 12px (`text-xs`) | 400 | default (`leading-normal` where set) |
| Control label | 14px (`text-sm`) | 400 | default |

### (B) Slide typography contract (R093/R094 — what this phase delivers)

| CSS Variable | Purpose | Values |
|---|---|---|
| `--slide-font-family` | Font-family stack applied to every slide surface | One of the curated `SLIDE_FONTS` family names below, falling back to `Inter, ui-sans-serif, system-ui, sans-serif` |
| `--slide-font-weight` | Numeric weight applied alongside the family | One of `300 \| 400 \| 500 \| 600 \| 700`, constrained per-family to the weights actually shipped (see Curated Font List below) |
| `--slide-font-scale` | Multiplier layered over each surface's existing fixed Tailwind size, via `calc()` | `0.85` (Small) · `1.0` (Medium, identity — no visual change) · `1.25` (Large) |

These three variables are set on one shared ancestor per render site (`PresentationViewer.vue`'s root, the Slides-grid container, and the Edit Slide drawer preview wrapper) and consumed via `font-family: var(--slide-font-family)`, `font-weight: var(--slide-font-weight)`, and `font-size: calc(<existing-rem-value> * var(--slide-font-scale))` — the existing fixed classes stay as the base value the scale multiplies, never a hand-rewritten new scale.

**Existing fixed base sizes each site's scale multiplies (unchanged as base values, do not alter these classes):**

| Site | Element | Existing base (unchanged) |
|---|---|---|
| Presenter (`PresentationViewer.vue`) | Body/lyric/scripture text | `text-5xl font-normal leading-[1.4]` |
| Presenter | Scripture reference | `text-6xl font-semibold leading-[1.15]` |
| Presenter | Speaker label | `text-2xl font-semibold leading-[1.3]` |
| Presenter | Copyright footer | `text-xs leading-[1.4]` |
| Slides grid (`SlideCard.vue`) | Card body-text preview | `text-[13px] leading-normal` |
| Edit Slide drawer preview | Preview body text | `text-[13px] leading-normal` |

**Discretionary decision (in scope of "Claude's discretion" over numeric scale values and CSS variable names):** `--slide-font-scale` applies uniformly to all three render sites, not the presenter alone. Rationale: the grid card and drawer preview exist specifically to preview "what's on the slide" (SlideCard's stated purpose), so their text should track the same family/weight/size decisions the presenter uses — leaving them out would make the Settings card's live preview a lie for two of the three surfaces success criterion 2 explicitly names. Medium (`1.0`) is the identity multiplier, so a church that never opens the setting sees **zero visual change** to the grid or drawer today — satisfying R093's "applies to every slide" without regressing the current compact-card layout for anyone who doesn't touch the control.

**Settings-card font-family picker's own displayed weight options** (14px `text-sm`, 400) are UI chrome — not affected by the slide-font variables.

## UI Considerations

Applicable state considerations resolved: 6 covered, 1 backstop, 2 unresolved

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Slide Typography form (family/weight/size) | ✅ covered | The picker is never unset — `DEFAULT_ORG_SETTINGS.slideTypography` merges to `{Inter, 400, md}` at the single `loadOrgContext` point, so there is no unfilled-form state to design for |
| loading | Font-family preview in the Settings picker (non-default families load on demand when previewed, per 46-CONTEXT.md) | ✅ covered | While a previewed (not-yet-loaded) family's woff2 is fetching, the preview panel keeps rendering the LAST successfully-loaded face rather than blanking — `font-display: swap` on non-presenter surfaces already gives this behavior natively; no spinner needed for a same-origin, self-hosted asset |
| error | Font-family preview fails to load its asset (self-hosted 404/corruption) | ✅ covered | Falls back to the CSS stack's next entry (`Inter, ui-sans-serif, system-ui, sans-serif`) — never a blank preview box. This is the browser's native font-stack fallback behavior, requiring no custom error UI |
| partial | Weight picker shows a weight the newly-selected family doesn't ship (e.g. user had 300 selected, switches family to one without 300) | ✅ covered | Changing `fontFamily` re-derives the weight options list from `SLIDE_FONTS[family].weights` and, if the current `fontWeight` isn't in that list, snaps the selection to `400` (every curated family ships 400) before the next save — proven by test, not left to chance |
| loading (R094 hard gate) | Presenter first paint | 🧪 backstop | `document.fonts.ready` + explicit `document.fonts.load('<weight> 1em "<family>"')` gates the transition out of the existing "Loading slideshow…" state — this is the phase's core behavioral requirement (R094) and must be proven by an automated test asserting the slide canvas never renders before the font-load promise resolves, not merely asserted in prose |
| error (font-load promise rejects/never resolves) | Presenter first-paint gate | ⚠ unresolved | 46-CONTEXT.md specifies the success gate but not a failure/timeout path. **Planner assumption, stated for confirmation:** wrap the `document.fonts.load()` call in a bounded timeout (recommend 3000ms) that proceeds to render on timeout rather than hanging the "Loading slideshow…" state indefinitely — a stuck black screen mid-service is a strictly worse failure than one flashed frame of a fallback font. The planner must pick the exact timeout value and confirm this trade-off before implementation |
| overflow | Presenter slide text at `--slide-font-scale: 1.25` (Large) with an already-long lyric/scripture line | ⚠ unresolved | Pre-existing risk independent of this phase (long lines can already overflow at the fixed base sizes) but Large scale makes it more likely. No auto-fit/shrink-to-fit is in scope per REQUIREMENTS.md's Out-of-Scope table ("Line height, alignment, safe-area margins... out with outline/shadow"). Flagged for the phase's human-verify pass on a real projector, per 46-CONTEXT.md's own framing that the flash/legibility gate is "judged on a real projector at human-verify time" |
| overflow | Slides-grid card body preview / drawer preview at Large scale | ✅ covered | Both already truncate via `line-clamp-6` (grid) and a scrollable preview region (drawer) independent of font metrics — scaling the font up shows fewer visible lines before the existing clamp/scroll takes over, which is the same mechanism already handling long song lyrics today, not a new failure mode |
| long-text | Font-family names in the `<select>` options | ✅ covered | The curated list's longest name ("Source Serif 4") is well within a native `<select>`'s option-rendering capacity; no custom dropdown/overflow handling needed |

## Application Mechanism (reference — mirrors 46-CONTEXT.md, restated here for the checker/executor)

- `OrgSettings.slideTypography: { fontFamily: string; fontWeight: number; fontScale: 'sm' | 'md' | 'lg' }`, default `{ fontFamily: 'Inter', fontWeight: 400, fontScale: 'md' }`, merged once in `auth.ts::loadOrgContext` — no second defaults-merge point.
- CSS custom properties `--slide-font-family`, `--slide-font-weight`, `--slide-font-scale` set from `authStore.settings.slideTypography` on one wrapper per render site; all three sites read the variables rather than hard-coding a font.
- Eager-load only the org's chosen family+weight at app init (closes R094's before-first-paint gate without shipping every curated family up front); other curated families lazy-load only when previewed in the Settings picker.
- Presenter hard-gates first paint on `document.fonts.ready` **and** an explicit `document.fonts.load()` for the chosen face, reusing the existing "Loading slideshow…" state.
- Grid and drawer preview use `font-display: swap` (soft gate, acceptable brief swap in an editing context).
- `ServicePrintLayout.vue` does not consume these variables — owner-locked exclusion, unchanged by this phase.
