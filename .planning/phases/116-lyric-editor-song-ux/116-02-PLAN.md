<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input -> persisted lyrics doc | Manually-entered credit text is written to Firestore and re-rendered to every viewer of the song. |
| editor state -> saveLyrics write | A credits save must persist the current lyric sections/order without corrupting them. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-116-04 | Tampering | saveCreditsEdit -> saveLyrics | medium | mitigate | Persist the edited copyright with `editableState.sections`/`performanceOrder` passed through unchanged (mirror `onSaveVersion`); never re-parse, so a credits edit can never drop or rewrite the lyric sections. |
| T-116-05 | Information Disclosure (stored XSS) | copyright-display / copyright-edit-form render | low | mitigate | Credit fields render through Vue text interpolation (`{{ }}`), which HTML-escapes; no `v-html` is introduced for any credit field. |
| T-116-06 | Elevation of Privilege | saveLyrics write path | low | accept | The lyrics subcollection Firestore rule already requires an org editor; a viewer's write fails at the rule as it does for the existing autosave path — no new client-side gate is added here (consistent with the editor's existing model). |
</threat_model>
