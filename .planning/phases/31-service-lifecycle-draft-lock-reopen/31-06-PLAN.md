<objective>
Close Phase 31: verify the lock end-to-end by hand, and hand the rules deployment to the
owner (D-16).

**★ Why this plan exists at all.** `31-RESEARCH.md` established three facts that combine
into a trap:
1. `firestore.rules` does **not** ship with the app bundle — it deploys separately.
2. This repo has **no CI** (`.github/workflows` does not exist).
3. `src/rules.test.ts` is **excluded** from the default vitest run (`vite.config.ts:85-86`).

So a broken or undeployed lock ships green twice over: `npx vitest run` says nothing about
it, and `npm run build` says nothing about it. Without this plan, the most likely outcome of
Phase 31 is a lock that passes every automated check and does not exist in production.
</objective>

<tasks>

## Task 1 — Confirm the emulator gate actually ran

Re-run `npm run test:rules` and record the result verbatim in the SUMMARY. Requires the
Firebase emulator and `.env.local` (see CLAUDE.md). Do NOT create `.env.local` — if it is
missing, STOP and tell the owner.

If this gate has not passed, nothing else in this plan should proceed.

## Task 2 — Deploy hand-off FIRST (D-16)

**★ This must happen BEFORE the three-layer test in Task 3, not after.** `firestore.rules`
deploys separately from the app bundle, so until it is deployed the LIVE rules are still
`allow write: if isOrgEditor(orgId)` — and a devtools write against a locked service will
succeed no matter how correct the source is. Running that check first would produce a
guaranteed false failure, and an agent reconciling a false failure against green tests is
just as likely to record a false pass.

**Do NOT run this yourself.** Present it to the owner and WAIT for confirmation:

```
firebase deploy --only firestore:rules
```

State plainly: **until this is run, the lock does not exist in production.** The UI will
look locked and the store guard will refuse writes, but anyone with a browser console can
still write to a locked service — the exact bypass this phase exists to close.

Record in the SUMMARY whether the owner confirmed the deploy. If they have not, say so
explicitly rather than implying the phase is live, and mark Task 3 item 10 as NOT RUN
rather than passed.

## Task 3 — BLOCKING human-verify checkpoint

Stop and present this checklist to the owner. Do not proceed, and do not write the SUMMARY
as passed, until they respond.

**Lock behaviour**
1. Open a Draft service. Everything is editable as before — Service Order, Slides, Roles.
2. Click **Mark as Planned**. Expect: one lock banner appears; Service Order rows become
   plain text with no drag handles, no Add item, no pickers; the Slides tab offers no Add
   slide / Import / drag / drawer edits; Roles shows names with no checkboxes.
3. Switch between all three tabs. Expect: exactly ONE banner, and it does not re-announce
   per tab.
4. Confirm **Export to PC**, **Present**, **Print** and **Share** all still work while
   locked.
5. **★ Confirm no empty state tells you to do something you cannot do** — check an empty
   service section, the slide grid, the plan rail, and Roles.

**Reopen**
6. Click **Reopen for editing** on the Planned service. Expect: one click, no dialog,
   editing restored.
7. **★ Confirm drag-and-drop works again immediately, with no page reload.** This is the
   Sortable-teardown regression — if the tab is undraggable after reopen, the fix broke it.
8. Export a service to Planning Center, then Reopen it. Expect: a confirm dialog carrying
   the Planning Center warning. Cancel it — status must be unchanged. Confirm it — status
   returns to Draft.
9. Re-export that reopened service. Expect: it can still target the SAME Planning Center
   plan (D-11). This is the case the naive rule denied.

**Enforcement beyond the UI**
10. **★ The three-layer test — run ONLY after Task 2's deploy is confirmed.** With a
    service set to Planned, open the browser devtools console and attempt a direct
    Firestore write to it, bypassing the UI entirely. Expect: **permission denied.** If
    this write succeeds AND the deploy is confirmed, the phase has not delivered R036 —
    that is the entire point of the rules layer, and it is the one thing no test in the
    default suite covers. If the deploy has NOT been confirmed, mark this item NOT RUN;
    a success here proves nothing except that the rules were never deployed.
11. Delete a service that was exported. Expect: the confirm dialog carries the extra
    Planning Center sentence, and deletion works.

**New-service date**
12. With plans already on the next two Sundays, open New Service. Expect: the date defaults
    to the third Sunday. Note whether the default team selection looks right for that date.
