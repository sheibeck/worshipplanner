# Phase 31 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** this phase adds a **lock layer over existing controls**. It does not restyle them
(31-CONTEXT.md § Phase Boundary). Phase 36 owns the Service Order UI rework and contextual action
bars; anything that amounts to a redesign is recorded in § Phase 36 Handoff below rather than
specified here. Every contract stays inside the existing dark-only, plain-Tailwind visual language
(`.planning/codebase/CONVENTIONS.md`: "Tailwind CSS utility classes only (no scoped CSS)", "Static
class maps to prevent dynamic class purging").

**Upstream decisions this spec implements, not re-opens:** D-01/D-02 (pill + named actions),
D-05 (one banner, controls removed not disabled), D-06 (all three tabs lock), D-07 (notes and sermon
topic lock too), D-08 (non-editing actions stay live), D-10 (friction only where there are
consequences), D-11 (reopen keeps `pcExportedAt`/`pcPlanId`).

### The lock computeds (naming is the planner's, the semantics are not)

| Value | Meaning |
|-------|---------|
| `isLocked` | `localService.status !== 'draft'` — widens `isExportedLocked` (`ServiceEditorView.vue:1288`), which is `status === 'exported'` today |
| `canEditService` | `authStore.isEditor && !isLocked` |
| `hasPcExportEvidence` | `!!(localService.pcExportedAt \|\| localService.pcPlanId)` — D-04's evidence gate; drives the banner body, the reopen dialog AND the delete-confirm sentence, never the status string |

> ### ★★ There is NO 1:1 substitution. Read the table below before editing a single line.
>
> An earlier draft of this spec described the existing `isExportedLocked` call sites as one uniform
> `authStore.isEditor && !isExportedLocked` pattern collapsing to `canEditService`. **That was wrong,
> and applying it mechanically inverts the lock.** The call sites fall into four distinct classes and
> three of them break under a blind find-and-replace:
>
> - A `:disabled="isExportedLocked"` binding rewritten to `:disabled="canEditService"` disables the
>   control **exactly when the user is allowed to edit** — the lock runs backwards.
> - A `v-else-if="authStore.isEditor && isExportedLocked"` branch is the **inverse** condition. These
>   are the read-only fallbacks §5 depends on; rewriting them to `canEditService` deletes the very
>   rendering the table promises and leaves a locked editor staring at nothing.
> - Three sites §5 requires (`:443`, `:579`, `:631`) are gated on `authStore.isEditor` **alone** today
>   and contain no `isExportedLocked` term at all, so a search for that symbol never finds them.

#### Per-line gate migration — `ServiceEditorView.vue`

**Class A — compound `v-if`, the only true 1:1 sites.** Current `v-if="authStore.isEditor && !isExportedLocked"`
→ **`v-if="canEditService"`**:

`:502` (sermon-passage `ScriptureInput`) · `:617` (clear-song ×) · `:666` (`SongSlotPicker`) ·
`:690` (scripture-slot `ScriptureInput`) · `:729` (Prayer link inputs) · `:776` (Message link inputs) ·
`:822` (Hymn inputs) · `:867` (section `<select>`) · `:880` (remove-slot ×) · `:897` (Add Element)

**Class B — editor-only `v-if`, no lock term today.** These are invisible to an `isExportedLocked`
grep and are the sites §5 newly brings under the lock:

| Line | Current | Target |
|---|---|---|
| `:443` | `v-if="authStore.isEditor"` (Teams checkbox block) | `v-if="canEditService"` |
| `:487` | `v-if="authStore.isEditor"` (Sermon Topic input) | `v-if="canEditService"` |
| `:579` | `v-if="authStore.isEditor"` (drag handle) | `v-if="canEditService"` |
| `:631` | `v-if="authStore.isEditor && aiDraftSongs.has(index)"` (AI draft row) | `v-if="canEditService && aiDraftSongs.has(index)"` |
| `:957` | `v-if="assignment.overriddenPersonIds !== null"` (Reset to schedule) | `v-if="canEditService && assignment.overriddenPersonIds !== null"` |
| `:970` | *(no gate at all)* — override picker `<div class="mt-2 flex flex-wrap gap-3">` | add `v-if="canEditService"` |

**Class C — `:disabled` bindings. DELETE the binding; do not rewrite it.** D-05 is "removed, not
disabled," and in every case the enclosing block is already removed by its Class A/B gate, so the
binding has nothing left to express:

| Line | Current | Target |
|---|---|---|
| `:453` | `:disabled="isExportedLocked"` (team checkbox) | **delete the attribute** — parent block gated at `:443`. Also drop `disabled:opacity-50` from `:454`'s class list |
| `:463` | `:disabled="isExportedLocked"` (Special name input) | **delete** — parent block gated at `:443`. Also drop `disabled:opacity-50` from `:464` |
| `:492` | `:disabled="isExportedLocked"` (Sermon Topic input) | **delete** — element gated at `:487`. Also drop `disabled:opacity-50` from `:493` |
| `:134` | `:disabled="!hasSermonContext \|\| aiSuggestingAll \|\| isExportedLocked"` (Suggest All Songs) | drop only the `isExportedLocked` term → `:disabled="!hasSermonContext \|\| aiSuggestingAll"`; the button itself gains `v-if="canEditService"` (§ 3) |

**Class D — inverse read-only branches. These must keep pointing at the LOCKED state.** Current
`v-else-if="authStore.isEditor && isExportedLocked"` → **`v-else-if="authStore.isEditor && isLocked"`**:

| Line | Renders | Note |
|---|---|---|
| `:510` | read-only sermon passage | Now reached for `planned` as well as `exported`. The `v-else` viewer branch at `:517` renders identical markup — collapsing the two is a legitimate simplification, but **is optional**; if the planner collapses them, `:502`'s `v-if="canEditService"` alone is sufficient and `:510` disappears entirely |
| `:703` | read-only scripture reference (`slotScriptureText`) | Same shape; `v-else` viewer branch at `:707` is identical, same optional collapse |

**Class E — untouched fallbacks.** These already render for anyone the Class A/B gates exclude, and
now silently absorb the locked editor. **Change nothing:** `:468` (viewer team list) · `:496` (viewer
sermon topic) · `:517` (viewer passage) · `:680` (`Song — Empty`) · `:707` (viewer scripture) ·
`:759` / `:806` (viewer link anchors) · `:846` (viewer hymn) · `:934` (Roles viewer note — see § 7).

**Also delete outright:** `:135`'s `:title` branch, whose copy reads
`'Service is exported — cycle badge back to Draft to edit'` — it instructs the user to operate the
three-way cycle badge D-01 deletes. Retire it in the same commit as `toggleStatus` (`:1796-1807`) and
the `<button>` pill branch (`:57-71`); leave the `:title`'s remaining `!hasSermonContext` branch intact.

> **★ Gate the handlers, not just the templates** (30-VERIFICATION.md I-01). Six of seven Slides-tab
> mutation entry points are guarded by template `v-if` alone. A lifecycle lock that only hides
> templates inherits that fragility. Every control this spec says is "removed" must ALSO have its
> handler return early when locked.

**Why amber for the banner, when the `planned` pill is yellow and the `exported` pill is green:**
one banner serves both statuses (D-05/D-06), so it cannot match either pill. Amber is already this
file's established "attention, not error" family — `text-amber-400` for "Unsaved changes" (`:110`),
the amber existing-plan block in the export dialog (`:288-289`), and the amber "Overridden" role
badge (`:954`). The banner joins that family rather than founding a new one.

**Why `amber-950` (opaque) and not the existing `bg-amber-900/20` translucent pattern:** the banner
is `sticky` (see § 1), so page content scrolls *underneath* it. A translucent fill would show that
content through the banner's own text. Opacity is a functional requirement here, not a style choice.

### ★ Failed lifecycle transitions need their own surface — the autosave line is not it

This phase introduces the **Firestore rules layer that can reject a status transition** (R036,
three-layer enforcement). That is a genuinely new failure mode, and the obvious host for it does not
work:

- The existing autosave error line (`ServiceEditorView.vue:100-106`) is **removed while locked** by
  § 3 of this spec. A rejected **Reopen** fires while the service is still locked — precisely when
  that line does not render. Without a dedicated surface the user clicks Reopen, nothing happens,
  and nothing explains why.
- Even at `draft`, where that line does render, its copy is
  `"Couldn't save this order — reverted. Try dragging again."` — wrong for a lifecycle transition.

**Contract:**

| Aspect | Requirement |
|---|---|
| State | One `lifecycleError: Ref<string \| null>`, set to the matching copy above on a rejected transition |
| Surface while **locked** (failed Reopen) | A third child of the lock banner — see § 1's markup. Amber banner, red text, on screen at every scroll position, and the Reopen button sitting beside it is the retry affordance |
| Surface while **draft** (failed Mark as Planned) | An inline `<span class="text-sm text-red-400" data-testid="lifecycle-error">` in the header Save area (`:83-208`), immediately **after** the Mark as Planned button. No new box, no toast, no modal — the same minimal inline idiom Phase 29 established (`:100-106`, `SlideGrid.vue:90-94`) |
| **Status must not flip optimistically** | On rejection the pill, the banner and every gate keep showing the **old** status. A UI that shows `Draft` while the store still holds `planned` is the "it didn't save" defect class this milestone exists to close (`PITFALLS.md:299`) |
| Clearing | Cleared when the next transition attempt starts, and on any successful transition |
| Not this phase's | No `aria-live`, no toast, no retry/backoff. Phase 32 owns the persistent, announced status region (R040/R041) and may absorb this line |

**Deliberately no confirm on "Mark as Planned."** Per D-10, friction goes only where there are
consequences. Marking a draft as Planned is one-click reversible from the banner that appears in the
same instant. A dialog here trains people to click through the one that matters.

**Deliberately no completeness gate on "Mark as Planned."** A draft with zero slots can still be
marked Planned. Nothing upstream asked for a "your service is empty" gate, and inventing one here
would be a new product rule, not a lock layer.

## Phase-Specific Component Contracts

### 1. The lock banner

**Placement.** A single element, rendered **once**, as the first sibling after the header row block
(`ServiceEditorView.vue:38-209`) and before the export success/error banners (`:374-395`) and the
tab bar (`:398-435`). It is therefore directly beneath the status pill it explains (D-05: "near the
status pill"), and structurally OUTSIDE all three `v-show` tab panels (`:437`, `:932`, `:998`) — so
switching tabs cannot re-render, re-mount, re-animate or re-announce it. That is D-06's "one banner"
guaranteed by position, not by a flag.

**Stickiness — and why it isn't a redesign.** `AppShell.vue:34` makes `<main class="flex-1
overflow-y-auto">` the page's scroll container, and nothing between it and this banner sets
`overflow`, so `sticky top-0` pins the banner to the top of the scrollport. This is a direct answer
to the owner's standing complaint, recorded in `PROJECT.md:220` and `.planning/research/PITFALLS.md:299`
— *"saves were invisible above the fold"* / *"Save-status indicator placed where it scrolls out of
view during a long edit session… user reports 'it didn't save' for what was actually a visibility
problem."* A locked service is exactly that failure mode waiting to happen: a user scrolls to the
bottom of the Service Order tab, finds no **Add Element** button, and has no explanation on screen.
Sticky is a one-class property on one new element — it changes nothing about the placement of any
existing control, which is what Phase 36 owns.

```html
<div
  v-if="authStore.isEditor && isLocked"
  class="sticky top-0 z-10 mb-3 flex flex-wrap items-center gap-3 rounded-md border border-amber-800 bg-amber-950 px-4 py-3"
  data-testid="service-lock-banner"
>
  <!-- Lock glyph: the SAME path already in this file at :64-66 -->
  <svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 20 20" fill="currentColor"
       class="h-4 w-4 flex-none text-amber-400" aria-hidden="true">
    <path fill-rule="evenodd" d="M10 1a4.5 4.5 0 00-4.5 4.5V9H5a2 2 0 00-2 2v6a2 2 0 002 2h10a2 2 0 002-2v-6a2 2 0 00-2-2h-.5V5.5A4.5 4.5 0 0010 1zm3 8V5.5a3 3 0 10-6 0V9h6z" clip-rule="evenodd" />
  </svg>

  <p class="min-w-0 flex-1 text-sm text-amber-200" data-testid="service-lock-banner-text">
    <span class="font-medium">{{ lockBannerLead }}</span>
    {{ lockBannerBody }}
  </p>

  <button
    type="button"
    data-testid="reopen-service-btn"
    class="flex-none rounded-md border border-amber-700 bg-amber-900/60 px-3 py-2 text-sm font-medium text-amber-100 transition-colors hover:bg-amber-900"
    @click="onReopenRequest"
  >
    Reopen for editing
  </button>

  <!-- Failed-transition surface. `basis-full` puts it on its own row under the
       lead/body and the Reopen button, which doubles as the retry affordance. -->
  <p
    v-if="lifecycleError"
    class="basis-full text-sm text-red-300"
    data-testid="service-lock-banner-error"
  >{{ lifecycleError }}</p>
</div>
```

- `lockBannerLead` / `lockBannerBody` are **computed**, per 31-PATTERNS.md § 5's instruction to keep
  conditional copy in a computed (mirroring `deleteConfirmBody:1222-1244`) rather than in template
  `v-if` branches. Lead reads from `localService.status`; body reads from `hasPcExportEvidence`.
- **`z-10`, not `z-30`.** `AppSidebar.vue:4` is `fixed … z-30` and its mobile backdrop
  (`AppShell.vue:6`) is `z-20`. The banner sits in a later DOM subtree sharing the same root stacking
  context, so at `z-30` it would paint **over an open mobile sidebar and its backdrop**. `z-10` keeps
  it above page content, below the sidebar (`z-30`), below its backdrop (`z-20`), below the add-menu
  dropdown (`:919`, `z-20`) and below every `Teleport`ed dialog (`z-50`, `:213/:241/:267`). Its tie
  with the add-menu click-away backdrop (`:912`, `z-10`) is inert — Add Element renders only when
  `canEditService`, the banner only when `isLocked`, so the two can never coexist. No existing
  z-index changes.
- `text-red-300` (not `red-400`) for the error line: it sits on the opaque `amber-950` fill rather
  than the `gray-950` page, and the lighter step keeps contrast where the file's other red text
  (`text-red-400` on gray) sits. This is the existing destructive family, not a new colour.
- `flex-wrap` + `min-w-0 flex-1` on the text: at narrow widths the Reopen button wraps to its own
  line rather than crushing the copy. `flex-none` keeps the glyph and button from shrinking.
- **No `aria-live`, no `role="alert"`, no `role="status"`.** This is persistent page furniture, not
  an announcement. A live region here would re-announce on every reactive touch and directly fight
  D-06's "one banner." The lock glyph is `aria-hidden` because the sentence already says "locked."
- **No enter/leave transition.** It appears when the status changes and stays put.

**Viewers (non-editors) do NOT see the banner** — `v-if` includes `authStore.isEditor`.

> **The call, and the reasoning** (31-CONTEXT.md § Deferred leaves this to discretion):
> a viewer cannot edit the Service Order or Roles tabs regardless of status — the editor controls are
> already `v-if="authStore.isEditor"`-gated (`:443, :488, :502, :579, :617, :666, :690, :729, :776,
> :822, :867, :880, :897`, and the Roles tab *button* is editor-gated at `:410`, with the panel's own
> viewer branch at `:934-936`). Showing a viewer
> a banner that says "editing is locked" would explain a restriction that is **not the reason they
> cannot edit**, and would hand them a **Reopen for editing** button they are not permitted to use —
> a dead affordance, which is precisely what D-05 exists to eliminate. Viewers keep the status pill
> (`:72-78`, unchanged), which is the honest signal: it tells them where the service is in its
> lifecycle without misattributing their own read-only experience to it.

## Accessibility Note

- **Status pill:** now a `<span>`, correctly out of the tab order. Do not add `role="status"` — that
  is a live region and would announce on every reactive touch. The visible text ("Draft" / "Planned"
  / "Exported") is the accessible name; the glyphs are decorative and carry `aria-hidden="true"`.
- **Lock banner:** deliberately **not** a live region and **not** `role="alert"`. It is persistent
  page furniture, present from render, not an event announcement. Making it live would re-announce on
  every tab switch and reactive update — the exact behaviour D-06 forbids. Its `<p>` is read in
  normal document order, immediately after the status pill it explains.
- **Reopen confirm dialog:** matches the existing confirm dialogs in this file exactly, including
  their known gaps — no `role="dialog"`, no `aria-modal`, no focus trap, no Escape handler
  (`:212-237`, `:240-263`, `:266-372` all lack these). **Do not fix that here.** Retrofitting dialog
  semantics to one of four dialogs would leave the app inconsistent and is a separate, additive
  commitment. Recorded in § Phase 36 Handoff.
- **Removed controls are removed, not `aria-disabled`** (D-05) — nothing appears in the tab order
  that cannot be operated, which is the accessibility win of "removed, not disabled."
- **Keyboard reordering** remains out of scope (29-UI-SPEC § Accessibility Note, REQUIREMENTS Future
  Requirements). Locking removes drag; it does not create a keyboard-drag obligation.
