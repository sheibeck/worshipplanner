<objective>
Enforce the draft lock on the `slideGroups` collection (R036), and — in the same commit —
stop the client from attempting writes it will now be denied.

**★ Why these two must not be separated.** `useSlideshowAssembly`'s materialization
watcher runs with `{ immediate: true }`: it writes to `slideGroups` when an editor merely
OPENS a service, with no user action. `rebuildOutcomes` does the same. Both read
`canWrite = isEditor` at `ServiceEditorView.vue:1366`. Ship the rule alone and **every
locked service throws permission-denied the moment it loads** — a worse failure than the
one this phase fixes. And because `src/rules.test.ts` is excluded from the default vitest
run, that regression would ship green.

Research's verdict on the enforcement approach was **suppress, not carve out**: narrowing
that one `canWrite` expression closes all three composable write sites plus four of seven
`SlideGrid` mutation entry points. A rules-layer carve-out for "load-time materialization"
is not expressible anyway — the rules layer cannot tell a materialize write from a
user edit.
</objective>

**Known soundness ceiling, accepted by research — do not try to close it.** A
`slideGroups` document's id IS the slot id, so the parent service is reachable only via
the `serviceId` FIELD. That makes `serviceId` spoofable on CREATE (research probe E6
executed this). The residual hole is accepted because the attacker must already be an org
editor who could simply delete the whole service. `serviceId` is made immutable on update,
which closes the re-parenting path that would otherwise be the real risk.

## Task 1 — The /slideGroups rule

Add this to `firestore.rules`, verbatim from research:

```javascript
      // Slide groups — one doc per slot (doc id IS the slot id), so the parent
      // service is reachable only via the serviceId FIELD. Two extra billed
      // reads per write (exists + get); 3 of the 10-call budget once
      // isOrgEditor's own get() is counted.
      match /slideGroups/{groupId} {
        function svcPath(sid) {
          return /databases/$(database)/documents/organizations/$(orgId)/services/$(sid);
        }
        function parentDraft(sid) {
          return exists(svcPath(sid)) && get(svcPath(sid)).data.get('status','draft') == 'draft';
        }
        function parentGone(sid) { return !exists(svcPath(sid)); }

        allow read: if isOrgMember(orgId);

        allow create: if isOrgEditor(orgId)
          && request.resource.data.keys().hasAll(['serviceId'])
          && parentDraft(request.resource.data.serviceId);

        // serviceId is immutable (mirrors quarterShares' orgId immutability,
        // firestore.rules:118) — otherwise a group could be re-parented from a
        // draft service onto a locked one and edited through the seam.
        allow update: if isOrgEditor(orgId)
          && resource.data.keys().hasAll(['serviceId'])
          && request.resource.data.serviceId == resource.data.serviceId
          && parentDraft(resource.data.serviceId);

        // Delete is deliberately MORE permissive than update: an orphan (parent
        // service deleted) or a legacy doc with no serviceId must remain
        // deletable, or it is wedged in the database forever with no cleanup path.
        allow delete: if isOrgEditor(orgId)
          && (!resource.data.keys().hasAll(['serviceId'])
              || parentGone(resource.data.serviceId)
              || parentDraft(resource.data.serviceId));
      }
```

**Do not tighten `allow delete` to match `allow update`.** An earlier research iteration
did exactly that and left orphan groups permanently unwritable AND undeletable. The
asymmetry is deliberate; keep the comment explaining it.
