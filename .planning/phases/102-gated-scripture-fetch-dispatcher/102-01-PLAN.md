<objective>
Introduce the single client-side scripture-fetch choke point (`src/utils/scriptureApi.ts`, the `isAiEnabled()` analog) and route both consumer components through it. The dispatcher owns two concerns currently duplicated inline in the components: (1) ESV vs NLT version dispatch, and (2) the per-org Bible-API gate (`authStore.isBibleApiEnabled`, Phase 101), checked FIRST so a disabled org never calls a proxy.

Purpose: R296 (no regression when enabled — the dispatcher relocates the existing inline dispatch, it does not re-implement fetching) and the client half of R297 (no proxy call + graceful degradation when disabled). The server half (defense-in-depth) is Plan 02.

Output: `src/utils/scriptureApi.ts` + its unit tests; `ScriptureInput.vue` and `CongregationalEditor.vue` refactored to call the dispatcher; both component test suites updated so the enabled path stays green and the disabled path is proven to no-op.
</objective>

    - Enabled + version 'NLT': dispatches to nltApi.fetchNltPassageText(query), does NOT call esvApi.fetchPassageText, returns { status: 'ok', text }.
    - Disabled (isBibleApiEnabled false): returns { status: 'disabled' } and invokes NEITHER underlying fetch fn (assert with spies — this is the R297 core assertion).
    - Enabled but the underlying fetch throws: returns { status: 'error' } (never re-throws) — mirrors today's component catch behavior so R296 error UX is unchanged.
  </behavior>
  <action>
Create `src/utils/scriptureApi.ts` exporting a discriminated result type and one async dispatcher:

- Result type `ScriptureFetchResult` = `{ status: 'ok'; text: string } | { status: 'disabled' } | { status: 'error' }`.
- `export async function fetchScriptureText(query: string, version: 'ESV' | 'NLT'): Promise<ScriptureFetchResult>`.

Behavior, in order: (1) read the auth store INSIDE the function body via `useAuthStore()` from `@/stores/auth` — NEVER at module-evaluation time (Pinia needs an active app instance; this is the same constraint documented on claudeApi.ts::isAiEnabled). (2) Gate FIRST: if `!authStore.isBibleApiEnabled`, `return { status: 'disabled' }` WITHOUT calling any fetch — this is the single-leg client gate (Phase 101's `isBibleApiEnabled` is already false-when-absent). (3) Otherwise dispatch by version inside a try/catch: `version === 'NLT' ? await fetchNltPassageText(query) : await fetchPassageText(query)` (imported from `@/utils/nltApi` and `@/utils/esvApi`), returning `{ status: 'ok', text }`. (4) On any thrown error, `return { status: 'error' }` — the dispatcher owns error mapping so the enabled-path failure mode stays identical to today (R296).

Do NOT re-implement or alter ESV/NLT parsing/trimming — the dispatcher only relocates the inline `version === 'NLT' ? ... : ...` dispatch and adds the gate.

Create `src/utils/__tests__/scriptureApi.test.ts`: `vi.mock('@/utils/esvApi')` and `vi.mock('@/utils/nltApi')` with spy fns (mirror the existing mock style in src/components/__tests__/ScriptureInput.test.ts); `vi.mock('@/stores/auth')` returning `useAuthStore: () => ({ get isBibleApiEnabled() { return mockBibleApiEnabled } })` with a flippable `let mockBibleApiEnabled`. Cover every case in the behavior block, asserting for the disabled case that BOTH fetch spies were `not.toHaveBeenCalled()`.
  </action>
