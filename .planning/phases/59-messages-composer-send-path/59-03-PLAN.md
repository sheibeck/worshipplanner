<objective>
Add the send half of the path: `sendQueuedMessage` (`onDocumentCreated` on `.../messages/{messageId}`,
the ONE Function holding `RESEND_API_KEY`). Its handler runs a transactional idempotency claim, re-resolves
recipients from scratch server-side, renders per-recipient tokens, sends via Resend (mocked in tests),
writes one `recipients/{id}` doc per recipient, rolls up `deliveryCounts`, and flips the message status.
A pure `functions/src/messageTokens.ts` isolates token rendering so the R138/R139 substitution logic is
unit-tested on its own.

Purpose: R131 (only this Function holds the provider secret; it re-resolves recipients via the 59-01 port
and discards the client's list — Anti-Pattern 1), R138 (server renders the four tokens authoritatively),
R139 (personalized per recipient — "their roles" is each person's own roles). Structure mirrors the shipped
`requestPptxRenderHandler`/`requestPptxRender` (`functions/src/index.ts`), but the transactional
`queued→sending` claim is GENUINELY NEW code (the PPTX precedent has no status claim — 59-RESEARCH.md
Pitfall 1) and MUST be tested for the duplicate-trigger no-resend case.
Output: `functions/src/messageTokens.ts` (+ test), `sendQueuedMessageHandler` + the secret-bound
`sendQueuedMessage` wrapper in `functions/src/index.ts`, and new describe blocks in
`functions/src/index.test.ts` with Resend mocked.

DEPLOY-GATED (v1.7 grant): ships built/tested/UNDEPLOYED against a MOCKED Resend. No real email, no secret
set, no deploy.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Firestore trigger → sendQueuedMessage (Admin SDK) | The message doc's recipientSelector/options are attacker-influenceable (written via the enqueue path); the handler re-resolves and re-validates rather than trusting them |
| sendQueuedMessage → Resend API | The ONLY place the provider key leaves Secret Manager; the send list and key must never reach the client |
| Retried onDocumentCreated (at-least-once delivery) | A duplicate trigger for the same doc must not double-send |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-59-03a | Spoofing / Elevation | client forges a recipient list to email arbitrary addresses | high | mitigate | sendQueuedMessage re-resolves recipients from Firestore via the 59-01 Admin-SDK port; the doc's recipientSelector is who-to-resolve intent, never a final email list (Anti-Pattern 1). |
| T-59-03b | Duplication | retried at-least-once trigger double-sends | high | mitigate | Transactional queued→sending claim; a second invocation sees a non-'queued' status and returns without sending. NEW code — the duplicate-trigger no-resend case is an explicit test (Pitfall 1). |
| T-59-03c | Information Disclosure | provider key / recipient emails leaking (bundle or logs) | high | mitigate | RESEND_API_KEY via defineSecret bound ONLY to this Function; never logged; do not log the key or full recipient emails at info level (59-RESEARCH.md V6/V7). |
| T-59-03d | Input Validation | a Firestore id with a disallowed char rejected by Resend tags | medium | mitigate | Validate the four ids are tag-safe [A-Za-z0-9_-] before send (Pitfall 3); they are the exact path segments Phase 60's webhook echoes back. |
| T-59-03e | Denial of Service / Availability | one bad address aborts the whole batch | medium | mitigate | Per-recipient try/catch → that recipient is status:'failed', the batch continues, the message rolls up to 'partial' (requestPptxRender/cleanupExpiredMedia per-item resilience). |
| T-59-03f | Elevation | sendCopyToSelf leaking to a client-supplied address | medium | mitigate | The copy address is resolved server-side from the requesting editor's member/auth record (requestedByUid), never from client input. |
| T-59-SC | Tampering | npm/pip/cargo installs | low | accept | Zero packages installed this plan (resend was installed + gated in 59-01). Resend is mocked in tests; no real send, no secret. |
</threat_model>
