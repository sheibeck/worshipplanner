## Planner assumptions and decisions recorded here (not settled by research)

1. **A3 — extend the existing types rather than add a `SlideContentKind`. CONFIRMED as a planner
   decision.** 42-UI-SPEC.md states the ready state is "byte-identical treatment to the existing
   `ImageSlide` path," which makes pending/failed variations on the same content kind rather than a
   new kind. A new discriminated `contentKind` would require a new arm in every exhaustive
   `switch (slide.contentKind)` across `slideDisplay.ts`, `PresentationViewer.vue`,
   `EditSlideDrawer.vue` and `slideActionMenuItems` — a far larger diff for no gain.
2. **The two new `AssemblyInputs` fields are OPTIONAL, not required.** Rationale: an absent map is the
   legitimate "no render data loaded" state, and for a deck with no `renderImportId` it must behave
   byte-identically to today (D-16). Making them required would force a churn of every existing
   `AssemblyInputs` fixture across ~4,200 lines of engine tests, which is a large surface for
   accidental breakage and buys nothing. **Verified:** `grep -rn 'renderImportId' src/` shows no
   existing test fixture sets the field, so every current IMPORTED test keeps its exact behaviour.
3. **Open Question 2 — settled by research, not bounced back.** Every ready-state slide takes the
   generic `'IMAGE'` eyebrow. Pitfall 1 shows no reliable per-index pairing exists, so any
   per-page label derived from parsed text would be unsound. `slideContentLabel` therefore needs no
   change at all: pending/failed/ready entries all carry `contentKind: 'image'` and already return
   `'IMAGE'`.
4. **`status: 'ready'` with `renderedCount` absent or < 1 resolves to FAILED, not to zero entries.**
   The server's own three-conjunct ready gate makes this state unproducible; a client that emitted
   zero entries for it would make a deck silently vanish mid-service. Failing loudly with the
   generic fallback sentence is the defined, non-blank state.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| render document fields → assembled slide content | `status`, `renderedCount` and `failureReason` decide what a congregation sees; a tampered document (T-42-01) crosses here |
| parsed deck text → congregation-facing slide | parsed text is a search/label artifact and must not be presented as the finished slide once a render exists |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-42-04 | Tampering | `failureReason` propagation | medium | mitigate | `failureReason` is copied onto `SlideBase.renderFailureReason` unchanged here, and its field doc comment states in situ that it must route through the failure-sentence lookup and never reach a template directly. The lookup with its generic fallback arm lands in 42-06; this plan's contribution is to keep the raw slug on a field named to make direct rendering look wrong. |
| T-42-05 | Tampering | image path source | medium | mitigate | `importedEntryContent` builds a ready-state `imageUrl` ONLY from `renderedUrls[pageNumber - 1]` — an array the composable produced from `renderedPagePath(orgId, renderImportId, n)`. No render-document field ever reaches an `<img>` source; the client `PptxRenderDoc` omits the path member entirely (42-02). |
| T-42-07 | Spoofing | deck ↔ render join and entry identity | high | mitigate | A render's pages appearing under the wrong deck is invisible to the operator and maximally public. Mitigated here by making `resolveImportedRender` return `parsed` unconditionally when `deck.renderImportId` is absent, so a deck that never requested a render can never resolve one; and by minting ready-state identities as `rendered-page-N` scoped inside the entry's own `importId`, so `derivedIdentityKey`'s `imported:{importId}:{innerSlideId}` key cannot collide across decks. Completed in 42-08 by the `${importId}:${renderedCount}` URL cache key. |
| T-42-09 | Denial of Service | reconciler input handling | low | mitigate | A tampered `renderedCount` (T-42-01) of an absurd magnitude would cause the caller to mint that many entries and, in 42-08, that many `getDownloadURL` calls. Scope is bounded to the attacker's own org and their own deck, and closing T-42-01 removes the write path entirely; accepted as residual after that fix. The reconciler itself performs no allocation proportional to a count it did not receive from a rules-gated read. |
| T-42-SC | Tampering | npm/pip/cargo installs | high | accept | No install task in this plan; `42-RESEARCH.md § Package Legitimacy Audit` records zero new dependencies. |
</threat_model>
