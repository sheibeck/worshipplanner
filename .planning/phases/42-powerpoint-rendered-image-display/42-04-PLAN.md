<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| render document → stored `SlideGroup` document | a render transition causes a Firestore WRITE to the group; a tampered render document (T-42-01) can therefore mutate persisted user data |
| derived entries ↔ user-added entries | the rebuild owns the former and must never touch the latter |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-42-01 | Tampering | forged render state driving a group rebuild | high | mitigate | Closed at the rules layer in 42-01. Residual risk considered here: a forged `ready`/`renderedCount` would rewrite a stored group's derived entries. Bounded by `survivingEntries`, which keeps every non-derivable (user-authored) entry regardless of what the derivation produces — asserted by Task 2 Block 4. The rules fix is the primary control; this is defence in depth. |
| T-42-07 | Spoofing | deck ↔ render join in the derivation | high | mitigate | Task 2 Block 1 asserts a deck with no `renderImportId` derives its parsed entries even when a render document for another id is present in the map, and that ready-state identities are page-scoped inside the entry's own `importId`. A render can therefore never surface under a deck that did not request it. |
| T-42-10 | Tampering | signature collision across distinct render states | medium | mitigate | Under the pre-existing `:`/`|` encoding, two distinct decks or render states could produce one signature, because PPTX slide text can contain both delimiters. Mitigated by delegating to `importedSourceSignature`'s ASCII control-character encoding (42-03) and asserted by Task 2 Block 2's collision case. |
| T-42-SC | Tampering | npm/pip/cargo installs | high | accept | No install task in this plan; `42-RESEARCH.md § Package Legitimacy Audit` records zero new dependencies. |
</threat_model>
