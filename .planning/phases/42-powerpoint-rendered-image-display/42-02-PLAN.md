<objective>
Build the render-status data layer: a client-side type that mirrors the server document's consumed
fields, the deterministic rendered-page Storage-path convention, a Pinia store that keeps one LIVE
per-`renderImportId` Firestore listener for the current service, and the Wave 0 test scaffolding the
rest of the phase depends on.

Implements D-04 (`onSnapshot`, not a one-shot `getDoc`) and D-20 (subscription lives in a store, so
the existing `useSlideshowAssembly` → store data flow is extended rather than paralleled).

Purpose: 42-PATTERNS.md flags this as the one genuinely new design in the phase — **nothing in this
codebase manages a dynamic set of live per-document `onSnapshot` listeners keyed off another
document's field.** Every existing store either subscribes to a whole collection or does a one-shot
per-id fetch. The listener lifecycle is written fresh and deliberately, not copied.

Output: three new modules, two new test files, and the module-scope mocks that unblock every later
plan's composable tests.
</objective>

    - A snapshot where `exists()` is true stores the document's data under its import id; a snapshot where `exists()` is false DELETES that id from the map rather than storing a placeholder.

    - `unsubscribeAll()` calls every outstanding `Unsubscribe` and empties the map; calling it twice is a no-op, not a throw.
    - Calling `syncSubscriptions` with an unchanged id set does not re-open any listener (the diff is by id, not by array identity).

    - tear everything down and return when `orgId` is null, or when `orgId` differs from
      `subscribedOrgId` (an org switch invalidates every path);
    - diff the incoming id set against `listeners.keys()`; for each ADDED id open
      `onSnapshot(doc(db, 'organizations', orgId, 'pptxRenders', id), …)` and record its `Unsubscribe`;

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Firestore render document → client display code | `status`, `renderedCount` and `failureReason` are consumed to decide what a congregation sees; a tampered document (see T-42-01) reaches this boundary |
| client → Firebase Storage | `renderedPagePath` builds a path the browser then resolves through `getDownloadURL` under `storage.rules`'s org gate |
| long-lived browser session → Firestore listener pool | a projection machine may hold this page open for hours across many service navigations |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-42-05 | Tampering | image path derived from render-document data | medium | mitigate | A render document's Storage-path field is server-written but writable today (T-42-01). If display code built an `<img>` source from it, a tampered document could point the projector at an arbitrary object. Mitigated structurally in Task 1: the client `PptxRenderDoc` omits that member entirely, so reading it is a compile error, and `renderedPagePath(orgId, renderImportId, pageNumber)` — built only from ids the client already trusts — is the sole producer of a rendered-page path. |
| T-42-06 | Denial of Service | `usePptxRenders` listener set | low | mitigate | Unbounded `onSnapshot` accumulation across service navigations exhausts connections and memory in a long-lived operator session (Pitfall 5). Mitigated in Task 2 by diffing the id set on every sync and calling `Unsubscribe` for departed ids, plus `unsubscribeAll()` for teardown; proven by a spy-call-count assertion. |
| T-42-07 | Spoofing | deck ↔ render join | high | mitigate | Showing one deck's pages under another deck's identity is invisible to the operator and maximally public. Mitigated here by keying every map on `ImportedDeck.renderImportId` — never on `ImportedSlot.importId`/`ImportedDeck.id`, which is a different identifier — and by removing an id's cached state the moment its listener is torn down, so a stale render can never outlive its subscription. Completed in 42-08 by the `${importId}:${renderedCount}` URL cache key. |
| T-42-SC | Tampering | npm/pip/cargo installs | high | accept | No install task in this plan; `42-RESEARCH.md § Package Legitimacy Audit` records zero new dependencies. |
</threat_model>
