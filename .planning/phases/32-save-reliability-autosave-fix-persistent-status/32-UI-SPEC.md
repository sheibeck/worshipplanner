# Phase 32 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** this phase does not change *what* gets saved, does not touch Phase 31's lock/reopen
UI, and does not redesign header or tab chrome (Phase 36 owns that). It (1) fixes the autosave-swallowing
bug, (2) adds ONE persistent, `aria-live` inline save-status indicator shared by four surfaces, and
(3) adds a minimal app-level failure toast. Everything here composes with — and does not restyle —
Phase 31's lock banner and `lifecycleError` surface, which stay exactly as shipped.

**Upstream decisions this spec implements, not re-opens (32-CONTEXT.md):** repro-test-first discipline;
`useSaveStatus` as a Pinia store sitting ABOVE `useAutoSave` (not rewriting it); status keyed by surface
id; `AutoSaveStatus` gains `'error'`; "above the fold" read as "parked in the global app header, far from
the content" → status lives in a sticky sub-header of the editing surface itself; `Saved HH:MM` never
fades; failure-only toast via a small hand-written host in `AppShell.vue`; `aria-live="polite"` on the
status region, `role="alert"` on the toast; Phase 31's `autosaveErrorSource` reorder/edit split is
preserved verbatim.

### The shared state model (naming is a recommendation for the planner, not a re-derivation of the store's internals)

| Value | Meaning |
|-------|---------|
| `AutoSaveStatus` | `'idle' \| 'pending' \| 'saving' \| 'saved' \| 'error'` — extends `src/composables/useAutoSave.ts:3`, which today has no `'error'` member at all |
| `useAutoSave.ts` fade timers | **Deleted.** Lines 87-93 (inside `scheduleSave`'s timeout) and 143-148 (inside `flush()`) each set a `setTimeout(..., 3000)` that resets a `'saved'` status back to `'idle'`. R040 replaces this: `'saved'` is terminal until the next `'pending'` transition. Both call sites go; `clearSavedFadeTimer` / `savedFadeTimer` become dead code and should be removed with them. |
| `useAutoSave.ts` error path | **New requirement, not currently met.** Today's `try { await saveFn() … } finally { saving = false }` has no `catch` — a rejected `saveFn()` propagates uncaught and never sets `status`. Per this codebase's own BL-02 lesson (`ServiceEditorView.vue:2054-2092`, hand-fixed there for exactly this reason), a rejection **must** set `status.value = 'error'`, never leave it stranded at `'saving'` and never silently drop to `'idle'`. Exact TypeScript shape (a thrown value, a returned discriminated result, an `onError` callback) is the planner's call — this spec fixes only the required behavior. |
| `useSaveStatus` | Pinia store at `src/stores/saveStatus.ts` (32-CONTEXT.md, not re-opened here). Keyed by a `surfaceId: string`. Convention for this phase's four callers: `` `service:${serviceId}` ``, `` `congregational:${readingId}` ``, `` `scripture:${readingId}` ``, `` `song-lyrics:${songId}` ``. Each entry carries at least `{ status: AutoSaveStatus, savedAt?: Date, errorText?: string }`. How a surface pushes into the store (a `watch()` in the component vs. an optional param threaded through `useAutoSave`) is an implementation detail; this spec fixes only the rendered contract in § Phase-Specific Component Contracts. |
| `useToasts` (new, this spec's discretion call) | A second, single-purpose Pinia store, `src/stores/toasts.ts` — kept separate from `saveStatus.ts` rather than folded in, matching the existing one-store-per-concern convention (nine stores, each one thing). Holds an array of `{ id, message }`; a `ToastHost.vue` component mounted in `AppShell.vue` renders it. See § 4. |

> **Resolution of CONTEXT's "component + variant prop vs. component + wrapper" discretion point:**
> **one component, no wrapper.** `SaveStatusIndicator.vue` takes a single `surfaceId` prop and reads its
> own entry from `useSaveStatus` reactively. Each of the four call sites passes a different `surfaceId`;
> none needs a bespoke wrapper, because the four surfaces already differ only in *where* they mount the
> component (§ 4/§ 5), not in what it renders.

## Phase-Specific Component Contracts

### 1. `useAutoSave.ts` — required behavior changes

These are the composable's contract, not a full rewrite — `useAutoSave` keeps owning the debounce, the
inflight guard, `flush()` and `cleanup()` (32-CONTEXT.md). Two changes are required for R040/R041 to be
true at all:

| Change | Why |
|---|---|
| Remove the 3-second `'saved' → 'idle'` fade (both call sites: inside `scheduleSave`'s timeout and inside `flush()`) | This is the exact behavior R040 replaces. `savedFadeTimer` / `clearSavedFadeTimer` become dead code and go with it. |
| Add a `catch` around `await saveFn()` in both the debounced path and `flush()`, setting `status.value = 'error'` | Today there is no catch at all — a rejection propagates uncaught and `status` is left wherever it was (often stranded at `'saving'`). `AutoSaveStatus` gains `'error'` as its fifth member. |

**Existing coverage that must survive:** `src/composables/__tests__/useAutoSave.test.ts`. Any new test
for the error path is additive, not a replacement.

### 2. `SaveStatusIndicator.vue` — the one shared component

```html
<!-- src/components/SaveStatusIndicator.vue -->
<div
  class="text-xs"
  aria-live="polite"
  aria-atomic="true"
  data-testid="save-status"
>
  <span v-if="entry.status === 'pending'" class="italic text-gray-400">Saving soon…</span>
  <span v-else-if="entry.status === 'saving'" class="italic text-gray-400">Saving…</span>
  <span v-else-if="entry.status === 'saved'" class="text-green-400">Saved {{ formattedSavedAt }}</span>
  <span
    v-else-if="entry.status === 'error'"
    class="text-red-400"
    data-testid="save-status-error"
  >{{ entry.errorText }}</span>
</div>
```

- **Props:** `surfaceId: string`. The component reads its own entry from `useSaveStatus` reactively —
  no per-surface wrapper component (see § Design System resolution above).
- **`aria-live="polite"` wraps ALL four rendered states, including `error`.** Routine transitions
  (pending/saving/saved) must not interrupt; a failure is *also* read in place, politely, by whichever
  screen-reader user is already focused near it — the toast (§ 4) is the separate, assertive interrupt.
  Do not add a second, nested `aria-live` region inside the error branch — one region for the whole
  component.
- **`aria-atomic="true"`:** each state transition fully replaces the text content (not an append); atomic
  announcement means the reader speaks the new sentence whole, not a diff.
- **Renders nothing (`idle`)** exactly as today's three editors already do — no placeholder box, no
  layout reservation. This is deliberate: before the first edit in a session there is nothing to report.
- Icon-free by design — text alone is what makes the `aria-live` announcement meaningful; a color-only or
  dot-only pending state (today's three editors' yellow dot, `title="Unsaved changes"`) is **replaced**
  by real text so it is announced, not just seen.

### 3. Placement — `ServiceEditorView.vue`: a new sticky status bar

**Why a *new* element rather than editing the existing "Save area" in place.** The existing Save area
(`ServiceEditorView.vue:97-207`) mixes the status text with Undo / Suggest All Songs / Mark as Planned /
Export — a `flex items-center gap-3` row that is **not sticky** and scrolls away with the rest of the
header once the user scrolls into a long Service Order list. That is precisely the failure mode
`PITFALLS.md:299` and `PROJECT.md:220` record ("save-status indicator placed where it scrolls out of
view … user reports 'it didn't save'") and precisely what Phase 31's lock banner was built to fix for the
*locked* case (31-UI-SPEC § 1, `sticky top-0 z-10`). This phase applies the same fix to the *editable*
case, which the banner structurally cannot cover — the banner and the status bar are mutually exclusive
(see below).

**The status bar occupies the exact same layout slot the lock banner occupies, and the two never
coexist.** For an editor, `canEditService = isEditor && !isLocked`: at `draft` the service is editable
and nothing is locked, so the status bar renders and the banner does not; at `planned`/`exported` the
service is locked, so the banner renders (31-UI-SPEC § 1) and the status bar does not (nothing can be
dirty on a locked service). A viewer (`!isEditor`) sees neither, for the same reason 31-UI-SPEC § 1
excludes viewers from the banner. Because the two are structurally exclusive, both can safely use
`sticky top-0 z-10` — they are never stacked, so there is no offset math to do.

```html
<!-- Rendered once, as a sibling immediately before the lock banner (31-UI-SPEC § 1),
     i.e. after the header row (:38-209) and before the export success/error
     banners (:556-573) and the tab bar (:398-435). Outside all three v-show tab
     panels, same reasoning as the lock banner: switching tabs must not re-mount
     or re-announce it. -->
<div
  v-if="canEditService"
  class="sticky top-0 z-10 mb-3 flex items-center gap-2 rounded-md border border-gray-800 bg-gray-900 px-4 py-2"
  data-testid="service-save-status-bar"
>
  <SaveStatusIndicator :surface-id="`service:${serviceId}`" />
</div>
```

- `z-10` — identical reasoning to 31-UI-SPEC § 1's banner: below the sidebar (`z-30`) and its backdrop
  (`z-20`), below every `Teleport`ed dialog (`z-50`), below the toast host (`z-[60]`, § 4). Since it is
  never on screen at the same time as the banner, there is no tie to resolve with it either.
  `mb-3` (12px) matches the banner's own bottom margin so the vertical rhythm doesn't jump between the
  two mutually-exclusive states.
- `bg-gray-900 border-gray-800` — the ordinary secondary-surface pairing (§ Color), not the banner's
  opaque amber. This is routine chrome, not a warning; it should read as quieter than the banner even
  though both are sticky and opaque for the same structural reason (content scrolls underneath either).
- **The existing "Save area" (`:97-207`) keeps Undo / Suggest All Songs / Mark as Planned / Export** —
  only the status `<template v-if="canEditService">...</template>` block (`:103-136`, including the
  redundant `isDirty` → `"Unsaved changes"` fallback at `:130-135`) is **deleted from there**. That
  fallback becomes provably dead once migrated onto `useAutoSave`: the composable's watcher sets
  `status.value = 'pending'` synchronously on every dirty mutation (`useAutoSave.ts:112`), so "dirty but
  not pending" can no longer occur. Do not re-implement it elsewhere — its disappearance is the
  de-duplication R040 asks for, not a regression.
- **Mobile / narrow width:** no special-casing needed. The bar's only content is a few words of text in
  a `flex items-center` row with no button — unlike the banner it has nothing that needs `flex-wrap`.

### 4. Failure toast — `ToastHost.vue`, mounted in `AppShell.vue`

**Scope boundary — read before wiring this up.** This toast is scoped to the **autosave `'error'`
state** (§ 1/§ 2) on all four surfaces. It is explicitly **not** wired to `lifecycleError`
(rejected `Mark as Planned` / `Reopen for editing`, 31-UI-SPEC's own surface) — 32-CONTEXT.md's Phase
Boundary lists "the Phase 31 lock/reopen semantics" as out of scope, and `lifecycleError`'s own contract
table (31-UI-SPEC § Copywriting Contract) already says explicitly "Phase 32 owns the persistent, announced
status region … **and may absorb this line**" as an option, not a mandate. Absorbing it would mean this
phase re-opening Phase 31's dedicated banner/inline-span design, which the phase boundary forbids. Leave
`lifecycleError` exactly as shipped.

```html
<!-- AppShell.vue — new sibling after </main>, still inside the flex column so it
     stays fixed regardless of scroll. -->
<main class="flex-1 overflow-y-auto">
  <slot />
</main>
<ToastHost />
```

```html
<!-- src/components/ToastHost.vue -->
<div
  class="fixed inset-x-4 bottom-4 z-[60] flex flex-col items-stretch gap-2
         sm:inset-x-auto sm:right-6 sm:bottom-6 sm:w-full sm:max-w-sm"
  data-testid="toast-host"
>
  <div
    v-for="toast in toastStore.toasts"
    :key="toast.id"
    role="alert"
    class="flex items-start gap-2 rounded-md border border-red-800 bg-red-950 px-4 py-3 text-sm text-red-400 shadow-2xl"
    :data-testid="`toast-${toast.id}`"
  >
    <svg xmlns="http://www.w3.org/2000/svg" class="h-4 w-4 flex-none" fill="none" viewBox="0 0 24 24" stroke="currentColor" stroke-width="2" aria-hidden="true">
      <path stroke-linecap="round" stroke-linejoin="round" d="M12 9v3.75m-9.303 3.376c-.866 1.5.217 3.374 1.948 3.374h14.71c1.73 0 2.813-1.874 1.948-3.374L13.949 3.378c-.866-1.5-3.032-1.5-3.898 0L2.697 16.126ZM12 15.75h.007v.008H12v-.008Z" />
    </svg>
    <p class="min-w-0 flex-1">
      <span class="font-medium">Save failed.</span> {{ toast.message }}
    </p>
    <button
      type="button"
      class="flex-none text-red-400 hover:text-red-300"
      aria-label="Dismiss"
      @click="toastStore.dismiss(toast.id)"
    >×</button>
  </div>
</div>
```

- **`z-[60]`** — above every existing `z-50` Teleport dialog/drawer (including `EditSlideDrawer.vue`,
  which is exactly where a `SongLyricEditor`-family failure could occur behind a modal). Nothing in this
  codebase currently uses `z-[60]` or higher, so this is a genuinely new top layer, deliberately reserved
  for this one purpose.
- **Position:** bottom-right on `sm:` and up (`sm:right-6 sm:bottom-6 sm:max-w-sm`, 384px cap); full
  width with 16px side margins below `sm:` (`inset-x-4 bottom-4`). Bottom-right avoids covering the
  center-screen confirm dialogs (`ServiceEditorView.vue`'s four Teleport dialogs all center via `inset-0
  flex items-center justify-center`) and avoids the top of the viewport, which the sticky status bar /
  lock banner already own.
- **`role="alert"` only — no additional `aria-live="assertive"`.** `role="alert"` already implies an
  assertive, atomic live region per the ARIA spec; pairing both is redundant.
- **Edge-triggered, not level-triggered.** A toast is pushed only on the transition **into** `'error'`
  for a given surface, never on every reactive tick while `status` remains `'error'`. Watch each
  surface's status for a `!== 'error' → === 'error'` edge (however the planner wires the store watch);
  an 800ms debounce retrying against a still-down network must not spam a new toast every 800ms.
- **Toast body mirrors the inline text, always.** No independent toast copy exists for the two failure
  variants — whatever `SaveStatusIndicator` just rendered inline for that surface (§ Copywriting
  Contract) is the exact string pushed to the toast. One string to maintain per failure mode, not two.
- **Dismissal:** auto-dismiss after 6000ms (long enough to read two sentences), plus the manual `×`
  button at any time. **No hover-to-pause** — kept deliberately minimal per 32-CONTEXT.md's "do not add
  a toast library for one use" instruction; this is a one-shot notification, not a persistent worklist.
- **Stacking:** an array in `useToasts`, rendered oldest-to-newest top-to-bottom with `gap-2` (8px)
  between cards, each with its own independent timer. In today's codebase at most one of the four
  autosaving surfaces is ever mounted simultaneously (`ScriptureSlideEditor` and `CongregationalEditor`
  are currently unmounted dead weight per the Phase 30/R047 handoff; `SongLyricEditor` and
  `ServiceEditorView` are separate routes) — so multi-toast stacking is a safety net for the future, not
  today's common case. Don't build more than the array + `gap-2` requires.

### 5. Placement — the three editor surfaces: no new sticky wrapper needed

`CongregationalEditor.vue`, `ScriptureSlideEditor.vue` and `SongLyricEditor.vue` already share one
layout: `<div class="flex h-full flex-col">` with a `shrink-0` header row
(`CongregationalEditor.vue:3-22`, `ScriptureSlideEditor.vue:3-22`, `SongLyricEditor.vue:4-28`) above a
`flex-1 overflow-y-auto` scrolling body. **Because the header is `shrink-0` and the *body*, not the
panel, is the scroll container, the header never scrolls out of view today** — no `sticky` class is
needed here; the layout already satisfies "visible without scrolling." This is a materially different
situation from `ServiceEditorView.vue`, where the whole page (including its header) scrolls inside
`AppShell.vue`'s `<main>` (§ 3).

**Change per surface:** replace the existing dot-and-title status markup (the `status-pending` /
`status-saving` / `status-saved` spans) with `<SaveStatusIndicator :surface-id="…" />` in the same header
slot:

| Surface | Header location | `surfaceId` |
|---|---|---|
| `CongregationalEditor.vue` | inside `:4`'s header row, replacing `:6-21` | `` `congregational:${currentReadingId}` `` |
| `ScriptureSlideEditor.vue` | inside `:4`'s header row, replacing `:6-21` | `` `scripture:${currentReadingId}` `` |
| `SongLyricEditor.vue` | inside `:8`'s `flex items-center gap-2` group, replacing `:11-27` | `` `song-lyrics:${props.songId}` `` |

**★ Existing `data-testid`s (`status-pending`, `status-saving`, `status-saved`) are retired.**
`SaveStatusIndicator` exposes `data-testid="save-status"` (and `save-status-error` for the failure
branch) instead — one stable handle across all four surfaces rather than three per-status ids duplicated
three times. Any test asserting the old ids needs updating as part of this migration; this is a
deliberate, not incidental, breaking rename — call it out in the plan rather than let it surface as an
unexplained test failure.

**No `canEditService`-style gate on these three.** None of them currently gates its header on
`authStore.isEditor` (confirmed: no `isEditor` reference in any of the three files) — access control for
these screens/panels happens upstream (route-level), not inside the component. This phase does not add
one; the indicator shows whenever the component is mounted, exactly as today's dot/title markup does.

### 6. Debounce — 800ms everywhere, one number, stated deliberately

32-CONTEXT.md flags a live inconsistency: R041's own text references "500ms" while `useAutoSave` defaults
to 800ms. **Resolution: 800ms, unchanged, for all four surfaces.** All three already-migrated editors
call `useAutoSave(...)` with no `debounceMs` override (confirmed: `CongregationalEditor.vue:228-231`,
`SongLyricEditor.vue:366-370`, both omit the third options argument), and `ServiceEditorView.vue`'s own
hand-rolled timer already uses `800` (`:2183`). Introducing 500ms for the migration would mean the one
surface being migrated *this phase* debounces differently from the three it's supposedly unifying with,
for a value that appears only descriptively in the requirement text, not as a hard number. 800ms stays
the app's one debounce constant.

### 7. `canEditService` gate — what occupies the space when a service is locked

**Nothing.** No status bar, no empty box reserving its height, no "editing disabled" caption in its
place. This mirrors 31-UI-SPEC § 3's own row-by-row table ("Autosave status text … removed"): a locked
service has nothing dirty by construction (all three tabs are read-only, R036), so there is nothing to
report. The lock banner directly below (31-UI-SPEC § 1) already explains *why* nothing can be edited —
adding a second, empty explanatory element here would be exactly the "state the reason twice" pattern
Phase 31's D-06 forbids.

## Empty / Edge States

| # | Situation | Rendering |
|---|-----------|-----------|
| E1 | Service Order, first load, no edits yet | Status bar renders (canEditService true at draft) but `SaveStatusIndicator` shows nothing — `idle` |
| E2 | A discrete one-shot mutation (e.g. picking a song) lands immediately after a prior save's own echo | Fires `'pending'` → `'saving'` → `'saved'` exactly like any other edit — this is the R039 repro case; see `32-CONTEXT.md` § Root-Cause Confirmation for the required test-first discipline |
| E3 | Autosave fails on any of the four surfaces | Inline `Couldn't save your changes — they're still here. Try again.` (or the reorder variant on ServiceEditorView) via `aria-live="polite"`, **plus** one `role="alert"` toast mirroring the same text, edge-triggered once |
| E4 | Autosave fails twice in a row without the status ever leaving `'error'` in between | Only the first transition raises a toast — no toast spam on a still-down network (§ 4) |
| E5 | Service transitions from `planned`/`exported` back to `draft` via Reopen | Status bar appears (nothing was dirty at the moment of reopen, so it renders `idle` — no status text — until the next edit) |
| E6 | Service transitions from `draft` to `planned`/`exported` via Mark as Planned / Export | Status bar disappears; the lock banner (31-UI-SPEC § 1) takes its slot |
| E7 | Viewer (non-editor), any service status | Neither the status bar nor the toast ever appears for that user — `canEditService` is false throughout, and only an editor's own autosave failures raise a toast |
| E8 | Narrow viewport (< ~640px), toast visible | Full width minus 16px side margins (`inset-x-4`), anchored to the bottom; no overlap with the sticky status bar or lock banner, which live at the top |
| E9 | Narrow viewport, status bar | No layout change needed — text-only content wraps normally inside a `flex-1` container, no button to wrap around |
| E10 | Two toasts fire close together (two different surfaces failing near-simultaneously) | Both render, stacked with `gap-2`, each dismissing independently on its own 6000ms timer or its own `×` |

## Accessibility Note

- **Status region:** one `aria-live="polite" aria-atomic="true"` wrapper per surface instance, covering
  all four rendered states including error. Never nest a second live region inside it.
- **Toast:** `role="alert"` (implicitly assertive + atomic per ARIA spec) — no redundant
  `aria-live="assertive"` attribute alongside it.
- **Manual dismiss:** the toast's `×` button carries `aria-label="Dismiss"` since its visible content is
  a bare glyph, not a word.
- **No focus trap, no auto-focus on the toast.** It is a passive notification, not a modal — matching
  this codebase's already-documented, deliberate choice not to retrofit dialog semantics ad hoc
  (31-UI-SPEC § Accessibility Note makes the same call for its four confirm dialogs).
- **Deleted `data-testid`s are an accessibility-adjacent test-debt item, not an a11y regression:** the
  three editors' old per-status ids (`status-pending`/`status-saving`/`status-saved`) carried no ARIA
  role of their own beyond a `title` attribute on the pending dot (not itself accessible to all screen
  readers) — the new text-based `aria-live` region is a strict improvement, not a like-for-like swap.
