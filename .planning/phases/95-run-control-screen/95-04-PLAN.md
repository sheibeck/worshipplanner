<objective>
Layer the output-window integration seam onto RunControlView: on Run, open BOTH output windows and place
them on their assigned monitors in the sanctioned "essentially one click" path, with a first-class amber
fallback when the monitors aren't matched or the permission isn't available. This is what makes the control
screen "stay in charge of both output windows" — the channel writer from 95-03 now has real windows to
drive, opened and positioned from the operator's Run gesture.

Purpose: R261 (the control screen opens/owns the standalone output windows) and R266 (the single-selection
state now drives real audience + confidence outputs). The placement mirrors Phase 92's synchronous-gesture
getScreenDetails idiom so the already-granted Window Management permission + requestFullscreen keep user
activation; every failure mode (needs-reprompt / denied / unavailable / blocked pop-out) degrades calmly to
un-positioned pop-outs plus the amber "Finish setting up your displays" banner and the monitor-setup link —
never a dead end, never a thrown error.

Output: an extended src/views/RunControlView.vue. Orchestration + placement + fallback behavioral tests
land in 95-06. Real two-monitor open+place+fullscreen is human-UAT (deferred to milestone end).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Run gesture -> getScreenDetails / window.open / requestFullscreen | Multi-screen placement + fullscreen require live user activation; the call chain must not await before getScreenDetails or the permission/placement silently fails |
| window.open child <- opener sessionStorage | The child output window inherits the picked org via sessionStorage ONLY when the opener relationship is preserved (no noopener); dropping it would strand the child org-less |
| saved monitor mapping (localStorage) -> live screen resolution | loadMapping reads untrusted localStorage; matchMapping/computeFingerprint treat it defensively (already hardened in Phase 91/92) and a mismatch falls back rather than mis-placing |
| opened windows -> teardown on exit | The opener holds raw Window handles; closing them on exit must be guarded (a cross-origin/closed window .close() can throw) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-95-10 | Denial of Service | window.open returning null (blocked/jsdom) | high | mitigate | Every window.open return is stored and immediately null-guarded (if (!win) return); moveTo/requestFullscreen only run on a non-null win; a blocked pop-out degrades to the amber fallback, never a thrown error that blanks the control screen. |
| T-95-11 | Spoofing | ?org= carried into the output URLs | low | mitigate | The URLs are built from serviceId + orgIdRef (the authenticated member's resolved org), and the child re-scopes via Firestore org-membership rules (inherited from Phases 93/94); a hand-edited org cannot read another org's content. |
| T-95-12 | Tampering | requestFullscreen `screen` placement | low | mitigate | The non-standard `screen` fullscreen option is cast + guarded; if the platform rejects it (activation lost, embedding), the catch is silent and each output window's own Enter-fullscreen affordance remains — the amber fallback covers the human-drag path. |
| T-95-13 | Information Disclosure | opener relationship kept (no noopener) | low | accept | Preserving the opener relationship is REQUIRED to carry the org via sessionStorage; both child routes are first-party same-origin app routes, so the retained opener reference crosses no origin boundary. Accepted per ARCHITECTURE.md. |
| T-95-SC | Tampering | package installs (npm) | n/a | accept | No package-manager installs — in-repo utils/components only; supply-chain checkpoint not applicable. |
</threat_model>
