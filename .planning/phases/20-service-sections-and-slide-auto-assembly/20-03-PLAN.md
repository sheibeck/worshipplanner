<objective>
Wrap the pure assembly engine (20-02) in a Vue composable so the assembled slideshow updates reactively
— delivering R006: reorder/add/remove a service element and the slideshow follows with no manual re-sync.
The composable builds the three content maps the engine needs (per-song current lyrics, canonical
Song.performanceOrder, org scripture readings) and exposes a `computed` result plus a section-grouped
view for the preview.

Purpose: This is the reactive glue that turns the deterministic pure function into live derived state.
The one real complexity is loading current lyrics for EVERY song in the service — the songLyrics store
subscribes to a single song at a time, so the composable must gather lyrics per distinct songId.

Output: `src/composables/useSlideshowAssembly.ts` + reactivity/grouping tests.
</objective>

  <behavior>
    - Given a reactive service whose slots are reordered, assembledSlideshow.value order changes to match, with no manual call
    - Adding a slot to the service adds the corresponding slides; removing a slot removes them
    - scriptureReadingsById is derived from the scriptureSlides store readings (keyed by reading id)
    - performanceOrderById is derived from songStore.songs (songId -> Song.performanceOrder ?? [])
    - songLyricsById holds current lyrics for EVERY distinct songId referenced by a SONG slot; a song with no lyrics doc is simply absent from the map (engine then skips it)
    - assembledSections groups assembledSlideshow by section in SERVICE_SECTIONS order, using SERVICE_SECTION_LABELS for labels, with a trailing/leading group for undefined-section (legacy) slides
  </behavior>
  <action>
    Implement `export function useSlideshowAssembly(service, orgId)` where `service` is a `Ref<Service | null>` /
    `ComputedRef<Service | null>` and `orgId` is a `Ref<string | null> | string`. Internally:
    (1) Use the scriptureSlides store's readings to build a reactive `scriptureReadingsById` Map (call subscribeReadings
    if not already subscribed for this org, mirroring the guard pattern used elsewhere: `if (!store.orgId)`; do not
    double-subscribe). (2) Build `performanceOrderById` from `useSongStore().songs`. (3) Maintain a reactive
    `songLyricsById` Map: watch the set of distinct songIds across service.slots and, when it changes, load the current
    (newest) lyrics doc for each missing songId via a getDocs query on organizations/{orgId}/songs/{songId}/lyrics ordered
    createdAt desc limit 1 (default performanceOrder to [] on docs missing the field, matching songLyrics store). Expose
    `assembledSlideshow: ComputedRef<AssembledSlide[]>` = `computed(() => service.value ? assembleSlideshow(service.value,
    { songLyricsById, performanceOrderById, scriptureReadingsById }) : [])`. Expose `assembledSections:
    ComputedRef<AssembledSection[]>` grouping the flat array (SERVICE_SECTIONS order + a group for undefined section).
    Expose an `isLoading` ref that is true while lyrics for the current song set are being fetched. Provide cleanup
    (clear watchers / unsubscribe only what this composable created) via onUnmounted. To keep the composable unit-testable,
    accept an OPTIONAL final options arg that allows injecting a lyrics-loader function so tests can supply lyrics without
    hitting Firestore; default to the real getDocs loader.
    Write tests that inject a fake lyrics loader + a stubbed scriptureSlides store and assert: reorder recomputes order,
    add/remove updates slides, and assembledSections groups by section including an undefined-section group.
  </action>
