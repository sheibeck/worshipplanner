<objective>
Fold Vocals into the Band team and stop any volunteer from serving on two conflicting teams on the
same service date, with Vocals as the single special-case exception (multi-person, and one instrument
plus vocals at once). One shared pure rule drives all three consumers.

Purpose: Deliver R250 (Vocals is a Band role, not a separate team), R251 (no cross-team double-booking
on one date — the auto-scheduler hard-blocks it), and R252 (Vocals is the sole exception: many people,
and sing-and-play). The rule already lives in ONE shared pure function (evaluateGroupCombo /
isGroupCompatible, D-10) consumed by the auto-scheduler (proposeQuarterSchedule) AND the manual grid
warn badge (QuarterGrid, D-11) AND the pairing path (propagatePairing, D-12 / Pitfall 2). This plan
rewrites that one rule and threads a vocal flag so all consumers inherit the change in lockstep.

Output: A narrowed RoleGroup union, a Role.vocal flag, the rewritten shared rule, a read-time compat
shim for legacy data, the production projection wiring, the roles-UI change, and the full test set —
all landing together (the type change is atomically coupled to every consumer; see notes below).

Why a single plan (not a wave-1 rule + wave-2 UI split): narrowing RoleGroup to 'band' | 'tech' |
'other' turns every `Record<RoleGroup, string>` map and every `group: 'vocals'` test fixture that still
names a vocals key into a `vue-tsc --build` error the instant the union changes. QuarterGrid.vue and
RolesConfigPanel.vue both hold such maps, so a "UI in wave 2" split would leave wave 1 unable to pass
its own `npm run type-check` gate. Everything that references the union with a vocals key must land in
the same plan.
</objective>

## Artifacts this phase produces

- **New `Role.vocal?: boolean` flag** — marks a vocal role explicitly (not by magic name), so churches can rename/add vocal roles freely.
- **Narrowed `RoleGroup` union** — `'band' | 'tech' | 'other'` (drops `'vocals'` as a team identity).
- **Changed shared-rule signatures** — `evaluateGroupCombo(roleIds, roleGroupOf, isVocal)`, `isGroupCompatible(assigned, candidate, roleGroupOf, isVocal)`, and a new `isVocal` param on `proposeQuarterSchedule` (default `() => false`).
- **New group-combo semantics** — Band and Tech mutually exclusive; Other combines freely with either; at most one Band *instrument* role per person per date, Vocals exempt; multiplicity otherwise governed by per-role counts (no new one-person cap).
- **Read-time compat shim** — `roster.ts` coerces stored `group: 'vocals'` to `{ group: 'band', vocal: true }` when mapping the roles snapshot; NO Firestore write migration.
- **`buildIsVocal` projection** — `quarters.ts` projects `Role.vocal` into the scheduler alongside `buildRoleGroupOf`.
- **Roles UI change** — standalone Vocals group option removed; a vocal role is a Band role with a "sing & play" checkbox.
- **Test set** — scheduler group-combo cases (tech+band blocked, tech+other allowed, band+other allowed, one-instrument+vocals allowed, two-instruments blocked, vocals multi-person allowed), the compat-shim store test, the QuarterGrid warn test, the RolesConfigPanel removed-option test, and every migrated `group: 'vocals'` fixture.
</artifacts>
