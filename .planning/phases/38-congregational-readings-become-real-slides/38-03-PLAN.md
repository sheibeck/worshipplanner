<objective>
Give a section slide the two affordances the owner asked for by name: *"We should be able to modify
them after we split them up, or delete them entirely."*

Delivers roadmap criterion 3 (edit one without altering its siblings) and the user-facing half of
criterion 4 (delete one on its own). Implements D2 (D-02) — once detached, section slides are
ordinary editable slides, with no write-back-to-the-reading path and no per-slide override concept.

Purpose: 38-01 made the entries independently storable; this plan makes them independently editable.
Output: the Edit Slide drawer edits one section's words and speaker; the slide card names the
speaker; deletion of a single section slide is reachable and unremarkable.
</objective>

  <files>src/components/slides/EditSlideDrawer.vue, src/components/slides/__tests__/EditSlideDrawer.test.ts</files>
  <behavior>
    - Opening the drawer on a section entry with mutation allowed renders an editable passage field seeded with that section's stored words.
    - Typing into it and flushing writes the group's slides with only that entry's stored words changed; every sibling entry is byte-identical to before, including its id, order and speaker.

    - Opening the drawer on a Reference-state scripture entry renders the existing read-only block and the existing route out to the congregational editor — no editable field appears.
    - Opening the drawer on a section entry with mutation disallowed renders the section's words read-only.
    - A section entry's words changing on the stored group while the drawer is open, with no edit pending, re-seeds the field; a change arriving while an edit IS pending does not clobber what the user is typing.
  </behavior>
  <action>
The drawer's Slide Text block branches on the STORED entry's `sourceRef.kind`, never on the resolved
slide's `contentKind` — read the long comment above that block and keep obeying it. Both a Reference
entry and a section entry are `scripture`-kind, so the new split happens INSIDE the scripture branch,
keyed on `congregationalSectionFromRef(props.entry.sourceRef)`. That helper is the single predicate
for this decision; do not add a second inline speaker check anywhere in this component.

Scripture branch, section entry, mutation allowed: render an editable multi-line field bound to the
existing `localBody` state, exactly as the `text` branch below it already does. Give it its own
`data-testid` so a test can tell the scripture editable field from the text-kind one. Mutation
disallowed: render the section's words in the existing read-only presentation.

Scripture branch, Reference entry: unchanged in every respect — the read-only block, the caption and
the button that opens the congregational-reading editor all stay exactly as they are. Phase 30's
hard lock is not repealed by this phase, only scoped to this state; the caption near it that
describes the lock must be rewritten to say which state it governs rather than left asserting a rule
the code no longer follows unconditionally.

Extend the existing debounced field machinery rather than adding a second write path:

- the field that carries a slide's words is already named `body` in this component's local state.
  Keep that name. What changes is where a flush puts the value: a `text`-kind entry keeps writing
  `body` on its own ref; a scripture SECTION entry writes `text` on its own ref. Branch at the point
  the flush maps the entry, and guard on the entry's own ref shape so no other kind can be reached
  by this write — the existing comment there explains exactly why that guard exists.
- the seeding that fills `localBody` when the selected entry changes must seed from a section
  entry's stored words too, and must still yield an empty string for every kind that has no words of
  its own.
- the external-change resync watcher must recognise a section entry's words changing on the stored
  group, under the same "only when nothing is pending" condition it already applies.
- the input handler's early return currently admits only `text`-kind entries. Widen it to admit a
  section entry as well, and no further.

Everything else about the write is unchanged: same debounce, same `baseSlides` compare-and-swap
argument, same stored `sourceSignature` passed through. That last one is load-bearing — the group's
detached state is recorded in that signature, and a drawer write that changed it would hand the
group back to the rebuild, which would re-materialize over the very edit just made.

Add the behavior cases to `src/components/slides/__tests__/EditSlideDrawer.test.ts`. The
sibling-untouched case is the one that proves criterion 3 and it must assert siblings by value, not
merely assert a count.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Drawer input → Firestore slide group | Free text typed by a planner is stored and later projected verbatim to a congregation |
| Drawer write → group `sourceSignature` | The field that records detachment travels through every drawer write |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-38-03-01 | Tampering | drawer field flush | high | mitigate | The flush branches on the selected entry's own ref shape, so a scripture write can never land on a lyric, copyright, imported or video entry — asserted by the sibling-untouched cases in Tasks 2 and 3 |
| T-38-03-02 | Elevation of privilege | speaker control and passage field | high | mitigate | Both are bound to the existing `canMutate` gate AND re-check it inside their handlers, matching the belt-and-braces pattern the loop control already uses; song groups and locked services stay read-only |
| T-38-03-03 | Tampering | `sourceSignature` passthrough | high | mitigate | Every write in this plan passes the group's stored signature unchanged; a changed signature would silently re-attach the group and let the next rebuild overwrite the user's edits |
| T-38-03-04 | Repudiation | concurrent drawer and grid writes | medium | mitigate | Reuses the existing `baseSlides` compare-and-swap argument, so a concurrent add/reorder/delete merges rather than being overwritten |
| T-38-03-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs no packages and adds no dependency |
</threat_model>
