# Phase 63 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope & Precedent (read first)

Phase 63 is a **small structural change** to `src/views/ServiceEditorView.vue`, not a new component and
not a new visual language. It:

1. **Adds a 4th tab button — "Messages"** — to the existing tab bar (currently Service Order · Slides ·
   Roles, `ServiceEditorView.vue:695-732`), appended **after Roles**.
2. **Relocates two already-shipped panels** out of the Service Order panel into a new
   `v-show="activeTab === 'messages'"` panel, stacked vertically, byte-for-byte unchanged internally:
   - the **Messaging defaults** panel (`data-testid="messaging-defaults-panel"`, currently ~L844);
   - the **`ServiceMessageHistory`** component (currently mounted ~L908).
3. **Fixes one gate (R150):** the history mount `v-if="isMessagingEnabled() && canEditService"`
   (`ServiceEditorView.vue:909`) drops `canEditService`, so the read-only history stays visible on a
   locked/exported service instead of vanishing (the Phase 60 / 60-03 defect).

**No new component, no invented visuals, no new tokens.** Every class string in this spec is copied from
an existing sibling in the same file. This is a contract for *reuse + relocation*, verified against the
actual code at the line numbers above.

**Focal point (visual hierarchy):** unchanged. Within the Messages panel the eye lands on the
**Messaging defaults** card first (top of the stack, same card tier as Teams / Sermon Context), then the
delivery history below it. The panel introduces no new emphasis, fill, or hierarchy — it inherits the
Service Order panel's existing rhythm.

### Accepted deviations — app-wide consistency (inherited from v1.7, do NOT re-flag)

Phases 58 and 59 recorded conventions the generic `gsd-ui-checker` rubric flags but which are
**deliberate, shipped app-wide conventions**. Phase 63 reuses the exact tab-button and card idioms that
already carry them; changing them would make this the single inconsistent surface. Accepted under the
v1.8 autonomous grant's "pick the reasonable default, state it" clause. **These are already-ruled — do
not re-flag:**

1. **Third font weight `font-medium` / 500 (Typography → ACCEPTED).** Every existing tab button uses
   `text-sm font-medium`. The new Messages tab button copies that class verbatim — it introduces no new
   weight. (Ruled Phase 58/59, deviation #1.)
2. **`12px` spacing (`mb-3`, `mt-3`, and the `px-4 py-2` control padding) (Spacing → ACCEPTED).** `12px`
   is a load-bearing app-wide token (`mb-3` under the tab bar, `mt-3` between the two relocated panels).
   It is a multiple of 4 and the de-facto scale here. (Ruled Phase 58/59, deviation #2.)
3. **`indigo` active-tab accent (Color → ACCEPTED).** The active tab uses `text-indigo-300
   border-indigo-500`; `indigo` is the app's single shipped accent across every tab, button, and modal.
   The Messages tab matches its three siblings exactly. (Ruled Phase 58/59, single-indigo rule.)

A future project-wide design-system pass is the correct venue for the rubric ideals, not this
relocation. Net: **no new tokens, no new component library, no new copy pattern.**

## Component Inventory

**Count: 1 new control (the tab button) + 1 new container (the panel) wrapping 2 relocated, unchanged
panels.** No new sub-components. Enumerated below.

### 1. "Messages" tab button (new — mirror of the Roles tab)

Appended as the **4th** button inside the existing tab-bar row (`ServiceEditorView.vue:695`, the
`<div class="flex items-center gap-1 mb-3 border-b border-gray-800 pb-0">`), **after** the Roles button.
Tab order becomes: **Service Order · Slides · Roles · Messages** (append-last; least disruption to the
established order, per `63-CONTEXT.md`).

- **Gating (mirror of Roles, plus the kill-switch):**
  `v-if="authStore.isEditor && isMessagingEnabled()"` (`isMessagingEnabled` from `src/utils/messaging.ts`).
  Roles is gated `v-if="authStore.isEditor"` alone; Messages adds the messaging kill-switch so a
  messaging-off org sees **no** Messages tab (consistent with the composer's messaging gating). A viewer
  (non-editor) never sees it — same as Roles.
- **Classes — copied verbatim from the sibling tab buttons (do not restyle):**

  ```html
  <button
    v-if="authStore.isEditor && isMessagingEnabled()"
    type="button"
    class="px-4 py-2 text-sm font-medium rounded-t-md transition-colors -mb-px border-b-2"
    :class="activeTab === 'messages'
      ? 'text-indigo-300 border-indigo-500 bg-gray-900'
      : 'text-gray-400 border-transparent hover:text-gray-200 hover:border-gray-600'"
    @click="activeTab = 'messages'"
  >
    Messages
  </button>
  ```

- **Label:** **"Messages"** (matches R149 wording and the ✉ composer's action label; single word, text
  only, no icon — consistent with the other three text-only tabs).
- **State type:** `activeTab` gains a `'messages'` member (union becomes
  `'service-order' | 'slides' | 'roles' | 'messages'`).

### 2. Messages panel (new container — `v-show="activeTab === 'messages'"`)

A sibling of the existing `service-order-panel` / slides / roles panels. Hosts the two relocated panels
**stacked vertically, in their current top-to-bottom order** (defaults first, history below), with the
existing `mt-3` (12px) gap between them preserved:

1. **Messaging defaults** panel (`data-testid="messaging-defaults-panel"`) — moved from ~L844.
   Its Draft-editable branch (`v-if="canEditService"`), its locked-read-only summary
   (`v-else-if="authStore.isEditor && isLocked"`, `data-testid="messaging-defaults-readonly"`), the
   viewer summary, and the `messagingSaveError` red line are **all unchanged**. Only its parent (which
   tab) changes.
2. **`ServiceMessageHistory`** component (`data-testid="service-message-history"`) — moved from ~L908,
   keeping its `class="mt-3"`, all props (`:messages`, `:recipients-by-message`, `:loading`, `:error`),
   and its `@new-message` / `@expand` handlers unchanged.

Illustrative shell (structure only — the two children are moved, not rewritten):

```html
<div v-show="activeTab === 'messages'" data-testid="messages-panel">
  <!-- (1) messaging-defaults-panel — moved here unchanged -->
  <!-- (2) ServiceMessageHistory — moved here, class="mt-3", R150 gate below -->
</div>
```

### 3. R150 gate fix on the relocated history

At its new mount, drop `canEditService` from the history's `v-if`:

```html
<!-- before (bug): v-if="isMessagingEnabled() && canEditService"  → vanishes when locked -->
<!-- after:        v-if="isMessagingEnabled()"                    → visible draft/locked/exported -->
```

The enclosing Messages tab already gates `authStore.isEditor && isMessagingEnabled()`, so inside the
panel the `isMessagingEnabled()` check is retained only as a **defensive** guard (implementer
discretion, per `63-CONTEXT.md`). The `canEditService` clause is **removed** — it was the entire R150
defect (`canEditService = isEditor && !isLocked` hid a read-only panel the moment the service locked).
Safe because the history has been read-only since Phase 60.

## Interaction & Validation Behavior

| Trigger | Behavior |
|---------|----------|
| Click "Messages" tab | Sets `activeTab = 'messages'`; the Messages panel `v-show`s in, the other three `v-show` out. Identical mechanism to the existing three tabs — no new state machinery. |
| Messaging turned OFF for the org | `isMessagingEnabled()` is false → the Messages **tab button is not rendered at all** (`v-if`). If it was the active tab when toggled off, the standard editor default tab (`'service-order'`) is shown; no orphaned empty panel. |
| Viewer (non-editor) opens the service | `authStore.isEditor` is false → tab button hidden, exactly like Roles. |
| Service is locked / exported | Tab still shows (editor + messaging gated). Inside: the defaults card renders its **locked read-only summary** branch, and the history renders (R150 fix) in its read-only state. |
| History has no messages | `ServiceMessageHistory` shows its existing empty branch — `data-testid="history-empty"`, **"Nothing sent yet"** (unchanged, `ServiceMessageHistory.vue:40`). |
| History loading / bounce / error | Unchanged Phase 60 behavior (loading, bounce "fix email", error branches all intact). |

No validation is introduced — this phase mutates no data. It moves markup and removes one gate clause.

## Accessibility

- **Tab semantics — match the siblings exactly (do not add ARIA the existing tabs lack).** The existing
  three tab controls are plain `<button type="button">` elements with `@click`; they do **not** use
  `role="tablist"`/`role="tab"`/`aria-selected` and implement no arrow-key roving-tabindex. The Messages
  button **mirrors this precisely** — a plain focusable `<button>`, reachable by Tab, activated by
  Enter/Space (native button behavior). Introducing a full ARIA tab pattern on only the 4th button would
  make it inconsistent with its three siblings and is explicitly out of scope for this small structural
  change. (If a future pass adds `role="tablist"` semantics, it must apply to all four buttons at once.)
- **Focus order:** the Messages button sits after Roles in DOM order, so it receives focus in natural
  reading order within the tab row.
- **Contrast:** active `text-indigo-300` on `bg-gray-900` and inactive `text-gray-400` on the editor
  surface both meet the app's shipped dark-theme contrast (identical to the three existing tabs).
- **Relocated panels:** their internal semantics (the defaults selects, the history list) are unchanged
  and carry whatever accessibility they shipped with in Phases 58/60.

## Responsive Behavior

- The tab-bar row is `flex items-center gap-1` on a `border-b` — it has **no `flex-wrap`**, so a 4th
  button does **not** wrap to a second line; the four buttons sit on one row. Confirmed: with short
  text-only labels (Service Order · Slides · Roles · Messages) the row **fits comfortably at the
  desktop-first widths the Service Editor targets** — "Messages" (`px-4 py-2`) is a short label and adds
  ~110px to an already-comfortable row.
- **Very narrow mobile:** because there is no `flex-wrap`, a 4th tab could push the row toward horizontal
  overflow on the narrowest viewports — but this is the **existing** behavior of the shipped 3-tab row,
  not a regression introduced here. **Default resolved (autonomy grant): leave the container as-is**
  (add no `flex-wrap`), matching the three siblings byte-for-byte; the Service Editor is a
  desktop-first planning surface. Adding `flex-wrap` to the shared container would restyle all four tabs
  at once and is deliberately **not** done in this relocation phase.
- No new breakpoint is introduced. The relocated panels keep their own existing responsive behavior.
