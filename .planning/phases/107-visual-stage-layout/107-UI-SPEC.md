## Spacing Scale

Declared values (must be multiples of 4), scoped to the NEW elements this phase introduces (stage tab panel chrome, the two zone containers, marker chips, the add-marker control, the edit-marker popover, and the read-only share/print render):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Marker chip internal padding (`px-2 py-1`-scale), kind-accent dot size/gap |
| sm | 8px | Gap between marker chip icon/label; add-marker control's internal field gaps |
| md | 16px | Zone container padding (`p-4`); gap between the on-stage and off-stage zone containers; edit-marker popover body padding |
| lg | 24px | Gap between the tab panel's top toolbar (Add marker row) and the canvas below |
| — | 44px | **Exception**: minimum touch-target size for the marker chip's drag-grab area and the delete/edit icon-buttons on the read-write canvas — smaller than the 8pt scale, required for reliable touch dragging per PITFALLS.md (real touch-device use is a named risk for this phase) |

Exceptions: the 44px touch-target minimum above (icon-only draggable/tappable targets). No other exceptions.

## Typography

Scoped to the NEW elements this phase introduces only (inherited app chrome — page headers, the existing tab bar, existing buttons elsewhere in `ServiceEditorView.vue` — is NOT re-declared here).

## Color

Reuses the app's existing gray-950/900/800 dark palette and indigo accent verbatim — no new hues introduced for structure, only for the optional per-marker `kind` accent (see below).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `gray-950` (`#030712`, existing app page background) | Off-stage zone container fill (`bg-gray-950`, `border-dashed border-gray-700`) — reads as "outside the main stage," reusing the page's own dominant tone rather than a new color |
| Secondary (30%) | `gray-900` (existing panel fill, e.g. the "Teams" config panel) | On-stage zone container fill (`bg-gray-900 border border-gray-800 rounded-lg`); marker chip base (`bg-gray-800 border border-gray-700`) |
| Accent (10%) | `indigo-500` / `indigo-600` (existing app primary accent) | Reserved for: the "Add marker" primary button (`bg-indigo-600 hover:bg-indigo-500`, matching `RoleSlideOver.vue`'s Save button); the focus ring on the add-marker/edit-popover text inputs (`focus:ring-1 focus:ring-indigo-500`); the drag-in-progress ring on a marker chip being actively dragged (`ring-2 ring-indigo-500`) — no other element uses indigo |
| Destructive | `red-400` / `red-900` (existing app destructive convention, e.g. the export-error dismiss icon) | The delete-marker icon button and its inline "Remove this marker?" confirm row only |

**Marker `kind` accent (light, optional — per CONTEXT.md, NOT a required constrained picker):** reuses the app's existing muted pill formula (`kindBadgeClass()` in `src/utils/slotTypes.ts`: `bg-{hue}-950 border border-{hue}-800 text-{hue}-300`), applied as a small left-edge accent bar/dot on the marker chip, not a full chip retint:

| Kind | Accent classes |
|------|-----------------|
| `instrument` | `bg-sky-950 border-sky-800 text-sky-300` |
| `mic` | `bg-emerald-950 border-emerald-800 text-emerald-300` |
| `monitor` | `bg-amber-950 border-amber-800 text-amber-300` |
| `other` / unset | `bg-gray-800 border-gray-600 text-gray-300` (same neutral pill as MISC/PRAYER elsewhere) |

Accent reserved for: the "Add marker" button, input focus rings, and the active-drag ring — never for zone backgrounds, marker chip base fill, or body text. The `kind` accent hues are a strictly separate, secondary system (mirrors `kindBadgeClass`) and must not be confused with the 10% indigo accent.

## UI Considerations

Applicable state considerations resolved: 15 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | on-stage zone, off-stage zone (list-collection) | ✅ covered | Each empty zone shows the "Drop markers here" placeholder (14px, `text-gray-500 italic`, matching the app's existing `text-sm text-gray-500` "No items yet" convention). When BOTH zones are empty, the canvas additionally shows the "No stage layout yet" heading+body pair above the two zones. |
| empty | add-marker control (form) | ✅ covered | The "Add marker" button stays disabled (existing `disabled:opacity-50` convention) until the free-text label field has non-whitespace content — mirrors `RoleSlideOver.vue`'s Save-button disable-on-invalid pattern. |
| empty | share/print stage plot (list-collection) | ✅ covered | On `ShareView.vue` and `ServicePrintLayout.vue`, the entire Stage Layout section is OMITTED (not rendered as an empty box) when the snapshot's `stageLayout` is absent or has zero markers — matches the existing `roleAssignments?.length` conditional-section pattern already in `ShareView.vue`. |
| loading | stage tab, on-stage zone, off-stage zone (nav, list-collection) | ✅ covered | No new loading state — the Stage Layout tab and its canvas render only after `ServiceEditorView.vue`'s existing service-load gate resolves, exactly like the Service Order/Slides tabs today; `stageLayout` arrives as part of the same already-loaded `Service` document, no second fetch. |
| error | add-marker control, marker chip drag persistence (form, interactive-control) | ✅ covered | No new error surface — stage-layout writes (add/edit/delete/drag) go through the existing debounced autosave path (mirroring `notes`), so a save failure surfaces through the existing `SaveStatusIndicator`/autosave-error banner already on the page, not a canvas-local error state. |
| populated | on-stage zone, off-stage zone (list-collection) | ✅ covered | Happy-path example: 4-6 marker chips per zone at typical church-band size (e.g. "Drums", "Piano", "Bass", "Acoustic Guitar" off-stage-side; "Lead Vocal", "Vocal 2", "Pulpit Mic" on-stage) — chips do not overlap at this density given percentage placement + a minimum chip footprint. |
| partial | on-stage zone, off-stage zone (list-collection) | ✅ covered | One zone populated and the other empty is a fully valid, common state (e.g. a church with no off-stage instruments yet) — each zone's empty/populated state is independent, never blocking the other or showing a combined error. |
| overflow | marker chip label (interactive-control) | ✅ covered | Marker chip label truncates with `truncate` + a `max-w` cap (matches the app's existing truncation convention on song-title chips) at a fixed chip width; the full label is available via the chip's `title` attribute and in the edit popover. |
| overflow | on-stage/off-stage zone (list-collection) | 🧪 backstop | Many markers densely packed in one zone (e.g. 15+) is expected to remain usable via zoom/scroll of the zone container rather than markers overflowing its bounds — verified by a held-out visual/property test asserting no marker's computed position falls outside its zone's `[0,100]` percentage bounds at high marker counts, not asserted here as a fixed pixel layout. |
| overflow | share/print stage plot (static-content) | ✅ covered | The read-only render at `@media print` uses the same percentage-based positions as the editor, so a densely-packed zone prints exactly as arranged on screen — no separate print layout logic to drift from the live canvas. |
| zero-one-many | on-stage zone, off-stage zone (list-collection) | ✅ covered | Zero → placeholder copy (above); one → a single centered-ish chip per its saved `xPct/yPct`; many → chips render at their independent saved positions with no forced re-layout — copy never pluralizes ("marker"/"markers" is not user-facing count copy here, only the placeholder text, which is count-agnostic). |
| long-text | marker chip label, add-marker input, edit-popover label field (interactive-control, form) | ✅ covered | The add-marker/edit-popover input has no enforced max length beyond a generous practical cap (mirrors `RoleSlideOver.vue`'s unconstrained name input); the input itself never truncates while typing — only the rendered chip does (see overflow row above). |
| long-text | share/print stage plot (static-content) | 🧪 backstop | A long marker label on the read-only share/print render must wrap or truncate without breaking the absolute-positioned layout of neighboring markers — verified by a held-out test asserting one marker's long label never shifts another marker's computed `left`/`top`, since positions are independent absolute placements, not a flow layout. |
| loading | on-stage zone, off-stage zone (viewport resize, R314) | ✅ covered | Not a loading state but adjacent to it: because positions are stored as `xPct/yPct` (percentage of zone bounds), a window resize recomputes pixel placement from the same stored percentage on every render — no resize-triggered refetch or recalculation step, no flash of incorrect position. |
| empty | edit-marker popover kind field (form) | ✅ covered | `kind` is optional — the popover's kind selector includes an explicit "No kind" / unset option, defaulting every new marker to unset (neutral gray accent) rather than forcing a choice, consistent with CONTEXT.md's "label is the source of truth, kind is optional" decision. |

## Interaction & Layout Notes (beyond the template's core tables)

These notes translate the CONTEXT.md/ARCHITECTURE.md/STACK.md decisions into concrete chrome so the executor has no ambiguity — kept here rather than inventing new template sections.

### Tab placement & lock gating
- New tab button `svc-tab-stage`, inserted in the existing `role="tablist"` block in `ServiceEditorView.vue` **after Roles, before Messages** (Service Order · Slides · Roles · Stage Layout · Messages), copying the exact button markup/class pattern of the other tab buttons verbatim (`px-4 py-2 text-sm font-medium rounded-t-md transition-colors -mb-px border-b-2`, active: `text-indigo-300 border-indigo-500 bg-gray-900`, inactive: `text-gray-400 border-transparent hover:text-gray-200 hover:border-gray-600`). Gated `v-if="authStore.isEditor"` like the Roles tab (tech/sound planning is an editor concern, matching Roles' own gate) — flag this gate choice for plan-time confirmation against 107-CONTEXT.md if a viewer-visible read case emerges.
- Panel `svc-panel-stage`, `v-show="activeTab === 'stage'"`, `role="tabpanel"`, `aria-labelledby="svc-tab-stage"` — matches the existing panel wiring exactly.
- Editability follows `canEditService` (Draft-only), identical gate to Service Order/Slides/Roles. When locked, the canvas renders in the SAME read-only mode as the share/print render (no drag handles, no add/edit/delete controls) — reuse the read-only rendering component here too rather than building a third rendering path. The existing amber lock banner (`service-lock-banner`) already covers messaging; no second banner is needed inside the Stage Layout panel.

### Canvas chrome
- Two zone containers stacked vertically on narrow viewports, side-by-side on wide viewports (on-stage larger/primary, off-stage narrower, matching the owner's "drums and piano off the stage on the side" mental model) — each zone is `position: relative` with a fixed aspect-ratio box (not free-height), so `xPct/yPct` maps predictably to pixel bounds.
- Zone headings sit directly above each zone: "ON STAGE" / "OFF STAGE (SIDE)", 12px/600/uppercase/tracking-wide, `text-gray-400` — matches the existing "Teams" section-header treatment.
- "Add marker" button sits in a toolbar row above both zones (24px gap below it to the canvas), opening an inline form (not a modal) with: free-text label input (autofocus), optional kind select (Instrument / Mic / Monitor / Other / none), and implicit placement (new marker drops at the zone's center, or the last-clicked empty position within a zone if the add flow supports click-to-place — plan-time detail, not blocking this contract).
- Marker chip: small rounded pill/tag (`bg-gray-800 border border-gray-700 text-gray-200 rounded-md`), a 3px kind-accent bar on its leading edge (or a 6px dot if a bar reads poorly at this size — implementer's call, not load-bearing), label text (14px/400, truncated), a drag-grab affordance covering the whole chip (`touch-action: none` per PITFALLS.md), and on hover/focus reveals small edit (pencil)/delete (trash) icon-buttons at 44px touch targets — same icon-button treatment as `MiscLabelBadge.vue`'s pencil icon.
- Clicking a marker chip (not dragging) opens the edit-marker popover: label input, kind select, a "Move to [other zone]" toggle/button, and the Remove-marker inline confirm row from the Copywriting Contract above.
- Drag interaction is exactly the STACK.md/CONTEXT.md-specified `pointerdown` → `setPointerCapture` → `pointermove` (visual position only, no persistence) → `pointerup` (compute containing zone by bounding-rect check, clamp `xPct/yPct` to `[0,100]`, persist via the debounced autosave path) — this UI-SPEC does not further constrain that mechanism, it is an ARCHITECTURE/PLAN concern; the visual result (chip follows the pointer 1:1, snaps into whichever zone it's dropped in) is the only UI-observable contract here.

### Read-only render (ShareView + print)
- One shared read-only rendering component/branch (per ARCHITECTURE.md's "same component reused in two contexts" note) consumes `ServiceSnapshot.stageLayout` — same two-zone layout, same zone headings, same marker chip visual (kind accent bar/dot + label), but with NO drag-grab affordance, NO hover-reveal edit/delete icons, and no pointer-capture wiring at all — purely `position: absolute; left: {xPct}%; top: {yPct}%` divs.
- On `ShareView.vue` (light theme, `bg-white text-gray-900`), the zone containers and marker chips must use ShareView's own light-mode equivalents (`bg-gray-50 border border-gray-200`, marker chip `bg-white border border-gray-300 text-gray-800`) rather than the editor's dark-mode classes verbatim — mirrors how `ShareView.vue` already re-themes every other section (light backgrounds, `text-gray-900` headings) rather than reusing `ServiceEditorView.vue`'s dark palette directly. Kind-accent hues stay the same family (sky/emerald/amber/gray) at a lighter tint (`-100`/`-700` pairing) to stay legible on white.
- On `ServicePrintLayout.vue` (`print:block bg-white text-gray-900`), same light-mode treatment, added as a new section following the existing Notes section, titled "Stage Layout" (text-sm font-semibold text-gray-700, matching the Notes heading), positioned to `break-inside-avoid` like every other print block.
