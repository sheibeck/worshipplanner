<objective>
R240 — remove the genuinely-duplicated song-browse filtering by extracting the tag include/exclude logic (currently copied byte-for-byte in `stores/songs.ts` and `SongSlotPicker.vue`) into one shared `filterSongsByTags()` in `src/utils/songSearch.ts`, and repoint both consumers at it. Together with the already-shared `songMatchesQuery`/`matchesToken` search core in the same module, this gives the Songs page and the service-plan song picker one shared song-browse-filter core — satisfying R240 without a redesign.

Purpose: Per RESEARCH.md the two surfaces' list RENDERING is UX-incompatible (a sortable multi-select data table vs. an AI/rotation-augmented selection dropdown), so a single shared list renderer would be a redesign the requirement explicitly rules out. The real, removable duplication is the tag-filter Set-intersection logic — two independent copies with identical semantics that would otherwise drift. Extracting it is behavior-neutral by construction (the util is a lift of the existing logic). An optional thin search+tag-filter wrapper component is deliberately left out per the researched boundary — this is not a scope reduction, it is the correct extraction that keeps both consumers' behavior exact.
Output: `filterSongsByTags()` in `songSearch.ts` with unit tests, and both consumers delegating to it with unchanged behavior (proven by the existing regression suites).
</objective>
