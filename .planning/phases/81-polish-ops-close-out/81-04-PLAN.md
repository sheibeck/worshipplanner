<objective>
R240 — deliver ONE shared song-browse component that powers BOTH the Songs page and the service-plan song picker, closing the genuine duplication between them. Per RESEARCH.md's PRIMARY recommendation (Architecture Patterns / Code Examples / Pitfall 6) and CONTEXT.md's locked decision, this is a TWO-part deliverable, both parts required: (a) extract the byte-for-byte-duplicated tag include/exclude logic (currently copied in `stores/songs.ts` and `SongSlotPicker.vue`) into one pure `filterSongsByTags()` in `src/utils/songSearch.ts`; AND (b) build a new `SongBrowser.vue` wrapper component that owns the search input + the `TagFilterChecklist` + the filtered-song computed (using `filterSongsByTags()`), exposing a scoped default slot for row/list markup, consumed by BOTH `SongsView.vue`'s `SongFilters.vue` call-site area and `SongSlotPicker.vue`.

Purpose: R240 / ROADMAP Phase 81 Success Criterion #4 both require "ONE shared song-browse component" — not merely a shared function. The two surfaces' ROW rendering is genuinely UX-incompatible (a sortable multi-select data table vs. an AI/rotation-augmented selection dropdown), so per RESEARCH Pitfall 6 we do NOT unify the row markup — the shared boundary is the search+filter SHELL (search input + tag checklist + tag-filtered computed), handed to each consumer through a scoped default slot that renders that consumer's own, unchanged rows. This de-duplicates the shell and the tag-filter logic while preserving each surface's behavior exactly.
Output: `filterSongsByTags()` in `songSearch.ts` with unit tests; a new `SongBrowser.vue` wrapper with its own component test; both consumers rewired to browse through `SongBrowser`, with unchanged filtered results and rows (proven by the existing regression suites).
</objective>
