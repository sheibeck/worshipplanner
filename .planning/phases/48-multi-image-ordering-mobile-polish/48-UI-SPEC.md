## Spacing Scale

Declared values (must be multiples of 4), matching the scale already in use across
`ServiceEditorView.vue` / `ContextualActionBar.vue` / `QuarterView.vue`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps (`gap-1`, `gap-1.5`) |
| sm | 8px | Compact inline spacing (`gap-2`, `p-2`) |
| md | 16px | Default control padding, row gaps (`gap-4`, `px-4`) |
| lg | 24px | Section padding (`px-6`) |
| xl | 32px | — |
| 2xl | 48px | — |

Exceptions (locked by this phase):
- **44×44px minimum touch target** for the two Slides-tab drag/menu affordances this phase touches
  (`SlideCard.vue`'s drag handle, `SlideActionMenu.vue`'s trigger) — both currently render a
  ~16–28px visual icon with **zero or minimal padding**, well under the touch-target floor. Fix via
  invisible hit-area padding compensated by an equal negative margin (`-m-2 p-2` / `-m-3.5 p-3.5`
  as needed to reach 44px), **not** by enlarging the icon itself — the visual footprint must stay
  identical to today's desktop rendering. Apply universally (not only at mobile breakpoints): a
  larger click target never regresses desktop mouse use, and a single unconditional class is
  simpler and less regression-prone than a responsive one.
- Action-bar button padding (`px-3 py-2`) is unchanged by this phase — Print/Share inherit
  `ContextualActionBar.vue`'s existing `BASE_CLASS` verbatim (see § Action Bar Migration below).

## Phase-Specific Component Contracts

### 1. Slides Tab Mobile Layout (R099) — Audit Findings

Audited `SlidesTab.vue`, `SlidePlanRail.vue`, `SlideGrid.vue`, `SlideCard.vue`,
`SlideActionMenu.vue` directly (not assumed). Three concrete mobile-blocking issues found, in
order of severity:

**Blocker 1 — fixed-width sidebar breaks the layout at 375px (the primary defect).**
`SlidesTab.vue:3` wraps `SlidePlanRail` and the grid content in a bare `flex flex-1 min-h-0` row
with no responsive variant. `SlidePlanRail.vue:2` is `w-[260px] shrink-0` — a **hard-coded pixel
width with no breakpoint**. At a 375px viewport this alone consumes 260px (70% of the screen)
before the grid — which needs `minmax(200px,1fr))` per card — ever gets a chance to lay out. The
grid does not just look cramped; it structurally cannot fit beside the rail on a phone.

*Fix contract:* `SlidesTab.vue`'s wrapping row becomes `flex flex-1 min-h-0 flex-col sm:flex-row`
(same `sm` breakpoint as QuarterView, per R100's mandate to use one consistent breakpoint
project-wide). `SlidePlanRail.vue`'s root becomes `w-full sm:w-[260px] shrink-0 border-b sm:border-b-0
sm:border-r border-gray-800`. Below `sm`, the rail's row list becomes a horizontally-scrolling strip
rather than a tall vertical list eating the phone's limited vertical space above the grid: the rows
container (`SlidePlanRail.vue:36`) becomes `flex flex-row gap-1.5 overflow-x-auto px-3 py-3
sm:flex-col sm:space-y-1.5 sm:overflow-x-visible sm:px-3 sm:pb-3 sm:py-0`, and each row button
(currently `w-full`, line 41) becomes `w-[220px] shrink-0 sm:w-full sm:shrink` so rows keep a
comfortable tap width inside the horizontal scroller instead of being crushed. The skeleton and
empty-state blocks (lines 11-30) need the same axis treatment (`flex flex-row sm:flex-col`) applied
to their wrappers so the loading/empty state doesn't stack 4 skeleton rows vertically above an
already-scarce phone viewport.

**Blocker 2 — drag-handle and menu-trigger tap targets are far under 44px.**
`SlideCard.vue:92-104`'s drag handle renders a bare `h-4 w-4` (16px) SVG inside a `flex-shrink-0`
span with **no padding at all** — the clickable/touchable area is the icon's own 16×16px bounding
box. `SlideActionMenu.vue:3-18`'s trigger button is marginally better (`p-1` + `h-5 w-5` icon =
~28×28px) but still well under the 44px floor. Both are exactly the two touch affordances R099's
touch-reorder feature depends on.

*Fix contract:* see § Spacing Scale exceptions above — invisible padding compensated by equal
negative margin, applied unconditionally (not mobile-only), so neither icon's visual size nor the
surrounding card layout shifts.

**Blocker 3 — SortableJS instance itself needs no reconfiguration, only touch options added.**
`SlideGrid.vue:964-1040`'s existing `Sortable.create(el, { handle: '.drag-handle', draggable:
'.slide-card', animation: 150, ghostClass: 'opacity-30', onEnd... })` already uses the
draggable-scoped index fix (`evt.oldDraggableIndex`/`newDraggableIndex`, not `oldIndex`/`newIndex`)
that the v1.4 root-cause research and this phase's own locked decision require reusing verbatim.
**Do not touch this configuration.** Per the locked decision (R099, `ZTXcpNRcJTalEQp42fTx`), only
ADD touch-only options to the same `Sortable.create` call: `delay: 150`, `delayOnTouchOnly: true`,
`touchStartThreshold: 5` (SortableJS defaults commonly used to distinguish a scroll gesture from a
drag-start on touch) — appended to the existing options object, not a second instance, not a
reconfigured `handle`/`draggable`/`animation`.

**Not found to be a blocker (checked, no fix needed):**
- `SlideGrid.vue`'s header row (`flex flex-wrap items-center gap-x-3 gap-y-2 ... px-6 py-3`) already
  wraps; no fixed widths inside it.
- The card grid itself (`grid-cols-[repeat(auto-fill,minmax(200px,1fr))]`) already degrades to a
  single column once the rail stops competing for width — 375px minus `px-6 py-4`'s 48px horizontal
  padding leaves 327px, comfortably above the 200px minimum.
- `EditSlideDrawer.vue:21` is already `w-full max-w-[480px]` — already phone-safe, no change needed.
- The group-media panel (`mx-6 ... flex-wrap`) already wraps its two controls; no fixed widths.

### 2. Service Edit Screen Button Stacking (R100) — the QuarterView Recipe to Copy

`QuarterView.vue:6` and `:13` are the two-part recipe to reproduce verbatim (same breakpoint,
`sm`, for consistency across the app):

```
<!-- Row wrapper: stacks the label block above the button cluster below `sm` -->
<div class="flex flex-col sm:flex-row sm:items-center sm:justify-between gap-4 ...">

<!-- Button cluster: each button full-width and stacked below `sm`,
     auto-width and inline at `sm` and above -->
<div class="flex flex-col sm:flex-row sm:flex-wrap sm:items-center sm:justify-end gap-2
            w-full sm:w-auto [&>*]:w-full sm:[&>*]:w-auto
            [&>*]:justify-center sm:[&>*]:justify-start">
```

**Apply to `ServiceEditorView.vue`'s header "Save area"** (the `div class="flex items-center
gap-3"` at line 97, containing Undo/Mark-as-Planned/ContextualActionBar): once Undo relocates
(R102, below) this row holds Mark as Planned + the action bar's items. Wrap it with the button-
cluster recipe above so it stacks full-width on a phone instead of the buttons compressing into an
unreadable single line.

**Apply to the bottom "Print, Share, Delete" row** (`ServiceEditorView.vue:1300-1349`,
`class="mt-6 pt-4 border-t border-gray-800 flex flex-wrap items-center gap-2 print:hidden"`) —
note this row **loses Print and Share** to the top action bar (R101, below) and keeps only Delete.
A single remaining button needs no stacking recipe; simplify this row's class to drop the now
orphaned `flex-1` spacer (`:1335`, which existed only to push Delete to the right of Print/Share)
and keep Delete right-aligned some other way (e.g. `justify-end` on the row) once it is the row's
only child.

**Header row itself** (`ServiceEditorView.vue:38`, `class="flex flex-col sm:flex-row
sm:items-start sm:justify-between gap-4 mb-3"`) is **already** using this exact recipe's first half
— no change needed there.

### 3. Action Bar Migration — Print and Share (R101)

Add two new items to `serviceEditorActionBar.ts`'s `buildServiceOrderItems` (the Service Order
tab's item list), positioned **after Save** (the row already reads
`Suggest All Songs → Export to PC → Save`; Print/Share are the two controls that used to live at
the page bottom, so they read as an appendix to the primary actions, not a competitor to Save's
primary weight):

```ts
function buildPrintItem(ctx: ActionBarContext): ActionBarItem {
  return {
    key: 'print',
    label: 'Print',
    icon: 'print',       // new icon key — the existing printer SVG from ServiceEditorView.vue:1310-1312
    onClick: ctx.handlers.onPrint,
  }
}

function buildShareItem(ctx: ActionBarContext): ActionBarItem | undefined {
  if (!ctx.isEditor) return undefined   // editor-only, same gate as today's bottom-row Share
  return {
    key: 'share',
    label: ctx.isSharing ? 'Sharing...' : ctx.shareCopied ? 'Link Copied!' : ctx.shareError ? ctx.shareError : 'Share',
    icon: 'share',        // new icon key — the existing share SVG from ServiceEditorView.vue:1326-1328
    onClick: ctx.handlers.onShare,
  }
}
```

Ordering in `buildServiceOrderItems`: `Suggest All Songs → Export to PC → Save → Print → Share`.
Rationale: Save stays the row's one `tone: 'primary'` (filled indigo) item — Print/Share both use
`ContextualActionBar`'s `default` gray tone, the same tone Present already uses, so three
gray-toned utility actions (Present-equivalent-weight) trail the one accent action, never compete
with it visually.

**`ContextualActionBar.vue`** needs two additions: the new `print`/`share` icon branches (reuse the
exact SVG paths already at `ServiceEditorView.vue:1310-1312` and `:1326-1331` verbatim — do not
redraw them), and `flex-wrap` added to its root (`class="flex items-center gap-3"` →
`"flex flex-wrap items-center gap-3"`) so a Service-Order tab with every possible item present
(Suggest All Songs + Export + Save + Print + Share, up to 5 buttons) wraps to a second line at
375px rather than clipping or forcing horizontal scroll.

**Both new items render on the Service Order tab only** — `buildSlidesItems` and the Roles branch
(`[]`) are untouched. Print and Share are service-level actions tied to the whole service document,
which is what the Service Order tab already represents; adding them to Slides or Roles would be a
scope expansion this phase does not call for.

**`ServiceEditorView.vue`'s bottom row loses Print and Share** (delete the two `<button>` blocks at
lines 1302-1314 and 1319-1333) but **keeps Delete exactly as it is today** — same gate
(`authStore.isEditor`), same confirm-dialog flow, same position (page bottom, below the fold, away
from the primary actions a destructive control must never sit beside).

### 4. Undo Becomes a Link (R102)

**Remove** the Undo `<button>` from the header's "Save area" (`ServiceEditorView.vue:98-112`).

**Add** an Undo link inside the sticky save-status wrapper (`ServiceEditorView.vue:255-263`,
`data-testid="service-save-status-bar"`), immediately after `<SaveStatusIndicator>`:

```html
<div
  v-if="canEditService && congregationalSlotIndex === null"
  :class="[
    'flex items-center gap-2',
    serviceSaveStatusVisible
      ? 'sticky top-0 z-10 mb-3 rounded-md border border-gray-800 bg-gray-900 px-4 py-2'
      : ''
  ]"
  data-testid="service-save-status-bar"
>
  <SaveStatusIndicator :surface-id="`service:${serviceId}`" />
  <button
    v-if="previousService"
    type="button"
    data-testid="undo-link"
    title="Undo last save (Ctrl+Z)"
    class="text-xs text-indigo-400 hover:text-indigo-300 underline transition-colors"
    @click="onUndo"
  >Undo</button>
</div>
```

Note the wrapper now **always** carries `flex items-center gap-2` (previously that layout was part
of the conditional chrome, applied only when `serviceSaveStatusVisible`) — this is a deliberate,
minimal widening of the always-on classes so the Undo link lays out correctly beside
`SaveStatusIndicator` even when the idle-state chrome (border/background/padding/sticky) is absent.
The border/background/padding/sticky positioning stay exactly as conditional as before; only the
flex layout becomes unconditional. This does not reintroduce the empty-box regression `31-UI-SPEC
E5` guards against — `SaveStatusIndicator` renders nothing visible at idle and the Undo link is
`v-if`-gated, so an idle service with no undo-able snapshot still renders a zero-content,
zero-visible-chrome `<div>`.

**Same gate as today**: `v-if="previousService"` (the surrounding wrapper already carries
`canEditService`, so the button's own condition drops the redundant `canEditService &&` prefix).
**Keep the Ctrl+Z keyboard binding** and `onUndo` handler completely unchanged — only the rendered
element and its class list change, from a bordered/backgrounded button among the primary actions to
an underlined text link beside the save-status text.

**Do NOT touch** the second `SaveStatusIndicator` instance inside the congregational-editor modal
(`ServiceEditorView.vue:519`) — that surface has no Undo affordance today and R102 does not ask for
one there; adding it would be scope creep into a different editing context.

### 5. Getting Started Dismiss Control (R103)

Add a dismiss `×` button to `GettingStarted.vue`'s header row (the `div class="px-6 py-4
border-b border-gray-800"` at lines 3-6, which currently holds only the title/subtitle):

```html
<div class="px-6 py-4 border-b border-gray-800 flex items-start justify-between gap-3">
  <div>
    <h2 class="text-sm font-semibold text-gray-100">Getting Started</h2>
    <p class="text-xs text-gray-500 mt-0.5">Get set up in a few quick steps</p>
  </div>
  <button
    type="button"
    aria-label="Dismiss Getting Started"
    data-testid="getting-started-dismiss"
    class="-m-1.5 p-1.5 rounded-md text-gray-500 hover:text-gray-300 hover:bg-gray-800 transition-colors shrink-0"
    @click="onDismiss"
  >
    <svg xmlns="http://www.w3.org/2000/svg" class="h-4 w-4" fill="none" viewBox="0 0 24 24" stroke="currentColor" stroke-width="2">
      <path stroke-linecap="round" stroke-linejoin="round" d="M6 18L18 6M6 6l12 12" />
    </svg>
  </button>
</div>
```

Icon and sizing (`h-4 w-4` inside `p-1.5`, `-m-1.5` hit-area compensation) copy the
congregational-editor modal's existing close button (`ServiceEditorView.vue:520-530`) exactly, for
visual consistency between the app's two icon-only dismiss controls.

**Root `v-if` becomes** `v-if="!allDone && !dismissed"` — the dismiss is independent of, and
composes with, the existing auto-hide (both § UI Considerations rows above). **`localStorage` key:**
`wp:gettingStartedDismissed` (flat, unscoped by org/uid — this is per-device onboarding chrome, not
church data, and one browser profile is realistically one person regardless of which org they're
currently viewing; matches `CollapsibleSection.vue`'s existing precedent of a flat, non-namespaced
key for pure UI-state rather than `songs.ts`'s org/uid-scoped pattern, which exists specifically for
per-tenant data isolation that does not apply here). Value: presence of the key (any value, e.g.
`'true'`) means dismissed; read once, synchronously, at `setup()` — no watcher, no reactive
subscription needed since nothing else in the app changes this value.

**No un-dismiss UI** — confirmed out of scope by 48-CONTEXT.md's Deferred Ideas.
