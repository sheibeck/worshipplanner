# Phase 126 — UI Design Contract: My Schedule (Volunteer Home)

> Visual and interaction contract for R378–R383. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker. Governs the volunteer landing page reached after Phase 125's magic-link sign-in.
> **This phase writes no Rehearse/Order/Stage view** — the "Rehearse →" / "Open" affordance
> navigates to Phase 127's standalone service view; My Schedule itself is read-and-go and has no
> edit affordances anywhere.

Design reference: the owner's **"Volunteer Home"** mock (Turn 14, *Worship Planner Slideshow
Design* Claude Design project), Nocturne palette. Its **layout, grouping, and card anatomy are
authoritative**; its color values are **not** — every color below is remapped to the app's existing
Tailwind v4 dark theme, verified against the live source of `VolunteerSignInView.vue`,
`VolunteerLinkCompleteView.vue`, `ServiceCard.vue`, `ServicesView.vue`, and
`121-UI-SPEC.md`/`SongTable.vue` (the most recent precedent for this exact remap exercise).

## Data Dependencies (read before implementing — affects what the contract can render)

The `rehearseAccess` projection (`src/utils/rehearseAccess.ts`, Phase 125) and the `Service` type
(`src/types/service.ts`) currently carry **no** `venue`, service `time`, or volunteer `callTime`
field anywhere in the data model (confirmed by direct source read — `Service` has `id/date/name/
progression/teams/status/slots/sermonPassage/notes/...`, no time-of-day or location field;
`OrgSettings` has no venue/service-time default either). `assignedEmailsLower` is also a **flat
set** — the projection does not yet carry *which* roles each assigned email holds.

This UI-SPEC treats **time · venue**, **call time**, and **the volunteer's own role chips** as
**optional, gracefully-omitted fields** rather than assuming they exist:

- **Time · venue** (R381): render `"{time} · {venue}"` only when both are present; `"{time}"` alone
  when only time is present; omit the line entirely when neither exists. Do not render an em-dash
  or "TBD" placeholder — an omitted line is quieter than a placeholder for data that may never be
  modeled this phase.
- **Call time** (R381): same — a `"Call time {time}"` line in the right zone, rendered only when
  present, otherwise omitted (the zone still holds the countdown + Rehearse action either way).
- **Volunteer's own role chips** (R381): the projection's `assignedEmailsLower` is a flat set with
  no per-person role breakdown. To render `"You're on: {role chips}"`, the planner must either (a)
  extend `buildRehearseAccess` to denormalize a `rolesByEmailLower: Record<string, string[]>` map
  (mirroring `resolveServiceRoleAssignments`'s output, PII-safe — role names only, no other person
  fields), or (b) resolve roles client-side from a source the volunteer session is already
  authorized to read. **(a) is recommended** — it keeps the volunteer client from needing any
  broader roster read, matching R377's isolation guarantee. This is a data-layer decision, not a
  visual one; the card contract below assumes a `roles: string[]` array is available per card
  however it's sourced.
- **Song / chart / track counts** (R381): fully derivable from the existing projection today —
  `songs.length` for song count, `attachments.filter(a => a.kind === 'pdf').length` per song summed
  for chart count (with `Y` = total songs, so "{X} of {Y} charts" reads as "X songs have at least
  one PDF, out of Y songs"), `attachments.filter(a => a.kind === 'mp3').length` summed for track
  count. **No projection extension needed** for this row.
- **Readiness** (R381): also fully derivable today from `songs[].attachments` — see the Readiness
  Indicator section below for the exact three-state rule.

If the planner chooses NOT to extend the projection this phase, the contract still holds: time,
venue, call time, and role chips simply render as absent per the rules above, and R381 is satisfied
for the fields that ARE modeled (date, name, song/chart/track counts, readiness, countdown) — this
is flagged `unresolved` in UI Considerations, not silently dropped.

## Spacing Scale

Base scale (multiples of 4) — used for all NEW spacing introduced by this feature:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | icon-gap / chip internal gap (`gap-1`, `gap-1.5`→6px inherited exception below) |
| sm | 8px | chip padding, meta-row gaps (`gap-2`, `px-2`) |
| sm+ | 12px | card internal zone gaps (`gap-3`), section-header gap to hairline rule |
| md | 16px | card padding (`p-4`), inter-card vertical rhythm (`space-y-4`) |
| lg | 24px | section-to-section spacing (`mb-6` between "This week" and "Later this month"), page horizontal padding on tablet+ (`sm:px-6`) |
| xl | 32px | top bar to greeting block gap, greeting block to first section gap |
| 2xl | 48px | not used at this surface size — reserved for page-level layout only |

**Inherited off-grid exception:** `gap-1.5` (6px) on role chips (icon-to-label gap) — reused
verbatim from `StageKindIcon.vue`'s established icon-adjacent-to-label spacing elsewhere in the app
(e.g. `AppSidebar.vue`'s nav-item icon gap), not a new value invented for this feature.

Page container: `max-w-[1060px] mx-auto px-4 sm:px-6 py-8` — the mock's ~1060px centered body,
translated to the app's existing `px-4 sm:px-6` responsive-gutter idiom (matches `ShareView.vue`'s
`px-6 py-8 sm:px-10` pattern in spirit; 1060 is narrower than ShareView's 1600 because this is a
single-column list, not a multi-column stage/order view).

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display | 24px (`text-2xl`) | 600 (semibold) | 1.2 — the "Good {time-of-day}, {name}" greeting only |
| Heading | 16px (`text-base`) | 600 (semibold) | 1.3 — service name on each card |
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 — summary line, time·venue, meta rows, countdown, footer note, empty-state body |
| Label | 12px (`text-xs`) | 500 (medium) | 1.4 — role chip text, "Next up" pill, section-header micro-labels (11px eyebrow, see below), date-block month/weekday |

Exactly 2 weights used: **400 regular** (body/metadata) and **600 semibold** (greeting, service
name, section-header eyebrows, the big day number, the primary CTA). No 500-medium weight is
introduced net-new by this phase (role-chip/pill text uses 500 medium **inherited** from the
Files-tab badge precedent in `121-UI-SPEC.md` — reusing rather than adding a third weight is the
intent; if the executor finds this awkward, collapsing chip/pill text to 400 regular is an
acceptable substitution that keeps the 2-weight budget honest).

Section-header eyebrow ("THIS WEEK" / "LATER THIS MONTH" / "PAST SERVICES"): 11px
(`text-[11px]`), 600 semibold, uppercase, `tracking-widest`, `text-gray-500` — inherited verbatim
from `ServicesView.vue:80`'s `text-xs font-semibold uppercase tracking-widest text-gray-500`
pattern (bumped from `text-xs`/12px to the mock's tighter 11px eyebrow only if the executor wants
exact mock parity; reusing the existing 12px class as-is is equally acceptable and lower-risk).

Big day number (date block): `text-3xl font-mono font-semibold` (30px) — the one place `font-mono`
is used on this screen, per the mock's "big mono day number."

## Surfaces & Components

**Primary visual anchor:** the Next-up card is the focal point of the page — it is the only card
with an accent border/ring and an outlined-accent CTA; every other element (greeting, section
headers, other cards) is deliberately quieter so the volunteer's eye lands on what to do next.

### 1. Top bar (new: `VolunteerTopBar.vue`, or inline in the view — planner's call)

Persistent header, present on My Schedule (and recommended for reuse by Phase 127's service view,
though that's out of this phase's scope to build):

```
[signal icon] Worship Planner                              [DR] Dana Reyes ▾
                                                              dana@example.com
```

`h-14 px-4 sm:px-6 border-b border-gray-800 bg-gray-900 flex items-center justify-between` — brand
mark left (`signal` icon `h-5 w-5 text-gray-400` + `text-sm font-semibold text-gray-100
tracking-tight` "Worship Planner", matching `AppSidebar.vue`'s exact brand text treatment); user
chip right, a `<button>` (opens a small menu — see §7 "check a different email" below):
avatar (`w-8 h-8 rounded-full bg-indigo-600 flex items-center justify-center text-xs font-medium
text-white` with initials, reusing `VolunteerSignInView.vue`'s exact avatar formula at a slightly
smaller inline size) + name (`text-sm font-medium text-gray-100`) + email beneath on its own line
(`text-xs text-gray-500`, hidden below `sm:` to save width on phones — show avatar + name only on
mobile) + trailing `chevron-down` (`h-4 w-4 text-gray-500`).

**A11y:** the chip is a real `<button aria-haspopup="menu" aria-expanded="...">`; opening reveals a
small menu (`role="menu"`, 2 items: "Check a different email" → the different-email flow, "Sign
out" → `volunteerAuth.signOut()`), matching the disclosure pattern already established for other
menus in the app.

### 2. Greeting + summary block

```
Good morning, Dana                                                    (text-2xl font-semibold text-white)
You're assigned to 3 upcoming services — next one is tomorrow.        (text-sm text-gray-400, mt-1)
```

- Greeting text: `"Good {time-of-day}, {firstName}"` where time-of-day is `morning` (00:00–11:59
  local), `afternoon` (12:00–17:59), `evening` (18:00–23:59) — computed client-side off
  `new Date()`, no server round-trip. `firstName` = the same first-name-only extraction already
  computed in `VolunteerSignInView.vue`'s `displayLabel` (reuse that computed, don't reinvent).
  Falls back to `"Welcome"` (no name clause) when the account has no display name and the email
  local-part would look awkward capitalized as a name.
- Summary line: `"You're assigned to {N} upcoming service{s} — next one is {countdown}{, at TIME
  if present}."` When `N === 0`, this line is **not rendered** — the empty state (§8) replaces the
  whole page body instead.
- Spacing: `mt-8` below the top bar, `mb-8` before the first section.

### 3. Section headers

```
THIS WEEK ─────────────────────────────────────────────
```

`flex items-center gap-3 mb-3`: eyebrow label (`text-[11px] font-semibold uppercase tracking-widest
text-gray-500 shrink-0`) + a hairline rule (`flex-1 border-t border-gray-800`). Three possible
headers in fixed order: **This week**, **Later this month**, **Past services** (collapsed by
default — see §6). A section with zero services in it is **not rendered** (no empty "This week"
header with nothing under it) — this mirrors `ServicesView.vue`'s existing "only show sections with
content" convention.

**Week/month boundary (Claude's discretion, documented so it's reproducible):** "This week" = the
service date falls between today and the coming Saturday inclusive (org-local timezone,
`OrgSettings.timezone`, v1.7 precedent). "Later this month" = every other upcoming date, including
one beyond the current calendar month (a genuine edge case with no dedicated section per R380's
two-bucket contract — flagged in UI Considerations, not silently mis-labeled).

### 4. Service card — three-zone anatomy (upcoming)

The **entire card is one interactive element** — a single `<router-link>` (or `<a>`, per the
routing decision below), never a link nested inside a link/button. This matches `ServiceCard.vue`'s
precedent of one primary router-link per card, and avoids the interactive-in-interactive a11y
anti-pattern the visible "Rehearse →" button would otherwise create if it were a separate nested
`<button>`.

```
┌────────────────────────────────────────────────────────────────────────┐
│ SEP        Sunday Worship                              [Next up]       │
│  14        9:00 AM · Main Sanctuary                                    │
│ Sun        ─────────────────────────────                               │
│            You're on:  🎸 Acoustic guitar   🎤 Harmony vocal            │
│            3 songs · 2 of 3 charts · 4 tracks                          │
│            ✓ All rehearsal files ready                Tomorrow         │
│                                                    [ Rehearse → ]       │
│                                                    Call time 7:45 AM    │
└────────────────────────────────────────────────────────────────────────┘
```

Container: `flex items-stretch gap-4 rounded-xl border p-4` —
neutral: `border-gray-800 bg-gray-900`; **Next-up variant:** `border-indigo-500/50 ring-1
ring-indigo-500/10 bg-gray-900`. `hover:border-gray-700` (neutral) / no hover-border change on
Next-up (already accented). Cards stack `space-y-3` within their section.

**Zone 1 — Date block** (`w-[72px] sm:w-[112px] shrink-0 flex flex-col items-center justify-center
text-center border-r border-gray-800 pr-3 sm:pr-4`):
- Month: `text-[11px] font-semibold uppercase tracking-wide text-gray-500`
- Day: `text-3xl font-mono font-semibold text-gray-100` (Next-up variant: `text-indigo-400`)
- Weekday: `text-xs text-gray-400`

**Zone 2 — Middle** (`flex-1 min-w-0 flex flex-col gap-1.5`):
- Row 1: service name (`text-base font-semibold text-gray-100 truncate`) + **Next up** pill
  (§ Color, only on the soonest card) inline, `flex items-center gap-2 justify-between`.
- Row 2: `"{time} · {venue}"` (`text-sm text-gray-400`) — omitted per Data Dependencies when absent.
- Row 3: `"You're on:"` (`text-xs text-gray-500`) + role chips, `flex flex-wrap items-center gap-1.5
  mt-1`. Chip: `inline-flex items-center gap-1.5 px-2.5 py-1 rounded-full bg-gray-800
  border border-gray-700 text-xs text-gray-200` + instrument icon + role label (e.g. "Acoustic
  guitar", "Harmony vocal", "Lead vocal" — the role's display name verbatim, not abbreviated).
- Row 4: meta counts (`text-xs text-gray-500`): `"{N} songs · {X} of {Y} charts · {Z} tracks"`.
- Row 5: readiness line (`flex items-center gap-1.5 text-xs`), icon + copy per state (§ Readiness
  Indicator below).

**Zone 3 — Right** (`w-[96px] sm:w-[212px] shrink-0 flex flex-col items-end justify-center gap-2
text-right`):
- Countdown: `text-sm font-medium` — `text-indigo-300` on the Next-up card, `text-gray-300`
  elsewhere.
- Rehearse CTA (visual only, not a nested interactive element — see anatomy intro): Next-up variant
  `inline-flex items-center gap-1 px-3 py-1.5 rounded-md border border-indigo-500 text-indigo-300
  text-sm font-medium`; other upcoming cards: `text-indigo-400 text-sm font-medium` (no border/fill).
  Label: **"Rehearse →"**.
- Call time (`text-xs text-gray-500`) — omitted per Data Dependencies when absent.

**A11y:** the card's `aria-label` carries full context the visible "Rehearse →" text lacks in a
screen-reader link list, e.g. `aria-label="Rehearse for Sunday Worship, September 14, tomorrow"`.
Readiness icons are `aria-hidden="true"` with the text carrying the meaning (never icon-only
meaning). Role chip icons are `aria-hidden="true"` (decorative — the label text is the accessible
content).

### 5. Service card — past variant

Same three-zone shape, but:
- Card container: no accent, slightly more muted — `border-gray-800/60 bg-gray-900/60`.
- Service name: `text-gray-500` (dimmed, per CONTEXT's "dimmed title").
- No "Next up" pill, no role-chip "You're on" emphasis change (chips still render, same style —
  they're historical fact, not muted further).
- Zone 3 CTA: **"Open service"** instead of "Rehearse →", styled as a plain text link
  (`text-gray-400 hover:text-gray-300 text-sm`) — no accent color, since past cards are archival,
  not action items.
- Countdown becomes a past-relative label (see Copywriting Contract) instead of a future one.
- Call time is typically irrelevant for a past service and may be omitted even when the field
  exists (planner's discretion — showing it is harmless but adds no value after the fact).

Past services render under a **collapsed-by-default** "Past services" section (matching
`ServicesView.vue`'s existing `showPast` toggle button + chevron-rotate pattern verbatim) rather
than always-visible, since they're reference material, not action items.

### 6. Readiness indicator — three states

| State | Icon | Color | Copy |
|-------|------|-------|------|
| All ready | `check-circle` | `text-green-400` | "All rehearsal files ready" |
| Partial | `exclamation-triangle` | `text-amber-400` | "{N} song{s} still missing media" |
| Waiting | `clock` | `text-amber-300` | "Waiting on charts from the leader" |

**Derivation rule** (off the existing projection, no new fields needed): for each song in the
service, "has media" = `song.attachments.some(a => a.kind === 'pdf' || a.kind === 'mp3')`.
- **All ready:** every song has media.
- **Partial:** at least one song has media AND at least one does not (N = count with none).
- **Waiting:** zero songs have any media at all.

### 11. Mobile reflow (R391)

Below `sm:` (640px), each card's three zones **stack vertically** instead of sitting side-by-side:

```
┌─────────────────────────────┐
│ SEP 14 · Sun      [Next up] │   ← date block collapses to one inline row
│ Sunday Worship               │
│ 9:00 AM · Main Sanctuary     │
│ You're on: 🎸 Acoustic guitar │
│ 3 songs · 2 of 3 charts      │
│ ✓ All rehearsal files ready  │
│ ─────────────────────────── │
│ Tomorrow                     │
│ [ Rehearse → ]  (full width) │
│ Call time 7:45 AM            │
└─────────────────────────────┘
```

Structural rule: `flex flex-col sm:flex-row` on the card container; Zone 1 (date) becomes a single
inline row (`MMM D · Weekday`, no border-right, `border-b border-gray-800 pb-2 mb-2` instead) rather
than a tall vertical block, since a full-height date column wastes width on a phone; the "Next up"
pill moves to the same inline row, right-aligned. Zone 3's CTA becomes a full-width button
(`w-full` on mobile, auto-width at `sm:`) beneath the countdown, matching the mock's intent that the
CTA stays a clear, thumb-reachable tap target on a phone. Role chips wrap (`flex-wrap`) rather than
overflowing off-screen or scrolling horizontally.

The top bar's user-chip email line hides below `sm:` (§1) to prevent header crowding on narrow
screens; the greeting and summary line font sizes are unchanged at mobile (no separate mobile type
scale needed — 24px/14px both fit a 320px viewport without wrapping awkwardly at reasonable name
lengths).

### 12. Routing note (affects the CTA's `href`/`to`, not its visuals)

Per 126-CONTEXT.md's build-safety note: do not add a lazy `import()` to a Phase-127 component that
doesn't exist yet. This UI-SPEC's contract for the executor is the **visible label and click
target only** — `"Rehearse →"` / `"Open service"` both navigate to the same per-service route
(e.g. `/volunteer/service/:serviceId`, exact path/name is the planner's call per CONTEXT). Whether
that route resolves to a real Phase-127 view or a Phase-126 placeholder view is an implementation
decision outside this visual contract's scope — either way, the card's clickable target, label, and
`aria-label` are as specified above.
