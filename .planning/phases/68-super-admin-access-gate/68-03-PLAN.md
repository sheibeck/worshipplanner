<objective>
Add the claim-only `isSuperAdmin()` Firestore rules helper and gate `appConfig/*` + `superAdmins/*` on it, with genuine emulator ALLOW **and** DENY tests (R178).

This is the REAL server-side access boundary (the client route guard in Plan 04 is only convenience). The helper is deliberately claim-only — `request.auth.token.superAdmin == true`, zero `get()`/`exists()` — because this repo has a documented production incident (CLAUDE.md, 2026-08-06) where a cross-document/cross-service rules lookup produced a deny-everyone outage. Per CLAUDE.md's rules-first discipline, a deny-only suite is exactly what once let a broken rule ship, so this plan writes the ALLOW cases too and orders them tests-first.

This plan writes ONLY the rules for `appConfig/*` — NOT the `appConfig/global` document contents or any schema (that is Phase 69). Do not create `functions/src/appConfig.ts` or write any appConfig doc here (Pitfall 7).

Purpose: The enforceable super-admin boundary for the two admin-only collections, proven both directions (R178).
Output: `firestore.rules` (helper + two match blocks) and new `src/rules.test.ts` describe block.

Note on running the rules suite (CLAUDE.md): the ALLOW/DENY tests run via `vitest.rules.config.ts` against a Firestore emulator; `src/rules.test.ts` is EXCLUDED from the default `npx vitest run`. Use `npx vitest run --config vitest.rules.config.ts` with an emulator already running, or `npm run test:rules` (which starts its own emulator and fails "port taken" if one is already up).
</objective>
