# Phase 71 — UI Design Contract

> Visual and interaction contract for the Enable → dry-run preview → confirm-to-flip flow added to
> `CleanupConfigCard.vue` (R188, R189, R190). Generated by gsd-ui-researcher. No interactive questions
> were needed — every open question below is resolved under the v1.9 autonomy grant, consistent with
> `70-UI-SPEC.md` (the contract this extends) and the existing modal-dialog precedent already in the
> app (`NewServiceDialog.vue`).

## Layout

The card shell, heading, and intro paragraph are unchanged from Phase 70. Each of the four cleanup
rows changes shape as follows (was: a bare disabled checkbox + `(read-only)` italic tag; becomes: the
same status checkbox, now paired with an explicit action):

```
┌─────────────────────────────────────────────────────────────────┐
│ Cleanup                                                          │
│ These control the four scheduled data-cleanup jobs...            │
│                                                                    │
│ [ ] Delete media after inactivity                       Enable   │  ← off: Enable action
│ [x] Delete orphaned PPTX renders                        Disable  │  ← on: Disable action (immediate)
│ [ ] Delete orphaned backgrounds                          Enable   │
│ [ ] Delete orphaned PPTX sources                         Enable   │
│                                                                    │
│ Enabling requires a dry-run preview and an explicit confirm...    │  ← updated shared note (replaces
│                                                                    │    Phase 70's "coming in a future
│                                                                    │    release" placeholder copy)
│ ───────────────────────────────────────────────────────────────  │
│ [existing Phase 70 retention/cap number fields, unchanged]        │
└─────────────────────────────────────────────────────────────────┘

  On Enable click → confirm dialog (Teleport'd to <body>, centered, backdrop):

  ┌───────────────────────────────────────────┐
  │  Enable media cleanup?                 [dialog title]
  │                                              │
  │  This will permanently delete up to        │
  │  47 objects (812.3 MB) on the next          │
  │  scheduled run. This cannot be undone.      │
  │                                              │
  │  [only for backgrounds when incomplete:]    │
  │  ⚠ Reference detection is incomplete...     │
  │                                              │
  │              [ Cancel ]   [ Enable ]        │
  └───────────────────────────────────────────┘
```

Row markup (each of the four rows follows this exact shape; only the label text and bound
`config`/`type`/`typeLabel` values differ):

```html
<div class="flex items-center justify-between gap-3">
  <label class="flex items-center gap-3 opacity-60 cursor-not-allowed">
    <input
      type="checkbox"
      :checked="store.resolvedConfig.cleanup.mediaEnabled"
      disabled
      class="h-4 w-4 rounded border-gray-700 bg-gray-800 text-indigo-600"
    />
    <span class="text-sm text-gray-200">Delete media after inactivity</span>
  </label>

  <button
    v-if="!store.resolvedConfig.cleanup.mediaEnabled"
    type="button"
    :disabled="stateFor('media').status === 'previewing'"
    @click="onEnableClick('media')"
    class="text-sm text-indigo-400 hover:text-indigo-300 disabled:opacity-60 disabled:cursor-not-allowed transition-colors"
  >
    {{ stateFor('media').status === 'previewing' ? 'Checking…' : 'Enable' }}
  </button>
  <button
    v-else
    type="button"
    :disabled="stateFor('media').status === 'disabling'"
    @click="onDisableClick('media')"
    class="text-sm text-gray-400 hover:text-gray-200 disabled:opacity-60 disabled:cursor-not-allowed transition-colors"
  >
    {{ stateFor('media').status === 'disabling' ? 'Disabling…' : 'Disable' }}
  </button>
</div>
<p v-if="stateFor('media').previewError" class="text-red-400 text-xs mt-1">{{ stateFor('media').previewError }}</p>
<p v-if="stateFor('media').disableError" class="text-red-400 text-xs mt-1">{{ stateFor('media').disableError }}</p>
<p v-if="stateFor('media').savedFlash" class="text-green-400 text-xs mt-1">{{ stateFor('media').savedFlash }}</p>
```

**The checkbox stays a pure status indicator** (`disabled` attribute retained, no `@change` handler on
it) — the write trigger is the explicit Enable/Disable button, never the checkbox itself. This keeps
the "enable never writes before confirm" guarantee unambiguous: there is no code path where toggling
the visual checkbox itself performs a write.

## Component Inventory

### `CleanupConfigCard.vue` (extended, not replaced)

| Field | AppConfig path | `previewCleanupDryRun` type arg | Row label | Dialog `typeLabel` |
|-------|----------------|----------------------------------|-----------|---------------------|
| Delete media after inactivity | `cleanup.mediaEnabled` | `media` | "Delete media after inactivity" | "media cleanup" |
| Delete orphaned PPTX renders | `cleanup.pptxRenderEnabled` | `orphanRenders` | "Delete orphaned PPTX renders" | "PPTX render cleanup" |
| Delete orphaned backgrounds | `cleanup.backgroundEnabled` | `backgrounds` | "Delete orphaned backgrounds" | "background cleanup" |
| Delete orphaned PPTX sources | `cleanup.pptxSourceEnabled` | `pptxSources` | "Delete orphaned PPTX sources" | "PPTX source cleanup" |

Only the `backgrounds` type ever carries `referencesComplete` in the callable response; the other three
never trigger the background-warning treatment.

### NEW: `CleanupEnableConfirmDialog.vue` (`src/components/admin/`)

A single, card-level dialog instance — only ONE cleanup row's dialog can be open at a time (a resolved
decision, see below), so the card owns one dialog mount, not four.

```ts
interface Props {
  open: boolean
  typeLabel: string              // e.g. "media cleanup" — see table above
  wouldDeleteCount: number
  wouldDeleteBytes: number       // raw bytes; component formats to MB internally
  referencesComplete?: boolean   // present (true/false) only when typeLabel === "background cleanup";
                                  // undefined for the other three types = warning never renders
  confirming: boolean            // true while the enable write (saveField) is in flight
  confirmError: string | null    // set if the enable write itself fails; dialog stays open, shows error
}

defineEmits<{
  confirm: []
  cancel: []
}>()
```

Reuses the exact `Teleport to="body"` + backdrop `Transition` + centered-panel `Transition` structure
already established by `NewServiceDialog.vue` (`fixed inset-0 z-40 bg-black/60` backdrop,
`fixed inset-0 z-50 flex items-center justify-center p-4` panel wrapper, `w-full max-w-md bg-gray-900
rounded-xl border border-gray-800 shadow-2xl` panel) — this is the FIRST reuse of that structural
pattern for a confirm dialog (vs. the lighter inline-row-confirm pattern in `OwnerConsoleView.vue`'s
Revoke / `TeamView.vue`'s Remove); see Resolved Design Decisions for why this phase earns the heavier
pattern.

Byte formatting: `(wouldDeleteBytes / 1024 / 1024).toFixed(1) + ' MB'` — identical precision/shape to
the existing `fileMb` precedent in `src/utils/pptxUpload.ts`, reused rather than inventing a new format.

## States & Interactions

### Per-row state machine (one `fieldStates`-style reactive entry per cleanup type, mirroring
`CleanupConfigCard.vue`'s existing `fieldStates` map for the retention fields)

| State | Trigger | Row rendering | Dialog rendering |
|-------|---------|----------------|--------------------|
| `idle` | Default / after any flow completes or is cancelled | `[ ] Enable` (off) or `[x] Disable` (on) | closed |
| `previewing` | Enable clicked; `previewCleanupDryRun({ type })` call in flight | Enable button → `Checking…`, disabled | closed |
| `preview-error` | `previewCleanupDryRun` call rejects (network/permission/internal) | Row shows inline `Couldn't check what would be deleted. Please try again.` (`text-red-400 text-xs mt-1`); Enable button returns to `Enable`, re-clickable | closed |
| `confirm-shown` | `previewCleanupDryRun` resolves | Enable button stays `Checking…`-disabled equivalent is unnecessary — row is inert while dialog owns focus | open, showing the echoed count (see Copywriting) |
| `enabling` | Confirm clicked inside the dialog | row unchanged | Confirm → `Enabling…`, disabled; Cancel also disabled (prevents closing mid-write) |
| `enabled` | `saveField('cleanup.{x}Enabled', true)` resolves | dialog closes; checkbox flips to checked (via the live `store.resolvedConfig` snapshot, not a local optimistic flag); row shows `Enabled!` (`text-green-400 text-xs mt-1`) for 2s, then the row settles into the `Disable` affordance | closed |
| write-failure (still `enabling`'s error branch, dialog stays `confirm-shown`-visually-open) | `saveField` rejects | row unchanged | dialog stays open; inline `Failed to enable. Please try again.` (`text-red-400 text-sm mt-2` inside the dialog body, mirrors every other save-error line in this codebase); Confirm re-enabled to retry, Cancel re-enabled to abort |

**Disabling (immediate, no dialog, no preview)** — a plain second per-row sub-state machine:

| State | Trigger | Rendering |
|-------|---------|-----------|
| `idle` | on (checked) | `Disable` button |
| `disabling` | Disable clicked | button → `Disabling…`, disabled |
| `idle` (success) | `saveField('cleanup.{x}Enabled', false)` resolves | checkbox flips unchecked via live store value; row shows `Saved!` (`text-green-400 text-xs mt-1`) for 2s |
| `disable-error` | `saveField` rejects | inline `Failed to save. Please try again.` (`text-red-400 text-xs mt-1`, identical copy to every existing save-error in this codebase); button returns to `Disable`, re-clickable |

### Zero-count case (R189's "arms the cron, doesn't necessarily delete anything today")

When `wouldDeleteCount === 0`, the dialog still opens (a zero count is a real, informative preview
result, not an error) and still allows enabling — it just uses different body copy (see Copywriting)
and a non-destructive (indigo, not red) Confirm button, since nothing is being deleted right now.

### Background-specific hard block (R190)

When `typeLabel === "background cleanup"` AND `referencesComplete === false`:
- The dialog renders the amber warning block (see Copywriting) ABOVE the Cancel/Confirm row.
- **The Confirm button is disabled** (`opacity-60 cursor-not-allowed`, no click handler fires) — this
  is a hard block, not a "discourage but allow" pattern, per the owner's explicit hard constraint in
  `71-CONTEXT.md`: *"never let the owner enable background cleanup while references are unproven."*
  There is no override path in this UI.
- Only `Cancel` is actionable. The owner's only path forward is to close the dialog, wait, and retry
  the preview later (background reference detection recovering is a server-side condition this UI
  cannot force).

## Accessibility

- **Focus trap — new to this codebase, hand-rolled, zero new dependencies.** No prior modal in this app
  (`NewServiceDialog.vue`, `PptxImportModal.vue`, etc.) implements a focus trap today; this phase is the
  first to add one, given the stakes (permanent data deletion) explicitly called out in the phase
  prompt. Implementation: on `open` becoming `true`, move focus to the Cancel button (a deliberate safe
  default — never the destructive Confirm button); a `keydown` listener on the dialog root traps `Tab`/
  `Shift+Tab` cycling between Cancel and Confirm only (the dialog has exactly two focusable elements
  when not blocked, or one — Cancel only — when the background warning disables Confirm); on close,
  focus returns to the row's `Enable` button that opened the dialog.
- `Escape` closes the dialog and is treated identically to clicking Cancel (never Confirm) — matches the
  existing `@click.self="onCancel"` backdrop-click-to-cancel convention already in `NewServiceDialog.vue`,
  extended to the keyboard.
- The dialog root carries `role="dialog"` `aria-modal="true"` `aria-labelledby="{id}-title"`
  `aria-describedby="{id}-body"`, pointing at the title and body elements.
- Every button in this contract (`Enable`, `Disable`, `Cancel`, dialog `Enable`/Confirm) has visible,
  literal text as its label — no icon-only or ambiguous controls, so no additional `aria-label` is
  needed beyond the visible text.
- The destructive action (the dialog's Confirm button, when `wouldDeleteCount > 0`) is marked BOTH
  visually (red fill, see Danger/Warning Visual Treatment) AND textually (the body copy states
  "permanently delete... This cannot be undone" immediately above it) — never color alone as the only
  signal, consistent with the rest of this app's established accessibility posture.
- The background-incomplete warning is never color-only: the `⚠` glyph + full sentence text carries the
  meaning; the amber background/border is reinforcement, not the sole indicator.
- The read-only status checkboxes keep the native `disabled` attribute (unchanged from Phase 70) — they
  are correctly excluded from tab order; the Enable/Disable/Cancel/Confirm buttons are the only
  interactive elements for this feature, and are all native `<button type="button">` elements (real tab
  stops, real `:focus` styling), not `<div>`s with click handlers.
- Focus states on Enable/Disable/Cancel/Confirm: `focus:outline-none focus:ring-1 focus:ring-indigo-500`,
  identical to every other interactive control in this app.

## Resolved Design Decisions (this document)

These were not explicitly answered by `71-CONTEXT.md`/`REQUIREMENTS.md`/`FEATURES.md`/`PITFALLS.md` and
are resolved here under the v1.9 autonomy grant, each consistent with the existing app and the phase's
"thin, safe extension" constraint:

1. **A real modal dialog (Teleport + backdrop), not the app's lighter inline-row-confirm pattern**
   (`OwnerConsoleView.vue`'s Revoke / `TeamView.vue`'s Remove). Those two precedents gate a reversible-ish,
   low-blast-radius action (revoking a grant, removing a roster row); this phase gates permanent,
   unrecoverable data deletion and the phase prompt explicitly asks for a dialog with title/body/buttons
   and a focus trap. `NewServiceDialog.vue` already establishes the Teleport/backdrop/Transition
   structure this reuses — no new structural pattern, just a new instance of an existing one, applied to
   a case that actually warrants it.
2. **Confirm is a hard, un-overridable block when `referencesComplete: false`**, not a "discourage but
   allow" warning — directly per `71-CONTEXT.md`'s quoted owner constraint ("never let the owner enable
   background cleanup while references are unproven"). There is no way to bypass this from the UI.
3. **The Confirm button is destructive-red only when `wouldDeleteCount > 0`**, and ordinary indigo when
   the count is 0 — the zero case arms a future cron but deletes nothing right now, so treating it with
   the same visual alarm as a 47-object deletion would over-warn and erode the red color's meaning for
   the case that actually matters.
4. **No specific cron time (e.g. "05:00 UTC") is surfaced in the confirm copy.** The four cleanup crons'
   exact schedules are not part of this UI-SPEC's verified inputs, and per-type schedule strings can
   drift independently of this UI; "on the next scheduled run" is accurate, matches R189's literal
   wording, and doesn't risk stating a wrong or stale time. If a future phase wants exact next-run times
   surfaced, that requires a new data source (not scoped here).
5. **Only one confirm dialog can be open at a time**, owned at the `CleanupConfigCard.vue` level (a
   single `activeDialog` ref keyed by cleanup type), not four independent dialog instances — simplest
   correct behavior given a human can only look at and confirm one destructive action at a time; also
   keeps the new focus-trap logic single-instance instead of needing to reason about z-index/focus
   stacking across concurrent dialogs.
6. **The status checkbox never gets an `@change` handler; Enable/Disable are separate explicit buttons.**
   Reusing the checkbox's native toggle event for the Enable path would require intercepting/reverting
   the DOM's own optimistic check-state before the preview+confirm flow even starts (awkward and easy to
   get subtly wrong); a dedicated button makes "clicking this never writes anything by itself" trivially
   true by construction.
7. **Byte formatting reuses `pptxUpload.ts`'s exact `(bytes / 1024 / 1024).toFixed(1)` shape** rather
   than a new formatter — consistency over introducing a second byte-formatting convention.
8. **The dialog's default focus target is Cancel, not Confirm** — a deliberate safe default for any
   destructive-action dialog (a stray Enter keypress while the dialog is opening should never land on
   the button that starts a deletion countdown).
9. **No typed-confirmation phrase (e.g. "type ENABLE") is required.** The Pitfalls research explicitly
   compares this project's echoed-real-count approach favorably against typed-phrase confirmation
   ("arguably stronger... since it shows concrete impact"); `71-CONTEXT.md`'s own example copy is a
   plain Confirm/Cancel dialog, not a typed phrase. Adding one would contradict the phase's "thin, safe
   extension" framing without a corresponding safety gain the count-echo doesn't already provide.
