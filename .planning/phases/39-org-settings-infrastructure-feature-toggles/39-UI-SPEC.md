## Component Pattern — Toggle Row (exact reuse, no new component)

**Decision: reuse the existing `vwModeInput` checkbox markup verbatim for both new toggles.** It is a native `<input type="checkbox">` styled with Tailwind, not a custom switch component — nothing about a settings on/off row in this codebase needs a dedicated toggle component, and inventing one (e.g., a sliding switch) would introduce a second visual toggle language for the same concept on the same screen. Confirmed: no toggle/switch component exists elsewhere in `src/components/` to reuse instead of hand-rolling — the checkbox pattern IS the established component.

Canonical markup (copy for both new toggles, changing only the `v-model`, `@change` handler, and label text):

```html
<label
  class="flex items-center gap-3"
  :class="authStore.isEditor ? 'cursor-pointer' : 'opacity-60 cursor-not-allowed'"
>
  <input
    v-model="aiEnabledInput"
    type="checkbox"
    :disabled="!authStore.isEditor"
    @change="onToggleAiEnabled"
    class="h-4 w-4 rounded border-gray-700 bg-gray-800 text-indigo-600 focus:ring-indigo-500 focus:ring-offset-0"
  />
  <span class="text-sm text-gray-200">Enable AI features</span>
</label>
```

Save-feedback rows (`Saved!` in `text-green-400 text-sm mt-2`, error in `text-red-400 text-sm mt-2`) also reuse the `vwSavedFeedback` / `vwSaveError` pattern verbatim, per-toggle (`aiSavedFeedback`/`aiSaveError`, `pcEnabledSavedFeedback`/`pcEnabledSaveError`).

## Layout — Two New Surfaces

### 1. New "AI Features" section (own card, placed after Vertical Worship section — last in the page, since it introduces the newest concept)

Structure, following the Vertical Worship section's exact shape (heading → explanation → toggle → helper text), but reordered per the owner's stated intent — **explain before offering the switch**:

```
<div class="rounded-lg bg-gray-900 border border-gray-800 p-4 mt-6">
  <h2 class="text-sm font-semibold text-gray-300 mb-3">AI Features</h2>

  <!-- Explanatory copy FIRST -->
  <p class="text-xs text-gray-400 mb-3">{intro copy}</p>
  <ul class="text-xs text-gray-400 space-y-1.5 mb-4 list-disc list-inside">
    <li><span class="font-medium text-gray-200">Song suggestions:</span> {desc}</li>
    <li><span class="font-medium text-gray-200">Scripture discovery:</span> {desc}</li>
    <li><span class="font-medium text-gray-200">Congregational reading split:</span> {desc}</li>
  </ul>

  <!-- Toggle SECOND -->
  <label class="flex items-center gap-3" :class="...">
    <input ... class="h-4 w-4 rounded border-gray-700 bg-gray-800 text-indigo-600 focus:ring-indigo-500 focus:ring-offset-0" />
    <span class="text-sm text-gray-200">Enable AI features</span>
  </label>
  <p class="text-xs text-gray-500 mt-2">{helper text}</p>

  <p v-if="aiSavedFeedback" class="text-green-400 text-sm mt-2">Saved!</p>
  <p v-if="aiSaveError" class="text-red-400 text-sm mt-2">{{ aiSaveError }}</p>
</div>
```

Note: this is the mirror image of the VW section's own order (VW puts toggle-then-explanation in a nested `bg-gray-950/40` panel). The AI section intentionally puts explanation first, flat (no nested panel), because the owner's requirement is specifically that a church sees what it's giving up **before** reaching the switch — VW's existing order (explain-after) is not the pattern to copy here even though its visual container is.

### 2. PC toggle inside the EXISTING "Planning Center Integration" section

Insert as a new block at the **top** of the existing section, before the credentials display/edit `<template>` blocks, with a divider matching the org-section's `border-t border-gray-800 pt-*` convention used elsewhere in this file for internal section dividers:

```
<div class="rounded-lg bg-gray-900 border border-gray-800 p-4 mt-6">
  <h2 class="text-sm font-semibold text-gray-300 mb-3">Planning Center Integration</h2>

  <!-- NEW: toggle block, ABOVE the existing credentials templates -->
  <label class="flex items-center gap-3" :class="...">
    <input ... />
    <span class="text-sm text-gray-200">Enable Planning Center integration</span>
  </label>
  <p class="text-xs text-gray-500 mt-2">{helper text}</p>
  <p v-if="pcEnabledSavedFeedback" class="text-green-400 text-sm mt-2">Saved!</p>
  <p v-if="pcEnabledSaveError" class="text-red-400 text-sm mt-2">{{ pcEnabledSaveError }}</p>

  <!-- Existing credentials block, now conditionally hidden -->
  <div v-if="pcEnabledInput" class="mt-6 pt-6 border-t border-gray-800">
    <template v-if="authStore.hasPcCredentials && !editingPcCreds"> ... existing ... </template>
    <template v-else> ... existing ... </template>
  </div>
</div>
```

Rationale for wrapping (not conditionally hiding the whole section): the section heading and the toggle itself must always be visible so a church can turn PC back on — only the credentials display/edit block hides, per the decision "credentials are retained, not cleared" and "hiding is correct... nothing should be built that assumes PC data can be deleted."

## Hide-Don't-Disable Contract — the four affected surfaces

Per the owner's `[FEAT]` research finding (hide entirely, never grey-out-with-tooltip) and R088/R089, here is exactly what "hidden" means at each surface. This is the section the planner should treat as the literal spec for each `v-if`.

| # | Surface | File | What hides | What stays |
|---|---------|------|------------|-------------|
| 1 | AI song suggestions | `SongSlotPicker.vue` | The entire "AI Picks" block (lines ~64-115: loading shimmer, error+retry, results list, "no sermon context" placeholder, AND the divider `<div v-if="resolvedAiSuggestions.length > 0 \|\| aiLoading \|\| aiError" class="border-t ...">` that separates it from "By Rotation") | "By Rotation" section, search, tag filter — unaffected. Add `v-if="authStore.aiEnabled"` around the whole "AI Picks" `<div>` block (the one currently gated only on `hasSermonContext !== false`) |
| 2 | AI scripture discovery | `ScriptureInput.vue` | The entire `<div v-if="showAiSuggest">` block (lines 4-114: search input+button, "Suggest scripture" link, AI error state, AI results list) | Freeform scripture text input, ESV link, preview button/panel — unaffected. Change the existing `v-if="showAiSuggest"` to `v-if="showAiSuggest && authStore.aiEnabled"` (compose with the existing prop rather than replacing it — `showAiSuggest` already scopes this to reading slots only) |
| 3 | Congregational-reading AI split | `CongregationalEditor.vue` | Only the "Split with AI" button (lines 45-60, the second `<button data-testid="ai-split-btn">`) | "Fetch Passage" button, reference input, section assignment/preview panels, speaker toggling — all unaffected, since hand-dividing must work identically with AI off. Wrap with `v-if="authStore.aiEnabled"` around that one button only — do not touch `canAiSplit`'s existing boundary logic, AND-compose it: `v-if="authStore.aiEnabled && canAiSplit"` is equivalent and keeps a single condition on the element |
| 4 | Planning Center features | `SettingsView.vue` + wherever Export/roster-import/song-import live | Credentials display/edit block inside the PC Settings section (see Layout §2 above); Export to Planning Center action; roster import entry point; song import entry point | The PC section heading and the new enable toggle itself always show. Already-imported roster data and already-`exported` service status are untouched — hiding the entry point never touches stored data (out of this phase's UI scope to enumerate every export/import button location; the planner's job is to grep for the PC utility's UI consumers and gate each entry point the same way, not to touch `authStore` state or Firestore data) |

**What "hidden" explicitly does NOT mean at any of these four surfaces:** `disabled` attribute + tooltip, `opacity-60` + `cursor-not-allowed`, or `v-show` (which still renders to the DOM, just display:none — acceptable technically, but the intent is full removal so no dead network-request-capable markup lingers; prefer `v-if`). This matches R088's explicit test requirement — hiding UI is necessary but not sufficient; the `claudeApi.ts`/PC-utility guard is the actual enforcement, and these four `v-if`s are the user-facing consequence of that guard, not a substitute for it.
