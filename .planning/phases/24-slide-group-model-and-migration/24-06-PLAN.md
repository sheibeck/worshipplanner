  <files>src/views/ServiceEditorView.vue, src/views/__tests__/ServiceEditorView.test.ts</files>
  <read_first>
    - src/views/ServiceEditorView.vue lines 1530-1610 — the `watch(() => serviceStore.services, ...)` load watcher with BOTH its branches (initial load and remote merge), and the autosave watcher's `autosaveInitialized` first-fire skip immediately below it
    - src/utils/slotTypes.ts (from 24-01) — `backfillSlotIds(service, reference?)` and its reference-stability contract
    - .planning/phases/24-slide-group-model-and-migration/24-PATTERNS.md § `src/views/ServiceEditorView.vue` and 24-RESEARCH.md § Pattern 2 — why both refs must receive identical ids
    - src/views/__tests__/ServiceEditorView.test.ts — the existing mount/mock conventions, including the 22-04 store-stub fix
  </read_first>
  <behavior>
    - Loading a service whose slots have no ids leaves `isDirty` false and fires no autosave.
    - `localService` and `originalService` receive byte-identical slot ids after load.
    - A second store snapshot of the same still-id-less remote document does not change any slot id already held locally.
    - A service whose slots already have ids is untouched.
  </behavior>
  <action>
In the load watcher, run `found` through `backfillSlotIds` BEFORE both `JSON.parse(JSON.stringify(...))`
assignments in EACH branch:
- Initial-load branch: `backfillSlotIds(found)` with no reference, then assign the same backfilled
  value to `localService` and `originalService`. They must be identical — if `originalService` misses
  the ids, the JSON-stringified comparison behind `isDirty` never matches again and the dirty
  indicator is permanently wrong.
- Remote-merge branch: `backfillSlotIds(found, localService.value)` — pass the current local service as
  the reference so an already-assigned id is reused rather than regenerated. Compute `remoteJson` from
  the BACKFILLED value, not from the raw `found`, or the comparison will differ on every snapshot and
  each snapshot will re-anchor every group to a brand-new slot id.

Do NOT add an explicit write-back of the ids on load. The autosave path already writes
`slots: reindexSlots(data.slots)` on the next real edit, and `reindexSlots`'s spread carries `id`
through — so the ids persist as a side effect of the next legitimate save. An explicit write on load
would be exactly the spurious-save-on-every-load behaviour CONTEXT.md warns against.

Do not touch the `autosaveInitialized` guard itself. Its unconditional first-fire skip after each
reload already absorbs the backfill; that is why the backfill belongs inside the assignment.

Add a `@/stores/slideGroups` reactive Pinia stub to `src/views/__tests__/ServiceEditorView.test.ts`
following the shape of the `@/stores/importedSlides` stub added in 22-04, then add the tests for the
behaviors above.
  </action>
  <acceptance_criteria>
    - A test mounts with an id-less service and asserts the service store's update action was not called (no autosave) after load settles.
    - A test asserts every slot id in `localService` equals the corresponding id in `originalService`.
    - A test emits a second identical id-less snapshot and asserts the locally held slot ids are unchanged.
    - `npx vitest run src/views/__tests__/ServiceEditorView.test.ts` exits 0.
  </acceptance_criteria>

The confirm dialog markup needs no structural change — only the computed body it already renders.

| T-24-06-02 | Tampering | slot spliced locally while its group delete failed | high | mitigate | The group delete is awaited BEFORE the splice; on failure the slot stays in place and the error surfaces through the view's existing error path, so local and remote never disagree silently. |
| T-24-06-03 | Repudiation | user cannot tell what a delete removed | high | mitigate | This is the R029 failure-visibility requirement itself; the confirm names the loss and is authored as a prohibition so the verifier checks the copy has not been softened. |
| T-24-06-04 | Tampering | orphaned group documents accumulating | medium | mitigate | Every remove-element path deletes the anchored group. | T-24-06-05 | Information Disclosure | wrong org id used for a group delete or bed write | high | mitigate | Both call `authStore.orgId`; no org id is taken from the route or from user input, and the Firestore `isOrgEditor(orgId)` rule scopes both operations independently. |
