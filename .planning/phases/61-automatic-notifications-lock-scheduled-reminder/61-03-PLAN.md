<objective>
Resolve the Phase 59 carryover: actually SEND user-scheduled messages. Phase 59's composer writes a
`status:'scheduled'` messages doc that `sendQueuedMessage` (an `onDocumentCreated` trigger, `:1372`) leaves inert
by design (`:1201` comment: "leaves a 'scheduled' doc inert for Phase 61's cron"). This plan adds a second sweep
to the daily cron that finds due scheduled messages, transactionally claims each `scheduled→dispatched` on the
original, and CREATES a fresh `status:'queued'` doc from it via the shared `createQueuedMessage` shaper — a
genuine create that re-fires `sendQueuedMessage`, idempotent under at-least-once retry.

Purpose: R141 (the composer's schedule-for-later option) — Phase 59 shipped the compose-and-store half; this
plan ships the dispatch half that was explicitly deferred to Phase 61. It is a distinct concern from the R145
reminder sweep (different collection group, its own `scheduled→dispatched` idempotency) and lands in its own
plan/wave (research § Key Design Problem recommendation; the task's decomposition note).

DECISIONS (locked, from 61-RESEARCH.md § Key Design Problem):
- Create a fresh `queued` doc (option a) — do NOT widen `sendQueuedMessage` to `onDocumentWritten` (rejected:
  re-entrancy on its own `sending`/`sent`/`deliveryCounts` writes for no benefit; research § Alternatives).
- Single-field query `where('status','==','scheduled')` + code-filter `scheduledFor <= now` → NO composite
  index (research § Firestore Indexes: "use the single-field query + code filter and add NO index").
- Both sweeps run inside the ONE existing `sendScheduledReminders` onSchedule invocation (one Cloud Scheduler
  job, one deploy), each independently try/caught. No new wrapper, no new secret.

Output: `dispatchDueScheduledMessagesHandler` in `functions/src/index.ts` wired into the `sendScheduledReminders`
wrapper (61-02), plus its `describe` block in `functions/src/index.test.ts`. Nothing deployed; no secret; no index.
</objective>
