## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (per-row save) | **"Save Team"** (mirrors `RolesConfigPanel.vue`'s "Save Role" wording exactly) — states: `Save Team` → `Saving…` (while in flight) → `Saved ✓` (emerald, 1.8s transient, matching Roles) |
| Primary CTA (add row) | **"Save Team"** (yes — identical label to the per-row save, exactly mirroring `RolesConfigPanel.vue`'s add-row button which also reads "Save Role", not "Add Role") → `Added ✓` transient on success |
| Panel sub-heading (hint under "Teams" h2) | "Teams your church uses for service planning. Attach a song-tag filter to constrain AI suggestions when that team is selected." |
| Empty state heading/body — Teams editor (zero teams configured) | "No teams yet." / "Add your first team below." (`text-xs text-gray-600`, matching Roles' "No roles in this group yet.") |
| Empty state — service-plan checkboxes (zero org teams) | "No teams configured — add teams in Volunteers → Teams." (`text-xs text-gray-500`, shown in place of the checkbox row in both `NewServiceDialog.vue` and `ServiceEditorView.vue`) |
| Empty state — song-tag filter select (zero song tags exist) | Select still renders with only its default option, labelled **"No filter"** — never disabled, never blocks Save |
| Error state | "Couldn't save team. Check your connection and try again." — surfaced via the app's existing `useToasts()` composable (`ToastHost.vue`), same channel used elsewhere in the app; do NOT introduce a second inline-error pattern |
| Destructive confirmation (soft-warn, per CONTEXT decision — NOT a hard block) | **Delete Team:** "Delete the '{name}' team? It will no longer appear as a choice for new or edited services, but any service that already selected it keeps that reference. This cannot be undone." — confirm button reads **"Delete Team"**, cancel reads **"Cancel"** (identical button pair/placement to `RolesConfigPanel.vue`'s delete-confirm) |

**Note on the "Special" free-text service-name field (carried decision, not new work this phase):** `NewServiceDialog.vue` and `ServiceEditorView.vue` currently reveal a free-text Service Name input only when `teams.includes('Special')`. This literal-string coupling is **left unchanged** for this phase — it is not named in R228–R231/R241 and CONTEXT.md's scope boundary does not call it out. Because the seed defaults (`['Choir','Orchestra','Communion','Special']`) preserve the literal team name `'Special'`, Berean's existing behavior is unaffected. If an admin later renames or deletes the `'Special'` team, the free-text field simply stops appearing — a known, accepted limitation, not a regression this phase must solve. Do not invent a new "named service" flag on the team doc; that is SEED-002's A1 follow-up, out of scope here.

## Implementation Notes (surface-by-surface, for planner/executor)

### 1. Teams editor panel — new "Teams" tab in `RosterView.vue`
- **Placement decision (Claude's Discretion, resolved):** add a third tab, **"Teams"**, to `RosterView.vue`'s existing tab bar (`Volunteers | Roles | Teams`), using the identical tab-button classes already there (`border-indigo-500 text-indigo-300 bg-gray-900` active / `border-transparent text-gray-400` inactive). This satisfies CONTEXT.md's "beside the Roles panel" option literally — the Roles panel already lives in `RosterView.vue`, not in `SettingsView.vue`.
- **Copy `RolesConfigPanel.vue`'s outer shape exactly:** `rounded-lg border border-gray-800 overflow-hidden` container; `px-4 py-3 bg-gray-900/50 border-b border-gray-800` header with `<h2 class="text-sm font-medium text-gray-300">Teams</h2>` + `<p class="text-xs text-gray-500 mt-0.5">` sub-copy; `divide-y divide-gray-800` row list; `px-4 py-4` per-row padding.
- **No group badges section** — unlike Roles (`band|tech|vocals|other`), teams are a single flat list; skip the `groupOrder`/badge-pill markup entirely.
- **Row layout (draft-based, explicit Save — not autosave):** `flex items-center gap-3` containing, in order: (1) team-name text input, `flex-1`, same classes as Roles' name input; (2) song-tag filter `<select>`, fixed width (`w-40 sm:w-48` — wider than Roles' `w-20` count input since tag names are longer), same input chrome (`rounded-md bg-gray-800 border border-gray-700 text-gray-100 text-sm px-3 py-1.5 focus:ring-1 focus:ring-indigo-500`); options = `<option value="">No filter</option>` + one `<option>` per entry in `songStore.allUserTags` (already computed, alphabetically sorted); (3) Save button (indigo→emerald transient, copy above); (4) Delete link (`text-xs text-red-400 hover:text-red-300`).
- **Inline delete-confirm** (not modal): identical `bg-red-900/20 border-red-800 p-3` panel with the soft-warn copy above, `Delete Team` (red) / `Cancel` (gray) button pair — same placement/markup as `RolesConfigPanel.vue`'s block.
- **Add Team row** at the bottom: `<h3 class="text-xs font-medium text-gray-400 uppercase tracking-wider mb-3">Add Team</h3>` + a row with name input (placeholder "Team name") + the same song-tag select + the "Save Team"/"Added ✓" button — identical structure to Roles' Add Role row, minus the group `<select>` (teams have no group).
- **Accessibility (ships correct from the start — this is the one deliberate deviation from copying Roles verbatim, per CONTEXT.md):** every input gets a real accessible name via `aria-label`, not placeholder-only. Concretely: the row name input gets `:aria-label="\`Team name for ${team.name}\`"` (add-row: `aria-label="New team name"`, in addition to its placeholder — redundant but explicit); the song-tag select gets `:aria-label="\`Song-tag filter for ${team.name}\`"` (add-row: `aria-label="Song-tag filter for new team"`). Do not restructure the single-line flex row into a stacked label+input layout — `aria-label` preserves the exact copied visual shape while giving real accessible names, matching CONTEXT.md's requirement without contradicting "copy the shape EXACTLY."

### 2. Service-plan team checkboxes — `NewServiceDialog.vue` + `ServiceEditorView.vue`
- Visual markup is **unchanged** — same pill-style checkbox (`bg-indigo-900/30 border-indigo-600 text-indigo-300` selected / `bg-gray-800 border-gray-700 text-gray-400` unselected) and the plain `h-4 w-4` checkbox + label pair in `ServiceEditorView.vue`'s editor branch. Only the **data source** changes: `v-for="team in availableTeams"` (dialog) / `v-for="team in AVAILABLE_TEAMS"` (editor) now iterate the shared teams store's ordered team-name list instead of the hard-coded 4-item array.
- `ServiceEditorView.vue`'s **locked/read-only viewer branch** (renders `localService.teams` directly as plain text pills, line ~786) needs **no change** — it never referenced `AVAILABLE_TEAMS`.
- **Ordinal-Sunday auto-selection removed (R231):** delete `sundayOrdinal()`, the `defaultForm()` ordinal branch, and the date-change watcher's team-mutation in `NewServiceDialog.vue`. `form.teams` initializes to `[]` unconditionally on every dialog open — a planner picks every service's teams manually, with no default and no visual difference in the checkbox row itself (it just starts with nothing checked).
- **Empty-state hint** (zero org teams — see UI Considerations) renders in place of the checkbox row in both files, using the exact copy in the Copywriting Contract above.

### 3. Per-team song-tag filter mechanism (no new UI surface)
- The AI-suggestion "Orchestra-only" filter (`ServiceEditorView.vue:3426`/`3537`, `isOrchestraService` check) is replaced by a generic helper that unions (OR) the `songFilterTag` of every currently-selected team that has one set, reading from the shared teams store. This is a **pure logic change** — no new visual element. The existing AI-suggestion panel's empty/zero-candidates state (already reachable today when the Orchestra filter zeroes the pool) already covers the "filtered pool is empty" case; no new empty-state copy is required here.
