<objective>
Rework share-token creation from "mint a fresh token and freeze a snapshot on every call" into
"resolve THE token for this service exactly once — creating it, or adopting one already circulated —
then write the current payload in place." This is R076 and R078; the automatic refresh on ordinary
edits (R077) is Plan 04 and builds directly on what this plan lands.

Purpose: `createShareToken` (`services.ts:353-441`) currently mints a new random token on every call
and freezes `serviceSnapshot` at share time. That single behaviour is the root cause of BOTH reported
symptoms — "the link changed" and "my role overrides aren't showing." They are not two bugs.

Output: a `serviceShareLinks/{serviceId}` identity document; an extracted `buildServiceSnapshot`
so the create and refresh paths cannot drift; an `ensureShareLink` action doing adopt-or-create then
write-in-place; `createShareToken` retained as a delegating wrapper so neither `onShare()` caller
changes; and the Wave 0 mock extension without which none of the adoption tests can even load.

**Read Plan 02's SUMMARY first** for the exact signatures of `mintShareToken`,
`shareTokenCreatedAtMillis` and `pickAdoptableToken`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Share code path → `services/{docId}` | The R036 draft-lock protects the service document with three narrow carve-outs. No share write may cross this boundary in that direction, ever. |
| Firestore query results → adoption | The adoption query filters on `serviceId` only and is therefore not org-scoped; documents belonging to other organisations can appear in its result set. |
| Store → `shareTokens/{token}` | This document is world-readable. Everything `buildServiceSnapshot` returns is published to anyone holding the URL. |
