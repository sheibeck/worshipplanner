<objective>
Open exactly the authorization surface Phase 41 needs, and prove it against the real Firestore
emulator: loosen `shareTokens`' currently-unconditional update denial to the org-scoped
`serviceShares` idiom, and add a new org-editor-scoped `serviceShareLinks/{serviceId}` block with no
public read. Then hand the undeployed rules file to the owner with the exact command.

Purpose: R077's auto-refresh is structurally impossible while `shareTokens` denies every update, and
R076's persistent link document has no rule at all today (the catch-all denies it). This plan is the
authorization half of the phase and is deliberately in Wave 1, in parallel with the store work,
because its file set (`firestore.rules`, `src/rules.test.ts`) is disjoint from the store's.

Output: a modified-but-undeployed `firestore.rules`, ~20 new emulator-backed rules tests replacing
one stale assertion, and two written owner-handoff records.

**The single most important structural fact in this plan:** RESEARCH.md proposed
`allow read: if isOrgEditor(resource.data.orgId)` for `serviceShareLinks`. That is **wrong as
written** and would brick the entire phase. `resource` is null when the document does not exist, and
`ensureShareLink`'s very first operation is a read of a document that does not exist. See Task 1.

**Wave note:** `41-VALIDATION.md`'s per-task map pencils the rules tests into Wave 3. They are Wave 1
here because nothing in them depends on the store rework and the file sets do not overlap. The
verification content of that map is unchanged; only its wave column is superseded.
</objective>
