<task type="auto" tdd="true">
  <name>Task 2: One append contract — sort, append, renumber (R050)</name>
  <files>src/components/slides/SlideGrid.vue, src/components/slides/__tests__/SlideGrid.test.ts</files>
  <behavior>
    - Adding a slide to entries whose array order disagrees with their order values produces a payload sorted by order, with the new entry last and orders contiguous 0..n.
    - Adding a slide to an empty group produces one entry with order 0.
    - Confirming a deck import appends every inner slide after all existing entries, in deck order, with contiguous orders.
    - The video/media append path produces the same contiguous, appended-last result.
    - For a group carrying no copyright entries, the newly added slide is the last card the grid renders.
  </behavior>
  <action>
`onAddSlide` (line 410), `onImportConfirmed` (line 477) and the media-append path (lines ~518-529)
each compute `Math.max(...entries.map((e) => e.order)) + 1` and then push onto the RAW `entries`
array. When array order and `order` values disagree, the two encodings of "the end" disagree too —
that divergence is R050's mechanism, and it is the same "trusted an index that was never normalized"
family as R049.

Add one private helper in this component and route all three paths through it:

  appendToGroup(entries: GroupSlideEntry[], additions: GroupSlideEntry[]): GroupSlideEntry[]

It sorts a copy of `entries` by `order`, concatenates `additions`, then renumbers every element to its
array index — so array order and `order` are the same statement afterwards. This is the exact
normalization the reorder path already performs (line 692); the helper makes it the component's one
contract instead of a behaviour only the reorder path has.

Keep passing the ORIGINAL, unsorted `entries` as the CR-02 `baseSlides` argument to
`replaceGroupSlides` — that argument is the pre-write snapshot for concurrent-write detection, not the
new value, and re-sorting it would defeat the merge.

**Investigate the reported "lands second-to-last" symptom before declaring R050 done.** Two candidate
mechanisms exist; check both and record which one was live in the SUMMARY:
1. The array-order / `order`-value divergence above, which this helper closes.
2. `slideGroupMaterializer.ts:314-317` re-places a SONG group's trailing copyright entry at the end of
   the merged output. For a song group that is correct behaviour, not a defect — the copyright slide
   belongs last (Phase 35 owns CCLI placement). If the reported symptom traces to a song group, record
   that finding and scope R050's assertion to groups without copyright entries rather than changing
   the materializer, which is out of this phase's scope.

Flip 29-01's R050 repro to `it` once it passes. If it was already converted to a plain `it` because it
passed on arrival, add the unsorted-entries case from the behaviour list — it must fail before this
helper exists.

| viewer role → slide mutation | A non-editor must not be able to reorder or append. |
