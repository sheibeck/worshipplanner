# Phase 29 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** this phase is a correctness fix (stable drag-and-drop) plus one structural
addition (a fifth Post-Service section). It is deliberately NOT a Service Order redesign — Phase 36
rebuilds that tab against the Claude Design "Turn 3" wireframes. Every contract below stays inside
the existing dark-theme, plain-Tailwind visual language documented in `CONVENTIONS.md` and does not
invent a parallel one. `DesignSync`/Claude Design tooling was not reachable from this research pass
(no such tool was available in this session) — nothing here conflicts with Turn 3 because nothing
here touches layout Turn 3 owns (tab structure, action bars, overall Service Order shell); this
phase only fixes drag mechanics and adds one section to the existing list-of-cards pattern.

adjacent code outside this phase's correctness-fix scope.

> edited or promoting the value to a documented permanent exception.
>
> **Decision: keep `space-y-1.5` / `mt-0.5` as-is for Phase 29.** Phase 36 rebuilds this entire tab

## Phase-Specific Component Contracts

### 1. Per-section drag containers

Replace the single flat `slotContainerRef` list with one Sortable root **per section**, iterating
the full `SERVICE_SECTIONS` array (now 5 members) unconditionally — not derived from which sections
happen to have items.

```html
<template v-for="section in SERVICE_SECTIONS" :key="section">
  <div class="section-header flex items-center gap-2 pt-3 pb-1 first:pt-0"
       :data-testid="`section-header-${section}`">
    <span class="text-xs font-semibold text-indigo-300 uppercase tracking-wider">
      {{ SERVICE_SECTION_LABELS[section] }}
    </span>
    <span class="flex-1 border-t border-gray-800"></span>
  </div>

  <div :ref="el => setSectionListRef(section, el)"
       class="space-y-1.5 rounded-lg transition-colors"
       :class="{ 'bg-indigo-950/20': dragOverSection === section }"
       :data-testid="`section-list-${section}`"
       :data-section="section">
    <!-- populated: .slot-item cards for this section only, :key="slot.id" -->
    <!-- empty: the placeholder from §2 below, non-draggable -->
  </div>
</template>
```

- The section header is **unchanged visually** from the existing `.section-header` class — it moves
  from "conditionally rendered per index" to "always rendered once per section," but its markup and
  classes do not change. It renders as a sibling of the section's list container, not inside it, so
  it is structurally excluded from that section's Sortable instance (it isn't even in the same DOM
  subtree) — a stronger guarantee than the old `draggable: '.slot-item'` selector-based exclusion.
- `SERVICE_SECTIONS` and `SERVICE_SECTION_LABELS` gain a fifth member (`'post-service'` /
  `'Post-Service'`) per `src/types/service.ts:13-22`. The existing section `<select>` dropdown at
  line 899 iterates the same array and needs no separate spec — it picks up Post-Service for free.
- Five separate `Sortable.create()` calls share one `group` name (e.g. `'service-slots'`) so items
  can move between them; `handle: '.drag-handle'`, `draggable: '.slot-item'`, `animation: 150`,
  `ghostClass: 'opacity-30'` carry over unchanged from the existing single-instance config
  (`ServiceEditorView.vue:1421-1429`).
- **Slides tab needs no equivalent per-section container.** `SlidePlanRail.vue` has no section
  headers today (D-06: order locked, no drag at all in the rail) and `SlideGrid.vue` shows slides
  for one selected slot at a time, never grouped by section. Post-Service flows through both
  automatically once `SERVICE_SECTIONS` includes it — no new Slides-tab UI construct is in scope.

### 2. Empty-section placeholder (also the live drop target)

```html
<div class="rounded-lg border border-dashed border-gray-800 p-4 text-center"
     :class="{ 'bg-indigo-950/20': dragOverSection === section }"
     :data-testid="`section-empty-${section}`">
  <p class="text-sm text-gray-500">No items yet</p>
  <p class="mt-1 text-xs text-gray-600">
    {{ section === 'post-service'
      ? 'Drag an item here, or set its Section to Post-Service — runs as people exit, e.g. a cycling announcement deck.'
      : `Drag an item here, or set its Section to ${SERVICE_SECTION_LABELS[section]}.` }}
  </p>
</div>
```

- Renders as the sole child of a section's list container when that section has zero slots. It sits
  in the same DOM subtree as `.slot-item` cards would, but — like the section header before this
  phase — is excluded from the `draggable: '.slot-item'` selector, so Sortable never treats it as a
  draggable member. This is a proven pattern already used in this codebase for excluding non-item
  siblings from drag eligibility; it is not a new risk.
- The section's list container (not the placeholder specifically) is the actual Sortable root and is
  therefore always a valid, live drop target, populated or not — this is native SortableJS behavior
  for an empty list and requires no special-casing beyond rendering the container unconditionally.
- This closes the known v1.2 defect where Pre-Service silently didn't render at all when empty.

### 3. Drag affordances and feedback

| State | Treatment |
|-------|-----------|
| Item mid-drag (the dragged card itself) | `opacity-30` via the existing `ghostClass: 'opacity-30'` config — unchanged, no new class needed |
| Section hovered during a cross-section drag (populated OR empty) | The hovered section's list container gets `bg-indigo-950/20` (see §1/§2 `:class` bindings above). Toggle via SortableJS `onMove`, setting a local `dragOverSection` ref to the section derived from `evt.to`'s `data-section` attribute; clear it in `onEnd`. |
| Invalid drop target | **Does not exist in this phase's scope.** Per 29-CONTEXT.md's Post-Service decision generalized across all five sections, every section accepts every slot kind — there is no per-section kind restriction anywhere in the current model. Do not build invalid-drop styling; there is nothing for it to distinguish itself from. |
| Drop completes | No special "landed" flash — the item simply renders in its new position via the stable `slot.id` key; SortableJS's own `animation: 150` reordering animation is the only motion cue, unchanged from today. |

### 4. Post-Service section presentation

- Label: **"Post-Service"** (`SERVICE_SECTION_LABELS['post-service']`), rendered with the exact same
  header treatment as the other four sections (§1) — no unique icon, color accent, or subtitle in
  the header itself. Adding bespoke chrome here would invent a parallel visual language ahead of
  Phase 36's Turn 3 rebuild, which this phase must not do.
- The one place Post-Service gets distinguishing treatment is its **empty-state placeholder copy**
  (§2), which names its purpose ("runs as people exit, e.g. a cycling announcement deck") since it's
  the newest and least self-explanatory of the five section names. This is copy-only, not new UI.
- Fixed position: always renders fifth/last, after Sending, matching `SERVICE_SECTIONS` array order.
- Flows through to print, share link, and Planning Center export ordered last (R042/CONTEXT.md) — no
  new visual spec needed there; those surfaces iterate the same `SERVICE_SECTIONS` source of truth
  and inherit the ordering for free once audited for hard-coded four-section assumptions.

### 5. Save-failure feedback (minimal — full indicator is Phase 32's)

**Explicitly deferred to Phase 32 (R040/R041):** the persistent "Saving… / Saved HH:MM" inline
status component, the `useSaveStatus` aggregator, and the failure toast. Do not build any of those
here — Phase 32 will replace whatever minimal thing this phase adds.

**In scope for this phase — the minimum so a save failure is never silent:**

- **`ServiceEditorView.vue`** already has an inline status region (`autosaveStatus`, lines 84-104:
  `'idle' | 'pending' | 'saving' | 'saved'`). Add a fifth state, `'error'`, and one more `<span>`
  branch in that same region, reusing the existing destructive color contract:
  ```html
  <span v-else-if="autosaveStatus === 'error'" class="text-xs text-red-400">
    Couldn't save this order — reverted. Try dragging again.
  </span>
  ```
  On a rejected write, revert `localService.slots` to the pre-drag snapshot and set
  `autosaveStatus.value = 'error'`. No toast, no modal — just this line, in the same location the
  existing Saving/Saved states already occupy (top of the editor, part of the "Save area").
- **`SlideGrid.vue`** has no equivalent status region today — a reorder failure there currently only
  `console.error`s (`SlideGrid.vue:707-708`), which is exactly the silent-failure pattern this phase
  must close. Add one inline text row using the same minimal pattern already established for
  `mediaUploadError` in the same file (`SlideGrid.vue:99-103`):
  ```html
  <div v-if="reorderError" class="mx-6 mt-3 text-[12px] text-red-400"
       data-testid="slide-grid-reorder-error">
    Couldn't save this change — reverted. Try again.
  </div>
  ```
  Revert the local `entries` array to the pre-drag snapshot and set `reorderError` on a rejected
  `replaceGroupSlides` call; clear it on the next successful write.
- Both are transient, inline, unstyled-beyond-color text — deliberately not a badge, not a toast, not
  `aria-live` (Phase 32 owns the `aria-live` status region per R041). The only requirement here is
  "not silent."

## Accessibility Note

Keyboard-accessible reordering is **explicitly out of scope** for this phase (recorded in
`REQUIREMENTS.md` under Future Requirements and in `29-CONTEXT.md`'s deferred section) — SortableJS
does not provide it, and building it is a separate, additive commitment for a later milestone. Do
not build keyboard drag interaction here.

What this phase DOES specify for the containers it builds:

- Each section's list container carries `data-section="{section}"` (already specified in §1) and
  should carry `role="list"` with `aria-label="{Section Label} items"` so assistive tech announces
  section boundaries even though drag itself isn't keyboard-operable yet.
- Each `.slot-item` card keeps its existing `data-testid="slot-{index}"`-style addressability;
  no new ARIA role beyond what already exists is required by this phase's changes alone.
- The empty-section placeholder (§2) is plain static text, not a form control — no additional ARIA
  needed beyond the parent list's `role="list"`/`aria-label`.
- The save-failure inline messages (§5) are plain text, not `aria-live` — that upgrade is explicitly
  Phase 32's (R041 specifies `aria-live` on the persistent status region this phase doesn't build).
