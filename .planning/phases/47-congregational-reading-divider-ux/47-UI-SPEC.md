# Phase 47 — UI Design Contract

> Visual and interaction contract for the hand-divide Leader/Congregation/All editor rework
> (`CongregationalEditor.vue`) plus the 3-way speaker label/colour extension in
> `PresentationViewer.vue` / `slideDisplay.ts`. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker. Runs under the v1.5 standing autonomy grant — no interactive questions were
> asked; all open items were resolved at researcher discretion per 47-CONTEXT.md and are called
> out explicitly below.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — confirmed no `components.json` in the repo root; this is a Vue 3 SFC project, not React/Next/Vite, so the shadcn init gate does not apply |
| Preset | not applicable |
| Component library | none — every UI primitive in this codebase (modals, chips, toggles, buttons) is a hand-authored Tailwind utility composition; there is no Radix/base-ui/Headless-UI dependency to match |
| Icon library | inline SVG, hand-authored, Heroicons-outline visual style (24×24 viewBox, `stroke="currentColor"` `stroke-width="2"`) — matches every existing icon in `CongregationalEditor.vue` and `PresentationViewer.vue`; no new npm icon package |
| Font | App chrome (this editor is app UI, not a slide): browser default sans-serif via Tailwind's default stack — no explicit `font-family` is set anywhere in `main.css` for non-slide surfaces, so none should be introduced here. Slide-facing surfaces only (`PresentationViewer.vue`) use `--slide-font-family` (Inter by default) per Phase 46 — **unchanged by this phase** except for the new third speaker-colour class |

**Modal shell (pre-existing, out of this phase's scope, stated for layout context):** the editor
renders inside `ServiceEditorView.vue`'s own Teleported panel — `bg-gray-900 border border-gray-700
rounded-xl shadow-2xl w-full max-w-2xl mx-4 max-h-[85vh]`, with the parent already owning the outer
header (`h2` "Congregational Reading" + close button + `SaveStatusIndicator`) and a scrollable body
(`px-6 py-4`). This means the working content width for everything below is effectively **≤ 624px**
(max-w-2xl minus the parent's horizontal padding) — design single-column, no side-by-side layouts.
`CongregationalEditor.vue`'s own internal header (`h3` "Congregational Reading" + its own close
button) duplicates the parent's — **pre-existing, not introduced or fixed by this phase**; leave as
found unless the executor finds it actually double-renders visibly, in which case flag rather than
silently removing (it may be dead markup already suppressed by CSS/layout, not verified here).

## Spacing Scale

Declared values (must be multiples of 4), matching what the codebase already uses throughout this
component and `PresentationViewer.vue`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, chip internal padding |
| sm | 8px | Compact element spacing (`gap-2`, `space-y-2`) |
| md | 16px | Default element spacing (`p-4`, `gap-3`, `space-y-3`/`4`) |
| lg | 24px | Section padding (`px-6 py-4` on the parent shell) |
| xl | 32px | Not used within this phase's surfaces |
| 2xl | 48px | Not used within this phase's surfaces |
| 3xl | 64px | Not used within this phase's surfaces |

Exceptions:

- **44px (`h-11 w-11` / `min-h-11 min-w-11`) minimum tap target** for the gap `+`/divider-remove
  affordance's hit area — larger than the nearest 8pt multiple, matching the existing 44px pattern
  already used by `presentation-exit`/`presentation-prev`/`presentation-next` in
  `PresentationViewer.vue`. The **visual** hairline/button stays small (24px circle); only the
  invisible click/tap wrapper is 44×44, so density in a fully-divided passage is not sacrificed for
  touch reach.
- **40px (`h-10`) minimum height** for each option inside the 3-way segmented-control chip — between
  the 8pt scale's 32px and the 44px icon-target guidance above, chosen because the chip is a labeled
  text control (not icon-only) sitting inside a compact card, and 44px on all three options would
  make a fully-divided 20-segment passage too tall to be usable inside the 85vh modal.

## Typography

Two typography contexts exist on these surfaces and must not be conflated:

**(A) Editor chrome** (`CongregationalEditor.vue` — app UI, unaffected by Phase 46's slide
typography setting):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (segment/passage text) | 14px (`text-sm`) | 400 (normal) | 1.625 (`leading-relaxed`) |
| Label (chip text, verse-range meta, seed-button labels) | 12px (`text-xs`) | 600 (semibold), uppercase, `tracking-wider` for chip/role labels only — seed-button and meta labels stay normal case | 1.5 |
| Heading (panel header, "Starting point" section label) | 14px (`text-sm`) | 600 (semibold) | 1.4 |
| Display | not applicable — this editor has no display-scale text |

**(B) Presenter (`PresentationViewer.vue`) — governed by Phase 46, NOT changed by this phase**
except that the speaker label gets a third colour class. Existing sizes/weights are restated here
only so the executor does not accidentally touch them while adding the `ALL` branch:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Speaker label (`presentation-speaker`) | `text-5xl` (48px base, scaled by `--slide-font-scale`) | `font-normal`, weight overridden by `--slide-font-weight` | 1.4 |
| Congregational section body (`presentation-congregational-section`) | `text-5xl` | `font-normal` / `--slide-font-weight` | 1.4 |
| Scripture reference (`presentation-scripture-reference`) | `text-5xl` | same | 1.4 |

Do not add a size/weight step for `ALL` relative to `LEADER`/`CONGREGATION` — FEATURES.md's
label-first, styling-second principle means colour (and the text label itself) carries the
distinction, not size or weight.

## Color

**60/30/10 split — editor chrome only** (the presenter's role colours below are a separate,
fourth semantic layer, not counted against this split, since they identify *content*, not UI
chrome):

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#030712` / `bg-gray-950` | App/page background behind the modal |
| Secondary (30%) | `bg-gray-800` / `bg-gray-900` (with `/30`–`/50` opacity variants already used in this file) | Modal shell, segment cards, the "Starting point" seed panel, the reference input field, inactive/unselected chip state |
| Accent (10%) | `indigo-400` / `-500` / `-600` | **Reserved for:** the "Fetch Passage" button (the one true primary CTA on this surface), all `focus:ring` states, and the gap `+` insert-divider affordance's hover/active fill (`hover:bg-indigo-600 hover:text-white hover:border-indigo-500`) |
| Destructive | `red-400` on `red-950/50` bg, `red-800/50` border (existing `fetch-error` styling, unchanged) | Fetch-failure banner (existing copy, reused verbatim), and the "Replace" button inside the re-seed confirm (see Copywriting Contract) — `bg-red-600 hover:bg-red-500 text-white` |

Accent reserved for: **Fetch Passage button, focus rings, the gap `+` affordance's hover state —
never** the three seed buttons (Split with AI / Alternate / Blank), which must read as equal-weight
peers per R096 and therefore stay neutral (`bg-gray-800 border-gray-700 text-gray-200
hover:bg-gray-700`), not indigo-accented. **This is a deliberate change from today's code**, where
"Split with AI" currently shares the same `text-indigo-400` treatment as "Fetch Passage" — that
implied a false hierarchy (AI as more "primary" than the other two seeds) that R096's
"equally-available starting points" language directly contradicts.

**Speaker/role colour (fourth semantic layer — content identity, not chrome):**

| Role | Colour | Rationale |
|------|--------|-----------|
| `LEADER` | `sky-300` (text) / `sky-900/50` (chip bg) / `sky-600/70` (card border-left) | **Locked, do not change** — restored 2026-08-05 out-of-band (STATE.md), presenter-side only today |
| `CONGREGATION` | `amber-300` / `amber-900/50` / `amber-600/70` | **Locked, do not change** — same restoration |
| `ALL` (new) | `violet-300` / `violet-900/50` / `violet-600/70` | **Researcher's discretionary pick** (CONTEXT.md left this open, suggesting emerald only as an example). Violet was chosen over emerald/green because: (1) it stays clearly separated in hue and luminance from both sky (blue) and amber (orange) — a blue/orange/violet triad has wider perceptual spacing than blue/orange/green; (2) green risks drifting toward brown/amber-adjacent under protanopia/deuteranopia, undermining exactly the separation the existing sky/amber pair was chosen to guarantee; (3) it stays visually distinct from the app's own `red`-reserved destructive colour and from the `indigo` UI-accent colour, so `ALL` is never mistaken for an error state or an interactive chrome element. Per FEATURES.md, colour is always a *secondary* cue here — the text label "All:" is present unconditionally on every render site, so this is a refinement, not the load-bearing distinction |

**Fix folded into this phase (discretionary, discovered during research):** `CongregationalEditor.vue`
today colours its LEADER control `indigo-300`/`indigo-900/50` — **not** `sky`, which is what the
presenter actually renders. The editor's preview must WYSIWYG-match the presenter, so this phase
also re-colours the editor's chip/preview LEADER state from indigo to `sky-300`/`sky-900/50`,
aligning it with `PresentationViewer.vue` for the first time. (Indigo remains the UI-accent colour
for Fetch Passage / focus rings / the gap `+`, so this also removes an existing collision between
"LEADER role colour" and "UI accent colour" that predates this phase.)

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | "Fetch Passage" — unchanged from today; the one true primary action on this surface |
| Seed action 1 (AI, conditional) | "✨ Split with AI" — small sparkle icon prefix (Heroicons-outline "sparkles" glyph) so it stays visually recognizable as the AI path even though it is no longer indigo-accented; `v-if="authStore.settings.aiEnabled"` |
| Seed action 2 | "Alternate Leader/Congregation" |
| Seed action 3 | "Start Blank" |
| Seed section heading | "Choose a starting point" |
| Empty state | No dedicated empty-state message — the unpopulated form (reference input with placeholder "e.g. Psalm 136:1-9" + the "Fetch Passage" button) IS the empty state, unchanged from today. No heading/body copy renders below it |
| Fetch error | "Could not load passage. Check your connection and try again." — **reused verbatim**, do not reword (existing `fetch-error` testid/copy) |
| AI split error | "Couldn't split this passage — your reading is unchanged. Build it by hand or try again." — **reused verbatim** (existing `AI_SPLIT_FAILURE_TEXT`); draft is left completely untouched on failure |
| Divider insert affordance (a11y) | `aria-label="Insert divider here"` on the gap `+` button |
| Divider remove affordance (a11y) | `aria-label="Remove divider"` on an existing-boundary hover control |
| Segmented chip options (a11y label + visible text, identical) | "Leader" / "Congregation" / "All" |
| Re-seed destructive confirmation | Heading: "Replace your dividers?" · Body: "Choosing a new starting point replaces your current dividers and labels. This can't be undone." · Buttons: "Replace" (red, primary) / "Cancel" (neutral, ghost) |

**No destructive confirmation is needed for removing a single divider** — merging two adjacent
segments back together preserves all text (nothing is deleted) and is instantly reversible by
clicking the same gap again to re-insert it. The only genuinely destructive, hard-to-recover action
this phase introduces is discarding an already hand-edited draft by picking a different seed — that
is what the confirmation above guards, gated on a simple `hasManuallyEdited` flag (set `true` on any
divider insert/remove or chip change; reset to `false` immediately after a seed is freshly applied).
The **first** seed pick on a freshly-fetched, never-edited passage applies immediately with no
confirm — there is nothing to lose yet.

## Interaction Contract — Divider Editing (R095)

Restated precisely for the planner/executor, since this is the phase's core new mechanism and
FEATURES.md's rejections must hold:

- **Boundaries are discrete**, snapped to `computeBoundaries(rawText)` (Phase 34, reused verbatim) —
  never an arbitrary text-range selection. This is *why* pattern (e) (free-range select-then-label)
  is rejected, not merely a stylistic choice.
- **The gap `+` (insert)**: rendered at every legal boundary point that is *not already* a divider,
  as a thin horizontal hairline (`border-t border-dashed border-gray-700`) that reveals a centered
  24px circular button (`rounded-full bg-gray-800 border border-gray-600 text-gray-300`) on
  hover/focus (desktop) or persistently at `opacity-40` (touch, per the backstop row above). Clicking
  it inserts a divider at that exact point, splitting one segment into two — the new segment
  inherits the **same** speaker role as the segment it split from (never resets to a default), so a
  user dividing a long Leader passage into two Leader parts does not have to re-pick the role twice.
- **An existing divider (remove)**: rendered as a solid line with a hover/focus-revealed 24px
  circular button using a minus glyph (`hover:bg-red-900/40 hover:text-red-300` — the only place red
  appears as an *interaction* cue rather than an error, since removing a boundary is the one
  reversible "undo a decision" gesture in this editor). Clicking it merges the two neighboring
  segments back into one, keeping the **first** (upper) segment's speaker role.
- **Rejected, do not build:** drag-handles (pattern b — text has no continuous dimension to drag
  along) and free-range/select-text-then-label (pattern e — real responsive readings never break
  mid-clause). If segment reordering is ever needed later, it is up/down move buttons, never drag —
  out of scope for this phase (CONTEXT.md § Deferred).
- **The 3-way segmented-control chip** (pattern c) sits in each segment card's header row:
  `inline-flex rounded-md border border-gray-700 bg-gray-900 p-0.5`, three `h-10` options
  (Leader / Congregation / All), each `px-2.5 text-xs font-semibold uppercase tracking-wider`.
  Selected state uses that role's own colour (`text-sky-300 bg-sky-900/50` for Leader, etc. — see
  Color § speaker/role colour table); unselected options are `text-gray-500` with
  `hover:text-gray-300`. This chip is simultaneously the labeling control (R096's `{text, role}`
  write) and the refrain-support mechanism (any segment, any role, independently) — no separate UI
  is needed for non-adjacent shared labels.
- **Segment card identity**: a 4px coloured left border strip (`border-l-4 border-l-{role}-600/70`)
  keyed to the segment's current role, on an otherwise uniform neutral card
  (`bg-gray-800/40 border-y border-r border-gray-700/50 rounded-lg`). This is a deliberate
  simplification from today's code, which differentiates LEADER with `font-semibold` body text and
  CONGREGATION with `pl-4` indentation — that two-state treatment does not scale cleanly to three
  roles (there is no sensible indent level for "All"), so body text is now uniform
  (`text-sm text-gray-100 leading-relaxed`) across all three roles, and role identity is carried
  entirely by the border strip + chip, consistent with FEATURES.md's label-first philosophy.
- **Preview panel** (existing, retained): mirrors the divided list read-only, extended from its
  current 2-way `indigo`/`amber` label colouring to the same 3-way `sky`/`amber`/`violet` used
  everywhere else in this spec, so the editor's own preview finally WYSIWYG-matches what the
  presenter actually projects (see Color § the indigo→sky fix above).

## Presenter & Grid-Card Changes (R097 substrate, ALL role)

- `PresentationViewer.vue`'s `speakerColorClass` (line ~657): extend the binary ternary to a 3-way
  map — `LEADER → text-sky-300`, `CONGREGATION → text-amber-300`, `ALL → text-violet-300`. Label
  text (line ~199) extends the same way: `Leader:` / `Congregation:` / `All:` — **label always
  rendered as text**, colour is never the sole distinguishing signal (FEATURES.md).
- `src/components/slides/slideDisplay.ts`'s `speakerDisplayName()` (line 143) gets a third branch:
  `'ALL' → 'All'`. Every call site that already consumes this helper (the rail label, the grid card
  badge, `EditSlideDrawer`-adjacent surfaces) picks up the third value automatically — no other
  call-site changes needed as long as the switch/ternary in `speakerDisplayName()` itself is
  widened from a binary check to a proper 3-way match.
- **R097 (first slide = reference, later slides = speaker label only):** this phase does not change
  `slideshowAssembler.ts`'s existing per-section slide generation — it *verifies* the existing
  behavior (Phase 38) holds unchanged for hand-divided readings and for the new `ALL` role, since
  the assembler is role-agnostic (`speaker` passes through as an opaque string union member). No new
  UI work is implied here beyond the type widening in `src/types/slide.ts`
  (`CongregationalSection.speaker: 'LEADER' | 'CONGREGATION' | 'ALL'`).
- **No print work** — congregational reading slides render only on slide surfaces (grid, drawer
  preview, presenter); `ServicePrintLayout.vue` is out of scope, consistent with Phase 46's print
  exclusion.
