<objective>
Close two server-side authorization gaps in `firestore.rules`: R232 restricts `inviteLookup` document creation to an editor of the target org (killing the self-invite privilege-forgery vector), and R233 makes an organization's `createdBy` field immutable after creation (killing the provenance-tampering vector). Both are one-clause changes that mirror idioms already live in the same file.

Purpose: A signed-in user can currently forge an invite into any church (self-elevation) and an editor can rewrite an org's authorship/audit trail. Both are already-diagnosed security defects (999.11 / PENDING-VERIFICATION C2).

Output: Modified `firestore.rules` (two clauses + one helper), emulator ALLOW/DENY tests in `src/rules.test.ts`, and the exact undeployed deploy command handed to the owner. Rules ship BUILT + TESTED + UNDEPLOYED per the standing v1.5+ deploy discipline.
</objective>

Per R232: in `firestore.rules`, the `match /inviteLookup/{email}` block (currently near lines 467-475) has `allow create: if isSignedIn();`. Change ONLY that create clause to also require editor authority over the org the payload targets — mirror the exact `isOrgEditor(request.resource.data.orgId)` idiom already used by the sibling `orgSlugs`/`orgNames` create gates. Leave `allow read` and `allow delete` on this block byte-for-byte unchanged: the first-login acceptance flow in `src/stores/auth.ts` reads-then-deletes its own invite by email and MUST keep working, and `assignOrgAdmin`/org provisioning write via the Admin SDK (bypass rules) — do not touch either path. NO client code change: `TeamView.vue` onInvite() already writes `orgId` onto the inviteLookup payload in the same batch as the invite doc.

<task type="auto">
  <name>Task 2: Make org createdBy immutable on update (R233)</name>
  <files>firestore.rules, src/rules.test.ts</files>
  <action>
Per R233: in `firestore.rules`, add a NEW sibling helper alongside `preservesLifecycleFields()` (near lines 113-126) that returns true only when an update does not affect `createdBy` — i.e. it negates `request.resource.data.diff(resource.data).affectedKeys().hasAny(['createdBy'])`. Then compose it into the `organizations/{orgId}` `allow update` clause (currently near line 161: `allow update: if isOrgEditor(orgId) && preservesLifecycleFields();`) by AND-ing the new helper on. Keep `preservesLifecycleFields()` and the `allow create` clause (which requires `request.resource.data.createdBy == request.auth.uid`) intact and untouched.

Do NOT fold `createdBy` into `lifecycleFields()`'s returned array (Anti-Pattern / Pitfall 2): that array is also consulted on CREATE to assert those keys are ABSENT, but `createdBy` is REQUIRED on create — widening the shared list would deny every legitimate org-create. A separate update-scoped helper is the only correct shape (the update call site is only reached when `resource` is non-null).

Add cases to `src/rules.test.ts` (the existing `describe('Editor vs viewer write permissions', ...)` block near line 121 is the right home):
  - DENY (change): seed the org doc `{ name, createdBy: 'userA' }` + seed `userA` as editor; as `userA`, `updateDoc(organizations/orgA, { createdBy: 'someoneElse' })` — assertFails.
  - ALLOW (ordinary edit, createdBy untouched): as the same editor, `updateDoc(organizations/orgA, { name: '...', updatedAt: <date> })` — assertSucceeds (a partial update never lists createdBy in affectedKeys).

IMPORTANT — the existing ALLOW regression "allows editor to write org doc" (~lines 122-141) currently uses a full-overwrite `setDoc(doc(...,'orgA'), { name, updatedAt })` with NO merge, which DROPS `createdBy` from the document. A removed key is an affected key, so the new guard correctly DENIES that write — meaning this existing test will now FAIL as written. Fix it so it exercises a real ordinary edit that preserves provenance: either switch it to `updateDoc` (partial update — the representative real-app path, since TeamView/Settings edits are partial updates) OR include the unchanged `createdBy: 'userA'` in the setDoc payload. Prefer `updateDoc`. Record this in the SUMMARY as a deliberate, necessary adjustment (not scope reduction): the setDoc-overwrite was a test convenience that a correct immutability guard must reject.
  </action>
