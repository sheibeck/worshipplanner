    httpsCallable(functions, 'onboardOrganization')({name, adminEmail}), set onboardedFeedback from the typed
    result ({name from input, status from result.data.status}), clear inputs, call refreshOrgs(); on catch
    set onboardError = friendlyCallableError(err) (which surfaces "That church name is taken." for
    already-exists). The button shows "Onboarding..." while isOnboarding, a momentary "Onboarded!" flash on
    success, else "Onboard church" (mirror the Grant/Granting.../Granted! recipe exactly), disabled while in
    flight. Success line: "Onboarded {name} — admin {status}." in text-green-400 (status verbatim from the
    callable — no client-side guessing).

    ASSIGN-ADMIN CONTROL (R203/R205), per org row: an inline click-to-reveal control toggled by
    `assigningOrgId === org.orgId` (mirror ConfigurationTab's revoke confirm/cancel, but as an ADD action —

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| super-admin browser → onCall callables | The tab sends only selectors ({name, adminEmail} / {orgId, email}) — never a privileged document write. All authority enforcement lives server-side (Plan 01). |

This plan adds no new trust boundary and no new privileged write path — it is a pure httpsCallable consumer
inside the already-super-admin-gated `/owner-console`. The server-side threats (authz, arrayUnion overwrite,
duplicate org, invite masking, orphan membership) are owned and tested by Plan 01's `<threat_model>`.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

Tested (row-scoped feedback case). |
