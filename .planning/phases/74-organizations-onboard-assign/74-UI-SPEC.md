# Phase 74 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase fills the Phase 72 `OrganizationsTab.vue` placeholder with the real
platform multi-tenancy surface: a list of every organization, an "onboard a church" form, and a
per-org "assign admin" affordance. It reuses the console's existing design system **verbatim** —
the same tokens, card shell, table idiom, and form/inline-confirm patterns already proven in
`ConfigurationTab.vue`'s super-admins roster (list) and grant form (onboard analog) and inline
revoke-confirm (assign-admin analog). No new tokens are introduced. Design surface: the org list
table, the onboard form, and the per-org assign-admin inline control, across their loading /
empty / error / populated / submitting / success states.

## Spacing Scale

Declared values (must be multiples of 4) — identical to the console-wide scale already locked in
`72-UI-SPEC.md`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (`gap-1`) | Inline control gaps (assign-admin input + buttons row) |
| sm | 8px (`gap-2`, `py-2`, `mt-2`) | Form row gaps, feedback-text top margin, table cell vertical rhythm inside a row |
| md | 16px (`px-4`, `mb-3`, `mt-4`) | Card padding, table cell horizontal padding, spacing between the onboard form and the table below it |
| lg | 24px | Not used directly by this phase's new markup (inherited from `AppShell`/page chrome) |
| xl | 32px | Not used directly by this phase's new markup (inherited from page-level wrapper) |

Exceptions: the per-org inline assign-admin email input uses a narrower `w-40` fixed width (still
`px-2 py-1` — a sub-4px-multiple-safe combination, matching Tailwind's compact input scale used
nowhere else yet in this console) to fit inside a table action cell without forcing row height —
this mirrors the existing inline revoke-confirm's compact text sizing (`text-xs`) rather than the
full-width `flex-1` inputs used in the top-level onboard form.

## UI Considerations

Applicable state considerations resolved: 12 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| loading | Org list (list-collection) | ✅ covered | "Loading organizations..." centered muted text row while `listOrganizations` is in flight, matching the roster's "Loading roster..." pattern (see Copywriting Contract). |
| empty | Org list (list-collection) | ✅ covered | "No organizations yet. Onboard one above." rendered as a full-width table row (`colspan="5"`), matching the roster's empty-state row exactly. |
| error | Org list (list-collection) | ✅ covered | "Couldn't load organizations. Refresh the page and try again." rendered below the card in `text-red-400`, matching the config-cards' `appConfigStore.loadError` pattern. |
| populated | Org list (list-collection) | ✅ covered | Table rows render church / org id / created date / member count / actions for each org returned by `listOrganizations`; list is refetched (one-shot, not realtime) after a successful onboard or assign action so counts/rows stay current. |
| zero-one-many | Org list (list-collection) | ✅ covered | Zero → the empty-state row above. One or many → identical row rendering per org, no singular/plural copy variance needed (member count is a plain number, not a noun phrase). No max-row cap or internal scroll container — the table grows with the page, same as the roster table. |
| overflow | Org list (list-collection) | 🧪 backstop | An unusually long church name wraps within its cell (no truncation/ellipsis) — same behavior as the roster's unclipped email column. Org id renders `text-xs font-mono` to stay visually compact regardless of id length. Held out as backstop since no fixture with a pathologically long name exists yet to prove wrap-not-clip visually. |
| empty | Onboard form (form) | ✅ covered | Both inputs render with their placeholders ("Church name" / "First admin email") and no pre-filled values; the Onboard button is enabled but a submit with either field blank surfaces the inline validation error rather than calling the callable. |
| loading | Onboard form (form) | ✅ covered | Onboard button shows "Onboarding..." and is `disabled`; both inputs are NOT separately disabled (matches the existing grant form, which only disables the button) to avoid inconsistent new behavior. |
| error | Onboard form (form) | ✅ covered | Inline `text-red-400` message below the form row for each failure path: name-taken, invalid input, and generic write failure (see Copywriting Contract for exact strings). |
| partial | Onboard form (form) | ✅ covered | Client-side validation (non-empty name + `isValidEmailFormat`-style check on the admin email) blocks submission before the callable is invoked, surfacing "Enter a church name and a valid admin email address." — mirrors the roster grant form's existing `isValidEmailFormat` guard. |
| long-text | Onboard form (form) | 🧪 backstop | A very long church name or email scrolls within the standard-width text input (browser-native behavior, no custom truncation) — held out as backstop, no fixture proves this visually yet. |
| loading | Assign-admin control (form, per org row) | ✅ covered | "Assign" button shows "Assigning..." and is `disabled`; the row's email input remains editable-but-inert visually consistent with the top-level onboard button's disable-only pattern. |
| error | Assign-admin control (form, per org row) | ✅ covered | Inline `text-xs text-red-400` message directly under that row's control only (keyed per `orgId`, not shared across rows) — see Copywriting Contract for exact strings. |
| partial | Assign-admin control (form, per org row) | ✅ covered | Client-side email-format validation blocks the call and surfaces "Enter a valid email address." before invoking `assignOrgAdmin`. |

No `nav` or `media` elements exist in this surface. No zero-one-many consideration applies to the
onboard form or assign-admin control (neither is a `list-collection`).

## Component Spec: Onboard Form

Mirrors the roster's grant form (`ConfigurationTab.vue:12-30`) exactly in structure and class
recipe, extended to two inputs:

```html
<div class="flex flex-col sm:flex-row gap-3">
  <input
    v-model="churchName"
    type="text"
    placeholder="Church name"
    class="flex-1 bg-gray-800 border border-gray-700 text-gray-100 rounded-md px-3 py-2 text-sm focus:outline-none focus:ring-1 focus:ring-indigo-500 placeholder-gray-500"
  />
  <input
    v-model="adminEmail"
    type="email"
    placeholder="First admin email"
    class="flex-1 bg-gray-800 border border-gray-700 text-gray-100 rounded-md px-3 py-2 text-sm focus:outline-none focus:ring-1 focus:ring-indigo-500 placeholder-gray-500"
    @keydown.enter="onOnboard"
  />
  <button
    type="button"
    @click="onOnboard"
    :disabled="isOnboarding"
    class="inline-flex items-center justify-center gap-2 bg-indigo-600 hover:bg-indigo-500 disabled:opacity-60 text-white rounded-md px-4 py-2 text-sm font-medium transition-colors"
  >
    {{ isOnboarding ? 'Onboarding...' : onboardedFeedback ? 'Onboarded!' : 'Onboard' }}
  </button>
</div>
<p v-if="onboardError" class="text-red-400 text-sm mt-2">{{ onboardError }}</p>
<p v-if="onboardedFeedback" class="text-green-400 text-sm mt-2">
  Onboarded {{ onboardedFeedback.name }} — admin {{ onboardedFeedback.status }}.
</p>
```

`onboardedFeedback.status` is `'added'` or `'invited'`, taken verbatim from the callable's typed
result — no client-side guessing.

## Component Spec: Organizations Table

Mirrors the roster table (`ConfigurationTab.vue:38-92`) exactly in structure and class recipe,
with five columns instead of three:

```html
<div v-if="!loaded" class="text-sm text-gray-400 py-8 text-center">
  Loading organizations...
</div>

<div v-else class="mt-4 rounded-lg border border-gray-800 overflow-hidden">
  <div class="overflow-x-auto">
    <table class="w-full text-sm">
      <thead>
        <tr class="bg-gray-800/50 border-b border-gray-700">
          <th class="px-4 py-3 text-left text-xs font-medium text-gray-400 uppercase tracking-wider">Church</th>
          <th class="px-4 py-3 text-left text-xs font-medium text-gray-400 uppercase tracking-wider">Org ID</th>
          <th class="px-4 py-3 text-left text-xs font-medium text-gray-400 uppercase tracking-wider">Created</th>
          <th class="px-4 py-3 text-left text-xs font-medium text-gray-400 uppercase tracking-wider">Members</th>
          <th class="px-4 py-3 text-left text-xs font-medium text-gray-400 uppercase tracking-wider">Actions</th>
        </tr>
      </thead>
      <tbody class="divide-y divide-gray-800">
        <tr v-for="org in organizations" :key="org.orgId" class="hover:bg-gray-800/20 transition-colors">
          <td class="px-4 py-3 text-gray-200">{{ org.name }}</td>
          <td class="px-4 py-3 text-gray-500 text-xs font-mono">{{ org.orgId }}</td>
          <td class="px-4 py-3 text-gray-400 text-sm">{{ formatDate(org.createdAt) }}</td>
          <td class="px-4 py-3 text-gray-400 text-sm">{{ org.memberCount }}</td>
          <td class="px-4 py-3"><!-- Assign-admin control, see below --></td>
        </tr>

        <tr v-if="organizations.length === 0">
          <td colspan="5" class="px-4 py-8 text-center text-sm text-gray-500">
            No organizations yet. Onboard one above.
          </td>
        </tr>
      </tbody>
    </table>
  </div>
</div>

<p v-if="listError" class="text-red-400 text-sm mt-3">
  Couldn't load organizations. Refresh the page and try again.
</p>
```

`formatDate` reuses the roster's existing date-only formatter (`admin.grantedAt` → `org.createdAt`,
same `{ toDate?: () => Date }` shape from Firestore `serverTimestamp()`).

## Component Spec: Assign-Admin Control (per-org row action)

Mirrors the roster's inline revoke-confirm interaction pattern (`ConfigurationTab.vue:56-79`) —
click-to-reveal an inline control, Confirm/Cancel-shaped — but as an ADD action (not destructive),
so it uses accent (indigo) rather than destructive (red) styling, and an email input instead of a
bare confirm:

```html
<template v-if="assigningOrgId === org.orgId">
  <div class="flex items-center gap-2">
    <input
      v-model="assignEmail"
      type="email"
      placeholder="Admin email"
      class="bg-gray-800 border border-gray-700 text-gray-100 rounded-md px-2 py-1 text-xs w-40 focus:outline-none focus:ring-1 focus:ring-indigo-500 placeholder-gray-500"
      @keydown.enter="onConfirmAssign(org)"
    />
    <button
      type="button"
      @click="onConfirmAssign(org)"
      :disabled="isAssigning"
      class="text-xs text-indigo-300 hover:text-indigo-200 transition-colors"
    >
      {{ isAssigning ? 'Assigning...' : 'Assign' }}
    </button>
    <button
      type="button"
      @click="cancelAssign"
      class="text-xs text-gray-400 hover:text-gray-200 transition-colors"
    >
      Cancel
    </button>
  </div>
  <p v-if="assignError[org.orgId]" class="text-red-400 text-xs mt-1">{{ assignError[org.orgId] }}</p>
  <p v-if="assignFeedback[org.orgId]" class="text-green-400 text-xs mt-1">{{ assignFeedback[org.orgId] }}</p>
</template>

<template v-else>
  <button
    type="button"
    @click="startAssign(org.orgId)"
    class="text-sm text-indigo-300 hover:text-indigo-200 transition-colors"
  >
    Assign admin
  </button>
</template>
```

`assignFeedback[org.orgId]` is either "Added as admin." or "No account yet — invited as admin.",
set directly from the callable's `{status: 'added' | 'invited'}` result, keyed per `orgId` so one
row's feedback never leaks into another's. `assignError`/`assignFeedback` clear when
`startAssign`/`cancelAssign` runs for that row, so re-opening the control after a prior
success/error starts clean.
