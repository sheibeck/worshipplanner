# Phase 128 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — hand-rolled Tailwind v4 utility classes, no component library, no `components.json` found. CONTEXT.md explicitly directs "reuse the app's existing Tailwind dark gray-950 design system... do NOT invent a new visual language." Introducing shadcn for one small, tightly-scoped phase inside a mature app with a fully established custom dark-card pattern would contradict that directive, so the shadcn init gate is skipped by design judgment, not by omission. |
| Component library | none (Radix/base-ui not present; every view hand-composes `<template>` markup) |
| Icon library | none — inline hand-authored SVG (checkmark, X, chevron, spinner) copied per-view, matching `VolunteerSignInView.vue` / `LoginView.vue` / `VolunteerLinkCompleteView.vue` exactly |
| Font | Tailwind default sans stack (`ui-sans-serif, system-ui, sans-serif`) — no custom app font is loaded; `'Inter'` in `src/assets/main.css` is scoped to `--slide-font-family` (presentation output only), not app UI |

This phase adds **zero new visual primitives**. Every surface below is a direct extension of the existing centered-card pattern already shipped in `VolunteerSignInView.vue`, `LoginView.vue`, and `VolunteerLinkCompleteView.vue`. The executor should copy those files' markup/class structure, not redesign.

## Spacing Scale

Declared values (must be multiples of 4) — unchanged from the existing pattern, no new values introduced:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps (e.g. `gap-2`≈8px is actually the smallest gap used; 4px reserved for tightest inline spacing) |
| sm | 8px | `space-y-3` form-field stacking, `gap-2` (icon+heading rows) |
| md | 16px | `px-4` page gutter, `space-y-4`/`space-y-5` section stacking inside the card |
| lg | 24px | `p-6` card interior padding, `mb-8` brand-to-card gap |
| xl | 32px | not used on this phase's surfaces (reserved, no exception needed) |
| — | 44px | Not applicable — no touch-target-only controls (icon buttons) on these surfaces; every control is a full-width text button or text link, already exceeding 44px tap height via `py-2`/`py-2.5` + `text-sm`/`text-xs` line height |

Exceptions: none. Container width stays `max-w-sm` (mirrors all three reference views) — do not widen for the extra church-name heading.

## Typography

Inherited exactly from `VolunteerSignInView.vue` / `LoginView.vue` / `VolunteerLinkCompleteView.vue`. Three sizes, three weights already present in the existing pattern — declared honestly rather than forced into an artificial 2-weight count, since reuse-first overrides the generic default here.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / form hint | 14px (`text-sm`) | 400 regular | Tailwind default for `text-sm` (1.25rem / ~1.43) — no `leading-*` override in any reference view |
| Secondary link / fine print | 12px (`text-xs`) | 400 regular | Tailwind default for `text-xs` (1rem / ~1.33) |
| Button / form label | 14px (`text-sm`) | 500 medium (`font-medium`) | Tailwind default for `text-sm` |
| Brand heading (h1) | 24px (`text-2xl`) | 600 semibold (`font-semibold`), `tracking-tight` | Tailwind default for `text-2xl` (2rem / ~1.33) |
| Church name (new, page-specific heading) | 20px (`text-xl`) or 18px (`text-lg`) — use `text-lg font-semibold text-white` | 600 semibold | Tailwind default for `text-lg` (1.75rem / ~1.56) |

Church name renders one size below the "Worship Planner" brand h1 (never larger) so the brand stays the visual anchor across every volunteer surface — mirrors the existing two-tier "Worship Planner" / subtitle pattern already in all three reference views.

## Color

No new hex values. Every color below is an existing Tailwind default token already used identically across `VolunteerSignInView.vue`, `LoginView.vue`, `VolunteerLinkCompleteView.vue`.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-gray-950` | Full-viewport page background on every new/edited surface |
| Secondary (30%) | `bg-gray-900` + `border-gray-800` (card), `bg-gray-800` + `border-gray-700` (inputs) | The centered card container; form inputs inside it |
| Accent (10%) | `indigo-600` (bg, buttons) / `indigo-500` (hover) / `indigo-400` (text links) | Reserved for: (1) the primary "Send my sign-in link" submit button, (2) the "Are you a volunteer? Get your sign-in link" entry on the login page, (3) the "Find your church" submit button on the generic lookup extension, (4) the "Request a new link" affordance on the verify-failure state, (5) focus rings (`focus:ring-indigo-500`) on every input/button. Never used for body text, borders, or decorative fills outside these five elements. |
| Destructive/Error | `red-400` (text) / `red-950` (bg) / `red-800` (border) | "Church not found" state body text box, and genuine failure copy (network error, malformed email, `invalid-argument` from the callable). **Never** used for a roster-miss — that path renders the identical success confirmation, per R395. |
| Success accent | `green-400` (text) / `green-900` (icon bg) | The enumeration-safe confirmation state's checkmark icon + confirmation text — mirrors `LoginView.vue`'s existing "reset link sent" success block exactly (same icon, same classes) |

Accent reserved for: the 5 elements listed above only. Everything else (church-not-found box, confirmation box, hint text, dividers) uses the dominant/secondary/error/success roles — never accent as a decorative color.

## UI Considerations

Applicable state considerations resolved: 9 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| loading | Public request page, slug resolution | ✅ covered | While `getDoc(orgSlugs/{slug})` is in flight, render a brief neutral loading state (spinner + "Loading…", matching `VolunteerLinkCompleteView.vue`'s existing `isVerifying` spinner block) instead of flashing "church not found" before the read resolves |
| error (structural, not roster) | Public request page, unknown/expired slug | ✅ covered | See Copywriting Contract "Church-not-found heading/body" row — distinct from and never confusable with the roster-miss confirmation, since slug validity is public information (not a membership secret) |
| submitting | Public request page, email form | ✅ covered | Button label swaps to "Sending…", disabled, mirrors `LoginView.vue`'s `isLoading`/`loadingMethod` pattern |
| populated → success | Public request page, after submit | ✅ covered | Form is replaced by the enumeration-safe confirmation block (see Copywriting Contract) — identical render path regardless of roster hit/miss/rate-limit outcome per R395 |
| error (client-side validation) | Public request page, email field | ✅ covered | "Enter a valid email address." shown inline before the callable is ever invoked — a pure format check, never membership-revealing (mirrors DENY-5 in RESEARCH.md's threat matrix) |
| zero-one-many | Verify-failure re-request target | ✅ covered | `route.query.slug` present → targets that church's request page by name+params; absent → falls back to the generic `volunteer-home` lookup extension (research's Open Question, resolved) |
| long-text | Church name heading | ✅ covered | No `truncate`/fixed-width clipping — the `max-w-sm` card already wraps naturally; heading uses `text-lg font-semibold` with no `whitespace-nowrap`, so a longer church name wraps to two lines gracefully instead of overflowing the card |
| populated | Login-page entry point | ✅ covered | Static text link, always rendered (not conditional on any data fetch) — no loading/empty variant needed |
| error (genuine failure) | Public request page, network/unexpected callable error | ✅ covered | Distinct generic "Something went wrong" copy — the ONE case allowed to differ from the enumeration-safe confirmation, because it reflects a client-side transport failure (callable never returned), not a roster outcome |
| overflow | Generic "find your church" lookup result list | 🧪 backstop | Spec assumes a single-match resolution (slug/name → exactly one org, mirrors `orgSlugs`' 1:1 slug design) with no disambiguation UI for a hypothetical multi-match; flag as a held-out check at verify time if the lookup input is ever matched against `orgNames` with fuzzy/partial matching rather than exact slug lookup |
| empty | Generic "find your church" input, submitted blank | 🧪 backstop | Expected to reuse the browser's native `required` attribute validation (same as every other email/text input in these three reference views) rather than a custom empty-state message; verify at implementation time that no custom empty-input copy was silently introduced that duplicates/conflicts with native validation |
