# Phase 135 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Restructure, not greenfield.** This phase reframes `src/views/DashboardView.vue` around a "needs your
attention" feed (R414–R419). It does NOT introduce a new visual system. Every token, color, and component
pattern below is lifted directly from the app's existing dark gray-950 card language — `DashboardView.vue`,
`ScheduleServiceCard.vue`, `SongsView.vue`, and `ServiceEditorView.vue`'s confirmation chips. The executor
should be copying/adapting existing classes, not inventing new ones.

## Layout & Widget Contracts

### Overall structure (top to bottom, single-column flow; internal grids per widget below)

1. Page header (unchanged) — `<h1 class="text-xl font-semibold text-gray-100">Dashboard</h1>` + welcome subtext.
2. `GettingStarted` (unchanged, editor-only, self-hides when complete).
3. **Empty/first-run branch (R419):** if `upcomingServices.length === 0`, render the all-caught-up card
   (see below) IN PLACE of items 4–5, then continue to Song library (6). Song library always renders
   regardless of schedule state — it's about song-data health, not the attention feed.
4. **Needs-attention feed (R415/R416)** — full width now (no longer sharing a 2-col grid with the removed
   Volunteer coverage section). Hero "Next service" card + compact list of the next up-to-5 services after
   it (unchanged 6-total cap from existing `upcomingAfterNext`).
5. **Attention cards row** — `grid grid-cols-1 lg:grid-cols-2 gap-6`: Unconfirmed volunteers (R417) +
   Editor presence roll-up (R418). When the presence card is hidden (empty), the unconfirmed card spans
   `lg:col-span-2` rather than leaving a dead column.
6. **Song library** (R414 keeps this, unchanged) — full width, `grid grid-cols-2 sm:grid-cols-3
   lg:grid-cols-5 gap-3` tiles, exactly as it exists today.

R414 removal: delete the "Volunteer coverage" `<section>` (current lines ~92-129: the Active
volunteers/Under-staffed roles block) and its now-dead `understaffedRoles`/`MIN_VOLUNTEERS_PER_ROLE`
computed/constant. Nothing replaces it directly — its grid slot is reclaimed by the feed becoming full width.

### Widget 1 — Needs-attention feed (R415)

**Structure:** unchanged from today's "Next service" hero card (`router-link` styled
`rounded-lg border border-gray-800 bg-gray-900 p-5 hover:bg-gray-800/50`) + the `upcomingAfterNext` compact
list (`divide-y divide-gray-800 border border-gray-800 rounded-lg`). Soonest-first, capped at 6 total
(1 hero + 5 list), matching the existing `.slice(1, 6)`.

**Readiness signal (R416) replaces the hero card's existing two pills and the list rows' single dot** with
one combined, worst-of-rollup signal per service, computed from three existing sources — no new data model:

1. Song-assignment stat: `serviceSongStats(service)` (existing function — `filled`/`total` SONG slots).
2. Media readiness: `readinessOf(songs)` from `@/utils/myScheduleGrouping` (existing v2.12 function — reuse
   verbatim, do not reimplement).
3. Lock state: `service.status` (`draft` vs `planned`/`exported`).

**Rollup priority (worst → best; render the FIRST that applies):**

| Order | Condition | State id | Dot/text color | Label |
|-------|-----------|----------|-----------------|-------|
| 1 (worst) | `total > 0 && filled < total` | `songs-needed` | amber (`bg-amber-500` dot, `text-amber-400` text) | "{total-filled} song{s} still needed" |
| 2 | `total > 0 &&` songs fully assigned but `readinessOf(songs).state !== 'ready'` | `media-missing` | amber (same tone as above — both are actionable gaps, distinguished by copy not color) | `partial` → "{missingCount} song{s} missing media"; `waiting` → "Songs missing media" |
| 3 | songs (if any) all assigned + media ready, but `service.status === 'draft'` | `draft` | gray (`bg-gray-500` dot, `text-gray-400` text) | "Draft" |
| 4 (best) | songs (if any) all assigned + media ready + not draft | `ready` | green (`bg-green-500` dot, `text-green-400` text) | "Ready" |

**Zero-song-slots edge case:** a service with `total === 0` (e.g. an announcements/scripture-only order with
no SONG slots) has nothing to be "songs-needed" or "media-missing" about — both checks require `total > 0`
and the rollup falls straight through to the draft/ready check. Do not let `readinessOf([])`'s `waiting`
state (its own zero-songs default) leak into this rollup as a false "missing media" reading.

This is a genuinely new 4-state derived value for the dashboard only — it is NOT the same enum as
`ScheduleServiceCard`'s 3-state `readinessOf` (which covers media only). Name it distinctly in code (e.g.
`dashboardReadinessOf`) so it's never confused with or substituted for the volunteer-facing one.

**Visual treatment:**
- Hero card: render as a `rounded-full` pill (reuse the exact pill markup/classes already on the hero card:
  `inline-flex items-center gap-1.5 px-2.5 py-1 rounded-full text-xs font-medium border`), colored per the
  table above (map amber/green/gray to the existing `bg-{color}-900/40 border-{color}-700/50
  text-{color}-300` pill recipe already used for the songs-assigned pill; gray uses the plain
  `bg-gray-800 border-gray-700 text-gray-400` recipe already used for "No scripture"). Keep the existing
  "Scripture set / No scripture" pill alongside it unchanged.
- List rows (`upcomingAfterNext`): keep the existing compact treatment but upgrade from a bare dot to
  **dot + inline text label** (`<span class="h-2 w-2 rounded-full {color}"></span><span class="text-xs
  {color-text}">{label}</span>`) — a dot alone fails the "not color alone" a11y bar this app already applies
  to `ScheduleServiceCard` (see its IN-03 review note). Drop the `title` tooltip attribute in favor of the
  always-visible text label.

**States:** populated (above); empty → existing dashed-border "No upcoming services. Create one to get
started." card (unchanged copy/markup); loading → services subscribe synchronously from the store cache, so
no separate loading skeleton is required (matches current behavior — do not add one).

### Widget 2 — Unconfirmed volunteers (R417)

**Data:** for the same bounded window as the feed (≤6 upcoming, Planned-only per CONTEXT's "next N upcoming
(Planned) services"), read each service's `confirmations` subcollection + `roleAssignmentsByEmailLower`.
An assignment counts as unconfirmed when it has no doc, or the doc's `status` is `needsReconfirmation`
(reuse `ConfirmationStatus`/`confirmationKey` from `@/utils/confirmations` verbatim — same vocabulary as
`ServiceEditorView.vue`'s roster chips).

**Card shell:** `rounded-lg border border-gray-800 bg-gray-900 p-5` (identical shell to the hero feed card),
header row `<h2 class="text-xs font-semibold uppercase tracking-widest text-gray-500">Unconfirmed
volunteers</h2>` with a trailing count badge when > 0 (reuse the amber chip recipe:
`bg-amber-900/40 border-amber-700/50 text-amber-300` pill showing the total unconfirmed count).

**Row:** one row per unconfirmed (person, role, service) tuple, each a `router-link` to that service
(`/services/{id}`), format: `{personName}` · `{roleName}` · `{serviceName}, {formatServiceDate}`. Use the
exact confirmation-chip visual (`bg-gray-800 text-gray-400 border-gray-700` for the implicit-unconfirmed
default, `bg-amber-900/40 text-amber-300 border-amber-800` for `needsReconfirmation`) so a planner sees the
identical color they'd see on the roster tab — no new chip vocabulary invented.

**Cap:** show at most 8 rows; if more exist append a trailing "+N more — view roster" link. (Discretion:
picked to keep the card from dominating the layout while the underlying data stays bounded to ≤6 services.)

**States:**
- Populated: rows as above.
- Empty (0 unconfirmed across the window): card STAYS visible with the copywriting-contract empty
  sub-state ("Everyone's confirmed for the next N services.") in `text-sm text-gray-400` — this is a
  positive confirmation the planner should see, not noise to hide (Claude's Discretion, resolved: always
  show this card when there are upcoming services).
- Loading: brief `text-sm text-gray-500`, "Checking confirmations…" (subcollection reads are async per
  service; acceptable to show this for the sub-second fan-out window).
- Error: per Copywriting Contract's Error state row.

### Widget 3 — Editor presence roll-up (R418)

**Data:** read-only aggregation of `services/{id}/presence` across the same bounded upcoming-services
window, filtered through `isPresenceStale(lastSeenMs, now, PRESENCE_STALE_TTL_MS)` from `@/utils/presence`
(same staleness filter `useServicePresence` applies) — stale editors are excluded, never shown greyed-out.
**Read-only:** this widget must NOT call `useServicePresence`'s `start()`/heartbeat path (that composable
writes a presence doc for the current viewer) — it needs a read-only variant/reuse of the same
collection-read shape, per 135-CONTEXT's explicit "do NOT write presence from the dashboard" instruction.

**Card shell:** identical `rounded-lg border border-gray-800 bg-gray-900 p-5` shell, header `<h2
class="text-xs font-semibold uppercase tracking-widest text-gray-500">Currently editing</h2>`.

**Row:** one row per active (non-stale) presence doc: `{displayName}` is editing `{serviceName}` →
`router-link` to `/services/{id}`. A small green pulse/dot (`bg-green-500`, optionally `animate-pulse`)
prefixes each row — the one place on this page a green dot means "live," not "ready," so keep it visually
distinct (paired with the word "editing" in the row text, never color alone).

**States:**
- Populated: rows as above.
- **Empty: hide the entire card** (Claude's Discretion, resolved: unlike the unconfirmed-volunteers card,
  zero active editors is the overwhelmingly common state every time this page loads — an always-present
  "no one is editing" card would be permanent noise for an ephemeral, low-signal fact). When hidden, the
  Unconfirmed volunteers card takes the full row width (`lg:col-span-2`).
- Loading: card simply doesn't render until the first snapshot resolves (no skeleton — presence reads are
  fast, local-cache-backed `onSnapshot`).
- Error: per Copywriting Contract's Error state row; on error, treat as empty (hide) rather than showing a
  broken widget — presence is a nice-to-have signal, never worth a visible error banner.

### Widget 4 — Empty / first-run state (R419)

Renders in place of the feed + attention-cards row when `upcomingServices.length === 0`. Shell matches the
existing feed's own empty-state pattern (`rounded-lg border border-dashed border-gray-700 p-6 text-center`)
but full width and slightly more prominent (this is now the primary content of the page in this state, not
a small sub-panel):

```
┌───────────────────────────────────────────┐
│              [checkmark icon]              │
│            You're all caught up            │
│  No upcoming services need your attention   │
│                right now.                   │
│         [ Schedule a service → ]            │
└───────────────────────────────────────────┘
```

Icon: reuse the same checkmark `<svg>` path already used in `GettingStarted.vue`'s done-state
(`M5 13l4 4L19 7`), sized `h-8 w-8`, `text-green-500`, centered — signals "nothing wrong," not an error.

## Responsive Behavior

- Page container unchanged: `px-6 py-8` (no new breakpoint-specific padding needed).
- Feed hero + list: unchanged single-column behavior — already renders full width at every breakpoint once
  it's no longer sharing the `lg:grid-cols-2` split with the removed Volunteer coverage section.
- Attention cards row: `grid grid-cols-1 lg:grid-cols-2 gap-6` — stacked full-width on mobile/tablet
  (`< 1024px`), side-by-side only at `lg:`. This matches the breakpoint already used for the page's own
  outer grid today.
- Card-internal rows (unconfirmed list, presence list): each row must remain readable at 375px width —
  reuse `min-w-0 truncate` on name/service text exactly as the existing hero card and `ScheduleServiceCard`
  do, so long names/service titles ellipsize instead of overflowing.
- No horizontal scrolling introduced anywhere on this page at any width.
- Touch targets: every `router-link` row keeps a minimum ~44px effective tap height via existing `py-2.5`
  (list rows) / `p-4`-`p-5` (cards) padding — no new custom touch-target sizing needed, these already meet
  the bar.

## Accessibility

- Readiness dot+label pairs communicate state via color AND text (never color alone) — see the "not color
  alone" rule applied in both the feed rollup and the presence "editing" row above.
- Every feed/widget row that links to a service is a single `router-link` wrapping the full row (not a
  nested interactive element), matching `ScheduleServiceCard`'s existing `aria-label`-carries-context
  pattern. Rows whose visible text doesn't fully convey context (e.g. a bare date/name) should carry an
  `aria-label` summarizing role/status, mirroring `ScheduleServiceCard.vue`'s `ariaLabel` computed.
  Simple, self-describing rows (name + date + status text already visible) do not need a redundant
  `aria-label`.
- Focus states: every new interactive row must carry a visible keyboard-focus ring. Reuse
  `ScheduleServiceCard.vue`'s exact focus utility (`focus:outline-none focus:ring-2
  focus:ring-indigo-500 focus:ring-offset-2 focus:ring-offset-gray-950`) — the existing hero card and
  `upcomingAfterNext` rows currently lack this and should pick it up as part of this restructure since
  they're being touched anyway.
- Contrast: all text/background pairs are reused verbatim from already-shipped components
  (`text-amber-400`/`text-green-400`/`text-gray-400` on `bg-gray-900`, chip text-on-tint pairs from
  `ServiceEditorView.vue`) — no new color pairing is introduced, so no new contrast verification is needed
  beyond what's already live in production.
- The "Currently editing" live-pulse dot is presentational only (`aria-hidden="true"` on the dot span);
  the adjacent text ("{name} is editing {service}") carries the full meaning for screen readers.
