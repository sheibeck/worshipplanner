# Phase 40.1: Close the Self-Service Membership Hole - Context

**Gathered:** 2026-08-06
**Status:** Ready for planning
**Mode:** Smart discuss (autonomous) — infrastructure/security phase, no user-facing surface

<domain>
## Phase Boundary

One rule, in one file. `firestore.rules:36-41` currently reads:

```
match /members/{uid} {
  allow read: if isOrgMember(orgId);
  allow write: if isOrgEditor(orgId);
  // Allow creator to write their own membership when creating an org or accepting an invite
  allow create: if isSignedIn() && request.auth.uid == uid;
}
```

That `allow create` lets **any signed-in user create `organizations/{ANY_ORG}/members/{their-uid}`** —
self-joining an organization they were never invited to. Because the document body is
client-controlled, they can also set `role: 'editor'` in the same write. **That is privilege
escalation, not merely unwanted membership.**

**In scope:** tightening that one `allow create` predicate, and the tests that prove both the denial
and the two legitimate flows still work.

**Out of scope:** every other rule in the file, the Storage rules (Phase 40, done), the sharing rules
(Phase 41), and any deploy.
</domain>

<decisions>
## Implementation Decisions

### The rule is loose ON PURPOSE — both flows must survive

The rule's own comment states the two legitimate creation paths:
*"Allow creator to write their own membership when creating an org or accepting an invite."*

1. **Org creation** — the founder writes their own first membership document. There is no existing
   member to authorize it and no invite, so no membership-based or invite-based predicate can cover
   this case. **This is the flow most likely to be silently broken by a careless tightening**, and
   breaking it means no new church can ever onboard.
2. **Invite acceptance** — a user with an outstanding invite writes their membership document. There
   is one real never-accepted invite in production, so this path has a live test case.

**A fix that only considers the invite path breaks flow 1. A fix that only considers org creation
leaves the hole open.** Both must be handled explicitly and both must be tested.

### Role must not be self-chosen

Denying self-join is necessary but not sufficient. A user accepting a genuine invite must not be able
to submit `role: 'editor'` when the invite granted `viewer`. Either:
- the rule constrains `request.resource.data.role` against the invite document's role, or
- the role is forced server-side and the client-submitted value is ignored.

Either is acceptable; the plan must pick one and prove it with a test that submits an escalated role
and expects denial.

### Proven by tests that actually run

`firestore.rules` uses **same-service** `exists()`/`get()`, which firebase-js-sdk#6803 does **not**
affect — unlike `storage.rules`. So unlike Phase 40, there is no emulator limitation here: every
case below is behaviourally testable against the running Firestore emulator, and **all of them must
be**. No structural source assertions as a substitute.

- DENY: signed-in user, no invite, self-creates membership in an arbitrary org
- ALLOW: user accepting a genuine outstanding invite
- ALLOW: founder creating their own first membership in a brand-new org
- DENY: user accepting a genuine invite but submitting an escalated role

### Nothing is deployed

`firestore.rules` is modified and tested but **not deployed**, per the v1.5 standing autonomy grant.
It is handed to the owner to ship **alongside Phase 40's deploy 2**, which already touches the rules
files — one deploy session, not two.

### Claude's Discretion

- Whether the predicate reads the invite document directly or delegates to a helper function.
- Test file placement — extend `src/rules.test.ts` (which already covers `firestore.rules` and
  currently passes fully) versus a new file.
- The exact shape of the invite lookup, subject to it being same-service and therefore emulator-testable.

</decisions>

<specifics>
## Specific Ideas

- The owner accepted this phase specifically so the fix can ride along with Phase 40's deploy 2
  rather than requiring a second deploy session. Keep the change small enough that it does not
  complicate that runbook.
- **The lesson from Phase 40 applies directly:** all-denies-pass-while-allows-fail is the signature
  of a rule that denies everyone. Here the inverse risk is live — a rule that *allows* everyone looks
  green if you only test the happy path. **Test the denial first**, and confirm it genuinely fails
  against the current (unfixed) rule before claiming the fix works.

</specifics>
