## User Constraints (from CONTEXT.md)

### Locked Decisions

**The rule is loose ON PURPOSE — both flows must survive.** The rule's own comment states the two
legitimate creation paths: *"Allow creator to write their own membership when creating an org or
accepting an invite."*

1. **Org creation** — the founder writes their own first membership document. There is no existing
   member to authorize it and no invite, so no membership-based or invite-based predicate can cover
   this case. This is the flow most likely to be silently broken by a careless tightening, and
   breaking it means no new church can ever onboard.
2. **Invite acceptance** — a user with an outstanding invite writes their membership document. There
   is one real never-accepted invite in production, so this path has a live test case.

A fix that only considers the invite path breaks flow 1. A fix that only considers org creation
leaves the hole open. Both must be handled explicitly and both must be tested.

**Role must not be self-chosen.** Denying self-join is necessary but not sufficient. A user
accepting a genuine invite must not be able to submit `role: 'editor'` when the invite granted
`viewer`. Either the rule constrains `request.resource.data.role` against the invite document's
role, or the role is forced server-side and the client-submitted value is ignored. Either is
acceptable; the plan must pick one and prove it with a test that submits an escalated role and
expects denial.

**Proven by tests that actually run.** `firestore.rules` uses same-service `exists()`/`get()`, which
firebase-js-sdk#6803 does not affect — unlike `storage.rules`. Every case below is behaviourally
testable against the running Firestore emulator, and all of them must be. No structural source
assertions as a substitute:
- DENY: signed-in user, no invite, self-creates membership in an arbitrary org
- ALLOW: user accepting a genuine outstanding invite
- ALLOW: founder creating their own first membership in a brand-new org
- DENY: user accepting a genuine invite but submitting an escalated role

**Nothing is deployed.** `firestore.rules` is modified and tested but not deployed. It is handed to
the owner to ship alongside Phase 40's deploy 2, which already touches the rules files — one deploy
session, not two.

## Summary

The vulnerability is real and exactly as described: `firestore.rules:39-40`'s `allow create: if
isSignedIn() && request.auth.uid == uid` authorizes a membership-document create based on nothing
but "you are creating a doc keyed by your own uid" — no relationship to the target org is checked at
all. Both legitimate flows this rule protects (org creation, invite acceptance) live in exactly one
function: `ensureUserDocument()` in `src/stores/auth.ts:264-350`. There is no other app code path
that creates a `members/{uid}` document (editors adding members directly go through the separate
`isOrgEditor(orgId)` **write** branch on the same match block, which already exists and is untouched
by this phase).

Both flows write inside a Firestore `writeBatch`, which matters more than it looks: **the two
flows need two *different* Firestore rules primitives, not one shared predicate.** Invite
acceptance reads a document (`organizations/{orgId}/invites/{email}`) that already existed *before*
this batch started — a plain `get()`/`exists()` correctly sees it, because `get()`/`exists()` in
Firestore security rules reflect the database state as of the start of the transaction/batch, not
any writes made earlier in the same batch. Org creation is the opposite case: the org document is
being created *in the same batch* as the membership document, so a plain `get()` on it may not see
it yet (rules evaluate each batch operation's `get()`/`exists()` against pre-batch state). Firestore
provides a purpose-built function for exactly this: `getAfter()`, documented as the mechanism for
"defin[ing] sets of writes that must take place together as a transaction or batch." Use `getAfter()`
for the org-creation branch, plain `get()`/`exists()` for the invite branch.

This distinction (Pitfall 1 below) is the single highest-risk unknown in this phase and is flagged
MEDIUM confidence — official docs describe both primitives' intended purpose clearly but do not spell
out byte-for-byte batch-internal ordering semantics in the pages fetched during this research. It is,
however, exactly the kind of claim the phase's own mandated tests will empirically prove or disprove
on the first real emulator run — treat the ALLOW (org-creation) test as the actual arbiter, not this
document.

**Primary recommendation:** Replace the single unconditional `allow create` with an OR of two
explicit branches — `getAfter()` on the org doc for org-creation (role forced to `'editor'`), and
`get()`/`exists()` on the invite doc for invite-acceptance (role compared against the invite's
stored `role` field). Extend the existing `src/rules.test.ts` (no new harness needed) with four new
tests matching the four CONTEXT.md-mandated cases, and confirm the DENY case genuinely fails against
today's unfixed rule before editing it.

## Both Legitimate Creation Flows, Traced

Both flows are implemented in **`src/stores/auth.ts`, function `ensureUserDocument(firebaseUser)`**
(lines 264-350), called from `onAuthStateChanged`, `loginWithGoogle`, `loginWithEmail`, and
`registerWithEmail`. It is the **only** app code that creates a `members/{uid}` document.

### Flow 1 — Invite acceptance (`auth.ts:280-317`)

```typescript
const email = firebaseUser.email?.toLowerCase()
if (email) {
  const lookupRef = doc(db, 'inviteLookup', email)
  const lookupSnap = await getDoc(lookupRef)
  if (lookupSnap.exists()) {
    const inviteData = lookupSnap.data()
    const inviteOrgId = inviteData.orgId as string
    const role = inviteData.role as 'editor' | 'viewer'

    const batch = writeBatch(db)
    batch.delete(lookupRef)                                              // 1. delete inviteLookup/{email}
    batch.delete(doc(db, 'organizations', inviteOrgId, 'invites', email)) // 2. delete org invite subdoc
    batch.set(doc(db, 'organizations', inviteOrgId, 'members', firebaseUser.uid), {
      role, joinedAt: serverTimestamp(),
      displayName: firebaseUser.displayName ?? '', email: firebaseUser.email ?? '',
    })                                                                    // 3. CREATE members/{uid}  <-- the write this rule guards
    batch.update(userRef, { orgIds: [inviteOrgId] })                     // 4. update users/{uid}
    await batch.commit()
  }
}
```

**What documents exist at the moment of this write:** `organizations/{inviteOrgId}/invites/{email}`
exists as of the *start* of this batch (it was created earlier, in a separate transaction, by an
org editor via TeamView — see below). It is being deleted by operation 2 in *this same* batch,
*before* operation 3 (the member create) runs — but that does not matter for a rule using plain
`get()`/`exists()`, because those reflect pre-batch-start state, not other operations' effects
within the same batch (see Pitfall 1). `inviteLookup/{email}` is also being deleted in this batch,
so the rule must not depend on it still existing at write time either.

### Flow 2 — Org creation (`auth.ts:320-347`)

```typescript
if (!hasOrg) {
  const batch = writeBatch(db)
  const orgRef = doc(collection(db, 'organizations'))
  const newOrgId = orgRef.id

  batch.set(orgRef, {
    name: `${firebaseUser.displayName || 'My'}'s Church`,
    createdAt: serverTimestamp(),
    createdBy: firebaseUser.uid,
  })                                                                     // 1. CREATE organizations/{newOrgId}
  batch.set(doc(db, 'organizations', newOrgId, 'members', firebaseUser.uid), {
    role: 'editor', joinedAt: serverTimestamp(),
    displayName: firebaseUser.displayName ?? '', email: firebaseUser.email ?? '',
  })                                                                     // 2. CREATE members/{uid}  <-- the write this rule guards
  batch.update(userRef, { orgIds: [newOrgId] })                          // 3. update users/{uid}
  await batch.commit()
}
```

**What documents exist at the moment of this write:** nothing pre-existing distinguishes this from
an attacker's self-join attempt except the sibling write, in the *same* atomic batch, creating
`organizations/{newOrgId}` with `createdBy: firebaseUser.uid`. **This is exactly the hypothesis named
in the task brief, confirmed:** the org document is created in the same batch. `role` is
**hardcoded to `'editor'`** — the client never asks the user to choose it — so a rule that forces
`role == 'editor'` on this branch changes nothing about legitimate behavior.

**Why an attacker cannot forge this branch against someone else's org:** `organizations/{orgId}`'s
own `allow create` rule (`firestore.rules:33`) requires `request.resource.data.createdBy ==
request.auth.uid`, and `create` only fires when the target document does not already exist. An
attacker cannot set `createdBy` on an **existing** org — Firestore evaluates a write to an existing
path as `update`, which requires `isOrgEditor(orgId)` (`firestore.rules:31`). So the only way
`getAfter(org).data.createdBy == request.auth.uid` can ever be true for an org the attacker doesn't
already administer is if the attacker is, in this same request, legitimately creating that exact org
— i.e., they are the founder. `[VERIFIED: firestore.rules read directly]`

## Recommended Rule Design

```javascript
match /members/{uid} {
  allow read: if isOrgMember(orgId);
  allow write: if isOrgEditor(orgId);

  // R104 — replaces the unconditional `isSignedIn() && request.auth.uid == uid`.
  // Both legitimate flows (see 40.1-RESEARCH.md) are handled explicitly; nothing
  // else authorizes a create.
  allow create: if isSignedIn() && request.auth.uid == uid && (
    // Flow 1: org creation. The org doc is created in the SAME atomic batch as
    // this write (ensureUserDocument, auth.ts:327 then :334) — getAfter(), not
    // get(), because get()/exists() reflect state as of the START of the
    // batch and will not see the sibling org-create operation. getAfter() is
    // Firestore's documented primitive for "these writes must land together."
    // Role is forced to 'editor', matching the hardcoded value the client
    // already sends on this path — no client discretion is lost.
    (getAfter(/databases/$(database)/documents/organizations/$(orgId)).data.createdBy == request.auth.uid
      && request.resource.data.role == 'editor')

    ||

    // Flow 2: invite acceptance. The invite doc predates this batch (created
    // earlier by an org editor via TeamView) and is being DELETED later in
    // THIS SAME batch (auth.ts:299) -- plain get()/exists() is correct here
    // specifically because it does NOT see that same-batch delete; it
    // reflects pre-batch state. request.auth.token.email is guarded non-null
    // first so `.lower()` never errors for an auth method with no email.
    // Role is compared against the invite's stored role, not trusted from
    // the client -- closes R104 criterion 4.
    (request.auth.token.email != null
      && exists(/databases/$(database)/documents/organizations/$(orgId)/invites/$(request.auth.token.email.lower()))
      && request.resource.data.role == get(/databases/$(database)/documents/organizations/$(orgId)/invites/$(request.auth.token.email.lower())).data.role)
  );
}
```

**Read-call budget:** worst case (both OR branches fully evaluated) is `getAfter(org)` + `exists(invite)`
+ `get(invite)` = 3 document-access calls, well inside the documented 10-per-operation /
20-per-batch limits (see Pitfall 2). `[VERIFIED: docs.cloud.google.com/firestore/quotas via WebSearch]`

**Alternative satisfying the same criteria (not recommended, noted for completeness):** force `role`
server-side via a Cloud Function instead of comparing it in the rule. Rejected here because it adds a
new Cloud Function trigger and a client-visible propagation delay to a phase whose own CONTEXT.md
scopes it to "one rule, in one file," and because the rule-comparison approach is directly,
synchronously testable against the emulator with no trigger-timing race — matching the phase's "proven
by tests that actually run" mandate more cleanly.

## The Invite Data Model

Two documents represent one outstanding invite, both written together in a single batch by an org
editor from `TeamView.vue:onInvite` (`src/views/TeamView.vue:260-281`), both normalized identically:

```typescript
function normalizeEmail(email: string): string {
  return email.trim().toLowerCase()
}
// ...
const normalized = normalizeEmail(email)
batch.set(doc(db, 'organizations', orgId, 'invites', normalized), {
  role: inviteRole.value,        // 'editor' | 'viewer'
  invitedBy: user.uid,
  invitedAt: serverTimestamp(),
  email: normalized,
  status: 'pending',
})
batch.set(doc(db, 'inviteLookup', normalized), {
  orgId,
  role: inviteRole.value,
  invitedAt: serverTimestamp(),
})
```

| Question | Answer |
|---|---|
| Which is authoritative for the rule fix? | `organizations/{orgId}/invites/{email}` — it is scoped under the `organizations/{orgId}` match block, so it's reachable inside the `/members/{uid}` rule with `orgId` already bound as a path variable. `inviteLookup/{email}` is top-level and keyed only by email, with no `orgId` segment to match against — using it would require an extra `get()` to first learn the orgId, then a second `get()`/`exists()` to check the invite itself, doubling read cost for no benefit. |
| How is the email normalized? | `email.trim().toLowerCase()` client-side (`TeamView.vue:217-219`), used as the literal document ID for both `invites/{email}` and `inviteLookup/{email}`. `[VERIFIED: TeamView.vue read directly]` |
| Is `request.auth.token.email` reliably available and matching normalization? | The app has exactly two sign-in methods (`loginWithGoogle`, `loginWithEmail`/`registerWithEmail`) — both Firebase Auth providers that populate `token.email` from a validated email address with no surrounding whitespace, so `.lower()` alone (no `.trim()` — Firestore rules strings have no built-in trim) is equivalent to the client's `trim().toLowerCase()` in practice. `firestore.rules` already uses `request.auth.token.email.lower() == email` twice today (lines 47, 172, 175) for the existing `inviteLookup`/`invites` delete rules, proven working by the passing test suite — this is an established, not novel, pattern in this file. `[VERIFIED: firestore.rules + src/rules.test.ts]` |
| What fields does an invite carry? | `role` ('editor'\|'viewer'), `invitedBy`, `invitedAt`, `email`, `status`. Only `role` is needed for the fix (criterion 4). |

**Gotcha not previously flagged:** `request.auth.token.email` can be `null` for auth methods this
app does not currently use (e.g., phone auth, anonymous auth). Guard with `request.auth.token.email
!= null &&` before calling `.lower()` — otherwise a null `.lower()` call errors the whole boolean
expression (Firestore rules fail closed on evaluation errors, so this degrades safely to DENY, not an
accidental ALLOW — but the explicit guard keeps the intent readable and avoids relying on
error-as-deny behavior). `[ASSUMED — ordinary Firestore auth token behavior, not independently
verified this session; low risk since this app has no phone/anonymous auth code path today]`

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Validating that two writes in one batch land together correctly | A Cloud Function that re-validates membership after the fact and deletes bad writes | `getAfter()` in the rule itself | `getAfter()` is Firestore's documented, synchronous, no-propagation-delay mechanism for exactly this; a Cloud Function would be async, race-prone, and let a bad write briefly exist before cleanup |
| Comparing a client-submitted role against the granted role | Trusting `request.resource.data.role` and validating server-side after commit | `request.resource.data.role == get(invite).data.role` inline in the rule | The rule can deny the write outright, synchronously, with no window where an over-privileged doc briefly exists |

**Key insight:** This rule needed no new library, function, or data model — the fix is entirely
within the existing rules file, using two different (both already-precedented-in-this-file)
Firestore rules primitives applied to the flow each actually matches.

## Common Pitfalls

### Pitfall 1: Using `get()` where `getAfter()` is required (or vice versa) — MOST LIKELY WAY TO SILENTLY BREAK ORG CREATION

**What goes wrong:** A tempting first draft writes
`get(/databases/$(database)/documents/organizations/$(orgId)).data.createdBy == request.auth.uid`
for the org-creation branch. Because the org document is created in the *same batch*, `get()` may
not see it — Firestore rules documentation states `get()`/`exists()` calls inside a transaction or
batch are evaluated per-operation, and `getAfter()` exists specifically to "define sets of writes
that must take place together as a transaction or batch" (i.e., see the state *after* all
same-transaction writes apply). If `get()` does not see the sibling org-create, the whole
org-creation branch always evaluates false, and the phase's own most-important success criterion —
"the founder creating their own first membership document" — fails, with no error message beyond a
generic `permission-denied`, since this is a security rule, not application code.

**Why it happens:** `get()`/`exists()` and `getAfter()` look interchangeable in casual reading of
Firestore rules examples, but they read the database at different points relative to the current
atomic operation. Most Firestore rules cookbook examples online use `get()` for single-document
reads unrelated to the current write, which is the common case and does not surface this distinction.

**How to avoid:** Use `getAfter()` for the org-creation branch (this document's recommendation), and
confirm empirically — the very first thing the plan should do after writing the new rule is run the
"ALLOW: founder creating their own first membership in a brand-new org" test (CONTEXT.md's mandated
case) against the real emulator, seeding via an actual `writeBatch` (not `seedDoc`, which bypasses
rules and would not exercise this code path at all) mirroring `ensureUserDocument`'s exact operation
order: org-create, then member-create, in one batch.

**Warning signs:** The invite-acceptance ALLOW test passes but the org-creation ALLOW test fails with
`permission-denied` even though the rule "looks correct" — that is the `get()` vs `getAfter()`
distinction manifesting, not a typo elsewhere.

### Pitfall 2: Assuming the invite-acceptance branch needs `getAfter()` too (it does not, and using it would break the flow)

**What goes wrong:** By analogy to Pitfall 1, a plan might reflexively use `getAfter()` for the
invite check as well "to be safe." This is actively wrong: the invite document is **deleted** earlier
in the *same* batch as the member-create (`auth.ts:299`, before `auth.ts:304`). `getAfter()` would
see the *post-batch* state — i.e., the invite already deleted — and the branch would always evaluate
false, breaking invite acceptance exactly the way an invite-only fix would break org creation
(CONTEXT.md's stated risk, just from the opposite direction).

**Why it happens:** Once a developer learns "same-batch sibling write needs `getAfter()`," it is easy
to over-apply that lesson without checking which direction the same-batch relationship runs in.

**How to avoid:** Use plain `get()`/`exists()` for the invite branch — it reads pre-batch-start
state, which is correct since the invite genuinely existed before this batch began; the fact that
this same batch is about to delete it is irrelevant to that pre-batch read.

**Warning signs:** The org-creation ALLOW test passes but the invite-acceptance ALLOW test fails.

### Pitfall 3: Forgetting the escalated-role DENY case tests the invite path, not the self-join path

**What goes wrong:** CONTEXT.md's fourth required case — "DENY: user accepting a genuine invite but
submitting an escalated role" — is easy to conflate with the first ("DENY: signed-in user, no
invite, self-creates membership"). They are different failure modes of the *same* branch: the first
proves the branch is false when no invite exists at all; the fourth proves the branch is false when
an invite exists but the submitted role doesn't match it. Testing only one does not prove the other.

**How to avoid:** Seed a real invite with `role: 'viewer'` in the escalated-role test, then attempt
`setDoc` with `role: 'editor'` and assert failure — distinct from the no-invite-at-all case, which
needs no seeded invite.

### Pitfall 4: The DENY test proves nothing if never run against the vulnerable rule

**What goes wrong (explicitly required by CONTEXT.md/the task brief to state):** A DENY-case test
written *after* the fix lands and only ever run against the *fixed* rule could be passing for an
unrelated reason — a typo in the test's own assertion direction, a seeding bug that makes the write
fail for a reason that has nothing to do with the rule under test, etc. The only way to know the DENY
test is actually exercising the vulnerability is to run it against **today's unmodified**
`firestore.rules` first and watch it fail (i.e., watch `assertFails(...)` itself throw, because the
write actually *succeeds* against the current loose rule).

**How to avoid:** Sequence: (1) write the DENY test against the current rule, run it, confirm it
FAILS (proving the vulnerability is real and the test correctly detects it); (2) apply the rule fix;
(3) re-run, confirm it now PASSES. Do not skip step 1 — it is the only evidence this phase is fixing
the thing it claims to fix, not just adding a test that happened to pass.

## Other Over-Permissive Findings (recorded per CONTEXT.md's Deferred Ideas — NOT in scope, NOT fixed)

- `organizations/{orgId}`'s `allow write: if isOrgEditor(orgId)` (`firestore.rules:31`) is
  document-level with no field restriction — an editor can rewrite `createdBy` on an org they already
  administer. This does not create a *new* privilege-escalation path for R104's fix (an editor
  already has unrestricted `write` access to `members/{uid}` for any uid via the sibling `allow
  write: if isOrgEditor(orgId)` rule on the members match block, so rewriting `createdBy` grants them
  no capability they don't already have directly) — but it is the kind of unscoped document-level
  write rule the codebase's own Phase 39 finding (in CONTEXT.md's Reusable Assets) already flags as a
  precedent worth tightening someday.
- `inviteLookup/{email}`'s `allow create: if isSignedIn()` (`firestore.rules:173`) lets **any**
  signed-in user create an `inviteLookup` doc for **any** email, including one they don't own, with an
  arbitrary `orgId`/`role` payload — this is a second, structurally similar self-invite vector (an
  attacker could write `inviteLookup/attacker@x.com` claiming `{orgId: 'victim-org', role:
  'editor'}` for their own email, then have `ensureUserDocument`'s invite-check pick it up on next
  sign-in). **This may be a related but distinct hole from R104** — R104 as scoped covers only the
  `members/{uid}` create rule, and the fix above still requires the invite to exist under
  `organizations/{orgId}/invites/{email}` (which is editor-write-only, unaffected by this
  `inviteLookup` looseness) for the rule's `exists()`/`get()` check to pass — so this
  `inviteLookup`-only forgery does **not**, by itself, defeat the R104 fix above, because the fix
  reads the org-scoped invite doc, not `inviteLookup`. Recorded as a finding for a future phase, not
  fixed here, per CONTEXT.md's explicit scope fence.
