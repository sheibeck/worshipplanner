<objective>
Close R104: replace `firestore.rules`' unconditional `allow create: if isSignedIn() &&
request.auth.uid == uid` on `organizations/{orgId}/members/{uid}` with a predicate that authorizes
exactly the two legitimate creation flows and nothing else — and prove all four behaviours against
the real Firestore emulator.

Purpose: today any signed-in user can self-join any organization at a role of their own choosing.
That is privilege escalation, and it is pre-existing (not introduced by v1.5). It is being fixed now,
in this position in the roadmap, so it ships in the same owner deploy session as Phase 40's deploy 2.

Output: a tightened rule, four new emulator tests, a recorded observation that the two DENY tests
genuinely failed against the vulnerable rule, and an owner handoff entry. **Nothing is deployed.**

The single most important structural fact in this phase: **the two legitimate flows need two
DIFFERENT Firestore rules primitives, and swapping them breaks one while appearing to fix the
other.** Read `40.1-RESEARCH.md` Pitfall 1 and Pitfall 2 before touching the rule.

branches, one per legitimate flow. Leave the sibling `allow read: if isOrgMember(orgId)` and
`allow write: if isOrgEditor(orgId)` exactly as they are — the latter is how an org editor legitimately
adds a member directly, and it is out of scope.

Both branches sit under a shared `isSignedIn() && request.auth.uid == uid` guard (you may still only
create a membership keyed by your own uid), and then:

Branch 1 — org creation. Prove the org document is being created in this same atomic batch with the
caller as its creator, using **`getAfter()`** on `/databases/$(database)/documents/organizations/$(orgId)`
and comparing its `createdBy` to `request.auth.uid`; additionally require
`request.resource.data.role == 'editor'`. `getAfter()` rather than `get()` because `get()`/`exists()`
reflect database state as of the START of the batch and will not see the sibling org-create operation.
Forcing the role costs nothing: the client already hardcodes `'editor'` on this path (auth.ts:335),
so no legitimate behaviour changes. An attacker cannot forge this branch against an org they do not
own — a `set()` against an ALREADY-EXISTING org document is evaluated as `update`, which requires
`isOrgEditor(orgId)` (firestore.rules:31), so the branch can only be true for someone genuinely
founding that org in this request.

Branch 2 — invite acceptance. Prove an outstanding invite exists for the caller's own email under
this org, using plain **`exists()`/`get()`** on
`/databases/$(database)/documents/organizations/$(orgId)/invites/$(request.auth.token.email.lower())`,
and require `request.resource.data.role` to equal that invite document's stored `role` field rather
than trusting the client's value — that role comparison is what closes criterion 4. Guard
`request.auth.token.email != null` BEFORE calling `.lower()`, so a provider that supplies no email
cannot error the expression (Firestore fails closed on evaluation errors, so it would degrade to
DENY rather than to an accidental ALLOW, but the explicit guard states the intent instead of relying
on that behaviour). Plain `get()`/`exists()` and NOT `getAfter()` here, precisely because this same
batch deletes the invite document (auth.ts:301) before the member create — `getAfter()` would see
the post-batch state, find the invite already gone, and break invite acceptance for everyone.

Read-call budget: worst case is one `getAfter` plus one `exists` plus one `get` = 3 document-access
calls per operation, well inside Firestore's 10-per-operation / 20-per-batch limits.

Carry the explanatory comments from the research document's rule block into the file. This file
already carries load-bearing rationale comments (see the `/services` and wildcard blocks); a bare
predicate here would be the odd one out, and the `get()`-versus-`getAfter()` asymmetry is exactly the
kind of thing a future editor would "simplify" into a bug.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Authenticated client → Firestore | A signed-in browser writes documents directly. `firestore.rules` is the ONLY enforcement layer for membership creation — there is no Cloud Function gate on this path today. |
| Client-supplied document body → stored membership document | `request.resource.data.role` is fully attacker-controlled. Whatever the rule does not constrain, the client decides. |
| Firebase Auth token → org identity | `request.auth.uid` and `request.auth.token.email` are the only caller identity the rule has. The email claim is what ties a caller to an invite. |
