### CR-01: Org-creation branch grants a permanent "founder" backdoor that survives explicit member removal

**Files modified:** `firestore.rules`, `src/rules.test.ts`
**Commit:** `bda074d`
**Applied fix:**

Added the recommended `!exists()` guard to the org-creation branch of `organizations/{orgId}/members/{uid}`'s
`allow create` rule. Before: `getAfter(org).data.createdBy == request.auth.uid` alone, which only
proves "createdBy currently equals my uid" (true forever, since `createdBy` is set once and never
cleared). After: `!exists(org) && getAfter(org).data.createdBy == request.auth.uid`, which additionally
requires the org to have **not existed** immediately before this operation — `!exists()` reads
pre-batch-start state and therefore cannot see the same batch's own sibling org-create write, so it is
only true for a genuinely new org.

Sequencing followed the mandated Pitfall-4 discipline: wrote the regression test first (`src/rules.test.ts`,
"DENIES a removed former founder from recreating their own editor membership") and ran it alone against
the **unmodified** rule — `assertFails(...)` threw "Expected request to fail, but it succeeded,"
confirming the write it describes actually succeeded against the vulnerable rule (proving the bypass is
real, not a hypothetical). Only then applied the `!exists()` fix. Also updated the Flow-1 inline comment
in `firestore.rules`, which previously asserted an unenforced same-batch invariant — it now states the
actual mechanism (`!exists()` proves pre-batch absence; `getAfter()` proves the post-batch value;
together they prove genuine same-batch creation). This comment fix is WR-01's fix, folded into the same
commit per the finding's own instruction ("Once CR-01's `!exists()` guard is added, update the
comment...") and per the task's execution rule not to treat it as a separate cosmetic change.

**Verification:**
- New regression test run against unmodified rule: **confirmed FAIL** (proves vulnerability real).
- Full rules suite after fix: `npx vitest run --config vitest.rules.config.ts` → **108/108 passing**
  (was 107/107 baseline; +1 net new test, zero regressions).
- Both legitimate flows unaffected: org-creation ALLOW test (real `writeBatch`, org-create then
  member-create in one batch, matching `ensureUserDocument` exactly) and invite-acceptance ALLOW test
  both still pass.
- Type gate: `npm run type-check` (`vue-tsc --build`) → clean, no errors.
- Compounding out-of-scope finding checked and confirmed closed as a side effect: an editor rewriting
  `createdBy` on an org they already administer (the recorded, unfixed `organizations/{orgId}`
  unrestricted-write finding) cannot defeat the new predicate, because `!exists(org)` is false for any
  org that already exists. Verified by reasoning against the rule text; the `organizations/{orgId}`
  rule itself was **not modified**, per scope.
- Neither `inviteLookup/{email}`'s `allow create: if isSignedIn()` nor `organizations/{orgId}`'s
  `allow write: if isOrgEditor(orgId)` was touched — confirmed via `git show --stat` on the fix commit
  (only `firestore.rules` and `src/rules.test.ts` changed) and a diff review of the commit contents.
- Nothing deployed — `firestore.rules` was only modified and tested locally against the emulator, per
  the standing constraint.
