# Phase 36 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder (36-CONTEXT.md § Phase Boundary):** rebuild the Service Order tab's layout against
"Turn 3 — Service Order tab"; extract one shared contextual-action-bar component used by Service Order,
Slides and Roles; move `Suggest All Songs`/`Copy for PC`/`Export to PC` out of the always-visible page
header into that bar; place `▶ Present` per design "1a"; move `＋ Add slide` into the bar; make the
group's existing drop zone double as the click-to-import affordance and delete the separate
`⇪ Import into this group` button; reorder tabs to Service Order · Slides · Roles. **This phase does not
re-implement any handler** — every moved control keeps its exact existing `canEditService` / `isLocked`
/ `canMutateGroup` / `canWriteGroupMedia` gate. `Print`, `Share`, `Undo`, `Mark as Planned`, `Delete
service` are **not** touched — see § Wireframe Findings, Finding 1 for why.

## Wireframe Findings — read this before the rest of the contract

Four questions this spec was required to answer from `docs/design/slides-tab.dc.html` directly (re-pulled
2026-08-03, 1071 lines), not from inference. Quoted line numbers are from that file as read during this
research pass.

### Finding 1 — There is no contextual action bar in the wireframe. Zero matches for "action bar" / "contextual" anywhere in the file (confirmed by direct grep, matching `docs/design/README.md`'s own verified-absent table). **R068's shared-bar component is original design work, not a wireframe transcription.**

What the wireframe *does* show, which is the actual design input this spec has to work from:

- **Turn 3 (Service Order, `id="3a"`, lines 59–77)** — the page header's right-aligned button row reads
  `⎙ Print · ⇱ Share · Suggest All Songs · Export to PC · Save` (line 65–69), and the tab strip below it
  reads `Service Order` (active) `· Roles · Slides` (line 72–76).
- **Turn 1 / "1a" (Slides tab, lines 707–723 and 843–858, both states)** — the SAME header slot instead
  reads `▶ Present · Save` (line 715–716, 851–852), with tab strip `Service Order · Roles · Slides` again,
  `Slides` active.

So the wireframe's *only* evidence for "contextual" behaviour is that **this one header slot already
shows different buttons on different tabs** — not a second row, not a bar with its own visual identity,
just the existing top-right button cluster changing contents per tab. There is no drawn "Roles" state for
this header at all (Turn 3 and 1a are the only two states drawn), so what belongs there for Roles is
undrawn — recorded as unresolved in § UI Considerations rather than invented.

**Recommendation (mine, not the wireframe's):** the shared `ContextualActionBar.vue` renders in the
**existing header row** — the same visual position/treatment `ServiceEditorView.vue:96-246` already
uses (ghost-bordered secondary buttons + one filled `Save`) — rather than as a new second row under the
tab strip. This matches both what the wireframe draws (buttons live in that one slot, contents vary) and
what the code already does (the header already sits outside every tab panel, `:701`) — the only change is
*which* buttons render there, driven by a declarative per-tab list instead of unconditional `v-if`s.
`Print`, `Share`, `Undo`, `Mark as Planned`, `Delete service` render in neither the wireframe's header nor
this phase's named scope (36-CONTEXT.md § Domain lists only `Suggest All Songs`, `Copy for PC`/`Export to
PC`, `＋ Add slide`, `Add music to this group`, `▶ Present`, and the tab reorder) — **they are out of
scope for this phase and stay exactly where they are** (header for Undo/Mark as Planned, bottom-of-page
for Print/Share/Delete), even though `Print`/`Share` also technically leak across tabs today. Flagged, not
fixed — see § UI Considerations, category `unresolved`.

### Finding 2 — ★★ The 34-11 collision, resolved from the wireframe: group music stays in the merged panel; only `＋ Add slide` moves.

`34-11-PLAN.md` (commits `98fdd29`/`2938d01`) merged group music and group background into one panel
(`SlideGrid.vue:77-122`, `data-testid="slide-grid-group-media-panel"`) in direct response to owner UAT
finding F2 — the owner read the two controls as "two unrelated sections" when they were separate sibling
rows. The code comment at `SlideGrid.vue:62-69` explicitly anticipates this phase and says the merge is
"deliberately confined to the wrapper structure... no relocation out of this file," leaving the broader
decision to Phase 36.

The relevant wireframe for this control is **not** Turn 3 (Service Order has no group-media panel at
all) — it is **"1a" (lines 768–778, 904–914)**, the Slides tab, where the group is selected via the plan
rail. There:

```
♪ Music for this group    pad_Cmaj_soft.mp3    plays across all 6 slides   ▶  ✕
```

renders as its own bordered row **directly below** the grid-local header that holds `＋ Add slide` /
`⇪ Import into this group` (lines 754–766) — not inside that header, and not inside any bar. **No
background-image control appears anywhere in the wireframe** — confirmed by `docs/design/README.md`'s own
verified-absent table ("Phase 33 (R055–R057) | background images as a feature | Still absent").

Putting the two facts together: the wireframe shows group music living beside `＋ Add slide` in the same
visual region, but as its **own** panel, never folded into a button row — and it has no opinion at all
about backgrounds, because backgrounds didn't exist yet when this turn was drawn. Moving music alone into
a page-level action bar would not match the wireframe (which keeps it as an inline panel) and would undo
the owner's own F2 fix (which explicitly merged it with background for the opposite reason — reading as
"related," not "scattered"). **Resolution: group music and group background stay together in
`SlideGrid.vue`'s existing merged panel, completely untouched by this phase. Only `＋ Add slide` moves
into the action bar (§ Finding 1 recommendation notwithstanding — see the discretionary call on where
`＋ Add slide` physically lands, below).** This is recorded as a requirement correction, not resolved
silently: `.planning/REQUIREMENTS.md`'s R053 entry now carries a dated correction note citing this exact
evidence. `ROADMAP.md`'s Phase 36 success criterion 4 ("`Add slide` and `Add music to this group` live in
the contextual action bar") is now stale on its "Add music" clause — flagged for the owner/planner to
correct at the next `ROADMAP.md` touch; this spec does not edit `ROADMAP.md` itself.

**★ Discretionary call, not wireframe-derived: where does `＋ Add slide` physically render?** `＋ Add
slide` (`SlideGrid.vue:20-26`) is scoped to whichever GROUP is currently selected in the plan rail — it is
not a tab-level action the way `Suggest All Songs` or `▶ Present` are. The wireframe keeps it in the
grid's own local header row (line 763), never in the page-level header. Physically relocating it into the
page-level `ContextualActionBar` would require new event plumbing (`SlideGrid` → `SlidesTab` →
`ServiceEditorView` → bar → back down to `SlideGrid`) for a control whose enabled state depends on
per-group selection state the page-level bar does not otherwise track. **Recommendation: `＋ Add slide`
stays physically rendered inside `SlideGrid.vue`'s own header row, matching the wireframe's layout
exactly, but is restyled to the exact same ghost-button classes `ContextualActionBar` uses** (§ Phase-
Specific Component Contracts §2) so it reads as the same visual/interaction *pattern* R068 asks for, even
though it is a second DOM instance rather than a second entry in the bar's declarative list. Flag this
explicitly to the planner: R053's literal text ("`Add slide`... move into the contextual action bar
(R068)") is satisfied in visual pattern, not in single-component architecture — the alternative (full
relocation with cross-component plumbing) is a legitimate but materially more expensive choice a planner
could still make; this spec does not forbid it, it recommends against it on cost/benefit grounds.

### Finding 3 — The Present button's placement, quoted directly from "1a."

`docs/design/slides-tab.dc.html:711-717` (state 1) and `:847-853` (state 2, drawer open):

```html
<div style="font-size:22px; font-weight:600;">Sunday, July 26, 2026</div>
<span ...>✓ Exported</span>
<div style="margin-left:auto; display:flex; gap:8px;">
  <button ...>▶ Present</button>
  <button ...>Save</button>
</div>
```

`▶ Present` sits in the **page-level header row**, right-aligned, **immediately left of `Save`**, in the
exact same header slot Turn 3 uses for `Print`/`Share`/`Suggest All Songs`/`Export to PC`/`Save`. This is
unchanged between the drawer-closed and drawer-open states (both quoted above render identically) — the
drawer floats over the page and does not affect the header (consistent with `docs/design/README.md`'s
"floats over the page; nothing underneath reflows").

Today `▶ Present` lives inside `SlidesTab.vue:3-23`, in its own bordered wrapper
(`border-b border-gray-800 px-3 py-2`) at the top of the TAB's own content — one level below the page
header, not inside it. **Per the wireframe, it must move up into `ServiceEditorView`'s page-level header
row** (the same row Save already occupies), rendered only while the Slides tab is active — i.e. it becomes
one of the Slides tab's entries in the shared action bar's declarative list, not a tab-local wrapper. See
§ Phase-Specific Component Contracts §4 for the exact prop-threading this relocation requires (the
`canPresent`/`presentStartIndex` computeds currently live in `SlidesTab.vue` and must still gate the
action correctly from their new host).

### Finding 4 — Turn 3 (Service Order), region-by-region, concrete enough to build against.

Read verbatim from `docs/design/slides-tab.dc.html:23-353`. Top to bottom:

1. **Page header** (unchanged position/content except the button-row swap in Finding 1): back link, date
   (editable via native date picker), status pill, right-aligned button row.
2. **Tab strip** — `Service Order` (active) `· Roles · Slides` **in the wireframe** (line 72-76 and again
   at 719-722/855-858 in 1a) — this is the OLD order, not R069's target. ★ **The wireframe was not
   redrawn after R069 was decided; the requirement wins per this project's own established precedent**
   (`docs/design/README.md § Known deltas`: "the mockup predates two of the user's instructions... where
   they disagree, the instructions win"). Target order for this phase is **Service Order · Slides ·
   Roles**, per R069 and `ROADMAP.md`'s Phase 36 success criterion 5, not what the wireframe literally
   draws.
3. **TEAMS row** (line 81-87) — unchanged from today: team checkboxes + "the Slides tab follows this
   order" caption.
4. **SERMON CONTEXT row** (line 89-101) — unchanged from today: Sermon Topic / Sermon Passage inputs.
5. **Five section bands** (lines 103-328): `PRE-SERVICE`, `WORSHIP`, `MESSAGE`, `SENDING`, `POST-SERVICE`
   — matches the app's existing five `SERVICE_SECTIONS` exactly (Phase 29/R050). Each band header is a
   label + gradient divider + slide-count caption + a **per-band `＋ Add item` link** (lines 108, 141, 241,
   262, 314) — new relative to today's code, which has one add control at the BOTTOM of the whole list,
   not per-band (`ServiceEditorView.vue:1199-1229`). See § Phase-Specific Component Contracts §7 for the
   exact, small `addSlot()` signature change this requires.
6. **Item rows** — drag handle (`⣿`), a kind badge (`SLIDE DECK` / `ANNOUNCEMENTS` / `SONG` / `SCRIPTURE
   READING` / `PRAYER` / `SERMON` / `MISC`), inline kind-specific content (title field / song picker with
   CCLI + `Change` + `✕` / passage search + field), and a right-side cluster: slide-count chip, `⋯`, `✕`.
   **★ Two elements here have no counterpart in the current codebase — flagged, not silently
   implemented, see § UI Considerations `unresolved`:**
   - the `⋯` kebab per row has no defined menu in the wireframe (no expanded state drawn anywhere in the
     file) and no equivalent in current code (`ServiceEditorView.vue`'s row only has a `section-select`
     dropdown and a plain `✕` remove button, `:1166-1189`) — **do not invent a menu for it**; treat it as
     undrawn.
   - the assigned-song row's `Change` link (lines 151, 223, 272) has no equivalent today — a song can only
     be swapped by clearing it first (`✕`, `onClearSong`) and then re-picking via `SongSlotPicker`. Adding
     a true non-destructive "Change" affordance is new interaction logic, not a layout change, and is
     **out of this phase's scope** per 36-CONTEXT.md's "does not re-implement handlers." Recommendation:
     do not add it this phase.
7. **`＋ Add to the service` palette** (lines 330-341) — a dashed-border row of type chips: `Song`,
   `Scripture`, `Prayer`, `Announcements`, `Sermon`, `Video`, `Slide deck`, `Offering`, `Misc` (**9**
   types). **The app's data model supports only 6 `SlotKind` values today** (`SONG | SCRIPTURE | PRAYER |
   MESSAGE | HYMN | IMPORTED`, `src/types/service.ts:7`), and the existing `Add Element` dropdown
   (`ServiceEditorView.vue:1223-1227`) only offers 5 of them as user-addable (`IMPORTED` has no manual-add
   entry point). Inventing `Announcements`/`Video`/`Offering`/`Misc` as real addable kinds would require
   new `SlotKind` variants, factory entries and rendering branches — a data-model change, not a layout
   rebuild, and explicitly out of 36-CONTEXT.md's scope. **Recommendation: adopt the palette's VISUAL
   treatment (a dashed-border row of chips replacing the current dropdown-menu button) but narrow the chip
   set to the 5 kinds `addSlot()` already supports** (`Song`, `Scripture`, `Prayer`, `Message`, `Hymn` —
   `Message` is this codebase's existing name for what the wireframe calls `Sermon`; do not rename the
   type, only reuse the wireframe's row styling). This is a **flagged discretionary narrowing**, not a
   silent scope cut — the planner should not "complete" the palette to 9 chips without a new requirement.
8. **Delete-service row** (lines 343-346) — unchanged: caption + `🗑 Delete service` button, right-aligned.
   Out of this phase's scope (not named in 36-CONTEXT.md § Domain).

### 7. Per-section `＋ Add item` — the `addSlot()` signature extension

**Small, additive, behavior-preserving.** `addSlot(kind: SlotKind, vwType?: VWType)`
(`ServiceEditorView.vue:2601-2613`) currently always inherits the section of the CURRENT LAST slot. To
route a per-band `＋ Add item` click into that band specifically, add one new optional parameter:

```ts
function addSlot(kind: SlotKind, vwType?: VWType, targetSection?: ServiceSection) {
  if (!canEditService.value) return
  if (!localService.value) return
  const currentSlots = localService.value.slots
  const section = targetSection ?? currentSlots[currentSlots.length - 1]?.section
  const newSlot = createSlot(kind, vwType, section)
  localService.value.slots.push(newSlot)
  localService.value.slots = reindexSlots(orderSlotsBySection(localService.value.slots))
  showAddMenu.value = false
}
```

Every EXISTING call site (`addSlot('SONG', 2)` etc. in the bottom-of-list dropdown, if that dropdown is
kept as a fallback, or replaced entirely by the palette per § Finding 4 item 7) omits the third argument
and behaves exactly as today. The new per-band `＋ Add item` links pass their own band's
`ServiceSection` value explicitly. This is the one net-new piece of logic this phase introduces, and it is
a pure additive parameter — no existing behavior changes for any caller that doesn't pass it.

## Accessibility Note

- **Action-bar buttons:** real `<button>` elements throughout (§2) — no change from today's existing
  header buttons, which are already native buttons.
- **`SlideDropTarget` click affordance:** `role="button" tabindex="0"` with `Enter`/`Space` activation
  parity, ONLY when `clickable` is true — matches 33-UI-SPEC §1's precedent for adding native-button-
  equivalent semantics to a non-button interactive element. `aria-label="Click to import, or drag files
  here"` since the tile's visible text is a drop-target instruction, not an accurate description of the
  click action.
- **Per-band `＋ Add item` / palette chips:** plain `<button>` with visible text as the accessible name —
  no `aria-label` needed.
- **Section-band header divider (`<span class="h-px ...">`):** decorative only, no `aria-hidden` needed
  since it carries no text content to suppress.
- **Save-status `aria-live` region (E7):** unchanged, verbatim — this phase's accessibility contract here
  is "do not regress," not "add new."
- **Tab strip:** unchanged — still plain `<button>` elements, no `role="tab"`/`tablist` introduced by this
  phase (§1); the reorder does not add or remove any accessibility semantics, it only changes visual/DOM
  order of the three existing buttons.
